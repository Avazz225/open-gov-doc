# federation-hub-service

**Purpose:** Federation Hub skeleton (Concept 7.4) — address book of connected installations + switchboard that mediates cross-installation workflow handovers, without being able to view the transferred content itself. **Deliberately not an internal service of an installation** — does not register with `registry-service`, has no `depends_on: gateway-service`, no event bus producer/consumer. Still shipped in `infra/docker-compose.yml` for local development/the self-loopback smoke test (dev-only convenience) — an operator would run it entirely separately in production, potentially even shared across multiple third-party installations (Concept 7.4 "operator model").

**Concept reference:** 7.4
**Own Postgres schema:** `federation` (tables `hub_identity`, `installation`, `handover`)

## Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/public-key` | Public signature key of the hub (RSA-2048) — installations fetch this once on first registration (trust-on-first-use, see ADR 0028) |
| `GET` | `/ca-certificate` | Self-signed root CA certificate of the hub (since **Post-Roadmap Phase 21 Session 2**, [ADR 0085](../adr/0085-federation-hub-certificate-layer-not-transport-mtls.md)) — counterpart to `/public-key`, certificate-pinning equivalent (trust-on-first-use), see "Certificate Layer" below |
| `POST` | `/installations` | Register (new `id`) or update (known `id`) — since P13-S4 (ADR 0039) signature-based instead of API-key-based: `X-Installation-Signature` must match the submitted `public_key_pem` for a new registration (self-consistency), or the already-stored one for a known `id` (`public_key_pem` itself is **not** taken over on an update, see `rotate-key`). Since **P21-S2** the hub additionally issues a certificate for the submitted key (`certificate_pem` in the response) |
| `GET` | `/installations` | Address book — ungated |
| `DELETE` | `/installations/{id}` | Deregister — `X-Installation-Signature` over the UTF-8 bytes of `installation_id` itself |
| `POST` | `/installations/{id}/rotate-key` | Key rotation (P13-S4/ADR 0039) — body `{new_public_key_pem}`, signed with the still-**current** private key (proof of continuity). Since **P21-S2** the certificate is also reissued (bound to the new key) |
| `POST` | `/installations/{id}/revoke` | Operator revocation (P13-S4/ADR 0039) — gated via `Authorization: Bearer <DMS_HUB_OPERATOR_KEY>`, **not** via the affected installation's own signature (which could be compromised) |
| `POST` | `/handovers` | Create a handover — **`handover_id` is supplied by the caller itself**, not generated by the hub (see "Found only during the live smoke test" below). `X-Installation-Id`/`X-Installation-Signature` determine the sending installation, checks version compatibility (`409` on incompatibility) and that the target is not revoked (`409`), commits the handover row **before** the delivery attempt, then delivers the encrypted payload synchronously to `to_installation`'s `callback_base_url` + `/federation/inbound`, returning the result directly (`delivered`/`pending_retry`/`delivery_failed`, since **P20-S5** see "Retry & Backoff" below) |
| `POST` | `/handovers/{id}/retry` | Manual restart of a `delivery_failed` OR (since **Phase 40 Session 3**) `result_delivery_failed` handover — dispatches on the handover's CURRENT status, one endpoint for the admin UI to call regardless of which of the two independent legs failed. `404` for unknown `id`, `409` for any other status OR if the relevant encrypted payload is no longer in the hub's process memory (e.g. after a restart), otherwise an immediate renewed delivery attempt on the failed leg |
| `POST` | `/handovers/{id}/result` | Report back a result — only by the handover's target installation (`403` otherwise), forwards to `from_installation`'s callback + `/federation/inbound-result`. Since **Phase 40 Session 3**, this delivery is retry-aware too (`result_pending_retry`/`result_delivery_failed`, see "Retry & Backoff" below) — previously fully synchronous with no retry at all |
| `GET` | `/handovers?status=...` | Collection endpoint (since **Phase 40 Session 3**) — previously only the single-`id` `GET` below existed. Basis for the admin UI's failure-visibility view (`?status=delivery_failed`/`?status=result_delivery_failed`), ungated like `GET /installations` |
| `GET` | `/handovers/{id}` | Status/metadata of a handover |
| `GET` | `/healthz` | Health check |

## Data Model

- `hub_identity`: singleton (`id=1`, same pattern as `signature-service`'s `InternalCa`) — its own RSA-2048 signature key pair, used to sign every delivery to an installation (`X-Federation-Hub-Signature`); since **P21-S2** additionally `ca_certificate_pem` — the same key pair packaged as a self-signed X.509 root CA certificate, see "Certificate Layer" below.
- `installation`: address book entry — `id` (chosen by the installation itself), `display_name`, `callback_base_url`, `public_key_pem` (since P13-S4 serves both as the cryptographic identity for incoming requests AND still for end-to-end encryption by OTHER installations — the hub itself never holds the matching private key), `version`/`min_compatible_peer_version`, `supported_process_types`/`supported_document_types` (JSON lists, currently only stored, no enforcement), `revoked_at`/`revoked_reason` (since P13-S4, `NULL` while not revoked), `certificate_pem`/`certificate_not_after` (since **P21-S2**, `NULL` for legacy rows not yet migrated).
- `handover`: **metadata only** (`from_installation_id`, `to_installation_id`, `process_type`, `status`, `attempts`/`next_retry_at` since **P20-S5**, `result_attempts`/`result_next_retry_at` since **Phase 40 Session 3** — mirrors the forward-delivery counters exactly, but for the separate return-path leg, timestamps) — no field for the ciphertext itself, which is forwarded synchronously and never persisted (literal implementation of Concept 7.4: "logs only metadata of the mediation process ... not the document contents themselves"). This also applies to the retry payload needed since P20-S5 — see "Retry & Backoff" below.

## Retry & Backoff (Post-Roadmap Phase 20 Session 5, [ADR 0081](../adr/0081-federation-hub-handover-retry-backoff-pending-retry.md))

The first delivery attempt remains **synchronous** in `POST /handovers` (fast response in the normal case). Since P20-S5 a failure is no longer immediately terminal: `status` switches to `pending_retry` with increasing `attempts` and a `next_retry_at` set via full-jitter backoff (`libs/dms-retry`), processed by a new, standalone `_handover_retry_poll_loop` (interval `handover_retry_poll_interval_seconds`, default 60s). Only after `max_handover_delivery_attempts` (default 5) failed attempts does `status` switch to the terminal `delivery_failed`, from which `POST /handovers/{id}/retry` allows an immediate manual restart.

**The cached payload deliberately lives only in process memory, never in the database**: as before this session, `handover` never stores the end-to-end encrypted payload itself (ADR 0028). So that a later retry can still redeliver it, the hub instead holds it transiently in `app.state.pending_handover_payloads` (keyed by `handover_id`) — as long as no delivery attempt has succeeded yet, the entry is kept, even beyond exhaustion into `delivery_failed` (that is exactly when `POST .../retry` needs it for the first time); it is only cleared on actual success. **Consequence**: a restart of the hub during an open retry window irretrievably loses this cache entry — both the automatic poll tick and a manual `POST .../retry` then mark the affected handover as `delivery_failed` instead of waiting indefinitely or reporting a false success; in this case the sending installation must submit a new handover with a new `handover_id` (`create_handover` creates rows without an existence check, a retry with the same ID after cache loss is not an option anyway). Verified live with a real `docker compose restart federation-hub-service` (see [ADR 0081](../adr/0081-federation-hub-handover-retry-backoff-pending-retry.md) "Consequences").

**Return-path retry (Phase 40 Session 3)**: `POST /handovers/{id}/result`'s hub→origin-installation delivery (the `_deliver(...+"/federation/inbound-result")` call inside `submit_handover_result`) previously had zero retry logic at all — a single failure landed immediately in the terminal `result_delivery_failed`, unlike the forward-delivery leg above. This session mirrors the SAME retry-then-give-up shape for this leg exactly: `result_pending_retry` (new status) with the same full-jitter backoff via `result_attempts`/`result_next_retry_at`, the same `settings.max_handover_delivery_attempts` knob (both legs deliberately share one setting, not a separately tunable one), driven by the SAME poll loop/interval (`_run_result_retry_tick`, called every tick alongside the existing `_run_retry_tick` — one loop, two independent legs, rather than a second `asyncio.create_task`). A second, equally ephemeral process-memory cache, `app.state.pending_handover_result_payloads`, holds the `encrypted_result` payload for the same reason and under the same restart-loses-it caveat as `pending_handover_payloads` above — see "Open Points" for why this doubles the memory-pressure exposure ADR 0147 already flagged for the forward-delivery cache. `POST /handovers/{id}/retry` now dispatches on the handover's CURRENT status (`delivery_failed` → forward leg, `result_delivery_failed` → result leg) so the admin UI (see "Admin UI Visibility" below) can call one endpoint uniformly regardless of which leg failed.

## Admin UI Visibility (Phase 40 Session 3)

`GET /handovers?status=delivery_failed`/`?status=result_delivery_failed` + `POST /handovers/{id}/retry` back a new `HandoverFailuresSection` in `apps/admin-ui`'s existing `ProcessingFailuresView` (`/processing-failures`, alongside the equivalent notification-/rendition-/OCR-result sections) — matching Concept-analogous visibility+manual-restart that `archival-service`/`notification-service`/`rendering-service`/`ocr-service` already had (the plan's own comparison set for this session). One structural difference from all four of those: **admin-ui calls this service DIRECTLY, not through the gateway**. This service deliberately does not register with `registry-service` (see the intro above — it isn't an internal service of any one installation, other installations' own admins reach the same hub too), so `gateway-service`'s registry-based proxy has no instance to route to. `apps/admin-ui/src/lib/config.ts` therefore carries a second, non-mutable base URL (`NEXT_PUBLIC_FEDERATION_HUB_BASE_URL`, default `http://localhost:8018`) alongside the gateway one, and `lib/api.ts`'s `federationHubRequest` fetches it without an `Authorization` header (this service has no admin-JWT model at all — its only gated endpoints, `rotate-key`/`revoke`, use signatures/an operator secret instead).

This is also the first time a browser calls this service directly, so it needed its own `CORSMiddleware` (`Settings.cors_allowed_origins`, same convention/defaults as `gateway_service.settings.Settings`) — every other endpoint here was consumed server-to-server until now.

## Certificate Layer (Post-Roadmap Phase 21 Session 2, [ADR 0085](../adr/0085-federation-hub-certificate-layer-not-transport-mtls.md))

The plan described this session as "mTLS / real installation identity" — closer examination showed that [ADR 0039](../adr/0039-federation-trust-hardening-request-signing-over-mtls.md) had already once evaluated real transport mTLS for this hub and rejected it with reasoning that still holds (no service in this repo terminates TLS itself). This session instead adds a real certificate layer **at the application level**, in addition to the existing signature check:

- The hub's own key pair (`hub_identity`) additionally acts as a small, self-signed internal root CA (`ca_certificate_pem`, same `cryptography` library/convention as `signature-service`'s `InternalCa`, ADR 0025) — no separate key pair.
- Every installation receives a hub-signed X.509 certificate (validity 1 year) at registration AND at every key rotation, binding its public key (`CommonName` = installation `id`).
- `authenticate_signed_request` (applies to `POST /handovers`/`.../result`) additionally checks, beyond the signature: the full certificate chain up to the hub CA, the validity window, AND that the `CommonName`/embedded key actually belong to the calling installation (`crypto_utils.verify_installation_certificate`) — prevents a certificate validly issued by the hub for a DIFFERENT installation from being substituted.
- Legacy installations without a certificate (`certificate_pem IS NULL`) are automatically certified retroactively on the next hub startup (`main.lifespan`); until then (or for a caller that deliberately does not present a CA certificate) the check skips this part (backward compatibility) — the signature check remains mandatory in every case.
- `GET /ca-certificate` (counterpart to `GET /public-key`) allows installations to fetch and pin the root CA certificate on first contact (certificate-pinning equivalent).
- Verified live against the real running stack: the retroactive migration ran against **219 real, already-existing installations** from earlier live verifications of this and previous sessions (startup duration 6.2s instead of the usual ~150ms, all 219 rows confirmed with a certificate afterward).

## Trust Model (ADR 0028, extended since P13-S4 with ADR 0039)

- **Installation → Hub**: since P13-S4 signature-based (RSA-PSS/SHA-256, `X-Installation-Signature`) instead of a hub-issued API key — verified against `Installation.public_key_pem`, the same key that already exists for end-to-end encryption anyway. Deliberately **no** real TLS client certificate at the TRANSPORT LEVEL (no other service in this project terminates TLS itself) — "mTLS-equivalent at the application level", see [ADR 0039](../adr/0039-federation-trust-hardening-request-signing-over-mtls.md) for the full reasoning. Since **P21-S2** ([ADR 0085](../adr/0085-federation-hub-certificate-layer-not-transport-mtls.md)) extended with a real X.509 certificate layer, still checked at the application level (see "Certificate Layer" above) — ADR 0039's reasoning against real transport mTLS continues to apply unchanged.
- **Hub → Installation**: unchanged — the hub signs every delivery with its own, once-generated key pair (RSA-PSS/SHA-256, `X-Federation-Hub-Signature`) — the target installation verifies using the public hub key fetched once during its own registration. No shared secret that the hub would have to store in plaintext.
- **End-to-end encryption of the payload**: rests entirely with the installations (`workflow_service.federation_crypto`) — the hub only forwards `encrypted_payload`/`encrypted_result` as an opaque string.
- **Version compatibility**: `POST /handovers` checks `(major, minor)` number pairs on both sides (`repository.is_version_compatible`), rejecting incompatible combinations with `409`. Since P13-S3, `POST /installations` already validates the format of `version`/`min_compatible_peer_version` at registration time (`version_utils.parse_version`, `422` for a non-numeric value) — a real bug previously only surfaced during a later, third-party `POST /handovers` mediation with `500`, see ADR 0028 addendum.
- **Key rotation/revocation (P13-S4)**: rotation is installation-driven and requires proof of continuity (signature with the old key); revocation is an operator action (`DMS_HUB_OPERATOR_KEY`, `None` by default = fully disabled), deliberately independent of the affected installation's own signature, since the compromise case is exactly the intended use case.
- Deliberate limitations of this skeleton (see "Open Points").

## Bugs found only during the live smoke test (self-loopback, see ADR 0028)

The self-loopback smoke test agreed at session start (an installation hands over to itself) uncovered two real bugs not visible with pure unit test coverage — both arise from the synchronous delivery, which in the self-loopback case reaches back into the same installation/the same process:

1. **Postgres transaction isolation**: `POST /handovers` originally only committed the handover row *after* the delivery attempt. In the self-loopback case, however, the target installation synchronously calls back into the hub (`POST .../result`) before the original transaction has been committed — the new, separate request did not yet see the row (`404`). Fix: `session.commit()` directly after creation, **before** the delivery attempt.
2. **`handover_id` generation order**: the hub originally generated `handover_id` itself and only returned it in the response. In the self-loopback case, however, the sending installation's own *local* bookkeeping (its `FederationTask` row) already needs this ID before the nested callback (`/federation/inbound-result`) can look it up there — a classic circular dependency case. Fix: the sending installation generates `handover_id` itself (UUID) and sends it along in the `POST /handovers` body, committing its own row locally **before** the hub call. Side effect: a clean, idempotency-key-like protocol that is also useful for real two-installation scenarios (the caller determines its own reference instead of having to wait for a server-generated ID).

Both fixes are pure sequencing/protocol changes with no effect on the actual mediation logic — for a real two-installation scenario (no self-reference) neither ordering problem would ever have occurred, since two entirely separate processes/databases are involved there.

## Usage (since P6-S9)

Two callers: `workflow-service` (`federation_client.py`) — registers itself on its own startup (opt-in via `DMS_FEDERATION_HUB_BASE_URL`), uses it to trigger federated BPMN steps (`taskType=federated`/`federated_return`) (see `docs/services/workflow-service.md` "Federation" for the other side of the protocol); since **P15-S4** additionally `auth-service` (its own, independent second registration for the optional federated contact search, 2.5 — see `docs/services/auth-service.md` "Contacts" and [ADR 0054](../adr/0054-kontakte-directory-independent-second-federation-identity-per-installation.md)). Confirmed live: `Installation` is indeed a generic address book entry that can be registered independently by any service — two rows for the same physical installation (distinguished only by the display-name suffix `" (Contacts)"`) work without any code change to this service. `auth-service` also does NOT use `POST /handovers` — the federated contact search calls peer installations directly (no hub relay); the hub there serves solely for address/key discovery via the already ungated, readable `GET /installations`.

## Sensors (Concept 10.1, Phase 40 Session 4)

This service's first sensors at all — it had none before this session, not even the generic HTTP
ones (`dms-metrics-client` was not even a dependency yet). Two custom gauges (group `capacity`),
directly against ADR 0147's memory-pressure risk for the two in-process retry payload caches
(ADR 0081/Phase 40 Session 3):

- `federation_hub.retry_cache.forward_pending` — live `len(app.state.pending_handover_payloads)`.
- `federation_hub.retry_cache.result_pending` — live `len(app.state.pending_handover_result_payloads)`.

Both are periodic-push gauges (`run_gauge_sampler_loop`, `settings.sensor_sample_interval_seconds`,
default 15s), same idiom as document-service/registry-service — unlike storage-service's pull-on-
scrape gauge, there is no ADR-0004-style tension here (this service already runs one background
poll loop, `_handover_retry_poll_loop`, so a second `asyncio.create_task` for the sampler is not a
qualitative change). Deliberately does NOT also expose the DB's `pending_retry`/`result_pending_
retry` row counts as a separate pair of sensors — those can diverge from the cache size after a
restart (documented limitation, see "Retry & Backoff" above), but four sensors for two caches would
exceed this session's own "two concrete sensors, not a blanket retrofit" scope; the cache size is
what actually drives the memory-pressure risk this session is about.

**Scrape-path wrinkle**: since this service isn't registered with `registry-service` at all (see
the intro above), `monitoring-service`'s registry-driven scrape-proxy can never discover it, and its
sensors would therefore never reach Prometheus/Grafana via the usual path even with the sensors
themselves correctly declared. `infra/prometheus.yml` therefore scrapes this service directly as a
second, separate static target (`job_name: federation-hub-service`), the same idiom already used for
`cadvisor` (also not registry-discovered) — bypassing `monitoring-service`'s aggregation entirely
for this one service.

## Open Points

- **No Alembic/no migrations** — like every other service in this early phase, additive tables via `create_all`.
- **`supported_process_types`/`supported_document_types` are not enforced** — the hub only stores them, but does not check whether a `POST /handovers` actually matches one of the types declared by the target installation. Would be a sensible future hardening (a clear error message instead of a `delivery_failed` that the target installation only rejects itself after delivery).
- ~~**API key with no rotation/revocation mechanism** other than full deregistration+re-registration.~~ — **stale text, corrected in Phase 40 Session 3**: this described the pre-ADR-0039 API-key model, which no longer exists (this bullet was simply never cleaned up after that session shipped, three sections above this one). The CURRENT (signature-based) model already has both: `POST /installations/{id}/rotate-key` (signed with the still-current key, proof of continuity) and `POST /installations/{id}/revoke` (operator-gated, independent of the installation's own signature - the compromise case). A regular re-registration is also NOT "full de-/re-registration" - it's an upsert (`register_or_update_installation`) that even reissues the certificate on every call (routine renewal, no key rotation needed). `Handover.from_installation_id`/`to_installation_id` aren't even `ForeignKey`s to `installation`, so there was never a cascade-delete risk either. No code changed for this bullet - it was a documentation correction, not a gap.
- ~~No mTLS/no real installation identity~~ — **partially resolved in Post-Roadmap Phase 21 Session 2** ([ADR 0085](../adr/0085-federation-hub-certificate-layer-not-transport-mtls.md)): a real X.509 certificate layer (own small hub CA, issued installation certificates) was added, see "Certificate Layer" above. **Deliberately still no real transport mTLS** — ADR 0039's reasoning (no service in this project terminates TLS itself) still applies unchanged; real transport TLS/mTLS remains an operator deployment decision (Concept 10.3).
- ~~**Synchronous delivery without retry/queue**~~ — **resolved in Post-Roadmap Phase 20 Session 5** ([ADR 0081](../adr/0081-federation-hub-handover-retry-backoff-pending-retry.md)) **for the forward-delivery leg, and in Phase 40 Session 3 for the separate return-path leg** (`POST /handovers/{id}/result`'s hub→origin-installation delivery, previously fully synchronous with no retry at all — see "Retry & Backoff" above): both legs now get automatic retry with full-jitter backoff up to `max_handover_delivery_attempts`, after which `delivery_failed`/`result_delivery_failed` + manual restart via the same `POST .../retry`. **Remaining, deliberately documented limitation on BOTH legs**: the payload needed to replay delivery lives only in the hub's process memory (never in the DB, see "Retry & Backoff" above) — a restart of the hub during an open retry window irretrievably loses it, and the affected handover then goes directly to the terminal failure status for that leg. ~~Still open: admin UI visibility/control for this (P20-S7).~~ — **closed in Phase 40 Session 3**, see "Admin UI Visibility" above.
- **No cleanup of old `handover` metadata rows** — grows unbounded, similar pattern to `registry-service`'s never-cleaned-up inactive instances.
- ~~**No sensor/monitoring connection** (follows in Phase 11)~~ — **closed in Phase 40 Session 4**, see "Sensors" above (retry-cache depth/pending count for both caches, directly relevant to the memory-pressure bullet below).
- ~~**Binary payload transport (e.g. a full XDOMEA/XJustiz package instead of small BPMN task data) is untested at scale**~~ — **built and partially mitigated in Post-Roadmap Phase 43 Session 1** ([ADR 0159](../adr/0159-dms-to-dms-xdomea-handoff-implementation.md), implements the Post-Roadmap Phase 37 Session 1 scoping, [ADR 0147](../adr/0147-cross-installation-xdomea-handoff-scoping.md)): `encrypted_payload`/`encrypted_result` are now genuinely exercised at real, multi-kilobyte-and-up sizes by `workflow-service`'s DMS-to-DMS XDOMEA handoff, live-verified end to end. Two concrete, mechanical fixes address what ADR 0147 flagged: `hub_delivery_timeout_seconds` (default 60s, was hardcoded 15s) on `app.state.http_client`, and a new `max_handover_payload_chars` (default ~100M, both `create_handover` and `submit_handover_result` reject an oversized payload with `413` before any target/version lookup). **Deliberately NOT resolved, a proportionate partial mitigation rather than the full fix**: this bounds the PER-HANDOVER worst case but does not solve unbounded memory use across many concurrent in-flight/retrying handovers — `pending_handover_payloads`/`pending_handover_result_payloads` are still plain in-process dicts, not an external store. A future session could still move retry storage off-heap (disk/Redis/Postgres) if real concurrent handoff volume ever makes that necessary; nothing found during this session's own live verification (a single handover) suggested that's needed yet.
- **`GET /handovers`/`POST .../retry` remain ungated** (Phase 40 Session 3) — consistent with this service's existing convention (`GET /installations` is likewise deliberately ungated, 7.4: address-book metadata, not content), but worth naming explicitly now that a mutating action (`retry`) is admin-UI-reachable: anyone who can reach this service's network address can trigger a retry or list handover metadata. Not addressed here — this service has no admin-token model at all yet (see "Admin UI Visibility" above), and adding one was out of scope for this session's plan item.
