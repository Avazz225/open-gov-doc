# user-ui

**Responsibility:** Authenticated web interface for end users — login, folder navigation incl. CRUD, document upload/download (version-aware since P5-S3), document metadata editing, native preview (image/PDF/HTML plus a Word-like view for Office documents, user feedback) with OCR text overlay, full-text/facet search (since P5-S4), electronic signature (since P6-S7), retention/legal hold/trash restore (since P7-S1) (Concept 8).
**Concept reference:** 8, 3.10, 5.2 (since P7-S1)
**No own Postgres schema** — purely client-side rendered SPA (static export, see [ADR 0006](../adr/0006-user-ui-static-export-spa.md)), no own backend process.

## Location in the repo

`apps/user-ui/` — deliberately **not** under `services/` (the Python service template does not fit a Node/React toolchain), see ADR 0006.

## Pages

| Route | Purpose |
|---|---|
| `/login/` | Login (username/password against the Auth Service via the gateway) |
| `/` | `DocumentWorkspace` (since P4-S4) — only reachable with a valid session (client-side redirect to `/login/` when not logged in) |
| `/share/` | Public share link view (`SharePage`, 4.2a, since P14-S10) — **the only page of this app without `RequireAuth`**, see its own section below |

Since **P6-S6**, `RequireAuth` (the auth guard behind every protected route) additionally renders a `MaintenanceBanner` (emergency shutdown, 4.8) as its first child — a pure status banner with no controls (the control itself, triggering/lifting, lives in the Admin UI, `/superuser/`), polls `GET /api/permission-service/maintenance-mode` every 30s, shows a notice text when maintenance mode is active, otherwise `null`, stays silent if the Permission Service is unreachable (fail-open). Implementation of the 4.8 requirement "clearly signaled from every regular UI access" also in the User UI, not just the Admin UI.

## Layout (P4-S4, user feedback after the first real browser test of the MVP; dockable workspace since P16-S1)

Originally (P4-S4) replaced the earlier flat `FolderBrowser` view (P4-S2) with a fixed, resizable three-column layout. **Since P16-S1**, `DockableDocumentArea` (`dockview-react`, see [ADR 0057](../adr/0057-dockbarer-arbeitsbereich-dockview-context-not-params.md)) takes over the entire explorer/document tabs/preview/metadata area as real, VS-Code-like docking (Concept 8) — the earlier fixed `Splitter` layout was dropped for this.

- **`IconRail`** (far left, outside the main content): icon-based cross-cutting navigation. "Documents", since P5-S4 "Search", since **P7-S1c** additionally "Approvals" (`✅`) and since **P7-S1d** additionally "Favorites" (`⭐`) (`WorkspaceView`) switch between the views of `DocumentWorkspace` (`activeView`/`onSelectView`) — previously "Search" was a deliberately visible, disabled placeholder. "Settings" has opened a popover with the `ThemeSwitcher` since P4-S6 instead of remaining disabled.
- **`DockableDocumentArea`** (new since P16-S1, active in the "Documents" view, but stays ALWAYS mounted - see below): hosts three dockview panel types -
  - **`explorer`** panel: renders `ExplorerPane` (see below) - Windows-Explorer-like folder navigation, but now WITHOUT its own tab bar (that carried the open documents until P16-S1, see next point).
  - **`documentPreview`** panel (one per open document): renders `PreviewPane` for exactly ONE document (`params.documentId`, fixed at panel-creation time). All open documents initially sit as tabs of the same dockview group ("document tabs now above the preview instead of above the explorer", the new default arrangement) - a tab can be dragged out into its own group to actually view two documents side by side/stacked simultaneously (Concept 8, provided by dockview itself, no custom code needed).
  - **`metadata`** panel (singular): renders `MetadataPanel` for the currently GLOBALLY active document panel (`onDidActivePanelChange`, filtered to `doc:` panels - a click within the explorer/metadata itself must not accidentally clear the display, see ADR 0057).
  - A **"Default arrangement"** button in the header rebuilds the factory arrangement without closing open documents (`resetLayout`, Concept 8: "resetting to the default arrangement is possible at any time").
  - Layout is stored **per device locally** in `localStorage` (`dms.workspace.dockLayout`, dockview's own `toJSON()`/`fromJSON()` serialization) - not cross-device like the color scheme, exactly as Concept 8 prescribes.
  - Stays **always mounted** when switching to an IconRail special area (contacts, templates, ...), only hidden via CSS - a switch would otherwise discard both the layout and all open documents (see ADR 0057).
- **`ExplorerPane`** (explorer panel): Windows-Explorer-like folder navigation with breadcrumb, folder CRUD (create/rename/delete — the backend endpoints already existed since P3-S3, only the UI for them was missing). The "New folder" form got a **folder class selector** (`applies_to="folder"` object types, same pattern as the document class selector in the upload form) via a bugfix after user feedback — `object_type_id` had already been accepted by the backend since P3-S3, but was never settable via the UI; the selector only appears if at least one folder class exists. Clicking a document opens it as a dockview panel (until P16-S1: as a tab in its own, hand-built tab bar here in the explorer - dropped since P16-S1, see above). Since P5b-S4 additionally: a user-toggleable **tree/list view** (`explorer.viewModeList`/`viewModeTree`, remembered in `localStorage` under `dms.explorer.viewMode`, no cross-device synchronization like the color scheme — see "Open Points") as well as the **class icon** (2.2a/2.2b) before each folder name in both views. Since **P7-S1** additionally a "show trash" toggle (`GET /api/document-service/documents/deleted?folder_id=...`), which shows documents deleted in the current folder with a "Restore" button per row — see its own section below.
- **`FolderTree`** (tree view, new since P5b-S4): builds the folder hierarchy structurally from the root, children are only loaded when a node is expanded (`listChildFolders`/`listDocumentsInFolder`). Clicking a folder name navigates directly there — the breadcrumb path is reconstructed client-side from the already-expanded ancestors, see [ADR 0015](../adr/0015-user-ui-folder-tree-client-side-breadcrumb.md) for the reasoning why no new backend endpoint was needed for this. Documents appear as non-expandable leaves under their folder, clicking opens them as in the list view. **Since P23-S8 also a right-click context menu** (delete/favorite/share link) — instead of duplicating the menu logic (delete-approval requirement, favorite status, share-link visibility all depend on `ExplorerPane`-local state), `ExplorerPane` passes its already-existing `openFolderContextMenu`/`openDocumentContextMenu` functions through as props to `FolderTree`; `FolderTree` only wires `onContextMenu={(e) => onFolderContextMenu(e, folder)}` (or the document equivalent) onto its rows. The same `ExplorerPane` `ContextMenu` instance/the same `contextMenu` state handles the display — the click coordinates are screen-relative (`event.clientX`/`clientY`), independent of which nested component the call came from, so no second menu is needed.

**Drag-and-drop folder move** (8, P23-S4, user request — pure frontend work, `PATCH /folders/{id}` with `parent_id` already existed unchanged): every folder row in both views (`ExplorerPane` list AND `FolderTree` tree) is draggable via native HTML5 `draggable`; a drop onto another folder row (or onto the tree root row) calls the new `moveFolder()` API function with the dragged folder and the target ID, followed by a reload of the affected view(s). Deliberately NO separate `dataTransfer` payload — the dragged folder is instead kept in local state (simpler, `dataTransfer` isn't readable during the `dragover` event anyway). Visual feedback via a new `.entry-row-drag-over`/`.tree-row-drag-over` class (same look as dockview's own drag-over indicator, `--dv-drag-over-*`). Two safeguards against a cycle: the backend endpoint only rejects "folder becomes its own direct parent folder" (`repository.update_folder`), `FolderTree` additionally checks client-side that the target is not a currently tree-visible descendant of the dragged folder (folder ID appears in the target's ancestor chain) — this only covers the part loaded in the tree, no substitute for a full server-side cycle check (see `docs/services/folder-service.md` "Open Points" for the remaining gap confirmed live in that session: a cycle forced via two separate `PATCH` calls makes both involved folders undeletable). `ExplorerPane`'s flat list view has no ancestor chain available and only checks "don't drop onto itself".
- **`MetadataPanel`** (metadata panel): metadata of the currently active document (see above). Since P5b-S4 the attribute form fields are no longer arranged in fixed attribute order (one field per row), but via the object type's **"display" form layout** (2.2b, `GET /api/object-type-service/object-types/{id}/layouts/display`) — `LayoutFormFields` renders the row/column grid, the object type schema (`GET .../object-types/{id}`) still supplies the attribute type (for the input field type) and value range. `required` now comes from the layout field, no longer from the raw attribute (an attribute can, per Concept 2.2b, be mandatory differently depending on the usage purpose). Without an assigned object type, only the title remains editable. Saves via the `PATCH /api/document-service/documents/{id}` present since P4-S4 - since P16-S1 a save additionally updates the title of the associated dockview tab (`panel.api.setTitle()`). Since **P5e-S3** additionally a dedicated `Kennzeichen` (file reference number) field, permanently displayed outside the layout grid, as soon as this reserved attribute key is set — see its own section below. Since **P6-S7** `MetadataPanel` additionally renders a `SignaturesPanel` section (3.10) below the form — see its own section below.
- **`SearchPane`** (own special area, "Search" view, new since P5-S4): search field + object type selector that shows matching attribute filters (range filter for `date`/`decimal`/`integer`, exact match otherwise). Since P5b-S4, the arrangement/labeling/selection of the filter fields follows the selected object type's **"search" form layout** (2.2b) instead of the raw attribute order — an admin can deliberately exclude individual attributes from the search mask or label them differently via the layout designer (Admin UI, P5b-S3). If the layout cannot be loaded, `SearchPane` falls back to a one-attribute-per-row layout (identical to the behavior before P5b-S4), so that search doesn't become unusable due to an Object Type Service outage. Clicking a result opens it via the same `openDocumentTab()` function as a document from the explorer and **since P16-S1** automatically switches to the documents view (previously a document opened from search remained unnoticed open in the background, since the preview was only visible within the documents view — see ADR 0057).
- **`UploadForm`** (upload dialog, triggered from `ExplorerPane`): before P5b-S4 knew nothing about object types at all (only file + title). Since P5b-S4, a **document class** can be selected on upload (`GET /api/object-type-service/object-types?applies_to=document`); its attribute fields are arranged via the **"upload" form layout** (2.2b), analogous to `MetadataPanel`/`SearchPane`. The object type hierarchy check (2.2a, `allowedParentTypes`) is still handled exclusively by the Document Service server-side on `POST /documents` — this UI does not duplicate that check, a violation simply shows the error message delivered by the server. **Since P5d-S2** a real modal dialog (`role="dialog"`, reuses the previously unused `.modal-backdrop`/`.modal-content` classes) instead of a form shown inline in `ExplorerPane` — additionally accepts drag-and-drop of files onto the entire open dialog surface (`onDragOver`/`onDrop`, not just onto the `<input type="file">`), closes after a successful upload as well as via an explicit close/cancel button.
- **`PreviewPane`** (one panel per open document, see above): since P5-S2 loads the thumbnail rendition generated by the Rendering Service and shows it as an image, provided one with status `ready` exists. Since P5-S3 additionally: version selector (`<select>`, only visible with more than one version) as well as a pixel-accurate text overlay from the OCR Service's word bounding boxes, letting recognized text be selected/copied directly over the image (user feedback after P5-S2). **Since P16-S1** the `aria-label` carries the document title (`"Preview: {title}"` instead of just `"Preview"`) - since multiple `PreviewPane` instances can now be in the DOM simultaneously (one panel per open document), a blanket label would no longer be unambiguous for screen reader users.

Until P16-S1 all three content columns were resizable via `Splitter` drag handles (`dms.explorer.leftWidth`/`dms.explorer.topHeight` in `localStorage`) - superseded by dockview's own resizing/persistence (see above). `Splitter.tsx` remains in the repo as an unused but functioning component (no compelling reason to delete it, see ADR 0057).

## Auth state

`src/lib/auth-context.tsx`: access/refresh token in `localStorage` (`dms.tokens`), proactive refresh shortly before expiry (`setTimeout` based on `expires_in`). A known, deliberate simplification of this foundation: no httpOnly cookie, see ADR 0006 "Open Points"/consequences.

## SSO/automatic login (ad-hoc post-roadmap feature, see ADR 0062)

`app/login/page.tsx` queries `GET sso-config` before rendering the password form; if SSO is active installation-wide (and no `?ssoError=1` parameter is already set, to avoid a redirect infinite loop after an already-failed attempt), the browser is immediately redirected — without ever showing the form — to a Keycloak URL obtained via `GET oidc/authorize`. A `state` value (`dms.sso.state`) stored in `sessionStorage` before the redirect serves as CSRF/replay protection.

New `app/login/callback/page.tsx`: reads `code`/`state` from the URL, compares `state` against the stored value, calls `POST oidc/callback` and takes over the session via `auth-context.tsx`'s now publicly exposed `applySession()` (previously internal, used by the regular form login) — no duplicated token storage path. On any error, back to `/login?ssoError=1`. A standalone client page instead of middleware/SSR, since `user-ui` is statically exported (no server for a server-side redirect callback, see Concept 8).

`logout()` in `auth-context.tsx` additionally calls (best-effort, does not block the local logout on a network error) the new `POST /logout` endpoint — without this, an SPNEGO-capable browser would immediately auto-log-in again on the next visit, since Keycloak's own SSO session would otherwise persist.

**Not verifiable in this sandbox**: the actual automatic login via a real Kerberos ticket (no domain controller available here). The existing password form remains fully available as a fallback — no user is locked out by the configuration.

## Preview (2.4/3.9, connected to the Rendering Service since P5-S2, additionally to the OCR Service since P5-S3, additionally client-side direct text display since P5d-S2, additionally `substitute_text` rendition display + multi-page navigation since a bugfixing pass after P7-S0, additionally native image/PDF/HTML preview + Word-like view for Office documents since a further user-feedback pass, additionally engine-dependent PDF branching + separate image text extract since an OCR user-feedback pass)

`components/PreviewPane.tsx` first loads the version list (`listDocumentVersions()`) when a document is opened (`useEffect`, dependency `activeDocument?.id`) and sets the selection to `current_version_number`; a second effect (dependency `[activeDocument?.id, selectedVersion, versions]`) decides based on the `content_type` of the selected version (from the same version list, a server-side-sniffed value since P5d-S1 instead of a client header):

**HTML rendered sandboxed (user feedback: `text/html` previously landed unintentionally in the text branch, since it satisfies its `text/*` prefix check, and was only shown as raw, escaped markup)**: if the content type is exactly `text/html`, the original content is loaded via `downloadDocumentVersion()` and rendered via an `<iframe sandbox="" referrerPolicy="no-referrer" srcDoc={...}>`. `content_type` comes from purely magic-byte-based sniffing with no allow/deny list (`document-service/content_type_sniffer.py`) — any uploaded file whose bytes look like HTML is trusted as `text/html`. The empty `sandbox=""` (no `allow-scripts`, no `allow-same-origin`, no `allow-forms`/`allow-popups`/`allow-top-navigation`) is therefore mandatory, not optional: it prevents an uploaded document from later executing scripts against the session of whoever is viewing it (stored XSS). This is the first untrusted-HTML rendering in this codebase (no prior iframe/`dangerouslySetInnerHTML` precedent in `apps/user-ui`/`apps/admin-ui`).

**Direct text display (P5d-S2, user feedback: `.txt`/`.json` had no working preview)**: if the content type is otherwise `text/*` or `application/json`, the original content is loaded directly via `downloadDocumentVersion()`, decoded as text (`Blob.text()`) and shown in a `<pre class="preview-text">` block (with a truncation notice from 200,000 characters onward) — no new rendering-service renderer, no rendition detour for already text-based content. Renditions/OCR are not even requested for this case.

Otherwise the effect first loads `listRenditions()`:

- **Word-like A4 view via the `pdf_archive` rendition** (user feedback: Office documents previously only had the flat `substitute_text` extraction, no formatted view) — rendering-service already automatically converts Office/text formats via LibreOffice into a real, paginated PDF (`pdf_archive`, originally intended only as an archive copy, 3.7/5.6). If a `ready` rendition of this type exists (excluding image and PDF sources, which have their own more direct raw-byte branch further below), it is loaded via `downloadRenditionContent()` and shown via the same `<embed type="application/pdf">` as native PDFs — no separate "Word viewer" needed, the LibreOffice conversion already delivers the page formatting. If the rendition is not yet finished/has failed, the preview falls back to the `substitute_text` rendition (bugfix after earlier user feedback: `.docx`/`.pptx`/`.ods` preview stayed empty despite an already-generated text extraction) — rough text is better than nothing.
- Otherwise the effect loads the OCR result (`listOcrResults()`). **For PDFs, since a further user-feedback pass, `ocrResult.engine` decides whether the word overlay or the native view takes precedence** (previously any existing OCR result unconditionally took precedence): `engine === "tesseract"` means the PDF is (still) a pure scan without a usable text layer (processing not yet run, failed, or a historical old version) — the overlay remains the correct, still-reachable **fallback** here. `engine === "native_text_layer"` (or no result at all) means the PDF already has a real text layer — whether from the start, or because the OCR Service has since embedded an invisible text layer (see `docs/services/ocr-service.md` "Searchable PDF") — and the native `<embed>` view below shows the real, searchable content directly, no overlay detour needed anymore. For images, the overlay behavior remains unchanged (any engine, as before) — if an OCR result exists, `ocrResult`/the rendition list is stored in state, the actual loading of the page image is handled by a **second, independent effect** (dependency `[ocrResult, selectedPage]`), so that a pure page change (see below) does not re-query renditions/OCR results.
- This second effect first tries `downloadOcrPageImage(token, ocrResultId, selectedPage)` (only for PDFs — the OCR Service rasterizes all pages itself, since rendering-service does not produce PDF thumbnails); if that fails (raster-image case, 409) or no overlay applies per the engine switch above, **in the first effect** one of two native fallback branches applies: an `application/pdf` document is loaded raw via `downloadDocumentVersion()` and shown via `<embed type="application/pdf">` (no rendition detour needed, the original is already a valid PDF); an `image/*` document is likewise shown via its raw bytes at **full resolution** as an `<img>` (user feedback: previously there was only a 256×256 thumbnail rendition, never the real image — this rendition is no longer consulted for any preview case, `ThumbnailRenderer` in rendering-service only supports image sources anyway).

Both image paths (OCR page image as well as native image) show the result as an `<img>` via a blob URL created with `URL.createObjectURL` — on change/unmount the previous blob URL is released again (`URL.revokeObjectURL`). If a `ready`/`needs_review` OCR result exists, a **text overlay** is additionally rendered from the word bounding boxes of the respectively selected page: a `<div>` per word, invisible (`color: transparent`) and positioned precisely as a percentage over the image (`left/top/width/height` as `%` of `page.width`/`page.height`, the same principle as pdf.js's text layer) — users can select and copy the recognized text directly over the document image. The font size of each word is adjusted to the actually rendered image height via a `ResizeObserver` on the `<img>`, so that selecting/double-click word selection stays accurate at any splitter width/zoom level. A `needs_review` result additionally shows a small warning notice, but does not hide the overlay (the text remains usable).

**Separate text extract for image documents** (user feedback, purely additive alongside the overlay): if an OCR result with non-empty `full_text` exists for an `image/*` document, an expandable `<details open className="ocr-text-extract">` below shows the complete recognized text in a `<pre class="preview-text">` — deliberately separate from the overlay ("no mixing"), a purely client-side display of an already-loaded field, no new backend call. This extract does not exist for PDFs — there, the native `<embed>` view (with a real, searchable text layer) makes a separate text block unnecessary.

**Page selection for multi-page PDFs** (bugfix after user feedback: previously only `ocrResult.pages[0]` was ever shown regardless of the actual page count, since the OCR Service itself only processed page 1, see `docs/services/ocr-service.md`): if `ocrResult.pages.length > 1`, a `<select>` appears analogous to the version selector ("select page"); the selection only sets `selectedPage`, the second effect above then specifically loads only the new page image.

Renditions/OCR results are deliberately an added benefit, not a blocker (2.4/3.9): if nothing suitable exists (wrong format, load error), the column falls back to a notice text — the download button (now version-aware, `downloadDocumentVersion()`) remains usable in every case.

**Polling for not-yet-finished renditions/OCR results** (P23-S3, user request): `rendering-service`/`ocr-service` each only create their rendition/OCR row AFTER processing completes (`status` only knows completed final states in both services — `ready`/`failed`/`failed_permanent` or additionally `needs_review`/`skipped` — there is no dedicated "pending" status in the API); a not-yet-finished result is thus recognizable by the row's **absence**, not by its status. Two separate, independently running polling mechanisms in `PreviewPane.tsx` (`RENDITION_POLL_INTERVAL_MS = 7000`, `RENDITION_POLL_MAX_ATTEMPTS = 8`, ~56s total window — deliberately limited, otherwise a format without a supported rendition or a document with OCR triggering disabled would keep polling forever):

- **Renditions** (Office/text formats without their own raw-byte path): the load loop waits BEFORE the preview decision — as long as neither `pdf_archive` nor `substitute_text` is ready, the display stays at "Loading preview…", a renewed `listRenditions()` call runs every 7s until one of the two renditions is ready or the upper limit is reached (then a notice text as before).
- **OCR overlay** (PDFs/images): the native PDF/image view appears immediately (unchanged, no waiting), a separate background poll runs in parallel and calls `setOcrResult(...)` as soon as a result is ready — the preview then switches afterward to the word-overlay view, without interrupting the already-visible native view.

Both polling loops run via the same `cancelled` flag pattern as the rest of the effect and stop cleanly on document/version change or unmount (no hanging timer after closing a tab).

**Version selector shows `is_conflict`/`comment`** (P23-S1, user request — these two fields already existed in `DocumentVersion` since P5-S3, but were invisible in the UI): every `<option>` of the version selector gets a `⚠` suffix in the visible label when `is_conflict === true`, as well as, when a `comment` is set, a native `title` attribute as a tooltip. Additionally (not only on hover) a `.badge.down` element with the text "Conflict" as well as a visible comment text below the `<select>` show the same fields of the currently selected version — the badge/comment `<span>`s are deliberately placed as siblings AFTER the `<label>`, not nested within it: nesting would have pulled their text into the accessible name of the `<select>` via the implicit label association (`getByLabelText("Select version")` would then no longer have matched). No diff viewer, no change to `document-service`/`api.ts` — purely visibility of already-loaded data.

**Download error display** (Post-Roadmap Phase 19 Session 11, [ADR 0076](../adr/0076-root-folder-mail-regex-dehydration-409.md)): `handleDownload()` in `PreviewPane` previously handled a failed click on the download button completely silently (empty `catch`) — particularly for a dehydrated (archived-out) document (`409` from `document-service`, see `docs/services/document-service.md`) this felt like clicking into a void. A new `downloadError` state (reset on document/version change) now shows a `<p className="error-text" role="alert">` below the preview — for `ApiError` with `status === 409` a targeted message with a retrieval hint (`preview.downloadErrorDehydrated`), for any other error a generic fallback message (`preview.downloadErrorGeneric`).

## Direct Office editing (ad-hoc post-roadmap feature, see ADR 0061)

Next to the download button, `PreviewPane` shows an "Open in {App}" button for Word/Excel/PowerPoint documents (`officeLaunchInfo(currentContentType)` in `src/lib/api.ts` — content-type→schema/extension/label mapping). Clicking it requests a short-lived `WebdavEditToken` from `document-service` (`createWebdavEditToken()`) and navigates the browser to the result of `officeLaunchUrl()` — an Office URI scheme address (`ms-word:ofe|u|...`/`ms-excel:ofe|u|...`/`ms-powerpoint:ofe|u|...`) with the token as basic-auth userinfo directly in the URL (`https://<token>:@<webdav-connector-host>/webdav/by-id/<document-id>.<ext>`), so that the locally installed Office program opens the file without an intermediate step/password dialog via WebDAV.

`webdav-connector` is the only service addressed via `api.ts` that does NOT run through the gateway (no WebDAV proxying planned) — therefore needs its own build-time address (`NEXT_PUBLIC_WEBDAV_CONNECTOR_BASE_URL`, analogous to `NEXT_PUBLIC_GATEWAY_BASE_URL`).

**Not verifiable in this sandbox**: the actual Office launch and whether the credentials dialog is thereby reliably suppressed (no Windows/Office available here) — the same sandbox boundary as with `apps/office-addin` (ADR 0045), deliberately documented here instead of silently assumed.

## Form layouts & class icons (2.2a/2.2b, since P5b-S4)

- **`components/LayoutFormFields.tsx`**: shared renderer for the row/column grid of a form layout, used equally by `MetadataPanel`, `SearchPane` and `UploadForm` (no triple-duplicated grid/breakpoint markup). Takes a `LayoutData` (`rows`/`responsive_breakpoint_px`) as well as a `renderField(field)` callback that supplies the actual input element per layout field (components thereby remain responsible for the content-specific field logic, `LayoutFormFields` only for arrangement/responsive behavior).
- **Responsive breakpoint** (since **P23-S6** via a real CSS container query instead of window width): `.layout-grid-container` carries `container-type: inline-size`, so that `@container` rules measure the actual width of THIS panel — a narrowly resized (dockview) panel in a wide window now correctly stacks single-column, independent of the window width (fixes the previous coupling, which was literally described as "window width" in the concept but undesirable in practice — see "Open Points", now closed). The threshold (`layout.responsive_breakpoint_px`, admin-configurable per object type) cannot be inserted as a CSS variable into an `@container` width condition (only style queries could do that, but they don't cover width) — `LayoutFormFields` therefore generates the rule as an **inline `<style>` block with the concrete pixel value**, scoped via a `data-layout-container` identifier unique per component instance (`useId()`), so that multiple simultaneously open panels with different layouts (e.g. two document tabs of different object types) don't interfere with each other. The previous `window.innerWidth` `resize` listener (`useIsBelowBreakpoint`) has been dropped entirely — a pure CSS solution, no more JS resize handling needed.
- **Class icons** (`lib/icons.ts`): the same curated seven-icon set as in the Admin UI object type editor (P5b-S3), deliberately duplicated instead of shared (ADR 0006). Since `icon` is only allowed server-side for folder classes (2.2a), documents always show the fixed 📄 — only folders resolve their actual class icon (`folderIcon()`, fallback 📁 without/with an unknown icon value).
- **Tree view** (`components/FolderTree.tsx`): see its own section above and [ADR 0015](../adr/0015-user-ui-folder-tree-client-side-breadcrumb.md).

## Bulk metadata editing (Concept §8, since P14-S12)

See [ADR 0050](../adr/0050-bulk-metadata-edit-frontend-loop-over-existing-patch-endpoints.md) for the full architectural reasoning. **Deliberately frontend-only** — no new backend endpoint, the new `components/BulkEditModal.tsx` calls the already-existing single-PATCH endpoint individually for each selected object (`updateDocumentMetadata`/new `updateFolderAttributes` in `lib/api.ts`), so that exactly the same constraint check applies as with a single edit.

- **Multi-selection in `ExplorerPane.tsx`**: new checkboxes per row in the list view (no counterpart in the tree view — explicitly outside the scope of this session), selection as a `Set<"kind:id">` key (same pattern as the existing favorites keys), automatically cleared on folder change or toggling the trash. As soon as at least one entry is selected, a second toolbar row appears ("N selected", "Bulk edit" button, "Clear selection" button).
- **`BulkEditModal.tsx`** (new): requires a **homogeneous selection** (only documents OR only folders, all with the same, set `object_type_id`) — otherwise a blocking notice text instead of a form, since a single form can only meaningfully render a single attribute schema. On a homogeneous selection, loads the shared object type + its layout (`getObjectType`/`getObjectTypeLayout`, reuses `LayoutFormFields.tsx`) and renders a form with one input field per attribute. **A field left empty means "leave unchanged for this object", not "clear"** — on submit, only actually filled fields are merged into a copy of each object's own existing `attributes` (server replaces `attributes` entirely, no server-side merge — identical pattern to `MetadataPanel.tsx`'s single editing). `title`/name is deliberately not part of the form (no meaningful shared adoption of an identical name). After submitting, the modal shows a **result list per object** (success/failure, on failure the error message extracted from the `400` body) — deliberately not atomic, each PATCH call succeeds/fails independently of the others.
- **`folder-service` prerequisite**: dedicated research before implementation found that `PATCH /folders/{id}` previously only ran the object type constraint check on an actual move — fixed (see `docs/services/folder-service.md`), otherwise bulk editing of folders would have effectively not enforced the required constraint check.

## Authenticated direct links (Post-Roadmap Phase 29, [ADR 0109](../adr/0109-direct-link-url-scheme.md))

`DocumentWorkspace.tsx` reads `?document=<id>`/`?folder=<id>` from `window.location.search` once on mount (not `useSearchParams()`, same Suspense-avoidance reasoning as the share link's `/share/` page above) and resolves them via the already-existing `GET /documents/{id}`/`GET /folders/{id}` plus the already-existing `openDocumentTab`/`openFolderPath` navigation functions — no new backend endpoint. A `403`/`404` surfaces via the normal `error` state instead of a silent fallback to the root folder. Structurally opposite to the public share link (anonymous, single-document, token-bearing) — a direct link carries no secret, just a stable resource ID resolved through the normal session/permission-check path, see ADR 0109 for the full comparison.

**"Copy link"**: new context menu entries in `ExplorerPane.tsx` (folder/document) and a button in `PreviewPane.tsx`, all calling `navigator.clipboard.writeText()` — the first use of the Clipboard API in this project (see the note on `ShareLinkModal.tsx` above for why it wasn't used there).

A human should click through the interface in a real browser before production use. **Likewise for the user-feedback fix on native preview**: `.txt`/`.html`/`.pdf`/`.jpg`/`.docx` test documents were actually uploaded against the running Compose stack — server-side sniffing delivered the expected `content_type` for all five; the `.docx` file automatically got a `ready` `pdf_archive` rendition (a real, LibreOffice-generated, paginated PDF with the correct text, verified via `pypdf`) and still a `ready` `substitute_text` rendition; `GET .../content` delivered the correct content-type header and byte-identical raw data for PDF/JPG/HTML respectively (for HTML explicitly including an untouched `<script>` tag — server-side storage sanitizes nothing, the sandbox in `PreviewPane` is the only, but per the test sufficient, protection). The actual DOM rendering (`<embed>`/`<iframe>`/`<img>`) is, for lack of a browser in this environment, only backed by the Vitest component tests (jsdom), not visually.

## Open Points

- Tokens in `localStorage` instead of an httpOnly cookie (XSS risk deliberately accepted, see ADR 0006).
- ~~Preview has, since the bugfixing pass after P7-S0, also shown `substitute_text` renditions (text), but still no own view for `pdf_archive` renditions — more a download than a preview candidate.~~ Closed (user feedback): `pdf_archive` is now the preferred preview path for Office documents (Word-like A4 view), native PDFs/images show their raw bytes directly, HTML is rendered sandboxed — see "Preview" section above.
- ~~Sandboxed HTML preview does not block loading of external subresources~~ — **fixed in Post-Roadmap Phase 21 Session 3** ([ADR 0086](../adr/0086-html-preview-external-subresource-blocking.md)): `document-service` neutralizes every external `src`/`href` reference server-side, BEFORE the HTML content ever reaches `user-ui` (`html_preview_guard.rewrite_external_references`, see `docs/services/document-service.md`) — solves the problem at the source instead of via a (only limitedly effective anyway for `srcDoc` content) CSP header. `referrerPolicy="no-referrer"` and `sandbox=""` remain unchanged as additional protection layers. Deliberately NOT covered: `srcset`/`poster`/`background` attributes as well as `url(...)` within `style` content (see ADR 0086 "Consequences").
- ~~Version history only shows the version number (no diff, no comment/conflict display UI despite existing backend fields such as `is_conflict`/`comment`)~~ — **fixed in P23-S1**: see "Version selector" paragraph above. Still no full diff viewer (deliberately outside the session scope).
- Search snippet with no highlighting markup (no sanitizing exists in this codebase, see the search section above).
- No workflow interaction (approvals/tasks) — the workflow engine only exists from Phase 6 onward.
- No automated browser E2E possible in this environment (no Chrome/Chromium installed) — to be caught up on once an environment with a browser is available (e.g. CI).
- Role-dependent views/branding (Concept 8, "customizability") not part of this foundation.
- i18n only structurally prepared (ADR 0007), no second language and no UI language switching.
- Theme preference has no conflict resolution mechanism between devices (last fetch wins) and no retry on a failed `PUT /me/preferences` (see ADR 0009 "Consequences").
- Known backend gap, originally surfaced at P4-S4: `DELETE /folders/{id}` (raw hard-delete fallback) still only checks for subfolders, not contained documents. For the regular deletion path used in the UI since **P7-S1b** (`POST .../folders/{id}/trash`), this is fixed — the trash correctly cascades to contained documents (see `docs/services/folder-service.md`); only the less-frequently-used hard-delete fallback itself still has the original gap.
- **Tree/list view preference only local in the browser** (`localStorage`, `dms.explorer.viewMode`), unlike the color scheme no cross-device synchronization on the user account (P5b-S4) — a deliberate simplification, since it is a pure display preference with no business consequence, but pragmatically less effort than another Keycloak-attribute round trip like the theme (ADR 0009).
- **Tree view can only navigate to folders already expanded in the tree** (see ADR 0015) — no deep link/no direct folder ID addressing, currently no restriction since there is no such input path in the UI.
- **Upload dialog does not duplicate the object type hierarchy check** (2.2a) — offers all document classes independent of the current folder; a violation of `allowedParentTypes` is only rejected server-side on `POST /documents` and shown as a generic error message, no pre-filtering of the selection list.
- **File-reference-number display resolution is purely client-side duplicated** (2.2, P5e-S3) — `ExplorerPane`/`FolderTree` resolve override-vs-global-default themselves, there is no central "resolved display" endpoint (see `docs/services/object-type-service.md` "file-reference-number generator"); this might need to be centralized with a third frontend consumer.
- **`Kennzeichen` field in the metadata panel does not validate the format on privileged changes** — a `dms-admin` user can enter any arbitrary string, even one that does not match the configured `kennzeichen_format` (backend deliberately does not validate this, see `docs/services/document-service.md`).
- **`MaintenanceBanner` (4.8, since P6-S6) is a pure status display with no controls** — triggering/lifting the emergency lock is only possible via the Admin UI, consistent with the existing role split (end users see the state but do not manage it).
- **QES only visible as a disabled option in the level selector**, no indication of what minimum level the current object type actually requires — a user only learns this via the backend error message on a too-low chosen level.
- **`RetentionPanel` (5.2/5.2a, since P7-S1) has no role restriction for setting/releasing a legal hold** — any logged-in user can do it, see its own section above.
- **Trash toggle only per currently open folder**, no installation-wide trash overview across all folders — deliberately minimal, the full "trash family" is Phase 15 "Special areas" per `IMPLEMENTATION_PLAN.md`.
- **`FolderRetentionModal` (5.2/5.2a, since P7-S1b) has no role restriction** — identical open question as with `RetentionPanel` (see above).
- **Approval inbox (`ApprovalsPane`, since P7-S1c) filtered only for `document.delete`/`folder.delete`, no reject-reason input field** — `rejectApprovalRequest` supports an optional reason, the UI currently calls it with no reason; per user feedback a preliminary stage toward a later-planned "administrative trash".
- **No Admin UI toggle for `document.delete`/`folder.delete` approval requirement** (5.2, since P7-S1c) — identical, already-existing gap as with `document.force_delete`/`folder.force_delete`/`document.force_unlock`, only configurable via the raw `PUT /approval-config/{action_type}` API.
- **Right-click context menu only for folder/document rows in the list view** (since P7-S1c) — `FolderTree` (tree view) still has no delete/context-menu interaction, unchanged since P5b-S4.
- **Favorites only for documents/folders, no case binders** (since P7-S1d) — a deliberate scope decision at plan approval, since `case-service` still has no own UI (see `PROGRESS.md`).
- **`FavoritesPane` resolves each favorite individually via HTTP** (since P7-S1d, `Promise.all` over `getDocument`/`getFolder`) — with very many favorites (practically unlikely for a personal bookmark feature) no batch endpoint, no paging.
- **No favorites marker in the `FolderTree` tree view** (since P7-S1d) — the ⭐ prefix so far only appears in `ExplorerPane`'s list view.
- ~~`TeamspacesPane` shows members as a raw `principal_id` UUID, no resolved username~~ — **fixed in Post-Roadmap Phase 19 Session 4** ([ADR 0069](../adr/0069-rueckwaerts-identitaetsaufloesung.md)): a new `GET /users/{id}` endpoint in `auth-service` plus a `usePrincipalNames` hook (`src/lib/usePrincipalNames.ts`), shared by `DelegationsPane` and `TeamspacesPane` to resolve raw IDs into usernames (falls back to the UUID on failure). No browser verification possible for this session (no browser tool in the sandbox), backed by `tsc`/`eslint`/`vitest`/`next build` as well as a live verification of the underlying backend endpoint via the gateway.
