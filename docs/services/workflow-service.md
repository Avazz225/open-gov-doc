# workflow-service

**Verantwortung:** Workflow Engine Grundgerüst (Konzept 7.1) — BPMN-2.0-Import und -Ausführung über [SpiffWorkflow](https://github.com/sartography/SpiffWorkflow) (LGPLv3, [ADR 0018](../adr/0018-spiffworkflow-lgpl-license.md)), Manual/Automatic Tasks, seit P6-S2 auch Timer/Boundary Events (SLA-Zeitüberwachung, [ADR 0020](../adr/0020-sla-timer-polling.md)), seit **P6-S7** zusätzlich der "Signature Task" (3.10, technisch eine Sonderform des Manual Task), seit **P6-S9** zusätzlich föderierte Prozessschritte über den Federation Hub (7.4, technisch ebenfalls Manual-Task-Sonderformen), seit **P12-S2** zusätzlich generische Connector-Service-Tasks (7.1 "Auslösen eines Connector-Aufrufs" — erster Nutzer `migration-service`, 7.2) + `POST /instances/{id}/retry` (Resumability für fehlgeschlagene automatische Schritte). UI folgt mit P6-S8 (`apps/process-designer`). Seit **P6-S6** teilweise gegated: Prozessdefinitionen anlegen/löschen erfordert die Capability `admin.object_config` (4.6-Retrofit), Instanzstart/Task-Abschluss bleiben für jeden authentifizierten Principal offen, respektieren aber den systemweiten Wartungsmodus (Not-Shutdown, 4.8) — siehe [ADR 0024](../adr/0024-not-shutdown-gateway-enforced.md).

**Konzept-Referenz:** 7.1, 4.6, 4.8, 3.10, 7.4, 7.2
**Eigenes Postgres-Schema:** `workflow` (Tabellen `process_definition`, `process_instance`, seit P6-S9 zusätzlich `federation_identity`, `federation_task`)

## API

| Methode | Pfad | Beschreibung |
|---|---|---|
| `POST` | `/process-definitions` | Anlegen (multipart: `bpmn_xml` Datei, `name`, optional `process_id`) — parst die BPMN-XML über SpiffWorkflow; ohne `process_id` wird automatisch aufgelöst, aber nur wenn die Datei genau einen ausführbaren Top-Level-Prozess enthält. `422` bei nicht parsbarer/mehrdeutiger BPMN-Datei. **Seit P6-S6**: erfordert `X-DMS-Principal` mit der Capability `admin.object_config` (4.6), sonst `403`. **Seit P6-S8**: `name` ist der Prozessfamilien-Schlüssel — ein bereits existierender Name erzeugt automatisch die nächste `version` statt `409` (siehe "Versionierung" unten) |
| `GET` | `/process-definitions?name=` | Ohne `name`: neueste Version je Prozessfamilie. **Seit P6-S8** mit `name`: vollständige Versionshistorie dieser Familie, neueste zuerst (nur Metadaten, ohne `bpmn_xml`) |
| `GET` | `/process-definitions/{id}` | Detail inkl. `bpmn_xml` — `404` |
| `DELETE` | `/process-definitions/{id}` | Löschen — `409` falls noch Prozessinstanzen existieren, sonst `204`. **Seit P6-S6**: gegated wie `POST /process-definitions` |
| `POST` | `/process-definitions/{id}/instances` | Instanz starten (`created_by`, optional `business_key`, `initial_data`, seit **P12-S2** optional `instance_id`) — führt alle bereiten automatischen Tasks sofort aus (`do_engine_steps()`), Status ist `"completed"`, wenn der Prozess dabei ohne Manual Task durchläuft, sonst `"running"`. **Seit P6-S6**: `503` bei aktivem `X-DMS-Maintenance-Active`-Header (4.8), sonst weiterhin offen für jeden authentifizierten Principal. **Seit P12-S2**: `instance_id` lässt den Aufrufer seine eigene Referenz bestimmen statt eine serverseitig generierte entgegenzunehmen (gleiches Muster wie `federation-hub-service`s `handover_id`, ADR 0028) — wichtig, wenn bereits der erste automatische Schritt fehlschlagen kann, siehe "Connector-Service-Tasks" unten |
| `POST` | `/instances/{id}/retry` | **Seit P12-S2**: Resumability für einen fehlgeschlagenen automatischen Schritt (z. B. ein `connector_call`, dessen `serviceUrl` nicht erreichbar war) — versetzt `ERROR`-Tasks zurück auf `READY` und führt `do_engine_steps()` erneut aus, ohne die Instanz neu zu starten. `404` bei unbekannter Instanz, `409` wenn sie nicht `running` ist. Kein zusätzliches Rollen-Gate über die Lizenzprüfung hinaus (wie Instanzstart/Task-Abschluss) |
| `GET` | `/instances/{id}` | Status/Metadaten — `404` |
| `GET` | `/instances?process_definition_id=&status=&business_key=` | Gefilterte Liste |
| `GET` | `/instances/{id}/tasks` | Aktuell bereite Manual/User Tasks (`id`, `name`, `lane`, `data`, seit **P6-S7** zusätzlich `extensions` — Camunda-`extensionElements`-Properties, leer bei gewöhnlichen Manual Tasks, `{taskType: "signature", requiredLevel: ...}` bei einem Signature Task) |
| `POST` | `/instances/{id}/tasks/{task_id}/complete` | Task abschließen (`completed_by`, optional `data`, seit **P6-S7** optional `signature_id`) — `404` bei unbekannter Instanz, `409` wenn `task_id` nicht (mehr) bereit ist (bereits abgeschlossen, falsche ID). **Seit P6-S6**: `503` bei aktivem Wartungsmodus, gleiches Muster wie Instanzstart. **Seit P6-S7**: ist die Task laut `extensions` ein Signature Task, ist `signature_id` Pflicht und muss auf eine beim `signature-service` existierende, zum Task-Dokument passende Signatur mit ausreichendem Niveau verweisen — sonst `400` (siehe "Signature Task" unten). **Seit P6-S9**: ein `taskType=federated`/`federated_return`-Task lehnt direkte Aufrufe mit `409` ab (wird ausschließlich automatisch über den Federation Hub abgeschlossen, siehe "Federation" unten) |
| `GET` | `/federation/installations` | **Seit P6-S9**: Proxy auf das Adressbuch des konfigurierten Federation Hub (7.4) — leere Liste ohne konfigurierten Hub, ungegated wie andere `GET`s |
| `POST` | `/federation/inbound` | **Seit P6-S9**: öffentlicher Endpunkt (kein `X-DMS-Principal`), vom Federation Hub aufgerufen — startet eine neue lokale Instanz aus einer eingehenden föderierten Übergabe. Authentisierung über `X-Federation-Hub-Signature` statt Principal, `401` bei ungültiger/fehlender Signatur, `422` bei unbekanntem Prozesstyp-Mapping oder nicht entschlüsselbarem Payload |
| `POST` | `/federation/inbound-result` | **Seit P6-S9**: öffentlicher Endpunkt, vom Federation Hub aufgerufen — schließt den ursprünglich wartenden `federated`-Task programmatisch mit dem zurückgemeldeten Ergebnis ab |
| `GET` | `/healthz` | Health-Check |

## Datenmodell

- `process_definition`: `id`, `name` (seit P6-S8 der Prozessfamilien-Schlüssel, nicht mehr global eindeutig, siehe "Versionierung" unten), `version` (Integer, Default 1, eindeutig zusammen mit `name`), `bpmn_process_id` (die interne Prozess-ID aus der BPMN-XML selbst, `<bpmn:process id="...">`), `bpmn_xml` (Text, die vollständige hochgeladene Datei), `created_at`/`updated_at`.
- `process_instance`: `id` (UUID), `process_definition_id` (FK), `business_key` (String, nullable, opake Cross-Service-Referenz z. B. auf eine künftige `document_id` — **nicht** gegen den Document Service validiert, gleiches Muster wie `folder_id`/`object_type_id` vor ihrer jeweiligen Durchsetzung in früheren Phasen), `status` (`"running"`\|`"completed"`), `workflow_state` (Text — vollständiger, von SpiffWorkflow serialisierter Ausführungszustand, siehe "State-Persistenz" unten), `created_by`, `created_at`/`updated_at`/`completed_at` (nullable).

## Versionierung (seit P6-S8, ADR 0027)

`name` ist der Prozessfamilien-Schlüssel: `POST /process-definitions` unter einem bereits existierenden Namen legt automatisch die nächste `version` an (`max(version je name) + 1`), statt mit `409` abgelehnt zu werden — zwei Definitionen mit demselben Namen sind der Normalfall. `GET /process-definitions` liefert per Default nur die neueste Version je Familie (`DISTINCT ON`), `GET /process-definitions?name=X` die vollständige Historie. Prozessinstanzen bleiben unverändert an eine konkrete `id` (also eine bestimmte Version) gebunden — eine neue Version wirkt sich nie rückwirkend auf bereits laufende oder abgeschlossene Instanzen aus, `POST .../{id}/instances`/`DELETE /process-definitions/{id}` mussten dafür nicht geändert werden. Grundlage für den "Speichern"-Fluss des neuen Process Designer (`apps/process-designer`, P6-S8): Name unverändert lassen erzeugt eine neue Version, ein geänderter Name eine neue Familie.

## SpiffWorkflow-Anbindung (`spiff_adapter.py`)

Die gesamte SpiffWorkflow-API-Oberfläche ist in einem einzigen Modul isoliert (`src/workflow_service/spiff_adapter.py`) — `repository.py` kennt SpiffWorkflow-Klassen nicht direkt, nur die eigenen Wrapper-Funktionen. Grund: SpiffWorkflows API ist nicht formal als stabil dokumentiert; ein künftiger Versions-Bump muss so nur an einer Stelle nachgezogen werden. Gegen die tatsächlich installierte Version (**3.1.2**) per `help()`/`inspect` verifiziert, nicht nur aus der Dokumentation übernommen — u. a. wurde dabei empirisch festgestellt, dass `BpmnWorkflow.set_data()` **nicht** ausreicht, um Prozessvariablen beim Start sichtbar zu machen (Daten werden beim Abschluss eines Tasks an dessen Kinder weitergereicht, nicht rückwirkend aus dem workflow-weiten `data`-Dict gelesen) — `initial_data` wird deshalb direkt auf dem zu Beginn bereiten Start-Task gesetzt.

- **Manual/User Tasks** (`<bpmn:manualTask>`/`<bpmn:userTask>`, beide haben `task_spec.manual == True`): bleiben nach `do_engine_steps()` bereit stehen, bis `POST .../complete` aufgerufen wird. `task_spec.lane` (Bahn-/Rollenname aus dem BPMN-Modell, `None` falls das Modell keine Lanes definiert) wird informativ mitgeliefert — **keine Auswertung/Durchsetzung** in dieser Session, siehe "Offene Punkte".
- **Automatic Tasks (Script Tasks)**: laufen über SpiffWorkflows eingebaute Standard-Python-Scripting-Umgebung automatisch, sobald sie bereit sind — keine eigene Connector-/Delegate-Registrierung in diesem Grundgerüst.
- **Timer/Boundary Events (P6-S2, SLA-Zeitüberwachung, 7.1)**: `spiff_adapter.check_timers()` kapselt `wf.refresh_waiting_tasks()`+`do_engine_steps()` und meldet gefeuerte Boundary-Timer (erkannt über `isinstance(task_spec, BoundaryEvent)`) zurück. Beide BPMN-Semantiken real gegen die installierte Version getestet: non-interrupting (`cancelActivity="false"`) lässt den ursprünglichen Task weiterlaufen, interrupting (`cancelActivity="true"`, BPMN-Default) storniert ihn — beides vollständig SpiffWorkflow-eigene Semantik, siehe Modul-Docstring.

**Seit P6-S7**: Parser auf `SpiffWorkflow.camunda.parser.CamundaParser` umgestellt (weiterhin identische `add_bpmn_str`/`get_process_ids`/`get_spec`-Oberfläche, `manualTask` mappt unverändert auf `ManualTask`), da nur dieser Parser `bpmn:extensionElements/camunda:properties` in `task_spec.extensions` einliest (Grundlage des Signature Task, siehe unten). Musste von einem passenden Serializer-Config begleitet werden: `CamundaParser` mappt `<bpmn:userTask>` zusätzlich auf Camundas eigene `UserTask`-Spec-Klasse statt der BPMN-Default-Klasse — `_SERIALIZER` nutzt seither `SpiffWorkflow.camunda.serializer.config.CAMUNDA_CONFIG` statt `BpmnWorkflowSerializer.configure()`, sonst schlägt die JSON-Serialisierung bereits bestehender `userTask`-Fixtures (z. B. der P6-S2-Boundary-Timer-Test) fehl. Alle 52 vorherigen Tests bleiben nach diesem Wechsel unverändert grün (siehe [ADR 0025](../adr/0025-signature-service-internal-ca-and-connector-plugin.md)).

## State-Persistenz (ADR 0019)

Jede Prozessinstanz speichert ausschließlich den vollständigen, von `BpmnWorkflowSerializer.serialize_json()` erzeugten JSON-Blob — **keine** separate, normalisierte Task-Tabelle. Begründung/Konsequenzen: siehe [ADR 0019](../adr/0019-workflow-full-state-serialization.md).

## SLA-Poll-Loop (P6-S2, ADR 0020)

Ein asyncio-Hintergrund-Task (`_sla_poll_loop` in `main.py`, gestartet in `lifespan`) prüft alle `sla_poll_interval_seconds` (Default 30s, `DMS_SLA_POLL_INTERVAL_SECONDS`) **jede** Instanz mit `status="running"`: deserialisieren, `spiff_adapter.check_timers()`, Blob neu persistieren, gefeuerte Boundary-Events als `workflow.task.escalated` publizieren. Kein Push-Mechanismus, keine verteilte Sperre bei mehreren `workflow-service`-Replikaten — siehe [ADR 0020](../adr/0020-sla-timer-polling.md) für die vollständige Begründung und die dokumentierten Grenzen. **Seit P6-S6**: prüft vor jedem Tick zusätzlich über den neuen `permission_client.py` (`is_maintenance_active()`, `GET /maintenance-mode` am Permission Service) direkt, ob der systemweite Wartungsmodus (4.8) aktiv ist, und überspringt den Tick dann komplett — kein eingehender Request, an den das Gateway einen `X-DMS-Maintenance-Active`-Header hängen könnte, daher die einzige Stelle in diesem Service mit einer eigenen Polling-Verbindung zum Permission Service statt Header-Auswertung.

## Autorisierung & Wartungsmodus (4.6/4.8, seit P6-S6)

Bewusst begrenzter Retrofit (Nutzerentscheidung: "Admin-Aktionen gaten, Alltagsnutzung offen", siehe [ADR 0024](../adr/0024-not-shutdown-gateway-enforced.md)):

- **Prozessdefinitionen anlegen/löschen** (BPMN-/Script-Task-Upload) erfordern die Capability `admin.object_config` — echter Aufruf gegen den Permission Service über einen neuen, dünnen `permission_client.py` (gleiches Muster wie `auth-service`s Rollen-Client aus P6-S5), `403` ohne die Capability oder ohne `X-DMS-Principal`-Header. `auth-service` legt dafür ein zweites technisches Konto `config-admin`/`config-admin` an (Domäne "Workflow-Konfiguration"). Da Skript-Code ausschließlich über diesen jetzt gegateten Upload ins System gelangt (keine separate Ausführungs-Route), sichert das faktisch auch die Script-Task-Ausführung ab, ohne einen eigenen Check dafür zu brauchen.
- **Instanzstart/Task-Abschluss bleiben bewusst ungegatet** für jeden authentifizierten Principal — normale Fachnutzung soll keine Domain-Admin-Rolle brauchen. Stattdessen respektieren beide Endpunkte den neuen systemweiten Wartungsmodus (4.8): `503`, solange der vom Gateway injizierte `X-DMS-Maintenance-Active`-Header `"true"` ist.
- **`created_by`/`completed_by` bleiben weiterhin reine, ungeprüfte Strings** — die Gating-Entscheidung betrifft nur, *ob* eine Aktion ausgeführt werden darf, nicht, ob der angegebene Name stimmt (unverändert seit P6-S1).
- **Seit P6-S9**: `POST /federation/inbound`/`.../inbound-result` sind öffentliche Routen (`gateway-service`s `public_routes`, kein `X-DMS-Principal` — der Federation Hub ist kein eingeloggter Nutzer), respektieren aber weiterhin den Wartungsmodus (503-Verhalten müsste ein aufrufender Hub selbst als Zustellungsfehlschlag interpretieren) — bewusst *nicht* in `maintenance_mode_allowed_routes` aufgenommen, da ein föderierter Schritt fachlich Alltagsverarbeitung ist, kein Admin-Vorgang (kein Sonderfall wie bei ADR 0025). Authentisiert wird stattdessen über `X-Federation-Hub-Signature` (ADR 0028).

## Lizenz-Demo-Modus/Sperrverhalten (Konzept 9.3, seit P9-S2)

`workflow-service` ist die einzige heute real existierende, separat lizenzierbare "Applikationskomponente" aus Konzept 9.1 (CMIS-Connector/Migration-Service existieren erst ab Phase 12). Ein neuer, dünner `license_client.py` (`LicenseStatusClient`, Vorbild `permission_client.py`) fragt den eigenen Lizenzstatus beim `registry-service` ab (`GET /license-status/workflow-service`, TTL-Cache 15s, fail-open `"licensed"`) — **nicht** direkt beim `license-service`, die Registry bleibt einzige Vermittlungsstelle (3.2b).

Eine neue `_license_gate(action)`-Dependency (`Depends(...)` statt wie beim Wartungsmodus manuell im Funktionskörper, da hier ein async Cross-Service-Aufruf statt eines simplen Header-Reads nötig ist):

- `"unlicensed"` sperrt vollständig, auch Lesezugriffe (`403`).
- `"demo"` erlaubt nur Lesezugriff (Konzept-Beispiel wörtlich) — schreibende Endpunkte (`POST`/`DELETE /process-definitions*`, `POST .../instances`, `POST .../tasks/{id}/complete`) antworten mit `403`.
- `"licensed"` lässt alles durch.

`/federation/*`-Endpunkte bleiben bewusst ungegatet — Föderation ist ein eigenständiges, in Phase 13 verankertes Thema, keine Vorentscheidung hier.

## Signature Task (3.10, seit P6-S7)

Ein `<bpmn:manualTask>` mit `bpmn:extensionElements/camunda:properties` `taskType=signature`/`requiredLevel=ses|aes|qes` wird als Signature Task erkannt — technisch bleibt es ein gewöhnlicher Manual Task (`.manual is True`, `ready_manual_tasks`/`find_ready_task` unverändert), fachlich verlangt der Abschluss aber eine echte Signatur:

- Die zu signierende `document_id` läuft über die bestehende generische `data`-Prozessvariable (kein neues Schema-Feld — workflow-service kennt kein Dokument-Konzept), z. B. per `initial_data` beim Instanzstart gesetzt.
- `POST .../tasks/{id}/complete` verlangt in diesem Fall `signature_id` im Body. Ein neuer, dünner `signature_client.py` (Muster wie `permission_client.py` aus P6-S6) fragt beim `signature-service` (`GET /signatures/{id}`) nach: die Signatur muss existieren, zum `document_id`-Wert der Task-Daten passen und mindestens `requiredLevel` erreichen (Rangfolge `ses < aes < qes`) — sonst `400`.
- Kein neues BPMN-Element, keine Modeler-Tooling-Änderung nötig — passend zur Konzeptformulierung "technisch eine Sonderform des Manual Task". Beispiel-Fixture: `tests/fixtures/signature_task.bpmn`.
- **Kein Prozess-Designer-Palette-Eintrag** in dieser Session — ein Signature Task muss die Extension-Attribute von Hand im hochgeladenen BPMN-XML setzen. Folgt mit P6-S8.

## Federation (7.4, seit P6-S9)

Zwei weitere Manual-Task-Sonderformen für installationsübergreifende Prozessschritte, vermittelt über einen [Federation Hub](federation-hub-service.md) — technisch bleiben beide gewöhnliche `bpmn:manualTask`-Elemente mit `camunda:properties`, kein neues BPMN-Element, gleiches Grundmuster wie der Signature Task:

- **`taskType=federated`** (Absenderseite): zusätzlich `targetInstallationId`/`targetProcessType`. Sobald bereit, wird der Task **automatisch** dispatcht (`main.py._dispatch_pending_federation_tasks`, aufgerufen nach Instanzstart/Task-Abschluss/SLA-Poll-Tick) — nie von einem Menschen abgeschlossen, ein direkter `.../complete`-Aufruf liefert `409`. Die aktuellen Task-Prozessdaten werden mit dem öffentlichen Schlüssel der Zielinstallation Ende-zu-Ende verschlüsselt (`federation_crypto.py`) und per `federation_client.py` an den Hub übergeben (`POST /handovers`). Der Task bleibt "ready" (fachlich: wartend), bis `POST /federation/inbound-result` ein Ergebnis zurückmeldet und ihn programmatisch abschließt.
- **`taskType=federated_return`** (Empfängerseite): wird ebenfalls automatisch dispatcht, sobald bereit — verschlüsselt die aktuellen Task-Daten für die Ursprungsinstallation (aus dem verknüpften `federation_task`-Datensatz, siehe unten) und schickt sie über den Hub zurück (`POST /handovers/{id}/result`), schließt sich danach selbst ab.
- **Selbstregistrierung** (`main.py._ensure_federation_identity`): opt-in über `Settings.federation_hub_base_url`. Beim allerersten Start mit konfiguriertem Hub wird ein eigenes RSA-2048-Schlüsselpaar erzeugt (`federation_crypto.generate_keypair`), der öffentliche Hub-Schlüssel einmalig abgerufen (Trust-on-First-Use) und die Installation beim Hub registriert (`FederationIdentity`-Singleton, `id=1`, gleiches Muster wie `signature-service`s `InternalCa`) — bei jedem weiteren Start eine idempotente Re-Registrierung (aktualisiert `callback_base_url`/`version`, falls sich Settings geändert haben; ein nicht erreichbarer Hub blockiert den eigenen Start nicht). `callback_base_url` zeigt bewusst auf den **eigenen Gateway** (`{installation_gateway_base_url}/api/workflow-service`), nicht auf die interne Container-Adresse — nur so respektiert eine eingehende Zustellung dieselbe Wartungsmodus-Logik wie jeder andere Request (siehe unten). Der beim Hub gemeldete `display_name` kommt seit P13-S1 aus der geteilten `settings.installation_display_name` (`dms_common.BaseServiceSettings`, 3a) statt einer nur hier bekannten, service-eigenen Einstellung — die zufällig erzeugte Hub-`installation_id` selbst bleibt bewusst unabhängig von der installationsweiten Fleet-/Lizenz-`installation_id` (siehe `docs/services/registry-service.md`).
- **`GET /federation/installations`**: dünner Proxy auf das Hub-Adressbuch, Grundlage für die Zielinstallations-Auswahl im Process Designer (`apps/process-designer`s `FederatedStepPropertiesProvider`) — leere Liste ohne konfigurierten Hub, keine Auth nötig (wie andere `GET`s).
- **`POST /federation/inbound`**: empfängt eine neue Übergabe. Öffentliche Route (siehe `gateway-service`s `public_routes`) — Authentisierung läuft über `X-Federation-Hub-Signature` (`federation_crypto.verify_body` gegen den beim eigenen Registrieren abgerufenen öffentlichen Hub-Schlüssel), nicht über `X-DMS-Principal`. Löst `targetProcessType` über `Settings.federation_process_type_map` (JSON, `{"<targetProcessType>": "<lokaler process_definition-Name>"}`) auf die **neueste Version** der zugeordneten lokalen Prozessdefinition auf, entschlüsselt den Payload mit dem eigenen privaten Schlüssel und startet eine neue Instanz (`created_by="federation-hub"`). Publiziert zusätzlich `workflow.federation.inbound_received` (siehe Events).
- **`POST /federation/inbound-result`**: empfängt die Rückmeldung eines selbst initiierten Handover, entschlüsselt das Ergebnis und schließt den wartenden `federated`-Task programmatisch ab (`completed_by="federation-hub"`).
- **`FederationIdentity`/`FederationTask`** (neue Tabellen, additiv über `create_all`, keine Alter-Migration nötig): `FederationIdentity` hält das eigene Schlüsselpaar/den Hub-API-Key/den gecachten öffentlichen Hub-Schlüssel. `FederationTask` verknüpft einen lokalen Task/eine Instanz mit einem `handover_id` beim Hub (`direction="outbound"|"inbound"`) — verhindert doppeltes Dispatchen und hält bei einer eingehenden Übergabe fest, an welche `origin_installation_id` ein späterer `federated_return`-Task sein Ergebnis zurückschickt. Eindeutigkeit gilt für `(handover_id, direction)`, nicht `handover_id` allein — beim Selbst-Loopback-Smoke-Test (eine Installation übergibt an sich selbst) landen sonst zwei Zeilen mit demselben `handover_id` in derselben Datenbank (siehe "Erst beim Live-Smoke-Test gefundene Bugs" unten).
- **`handover_id` wird von der Absenderinstallation selbst erzeugt** (`uuid.uuid4()`), nicht vom Hub — ihre eigene `FederationTask`-Zeile wird **vor** dem Hub-Aufruf committet, damit ein verschachtelter Rückruf des Hub bis in dieselbe Installation (Selbst-Loopback) die Zeile bereits sieht (Postgres-Transaktionsisolation). Siehe `docs/services/federation-hub-service.md` für die vollständige Fehleranalyse.
- **Benachrichtigung** (Roadmap-Notiz "Benachrichtigung der Zielinstallation"): `workflow.federation.inbound_received` trägt ein optionales `notify_email`-Feld (aus der Payload der Absenderseite, gleiches Muster wie `escalation_email` beim SLA-Timer) — `notification-service` verschickt bei vorhandenem Wert eine E-Mail, siehe `docs/services/notification-service.md`.
- Kein eigener Palette-Eintrag im Process Designer nötig (wie beim Signature Task) — eine neue Properties-Panel-Gruppe "Föderation" auf Manual Tasks, sichtbar nur wenn der Hub mindestens eine Installation kennt (siehe `docs/services/process-designer.md`).

## Connector-Service-Tasks (7.1 "Auslösen eines Connector-Aufrufs", seit P12-S2)

Anders als Signature Task/Federation (beides Sonderformen des **Manual** Task, da ein Mensch oder ein externer Vermittlungsdienst über den Abschluss entscheidet) ist ein Connector-Service-Task ein echter `bpmn:serviceTask` — läuft **automatisch** wie ein Script Task, ohne auf irgendetwas zu warten. Erster Nutzer ist `migration-service` (7.2), das Muster ist aber bewusst generisch — `workflow-service` kennt `migration-service` nicht.

- **`taskType=connector_call`/`serviceUrl=...`** (`camunda:properties` auf einem `bpmn:serviceTask`): `spiff_adapter.py`s `ConnectorServiceTask`-Spec-Klasse (per `OVERRIDE_PARSER_CLASSES` registriert, SpiffWorkflows eigener dokumentierter Erweiterungspunkt) ruft bei `_execute()` einen modul-weiten, per `register_connector_task_handler()` injizierbaren Callback auf. `main.py` registriert dafür einen Handler, der synchron `httpx.post(serviceUrl, json=dict(task.data))` ausführt (SpiffWorkflow/`do_engine_steps()` ist durchgehend synchron, kein neuer async/sync-Bruch) und die JSON-Antwort in die Prozessdaten zurückmerged. Ein `serviceTask` **ohne** `taskType=connector_call` bleibt unverändert ein echtes No-Op (Rückwärtskompatibilität).
- **`{platzhalter}`-Substitution in `serviceUrl`** (`str.format(**data)` mit den aktuellen Prozessdaten) — erlaubt z. B. eine pro Instanz unterschiedliche `transfer_id` in der URL, ohne die BPMN-Datei pro Instanz individuell erzeugen zu müssen.
- **Real gefundene SpiffWorkflow-Eigenheiten** (nicht offensichtlich aus der Doku): (1) `ServiceTask` ist in keiner Default-Serializer-Konfiguration registriert — `ConnectorServiceTask` muss explizit auf `BpmnTaskSpecConverter` gemappt werden, sonst schlägt die Serialisierung mit "not JSON serializable" fehl. (2) `_execute()` muss `True` zurückgeben, um den Task tatsächlich abzuschließen — ein falsy Rückgabewert (SpiffWorkflows eigener `ServiceTask`-Default) lässt ihn dauerhaft in `STARTED` hängen. (3) Nur `CamundaTaskParser` (nicht die Basis-`TaskParser`) liest `camunda:properties` überhaupt in `task_spec.extensions` ein.

### Resumability: `POST /instances/{id}/retry`

Ein fehlgeschlagener `connector_call` (z. B. Ziel nicht erreichbar) versetzt SpiffWorkflow den Task nach `ERROR` — ein einfaches erneutes `do_engine_steps()` reicht nicht (nur `READY`-Tasks werden verarbeitet). `spiff_adapter.retry_errored_tasks()` nutzt SpiffWorkflows offizielle `reset_branch()`-API, um `ERROR`-Tasks zurück auf `READY`/`FUTURE` zu versetzen (Task-Daten bleiben erhalten), danach lässt `POST /instances/{id}/retry` `do_engine_steps()` erneut laufen.

`start_instance`/`complete_task`/`retry_instance` in `repository.py` persistieren den `workflow_state`-Blob dafür jeweils in einem `try`/`finally` statt erst nach erfolgreichem Abschluss — ohne das gäbe es bei einem Fehlschlag des allerersten automatischen Schritts gar keine Instanz-Zeile mit dem richtigen Zwischenstand zum Fortsetzen (real gefunden). `main.py`s drei betroffene Endpunkte committen aus demselben Grund auch im `except`-Zweig, bevor die Exception weitergereicht wird — sonst würde `get_session()`s Context-Manager den bereits geflushten Zwischenstand beim Schließen der Session zurückrollen.

### Caller-bestimmte Instanz-ID

`ProcessInstanceCreate.instance_id` (optional) lässt den Aufrufer seine eigene Referenz für eine neue Instanz bestimmen, statt eine serverseitig generierte entgegenzunehmen — gleiches Muster wie `federation-hub-service`s `handover_id` (ADR 0028). Wichtig für einen Aufrufer wie `migration-service`, der die ID bereits **vor** dem Start persistieren will: schlägt bereits der erste automatische Schritt fehl, wäre die (dennoch angelegte) Instanz sonst nicht wiederauffindbar für einen späteren `/retry`-Aufruf.

B. der `needs_review`-Flag aus `ocr.completed`, siehe `docs/services/ocr-service.md` "Offene Punkte") — diese Anbindung bleibt auf eine spätere Phase-6-Session verschoben, vermutlich zusammen mit dem generischen Approval-Mechanismus (P6-S4).

## Offene Punkte

- **Rollenprüfung seit P6-S6 nur für Prozessdefinitionen** (`admin.object_config`) — Instanzstart/Task-Abschluss bleiben bewusst für jeden authentifizierten Principal offen (Nutzerentscheidung, siehe "Autorisierung & Wartungsmodus" oben und [ADR 0024](../adr/0024-not-shutdown-gateway-enforced.md)); `completed_by`/`created_by` sind weiterhin reine, ungeprüfte Strings.
- **Script Tasks führen serverseitig beliebigen, in der BPMN-XML eingebetteten Python-Code aus** (SpiffWorkflows Standard-Scripting-Umgebung) — seit **P6-S6** faktisch durch das `admin.object_config`-Gating am Upload-Endpunkt abgesichert (kein separater Ausführungs-Endpunkt, Skript-Code gelangt ausschließlich über den jetzt gegateten Upload ins System). Vor produktivem Mehrnutzerbetrieb mit BPMN-Import durch nicht vollständig vertrauenswürdige Domain-Admins weiterhin zu revisitieren.
- **SLA-Poll-Präzision an das Poll-Intervall gekoppelt** (Default 30s) — keine Echtzeit-Erkennung einer Eskalation, siehe ADR 0020.
- **Keine verteilte Sperre bei mehreren `workflow-service`-Replikaten** — ein horizontal skaliertes Deployment würde denselben Boundary-Timer mehrfach feuern/publizieren, siehe ADR 0020 "Konsequenzen".
- **Nur `DurationTimerEventDefinition`-basierte Boundary-Timer real getestet** (P6-S2) — `CycleTimerEventDefinition` (wiederkehrende Eskalation) und `TimeDateEventDefinition` (fester Zeitpunkt) werden von SpiffWorkflow nativ unterstützt, sind aber diese Session nicht mit einem eigenen Test abgedeckt.
- **Case-Service-Anbindung seit P6-S3**: `case-service` konsumiert `workflow.instance.completed` und matcht über `business_key` (den es beim Instanzstart auf die eigene Case-ID setzt) — workflow-service selbst musste dafür nicht geändert werden, siehe `docs/services/case-service.md`.
- **Signature Tasks seit P6-S8 mit Modeler-Unterstützung** (`apps/process-designer`s `SignatureTaskPropertiesProvider`) — die Extension-Attribute müssen nicht mehr von Hand im BPMN-XML gesetzt werden.
- **Föderierte Prozessschritte seit P6-S9 umgesetzt** (siehe "Federation" oben) — offene Grenzen dieses Grundgerüsts: keine Durchsetzung erklärter `supported_process_types`/`supported_document_types` auf Hub-Seite, keine Retry-Warteschlange bei vorübergehend nicht erreichbarem Ziel (sofortiges `delivery_failed`), kein mTLS/keine echte Installations-Identität (siehe ADR 0028), Prozesstyp-Zuordnung auf Empfängerseite rein konfigurationsbasiert (kein automatischer Katalog-Abgleich zwischen Installationen), genau ein eingehender Handover je lokal gestarteter Instanz angenommen (`get_inbound_federation_task_for_instance`).
- **Import-Validierung ist rein strukturell** (SpiffWorkflow kann die Datei parsen, Prozess-ID auflösbar) — die in 7.1 beschriebene tiefere Validierung gegen im System verfügbare Objekttypen/Ordnerziele/Instanz-Ziele setzt Task-Typen voraus, die es in diesem Grundgerüst noch nicht gibt (z. B. ein "Dokument anlegen"-Task-Typ).
- **`business_key` ist eine unvalidierte opake Referenz** — kein Abgleich gegen den Document Service, ob eine angegebene `document_id` tatsächlich existiert.
- **Kein Rollback auf eine ältere Version als neue "neueste" Version** — eine alte Version bleibt öffnen-/startbar, ein erneutes "Vorne-Setzen" bräuchte einen manuellen erneuten Upload ihres `bpmn_xml`, keinen eigenen Endpunkt (seit P6-S8, siehe ADR 0027).
- **Keine Race-Condition-Sperre bei der Versionsvergabe** (kein `SELECT ... FOR UPDATE`) — ein echter Parallel-Konflikt zweier gleichzeitiger Speicherversuche unter demselben Namen scheitert unbehandelt an der `(name, version)`-Unique-Constraint (`500`), dieselbe bewusste Vereinfachung wie bei document-services Versionsnummern-Vergabe.
- **Kein Rückwirkungs-Check beim Löschen einer Prozessdefinition auf Task-Ebene** — nur die Existenz irgendeiner Instanz wird geprüft, nicht ob diese noch tatsächlich läuft.
