# workflow-service

**Responsibility:** Workflow engine foundation (Concept 7.1) — BPMN 2.0 import and execution via [SpiffWorkflow](https://github.com/sartography/SpiffWorkflow) (LGPLv3, [ADR 0018](../adr/0018-spiffworkflow-lgpl-license.md)), Manual/Automatic Tasks, since P6-S2 also Timer/Boundary Events (SLA time monitoring, [ADR 0020](../adr/0020-sla-timer-polling.md)), since **P6-S7** additionally the "Signature Task" (3.10, technically a special form of the Manual Task), since **P6-S9** additionally federated process steps via the Federation Hub (7.4, technically also Manual Task special forms), since **P12-S2** additionally generic connector service tasks (7.1 "triggering a connector call" — first user `migration-service`, 7.2) + `POST /instances/{id}/retry` (resumability for failed automatic steps), since **P14-S4** additionally DMN 1.3 decision tables/Business Rule Task (own SpiffWorkflow DMN support, `dmn-definitions` CRUD + export/import via the configuration export 7.3), since **P14-S5** additionally regional business calendars for SLA deadline calculation (`business-calendars` CRUD + a new `business_days(n, calendar_name)` function callable in BPMN timer duration expressions, [ADR 0042](../adr/0042-business-calendar-script-engine-injection.md)). UI follows with P6-S8 (`apps/process-designer`). Since **P6-S6** partially gated: creating/deleting process definitions requires the capability `admin.object_config` (4.6 retrofit), instance start/task completion remain open to every authenticated principal but respect the system-wide maintenance mode (emergency shutdown, 4.8) — see [ADR 0024](../adr/0024-not-shutdown-gateway-enforced.md).

**Concept reference:** 7.1, 4.6, 4.8, 3.10, 7.4, 7.2
**Own Postgres schema:** `workflow` (tables `process_definition`, `process_instance`, since P6-S9 additionally `federation_identity`, `federation_task`, since P14-S4 additionally `dmn_definition`, since P14-S5 additionally `business_calendar`)

No additional role gate beyond the license check (like instance start/task completion) |

## Data Model

- `process_definition`: `id`, `name` (since P6-S8 the process family key, no longer globally unique, see "Versioning" below), `version` (integer, default 1, unique together with `name`), `bpmn_process_id` (the internal process ID from the BPMN XML itself, `<bpmn:process id="...">`), `bpmn_xml` (text, the complete uploaded file), `created_at`/`updated_at`.
- `process_instance`: `id` (UUID), `process_definition_id` (FK), `business_key` (string, nullable, opaque cross-service reference e.g. to a future `document_id` — **not** validated against the Document Service, same pattern as `folder_id`/`object_type_id` before their respective enforcement in earlier phases), `status` (`"running"`\|`"completed"`), `workflow_state` (text — the full execution state serialized by SpiffWorkflow, see "State persistence" below), `created_by`, `created_at`/`updated_at`/`completed_at` (nullable).
- `dmn_definition` (since P14-S4): `id`, `name` (family key, same versioning pattern as `process_definition`), `version`, `decision_id` (the internal `<decision id="...">` from the DMN XML — the actual key by which a `businessRuleTask`'s `camunda:decisionRef` references it, NOT `name`), `dmn_xml` (text), `created_at`/`updated_at`.
- `business_calendar` (since P14-S5): `id`, `name` (unique, NO versioning pattern — update-in-place via `PUT`), `non_working_dates` (JSON list of ISO date strings, only the ADDITIONAL, calendar-specific non-working days — weekends always count as non-working regardless, see "Business calendars" below), `is_default` (boolean, at most one row `true` at a time), `created_at`/`updated_at`.

## Versioning (since P6-S8, ADR 0027)

`name` is the process family key: `POST /process-definitions` under an already existing name automatically creates the next `version` (`max(version per name) + 1`), instead of being rejected with `409` — two definitions with the same name are the normal case. `GET /process-definitions` returns by default only the newest version per family (`DISTINCT ON`), `GET /process-definitions?name=X` the complete history. Process instances remain bound, unchanged, to a specific `id` (i.e. a specific version) — a new version never affects already-running or already-completed instances retroactively; `POST .../{id}/instances`/`DELETE /process-definitions/{id}` did not need to change for this. Basis for the "save" flow of the new Process Designer (`apps/process-designer`, P6-S8): leaving the name unchanged creates a new version, a changed name creates a new family.

**Since P25-S2**: `POST /process-definitions/{id}/restore` is a second creation entry point alongside the regular upload (`POST /process-definitions`) — instead of newly uploaded content, it reuses the `bpmn_xml`/`bpmn_process_id` of an already existing (even no-longer-current) version of the same family to create the next version from it. Both entry points run through the same `repository.create_process_definition` and therefore through the same version numbering/advisory-lock logic, see the API table above.

**Since P25-S1 ([ADR 0096](../adr/0096-workflow-definition-version-race-advisory-lock.md))**: assignment of `next_version` (for both process and DMN definitions, see below) is protected against real concurrency — `create_process_definition`/`create_dmn_definition` take a transaction-bound Postgres advisory lock on `name` before reading `max(version)` (`pg_advisory_xact_lock`, own namespace per definition type), instead of reading unlocked as before. Multiple genuinely simultaneous save attempts under the same `name` (even for a brand-new family without a prior row) are thereby guaranteed distinct, gapless consecutive version numbers instead of an unhandled `IntegrityError`/`500` at the `(name, version)` unique constraint. Details/rationale (in particular why no counter-table pattern like `object-type-service`/`case-service`) see ADR 0096.

## SpiffWorkflow integration (`spiff_adapter.py`)

The entire SpiffWorkflow API surface is isolated in a single module (`src/workflow_service/spiff_adapter.py`) — `repository.py` does not know SpiffWorkflow classes directly, only the service's own wrapper functions. Reason: SpiffWorkflow's API is not formally documented as stable; a future version bump then only needs to be followed up in one place. Verified against the actually installed version (**3.1.2**) via `help()`/`inspect`, not just taken from the documentation — among other things it was empirically established that `BpmnWorkflow.set_data()` is **not** sufficient to make process variables visible at start (data is passed to a task's children upon its completion, not read retroactively from the workflow-wide `data` dict) — `initial_data` is therefore set directly on the start task that is ready at the beginning.

- **Manual/User Tasks** (`<bpmn:manualTask>`/`<bpmn:userTask>`, both have `task_spec.manual == True`): remain ready after `do_engine_steps()` until `POST .../complete` is called. `task_spec.lane` (lane/role name from the BPMN model, `None` if the model defines no lanes) is delivered informationally — **no evaluation/enforcement** in this session, see "Open Points".
- **Automatic Tasks (Script Tasks)**: run automatically via SpiffWorkflow's built-in standard Python scripting environment as soon as they are ready — no own connector/delegate registration in this foundation.
- **Timer/Boundary Events (P6-S2, SLA time monitoring, 7.1)**: `spiff_adapter.check_timers()` wraps `wf.refresh_waiting_tasks()`+`do_engine_steps()` and reports fired boundary timers (detected via `isinstance(task_spec, BoundaryEvent)`) back. Both BPMN semantics tested for real against the installed version: non-interrupting (`cancelActivity="false"`) lets the original task keep running, interrupting (`cancelActivity="true"`, BPMN default) cancels it — both entirely SpiffWorkflow's own semantics, see module docstring.

**Since P6-S7**: parser switched to `SpiffWorkflow.camunda.parser.CamundaParser` (still identical `add_bpmn_str`/`get_process_ids`/`get_spec` surface, `manualTask` still maps to `ManualTask`), since only this parser reads `bpmn:extensionElements/camunda:properties` into `task_spec.extensions` (basis of the Signature Task, see below). Had to be accompanied by a matching serializer config: `CamundaParser` additionally maps `<bpmn:userTask>` to Camunda's own `UserTask` spec class instead of the BPMN default class — `_SERIALIZER` has since used `SpiffWorkflow.camunda.serializer.config.CAMUNDA_CONFIG` instead of `BpmnWorkflowSerializer.configure()`, otherwise JSON serialization of already-existing `userTask` fixtures (e.g. the P6-S2 boundary timer test) fails. All 52 previous tests remain green unchanged after this switch (see [ADR 0025](../adr/0025-signature-service-internal-ca-and-connector-plugin.md)).

## DMN 1.3 decision tables / Business Rule Task (7.1, since P14-S4)

`CamundaParser` (base class since P6-S7) is itself already a subclass of `SpiffWorkflow.dmn.parser.BpmnDmnParser` (empirically verified via `CamundaParser.__mro__`) — `businessRuleTask` is already mapped there via `OVERRIDE_PARSER_CLASSES` to `BusinessRuleTaskParser`/`BusinessRuleTask`, no own override needed (unlike for the connector service task, see above). `parser.add_dmn_str(xml)` loads a DMN file into the same parser, keyed by its own `<decision id="...">` — `BusinessRuleTaskParser.create_task()` reads `camunda:decisionRef` from the `<bpmn:businessRuleTask>` element and resolves it exactly against this key. Both `add_dmn_str`/`add_bpmn_str` must be called BEFORE `parser.get_spec()` — the order between the two doesn't matter, so `_new_parser()` loads all given DMN definitions before the BPMN file itself. `DMNEngine` (evaluation at runtime) is called transparently by SpiffWorkflow itself from `BusinessRuleTaskMixin._run_hook()`, exactly as for any other automatic task (`do_engine_steps()`) — this module never instantiates it directly, the evaluation is SpiffWorkflow's own simplified Python expression semantics (not a full OMG FEEL implementation), inputs/outputs read/write the same generic `task.data` dict as any other task type.

**"Exactly one `<decision>` per DMN file" limit**: SpiffWorkflow itself supports only exactly one decision per file (`ValidationException("Multiple decision tables are not current supported.")`), but this check only happens LAZILY inside `DMNParser.parse()`, triggered by `BpmnDmnParser.get_decision()` when resolving a referencing `businessRuleTask` — a pure DMN upload without an accompanying BPMN reference would never see the error. `spiff_adapter.parse_dmn()` therefore explicitly calls `dmn_parser.parse()` itself, to enforce the check already at upload time (empirically verified: `len(parser.dmn_parsers)` alone CANNOT check this limit, since `add_dmn_xml()` always creates exactly one entry per file, keyed by the ID of the FIRST decision in the document). A bug in the installed SpiffWorkflow version: the `ValidationException` for the multiple-decision case internally passes a `list` instead of an lxml element and thereby itself throws an `AttributeError` instead of surfacing cleanly — `parse_dmn()` catches both cases via `except Exception`.

**"Always load all newest DMN definitions" simplification**: `repository.list_latest_dmn_xml()` loads the respectively newest version of EVERY DMN family into the parser before EVERY BPMN parse (`create_process_definition`/`start_instance`) — not just the ones actually referenced by the specific BPMN file. A deliberate, documented simplification for this reference implementation (no static scanning of the BPMN XML for `camunda:decisionRef` attributes before parsing): unreferenced decisions are harmless, only costing a bit of extra parse time. Consequence: a DMN family must already exist BEFORE a BPMN file referencing it is uploaded/re-parsed (`start_instance` re-parses on every instance start) — otherwise `422` (`InvalidBpmnError`, SpiffWorkflow's own `ValidationException` when resolving the unknown `decisionRef`).

**Deliberately NO "in use" check on `DELETE /dmn-definitions/{id}`** (unlike for process definitions) — that would require scanning all BPMN XML texts for `camunda:decisionRef`. A deletion can make an existing process definition fail with `422` on its next instance start; already-running instances are unaffected (their `workflow_state` already fully contains the decision loaded at start time, see "State persistence" below).

**Frontend (`apps/process-designer`, P14-S4)**: the already-registered `CamundaPlatformPropertiesProviderModule` (in use since P6-S7/P6-S9 for Signature/Federation tasks) already renders an "Implementation" group with `Type: DMN`/`Decision reference`/`Binding`/`Tenant ID`/`Result variable` for a selected Business Rule Task fully, without this project having to write its own properties panel provider for it (empirically confirmed via a real Playwright browser test, not just taken from the `bpmn-js-properties-panel` docs). The decision tables themselves are edited via a new standalone list + an own `dmn-js` editor (see `docs/services/process-designer.md`, [ADR 0021](../adr/0021-bpmn-io-license-watermark.md) addendum).

## Business calendars (7.1, since P14-S5, [ADR 0042](../adr/0042-business-calendar-script-engine-injection.md))

Freely named, CRUD-maintained calendars of additional non-working days (holidays) - weekends (Sat/Sun) ALWAYS count as non-working regardless. Effective via a new function callable in any BPMN timer duration expression: `business_days(n, calendar_name=None)` returns an ISO 8601 duration (`"P<x>D"`) that converts `n` business days from "now" into the corresponding number of calendar days - a BPMN file writes e.g. `<bpmn:timeDuration>business_days(3, "de-national")</bpmn:timeDuration>` instead of a static `"P3D"` literal.

**Technical basis**: SpiffWorkflow's `DurationTimerEventDefinition.has_fired()` evaluates the duration expression exactly once - on the very first call, as soon as the associated timer task becomes `WAITING` - via a `script_engine` configurable per workflow. `spiff_adapter.py` constructs its own `PythonScriptEngine` instance for this with `TaskDataEnvironment(environment_globals={"business_days": ...})` and assigns it both on `new_workflow()` and again after every `deserialize()` (`wf.script_engine` is not part of the serialized state). This evaluation point is already exactly the right one ("now, when this specific task actually becomes ready") - no precomputation at instance start needed, see ADR 0042 for the full rationale.

**Assignment (Concept 7.1: "assignable to a process/an installation")**: an explicitly named calendar (`business_days(3, "de-national")`) is the process assignment (lives directly in the BPMN model). Without a `calendar_name` argument, the installation default calendar (`is_default=true`) is used instead, if one is maintained, otherwise just the weekend rule.

**No versioning pattern** (unlike `ProcessDefinition`/`DmnDefinition`, ADR 0027) - a calendar is a continuously maintained reference-data row (e.g. adding new holidays yearly), `name` remains permanently unique, editing runs via `PUT`.

**In-memory cache instead of DB access from within the evaluation**: SpiffWorkflow's engine is consistently synchronous, an `async` DB read would not be callable from within `has_fired()` - `spiff_adapter.py` therefore holds a module-wide cache (`register_business_calendars()`), which `repository.py` refreshes after every write access and `main.py`'s lifespan loads once at service startup.

## State persistence (ADR 0019)

Every process instance stores exclusively the complete JSON blob produced by `BpmnWorkflowSerializer.serialize_json()` — **no** separate, normalized task table. Rationale/consequences: see [ADR 0019](../adr/0019-workflow-full-state-serialization.md).

## SLA poll loop (P6-S2, ADR 0020)

An asyncio background task (`_sla_poll_loop` in `main.py`, started in `lifespan`) checks every `sla_poll_interval_seconds` (default 30s, `DMS_SLA_POLL_INTERVAL_SECONDS`) **every** instance with `status="running"`: deserialize, `spiff_adapter.check_timers()`, re-persist the blob, publish fired boundary events as `workflow.task.escalated`. No push mechanism, no distributed lock across multiple `workflow-service` replicas — see [ADR 0020](../adr/0020-sla-timer-polling.md) for the full rationale and the documented limitations. **Since P6-S6**: before every tick, additionally checks directly via the new `permission_client.py` (`is_maintenance_active()`, `GET /maintenance-mode` at the Permission Service) whether system-wide maintenance mode (4.8) is active, and then skips the tick entirely — no incoming request to which the gateway could attach an `X-DMS-Maintenance-Active` header, hence the only place in this service with its own polling connection to the Permission Service instead of header evaluation.

## Authorization & maintenance mode (4.6/4.8, since P6-S6)

Deliberately limited retrofit (user decision: "gate admin actions, leave everyday usage open", see [ADR 0024](../adr/0024-not-shutdown-gateway-enforced.md)):

- **Creating/deleting process definitions** (BPMN/script task upload) require the capability `admin.object_config` — a real call against the Permission Service via a new, thin `permission_client.py` (same pattern as `auth-service`'s role client from P6-S5), `403` without the capability or without the `X-DMS-Principal` header. `auth-service` creates a second technical account `config-admin`/`config-admin` for this (domain "workflow configuration"). Since script code only enters the system via this now-gated upload (no separate execution route), this effectively also secures script task execution, without needing an own check for it.
- **Instance start/task completion** respect system-wide maintenance mode (4.8): `503` as long as the gateway-injected `X-DMS-Maintenance-Active` header is `"true"`. Since **Post-Roadmap Phase 19 Session 9** ([ADR 0074](../adr/0074-workflow-instance-task-rbac.md)) both additionally check `workflow.write` via `permission-service` (replaces the earlier, deliberately hardcoded-open P6-S6 decision "normal business use shouldn't need a domain admin role" with an admin-editable "everyone" permission with the same de facto behavior).
- **`created_by`/`completed_by` remain purely unchecked strings** — the gating decision only affects *whether* an action may be performed, not whether the given name is correct (unchanged since P6-S1).
- **Since P6-S9**: `POST /federation/inbound`/`.../inbound-result` are public routes (`gateway-service`'s `public_routes`, no `X-DMS-Principal` — the Federation Hub is not a logged-in user), but still respect maintenance mode (a calling hub would itself have to interpret 503 behavior as a delivery failure) — deliberately *not* included in `maintenance_mode_allowed_routes`, since a federated step is functionally everyday processing, not an admin action (no special case as with ADR 0025). Authentication instead runs via `X-Federation-Hub-Signature` (ADR 0028).

## BPMN import review gate (Post-Roadmap Phase 21 Session 4, ADR 0087)

`POST /process-definitions` additionally asks `permission-service` before actual creation whether the action type `workflow.process_definition.import` currently requires approval (`GET /approval-config/{action_type}`, new, plain `approval_client.py`, identical pattern to `config_service`'s/`document_service`'s classes of the same name). By default (no approval requirement configured) behavior is **byte-identical** to before — `201` + `ProcessDefinitionOut`. If the approval requirement is enabled, instead an approval request is created at `permission-service` (BPMN text, name and optional `process_id` as `payload`), `202` with `{status: "pending_approval", approval_request_id}` is returned — **no** creation, no BPMN validation at this point. A new, plain consumer (`consumer.py`, `ensure_stream=False`, own durable name `workflow-service-approval`) reacts to the already-existing `permission.approval.approved` event, filters on this action type and applies the deferred import via the same `repository.create_process_definition` function also used by the immediate path (including the BPMN validation already present there — invalid BPMN fails while consuming, logged instead of reported, since there is no longer an HTTP caller). `apps/process-designer` recognizes the `202` case (`isPendingApproval()`) and shows a notice instead of navigating to the (not yet existing) definition. Full rationale, in particular why the success case is deliberately NOT wrapped in a uniform status envelope as with `config-service`: [ADR 0087](../adr/0087-bpmn-import-review-gate.md).

## Delegation during absence (4.4a, since P14-S11)

`POST .../tasks/{id}/complete` requires the base permission `workflow.write` for EVERY completion since Post-Roadmap Phase 19 Session 9 (ADR 0074, `completed_by` still remains an unchecked free-text field, see above) — only if the request additionally passes `on_behalf_of_principal_id` does a further, more specific check apply: `_require_delegation_if_on_behalf_of()` requires a real `X-DMS-Principal` header (`401` otherwise, NOT `completed_by` — otherwise any caller could claim an arbitrary delegation) and calls `permission_client.py`'s `check_delegation()` against `GET /delegations/check` at the Permission Service (`403` without a matching active delegation). A delegation's process scope (`scope_process_definition_ids`) is checked against `ProcessInstance.process_definition_id`. On success, the published `workflow.task.completed`/`workflow.instance.completed` events additionally carry the new `on_behalf_of` field (= the represented person) alongside the existing `actor` (= `completed_by`). Full architectural rationale: [ADR 0048](../adr/0048-delegation-lives-in-permission-service-no-task-assignee-retrofit.md).

## License demo mode/lock behavior (Concept 9.3, since P9-S2)

`workflow-service` is the only currently real, separately licensable "application component" from Concept 9.1 (CMIS Connector/Migration Service only exist from Phase 12 onward). A new, thin `license_client.py` (`LicenseStatusClient`, modeled on `permission_client.py`) queries its own license status at `registry-service` (`GET /license-status/workflow-service`, TTL cache 15s, fail-open `"licensed"`) — **not** directly at `license-service`, the registry remains the sole intermediary (3.2b).

A new `_license_gate(action)` dependency (`Depends(...)` instead of manually in the function body as with maintenance mode, since an async cross-service call is needed here instead of a simple header read):

- `"unlicensed"` blocks entirely, including read access (`403`).
- `"demo"` allows read access only (verbatim concept example) — write endpoints (`POST`/`DELETE /process-definitions*`, `POST .../instances`, `POST .../tasks/{id}/complete`) respond with `403`.
- `"licensed"` lets everything through.

`/federation/*` endpoints deliberately remain ungated — federation is a standalone topic anchored in Phase 13, no pre-decision made here.

## Signature Task (3.10, since P6-S7)

A `<bpmn:manualTask>` with `bpmn:extensionElements/camunda:properties` `taskType=signature`/`requiredLevel=ses|aes|qes` is recognized as a Signature Task — technically it remains an ordinary Manual Task (`.manual is True`, `ready_manual_tasks`/`find_ready_task` unchanged), but functionally its completion requires a real signature:

- The `document_id` to be signed runs through the existing generic `data` process variable (no new schema field — workflow-service knows no document concept), e.g. set via `initial_data` at instance start.
- `POST .../tasks/{id}/complete` requires `signature_id` in the body in this case. A new, thin `signature_client.py` (pattern like `permission_client.py` from P6-S6) queries `signature-service` (`GET /signatures/{id}`): the signature must exist, match the task data's `document_id` value and reach at least `requiredLevel` (rank order `ses < aes < qes`) — otherwise `400`.
- No new BPMN element, no modeler tooling change needed — matching the concept wording "technically a special form of the Manual Task". Example fixture: `tests/fixtures/signature_task.bpmn`.
- **No process designer palette entry** in this session — a Signature Task's extension attributes must be set by hand in the uploaded BPMN XML. Follows with P6-S8.

## Federation (7.4, since P6-S9)

Two further Manual Task special forms for cross-installation process steps, mediated via a [Federation Hub](federation-hub-service.md) — technically both remain ordinary `bpmn:manualTask` elements with `camunda:properties`, no new BPMN element, same basic pattern as the Signature Task:

- **`taskType=federated`** (sender side): additionally `targetInstallationId`/`targetProcessType`. As soon as ready, the task is dispatched **automatically** (`main.py._dispatch_pending_federation_tasks`, called after instance start/task completion/SLA poll tick) — never completed by a human, a direct `.../complete` call returns `409`. The current task process data is encrypted end-to-end with the target installation's public key (`federation_crypto.py`) and handed to the hub via `federation_client.py` (`POST /handovers`). The task stays "ready" (functionally: waiting) until `POST /federation/inbound-result` reports a result back and completes it programmatically.
- **`taskType=federated_return`** (receiver side): is also dispatched automatically as soon as ready — encrypts the current task data for the originating installation (from the linked `federation_task` record, see below) and sends it back via the hub (`POST /handovers/{id}/result`), then completes itself.
- **Self-registration** (`main.py._ensure_federation_identity`): opt-in via `Settings.federation_hub_base_url`. On the very first start with a configured hub, an own RSA-2048 key pair is generated (`federation_crypto.generate_keypair`), the hub's public key is fetched once (trust-on-first-use), and the installation is registered at the hub (`FederationIdentity` singleton, `id=1`, same pattern as `signature-service`'s `InternalCa`) — on every further start, an idempotent re-registration (updates `callback_base_url`/`version` if settings have changed; an unreachable hub does not block the service's own startup). `callback_base_url` deliberately points to the **own gateway** (`{installation_gateway_base_url}/api/workflow-service`), not to the internal container address — only this way does an incoming delivery respect the same maintenance-mode logic as any other request (see below). The `display_name` reported to the hub has, since P13-S1, come from the shared `settings.installation_display_name` (`dms_common.BaseServiceSettings`, 3a) instead of a service-own setting known only here — the randomly generated hub `installation_id` itself deliberately remains independent from the installation-wide fleet/license `installation_id` (see `docs/services/registry-service.md`). **Since P13-S4**: every registration/re-registration is additionally signed with the own private key (`federation_client._signed_headers`, `X-Installation-Signature`) — no more hub-issued `api_key`, see "Trust hardening" below.
- **Trust hardening/key rotation (P13-S4, ADR 0039)**: `federation_client.py` now signs every write request to the hub (registration, deregistration, handover creation, result report) with the own `FederationIdentity.private_key_pem` instead of a hub-issued `api_key` (the `api_key` column is dropped entirely, removed via migration). `POST /federation/rotate-key` (see API table above) allows a controlled key change with proof of continuity. Full rationale/consequences (deliberately no real mTLS, revocation remains an operator action at the hub, no enforced rotation cadence): see [ADR 0039](../adr/0039-federation-trust-hardening-request-signing-over-mtls.md) and [federation-hub-service.md](federation-hub-service.md).
- **`GET`/`PUT /federation/config`** (since P13-S3): the version compatibility range (`version`/`min_compatible_peer_version`) has, since this session, lived in an own `FederationConfig` DB row instead of directly in `Settings` - 7.4 literally requires it to be "part of the already-versioned configuration schema (7.3)". `GET` is ungated (pure metadata), `PUT` requires the same `admin.object_config` capability as the BPMN upload and, if federation is active, immediately triggers a re-registration at the hub with the new values (no container restart needed anymore). New `config-service` category `federation_config` (see `docs/services/config-service.md`) makes this range reachable via the regular configuration import.
- **`GET /federation/installations`**: thin proxy on the hub address book, basis for the target installation selection in the Process Designer (`apps/process-designer`'s `FederatedStepPropertiesProvider`) — empty list without a configured hub, no auth needed (like other `GET`s).
- **`POST /federation/inbound`**: receives a new handover. Public route (see `gateway-service`'s `public_routes`) — authentication runs via `X-Federation-Hub-Signature` (`federation_crypto.verify_body` against the hub's public key fetched during self-registration), not via `X-DMS-Principal`. Resolves `targetProcessType` via `Settings.federation_process_type_map` (JSON, `{"<targetProcessType>": "<local process_definition name>"}`) to the **newest version** of the assigned local process definition, decrypts the payload with the own private key and starts a new instance (`created_by="federation-hub"`). Additionally publishes `workflow.federation.inbound_received` (see Events).
- **`POST /federation/inbound-result`**: receives the result of a self-initiated handover, decrypts the result and programmatically completes the waiting `federated` task (`completed_by="federation-hub"`).
- **`FederationIdentity`/`FederationTask`** (new tables, additive via `create_all`, no alter migration needed): `FederationIdentity` holds the own key pair/the hub API key/the cached hub public key. `FederationTask` links a local task/instance with a `handover_id` at the hub (`direction="outbound"|"inbound"`) — prevents duplicate dispatching and, for an incoming handover, records which `origin_installation_id` a later `federated_return` task sends its result back to. Uniqueness applies to `(handover_id, direction)`, not `handover_id` alone — in the self-loopback smoke test (an installation hands over to itself), two rows with the same `handover_id` would otherwise end up in the same database (see "Bugs found only during the live smoke test" below).
- **`handover_id` is generated by the sending installation itself** (`uuid.uuid4()`), not by the hub — its own `FederationTask` row is committed **before** the hub call, so that a nested callback from the hub reaching back into the same installation (self-loopback) already sees the row (Postgres transaction isolation). See `docs/services/federation-hub-service.md` for the full failure analysis.
- **Notification** (roadmap note "notification of the target installation"): `workflow.federation.inbound_received` carries an optional `notify_email` field (from the sender side's payload, same pattern as `escalation_email` for the SLA timer) — `notification-service` sends an email when a value is present, see `docs/services/notification-service.md`.
- No own palette entry needed in the Process Designer (as with the Signature Task) — a new "Federation" properties panel group on Manual Tasks, visible only when the hub knows at least one installation (see `docs/services/process-designer.md`).

## Connector service tasks (7.1 "triggering a connector call", since P12-S2)

Unlike the Signature Task/Federation (both special forms of the **Manual** Task, since a human or an external mediation service decides on completion), a connector service task is a real `bpmn:serviceTask` — runs **automatically** like a Script Task, without waiting on anything. The first user is `migration-service` (7.2), but the pattern is deliberately generic — `workflow-service` does not know `migration-service`.

- **`taskType=connector_call`/`serviceUrl=...`** (`camunda:properties` on a `bpmn:serviceTask`): `spiff_adapter.py`'s `ConnectorServiceTask` spec class (registered via `OVERRIDE_PARSER_CLASSES`, SpiffWorkflow's own documented extension point) calls a module-wide callback, injectable via `register_connector_task_handler()`, in `_execute()`. `main.py` registers a handler for this that synchronously runs `httpx.post(serviceUrl, json=dict(task.data))` (SpiffWorkflow/`do_engine_steps()` is consistently synchronous, no new async/sync break) and merges the JSON response back into the process data. A `serviceTask` **without** `taskType=connector_call` remains an unchanged, real no-op (backward compatibility).
- **`{placeholder}` substitution in `serviceUrl`** (`str.format(**data)` with the current process data) — allows e.g. a per-instance different `transfer_id` in the URL, without needing to generate the BPMN file individually per instance.
- **Real SpiffWorkflow quirks found** (not obvious from the docs): (1) `ServiceTask` is not registered in any default serializer configuration — `ConnectorServiceTask` must be explicitly mapped to `BpmnTaskSpecConverter`, otherwise serialization fails with "not JSON serializable". (2) `_execute()` must return `True` to actually complete the task — a falsy return value (SpiffWorkflow's own `ServiceTask` default) leaves it permanently stuck in `STARTED`. (3) Only `CamundaTaskParser` (not the base `TaskParser`) reads `camunda:properties` into `task_spec.extensions` at all.

### Resumability: `POST /instances/{id}/retry`

A failed `connector_call` (e.g. target unreachable) puts SpiffWorkflow's task into `ERROR` — a simple re-run of `do_engine_steps()` is not enough (only `READY` tasks are processed). `spiff_adapter.retry_errored_tasks()` uses SpiffWorkflow's official `reset_branch()` API to move `ERROR` tasks back to `READY`/`FUTURE` (task data is preserved), after which `POST /instances/{id}/retry` runs `do_engine_steps()` again.

`start_instance`/`complete_task`/`retry_instance` in `repository.py` persist the `workflow_state` blob for this in a `try`/`finally` rather than only after successful completion — without this there would be no instance row at all with the correct intermediate state to resume from if the very first automatic step failed (found in practice). `main.py`'s three affected endpoints commit for the same reason in the `except` branch too, before the exception is re-raised — otherwise `get_session()`'s context manager would roll back the already-flushed intermediate state when closing the session.

### Caller-determined instance ID

`ProcessInstanceCreate.instance_id` (optional) lets the caller determine their own reference for a new instance instead of accepting a server-generated one — same pattern as `federation-hub-service`'s `handover_id` (ADR 0028). Important for a caller like `migration-service`, which wants to persist the ID already **before** starting: if even the first automatic step fails, the (still-created) instance would otherwise not be findable for a later `/retry` call.

## Open Points

- ~~Role check since P6-S6 only for process definitions (`admin.object_config`) — instance start/task completion deliberately remain open to every authenticated principal~~ — **fixed in Post-Roadmap Phase 19 Session 9** ([ADR 0074](../adr/0074-workflow-instance-task-rbac.md)): both now check `workflow.write` via `permission-service` (the "everyone" group retains the previous open behavior, but makes it admin-editable). `completed_by`/`created_by` remain purely unchecked strings — the gating decision only affects *whether* an action may be performed, not whether the given name is correct.
- ~~Script Tasks execute arbitrary Python code embedded in the BPMN XML server-side (SpiffWorkflow's standard scripting environment) — effectively secured since P6-S6 by the `admin.object_config` gating at the upload endpoint, but a single domain admin could previously enable this unobserved~~ — **optional four-eyes gate added in Post-Roadmap Phase 21 Session 4** ([ADR 0087](../adr/0087-bpmn-import-review-gate.md), see "BPMN import review gate" above): with the approval requirement enabled, a second admin must confirm every BPMN import before the contained script code becomes instance-startable. Deliberately *optional* (default remains ungated, as with `config-service`'s P17-S3 retrofit) — an installation without multiple trusted domain admins can leave the gate unused.
- **SLA poll precision is tied to the poll interval** (default 30s) — no real-time escalation detection, see ADR 0020.
- **No distributed lock across multiple `workflow-service` replicas** — a horizontally scaled deployment would fire/publish the same boundary timer multiple times, see ADR 0020 "Consequences".
- **Only `DurationTimerEventDefinition`-based boundary timers actually tested** (P6-S2) — `CycleTimerEventDefinition` (recurring escalation) and `TimeDateEventDefinition` (fixed point in time) are natively supported by SpiffWorkflow, but are not covered by an own test this session.
- **Case Service integration since P6-S3**: `case-service` consumes `workflow.instance.completed` and matches via `business_key` (which it sets to its own case ID at instance start) — workflow-service itself did not need to change for this, see `docs/services/case-service.md`.
- **Signature Tasks with modeler support since P6-S8** (`apps/process-designer`'s `SignatureTaskPropertiesProvider`) — the extension attributes no longer need to be set by hand in the BPMN XML.
- **Federated process steps implemented since P6-S9** (see "Federation" above) — open limitations of this foundation: no enforcement of declared `supported_process_types`/`supported_document_types` on the hub side, no retry queue for a temporarily unreachable target (immediate `delivery_failed`), process type mapping on the receiver side is purely configuration-based (no automatic catalog matching between installations), exactly one incoming handover assumed per locally started instance (`get_inbound_federation_task_for_instance`). **Closed since P13-S4 (ADR 0039)**: installation→hub authentication is now signature-based instead of a copyable API key, incl. rotation (`POST /federation/rotate-key`); still open: no monitoring hookup for repeatedly failing signature checks at the hub, no enforced rotation cadence.
- **Import validation is purely structural** (SpiffWorkflow can parse the file, process ID resolvable) — the deeper validation described in 7.1 against object types/folder targets/instance targets available in the system requires task types that don't yet exist in this foundation (e.g. a "create document" task type).
- **`business_key` is an unvalidated opaque reference** — no check against the Document Service whether a given `document_id` actually exists.
- **No rollback to an older version as the new "newest" version** — an old version remains openable/startable, re-"promoting" it to the front would need a manual re-upload of its `bpmn_xml`, no own endpoint (since P6-S8, see ADR 0027).

FOR UPDATE`) — a real parallel conflict of two simultaneous save attempts under the same name fails unhandled at the `(name, version)` unique constraint (`500`), the same deliberate simplification as with document-service's version number assignment.~~ — **fixed in P25-S1** ([ADR 0096](../adr/0096-workflow-definition-version-race-advisory-lock.md), see "Versioning" above): a transaction-bound Postgres advisory lock on `name` serializes concurrent save attempts of the same family, instead of a `SELECT ... FOR UPDATE` counter row (which doesn't exist here unlike with `object-type-service`/`case-service`). Still open: `create_dmn_definition`'s `DuplicateDecisionIdError` check against OTHER families (cross-family, not the version-assignment race condition WITHIN a family fixed here) has its own, analogous race condition, deliberately not fixed here as well, see ADR 0096 "Consequences".
- **No retroactive check at task level when deleting a process definition** — only the existence of any instance is checked, not whether it is actually still running.
- **DMN (P14-S4)**: `DELETE /dmn-definitions/{id}` does not check whether a BPMN process definition still references it via `camunda:decisionRef` (see "DMN 1.3 decision tables" above) — such a process definition fails with `422` on its next instance start, instead of blocking the deletion itself. Every BPMN parse always loads ALL newest DMN definitions (no static analysis of which `decisionRef`s a specific file actually needs) — to be revisited with very many DMN families and correspondingly more parse time, uncritical for a reference implementation. Evaluation is SpiffWorkflow's own simplified expression semantics, not a full OMG FEEL implementation (e.g. no FEEL-native date/list functions beyond what the underlying Python expression already offers).
- **Business calendars (P14-S5, ADR 0042)**: `DELETE /business-calendars/{id}` does not check whether a BPMN file still references the calendar name via `business_days(n, "...")` — such an instance only fails with an `UnknownBusinessCalendarError` when it reaches the affected timer task. Only a single global timezone (UTC) for weekday calculation, no installation-specific timezone. No prebuilt calendar templates (e.g. German holidays) — deliberately reserved for Phase 17 (configuration packages).
- **Delegation (4.4a, P14-S11) only checks the process scope of a delegation** (`scope_process_definition_ids`) — `scope_object_type_ids`/`scope_folder_resource_ids` are carried by `permission-service` but not evaluated here (see ADR 0048). A regular, non-delegated completion remains fully ungated — the delegation check only applies when `on_behalf_of_principal_id` is explicitly set.
