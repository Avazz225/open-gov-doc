# workflow-service

**Verantwortung:** Workflow Engine Grundgerüst (Konzept 7.1) — BPMN-2.0-Import und -Ausführung über [SpiffWorkflow](https://github.com/sartography/SpiffWorkflow) (LGPLv3, [ADR 0018](../adr/0018-spiffworkflow-lgpl-license.md)), Manual/Automatic Tasks, seit P6-S2 auch Timer/Boundary Events (SLA-Zeitüberwachung, [ADR 0020](../adr/0020-sla-timer-polling.md)), seit **P6-S7** zusätzlich der "Signature Task" (3.10, technisch eine Sonderform des Manual Task), seit **P6-S9** zusätzlich föderierte Prozessschritte über den Federation Hub (7.4, technisch ebenfalls Manual-Task-Sonderformen), seit **P12-S2** zusätzlich generische Connector-Service-Tasks (7.1 "Auslösen eines Connector-Aufrufs" — erster Nutzer `migration-service`, 7.2) + `POST /instances/{id}/retry` (Resumability für fehlgeschlagene automatische Schritte), seit **P14-S4** zusätzlich DMN-1.3-Entscheidungstabellen/Business Rule Task (eigenes SpiffWorkflow-DMN-Support, `dmn-definitions`-CRUD + Ex-/Import über den Konfigurationsexport 7.3), seit **P14-S5** zusätzlich regionale Geschäftskalender für die SLA-Fristberechnung (`business-calendars`-CRUD + eine neue, in BPMN-Timer-Dauerangaben aufrufbare `business_days(n, calendar_name)`-Funktion, [ADR 0042](../adr/0042-business-calendar-script-engine-injection.md)). UI folgt mit P6-S8 (`apps/process-designer`). Seit **P6-S6** teilweise gegated: Prozessdefinitionen anlegen/löschen erfordert die Capability `admin.object_config` (4.6-Retrofit), Instanzstart/Task-Abschluss bleiben für jeden authentifizierten Principal offen, respektieren aber den systemweiten Wartungsmodus (Not-Shutdown, 4.8) — siehe [ADR 0024](../adr/0024-not-shutdown-gateway-enforced.md).

**Konzept-Referenz:** 7.1, 4.6, 4.8, 3.10, 7.4, 7.2
**Eigenes Postgres-Schema:** `workflow` (Tabellen `process_definition`, `process_instance`, seit P6-S9 zusätzlich `federation_identity`, `federation_task`, seit P14-S4 zusätzlich `dmn_definition`, seit P14-S5 zusätzlich `business_calendar`)

## Datenmodell

- `process_definition`: `id`, `name` (seit P6-S8 der Prozessfamilien-Schlüssel, nicht mehr global eindeutig, siehe "Versionierung" unten), `version` (Integer, Default 1, eindeutig zusammen mit `name`), `bpmn_process_id` (die interne Prozess-ID aus der BPMN-XML selbst, `<bpmn:process id="...">`), `bpmn_xml` (Text, die vollständige hochgeladene Datei), `created_at`/`updated_at`.
- `process_instance`: `id` (UUID), `process_definition_id` (FK), `business_key` (String, nullable, opake Cross-Service-Referenz z. B. auf eine künftige `document_id` — **nicht** gegen den Document Service validiert, gleiches Muster wie `folder_id`/`object_type_id` vor ihrer jeweiligen Durchsetzung in früheren Phasen), `status` (`"running"`\|`"completed"`), `workflow_state` (Text — vollständiger, von SpiffWorkflow serialisierter Ausführungszustand, siehe "State-Persistenz" unten), `created_by`, `created_at`/`updated_at`/`completed_at` (nullable).
- `dmn_definition` (seit P14-S4): `id`, `name` (Familienschlüssel, gleiches Versionierungsmuster wie `process_definition`), `version`, `decision_id` (die interne `<decision id="...">` aus der DMN-XML — der tatsächliche Schlüssel, über den ein `businessRuleTask`s `camunda:decisionRef` sie referenziert, NICHT `name`), `dmn_xml` (Text), `created_at`/`updated_at`.
- `business_calendar` (seit P14-S5): `id`, `name` (eindeutig, KEIN Versionierungsmuster — Update-in-Place über `PUT`), `non_working_dates` (JSON-Liste von ISO-Datumsstrings, nur die ZUSÄTZLICHEN, kalenderspezifischen arbeitsfreien Tage — Wochenenden gelten unabhängig davon immer als arbeitsfrei, siehe "Geschäftskalender" unten), `is_default` (Boolean, höchstens eine Zeile gleichzeitig `true`), `created_at`/`updated_at`.

## Versionierung (seit P6-S8, ADR 0027)

`name` ist der Prozessfamilien-Schlüssel: `POST /process-definitions` unter einem bereits existierenden Namen legt automatisch die nächste `version` an (`max(version je name) + 1`), statt mit `409` abgelehnt zu werden — zwei Definitionen mit demselben Namen sind der Normalfall. `GET /process-definitions` liefert per Default nur die neueste Version je Familie (`DISTINCT ON`), `GET /process-definitions?name=X` die vollständige Historie. Prozessinstanzen bleiben unverändert an eine konkrete `id` (also eine bestimmte Version) gebunden — eine neue Version wirkt sich nie rückwirkend auf bereits laufende oder abgeschlossene Instanzen aus, `POST .../{id}/instances`/`DELETE /process-definitions/{id}` mussten dafür nicht geändert werden. Grundlage für den "Speichern"-Fluss des neuen Process Designer (`apps/process-designer`, P6-S8): Name unverändert lassen erzeugt eine neue Version, ein geänderter Name eine neue Familie.

**Seit P25-S2**: `POST /process-definitions/{id}/restore` ist ein zweiter Anlage-Einstiegspunkt neben dem regulären Upload (`POST /process-definitions`) — statt neu hochgeladenem Inhalt wird `bpmn_xml`/`bpmn_process_id` einer bereits existierenden (auch nicht mehr aktuellen) Version derselben Familie wiederverwendet, um daraus die nächste Version anzulegen. Beide Einstiegspunkte laufen durch dieselbe `repository.create_process_definition` und damit durch dieselbe Versionsnummern-/Advisory-Lock-Logik, siehe API-Tabelle oben.

**Seit P25-S1 ([ADR 0096](../adr/0096-workflow-definition-version-race-advisory-lock.md))**: die Vergabe von `next_version` (sowohl für Prozess- als auch DMN-Definitionen, siehe unten) ist gegen echte Nebenläufigkeit abgesichert — `create_process_definition`/`create_dmn_definition` nehmen vor dem Lesen von `max(version)` einen transaktionsgebundenen Postgres-Advisory-Lock auf `name` (`pg_advisory_xact_lock`, eigener Namespace je Definitionstyp), statt wie zuvor unlocked zu lesen. Mehrere echt gleichzeitige Speicherversuche unter demselben `name` (auch für eine brandneue Familie ohne bisherige Zeile) erhalten dadurch garantiert distincte, lückenlos aufeinanderfolgende Versionsnummern statt eines unbehandelten `IntegrityError`/`500` an der `(name, version)`-Unique-Constraint. Details/Begründung (insbesondere warum kein Zähler-Tabellen-Muster wie bei `object-type-service`/`case-service`) siehe ADR 0096.

## SpiffWorkflow-Anbindung (`spiff_adapter.py`)

Die gesamte SpiffWorkflow-API-Oberfläche ist in einem einzigen Modul isoliert (`src/workflow_service/spiff_adapter.py`) — `repository.py` kennt SpiffWorkflow-Klassen nicht direkt, nur die eigenen Wrapper-Funktionen. Grund: SpiffWorkflows API ist nicht formal als stabil dokumentiert; ein künftiger Versions-Bump muss so nur an einer Stelle nachgezogen werden. Gegen die tatsächlich installierte Version (**3.1.2**) per `help()`/`inspect` verifiziert, nicht nur aus der Dokumentation übernommen — u. a. wurde dabei empirisch festgestellt, dass `BpmnWorkflow.set_data()` **nicht** ausreicht, um Prozessvariablen beim Start sichtbar zu machen (Daten werden beim Abschluss eines Tasks an dessen Kinder weitergereicht, nicht rückwirkend aus dem workflow-weiten `data`-Dict gelesen) — `initial_data` wird deshalb direkt auf dem zu Beginn bereiten Start-Task gesetzt.

- **Manual/User Tasks** (`<bpmn:manualTask>`/`<bpmn:userTask>`, beide haben `task_spec.manual == True`): bleiben nach `do_engine_steps()` bereit stehen, bis `POST .../complete` aufgerufen wird. `task_spec.lane` (Bahn-/Rollenname aus dem BPMN-Modell, `None` falls das Modell keine Lanes definiert) wird informativ mitgeliefert — **keine Auswertung/Durchsetzung** in dieser Session, siehe "Offene Punkte".
- **Automatic Tasks (Script Tasks)**: laufen über SpiffWorkflows eingebaute Standard-Python-Scripting-Umgebung automatisch, sobald sie bereit sind — keine eigene Connector-/Delegate-Registrierung in diesem Grundgerüst.
- **Timer/Boundary Events (P6-S2, SLA-Zeitüberwachung, 7.1)**: `spiff_adapter.check_timers()` kapselt `wf.refresh_waiting_tasks()`+`do_engine_steps()` und meldet gefeuerte Boundary-Timer (erkannt über `isinstance(task_spec, BoundaryEvent)`) zurück. Beide BPMN-Semantiken real gegen die installierte Version getestet: non-interrupting (`cancelActivity="false"`) lässt den ursprünglichen Task weiterlaufen, interrupting (`cancelActivity="true"`, BPMN-Default) storniert ihn — beides vollständig SpiffWorkflow-eigene Semantik, siehe Modul-Docstring.

**Seit P6-S7**: Parser auf `SpiffWorkflow.camunda.parser.CamundaParser` umgestellt (weiterhin identische `add_bpmn_str`/`get_process_ids`/`get_spec`-Oberfläche, `manualTask` mappt unverändert auf `ManualTask`), da nur dieser Parser `bpmn:extensionElements/camunda:properties` in `task_spec.extensions` einliest (Grundlage des Signature Task, siehe unten). Musste von einem passenden Serializer-Config begleitet werden: `CamundaParser` mappt `<bpmn:userTask>` zusätzlich auf Camundas eigene `UserTask`-Spec-Klasse statt der BPMN-Default-Klasse — `_SERIALIZER` nutzt seither `SpiffWorkflow.camunda.serializer.config.CAMUNDA_CONFIG` statt `BpmnWorkflowSerializer.configure()`, sonst schlägt die JSON-Serialisierung bereits bestehender `userTask`-Fixtures (z. B. der P6-S2-Boundary-Timer-Test) fehl. Alle 52 vorherigen Tests bleiben nach diesem Wechsel unverändert grün (siehe [ADR 0025](../adr/0025-signature-service-internal-ca-and-connector-plugin.md)).

## DMN-1.3-Entscheidungstabellen / Business Rule Task (7.1, seit P14-S4)

`CamundaParser` (seit P6-S7 Basisklasse) ist bereits selbst eine Unterklasse von `SpiffWorkflow.dmn.parser.BpmnDmnParser` (empirisch per `CamundaParser.__mro__` verifiziert) — `businessRuleTask` ist dort bereits über `OVERRIDE_PARSER_CLASSES` auf `BusinessRuleTaskParser`/`BusinessRuleTask` gemappt, kein eigener Override nötig (anders als beim Connector-Service-Task, siehe oben). `parser.add_dmn_str(xml)` lädt eine DMN-Datei in denselben Parser, geschlüsselt über deren eigene `<decision id="...">` — `BusinessRuleTaskParser.create_task()` liest `camunda:decisionRef` vom `<bpmn:businessRuleTask>`-Element und löst ihn exakt gegen diesen Schlüssel auf. Beide `add_dmn_str`/`add_bpmn_str` müssen VOR `parser.get_spec()` aufgerufen sein — Reihenfolge zwischen beiden ist egal, `_new_parser()` lädt deshalb alle übergebenen DMN-Definitionen vor der BPMN-Datei selbst. `DMNEngine` (Auswertung zur Laufzeit) wird von SpiffWorkflow selbst transparent aus `BusinessRuleTaskMixin._run_hook()` aufgerufen, genau wie bei jedem anderen automatischen Task (`do_engine_steps()`) — dieses Modul instanziiert es nie direkt, die Auswertung ist SpiffWorkflows eigene, vereinfachte Python-Ausdrucks-Semantik (keine vollständige OMG-FEEL-Implementierung), Eingaben/Ausgaben lesen/schreiben dasselbe generische `task.data`-Dict wie jeder andere Tasktyp.

**"Genau eine `<decision>` je DMN-Datei"-Grenze**: SpiffWorkflow selbst unterstützt nur genau eine Decision je Datei (`ValidationException("Multiple decision tables are not current supported.")`), diese Prüfung passiert allerdings erst LAZY innerhalb von `DMNParser.parse()`, ausgelöst durch `BpmnDmnParser.get_decision()` beim Auflösen eines referenzierenden `businessRuleTask` — ein reiner DMN-Upload ohne begleitende BPMN-Referenz würde den Fehler nie sehen. `spiff_adapter.parse_dmn()` ruft `dmn_parser.parse()` deshalb selbst explizit auf, um die Prüfung schon beim Upload zu erzwingen (empirisch verifiziert: `len(parser.dmn_parsers)` allein kann diese Grenze NICHT prüfen, da `add_dmn_xml()` pro Datei immer genau einen Eintrag anlegt, geschlüsselt über die ID der ERSTEN Decision im Dokument). Ein Bug der installierten SpiffWorkflow-Version: die `ValidationException` für den Mehrfach-Fall übergibt intern eine `list` statt eines lxml-Elements und wirft dabei selbst einen `AttributeError` statt sauber durchzukommen — `parse_dmn()` fängt beide Fälle über `except Exception` ab.

**"Immer alle neuesten DMN-Definitionen laden"-Vereinfachung**: `repository.list_latest_dmn_xml()` lädt vor JEDEM BPMN-Parse (`create_process_definition`/`start_instance`) die jeweils neueste Version JEDER DMN-Familie in den Parser — nicht nur die von der konkreten BPMN-Datei tatsächlich referenzierten. Bewusste, dokumentierte Vereinfachung für diese Referenzimplementierung (kein statisches Scannen der BPMN-XML nach `camunda:decisionRef`-Attributen vor dem Parse): unreferenzierte Decisions sind harmlos, kosten nur etwas zusätzliche Parse-Zeit. Konsequenz: eine DMN-Familie muss bereits existieren, BEVOR eine sie referenzierende BPMN-Datei hochgeladen/erneut geparst wird (`start_instance` parst bei jedem Instanzstart neu) — sonst `422` (`InvalidBpmnError`, SpiffWorkflow-eigene `ValidationException` beim Auflösen des unbekannten `decisionRef`).

**Bewusst KEINE "in use"-Prüfung bei `DELETE /dmn-definitions/{id}`** (anders als bei Prozessdefinitionen) — das würde ein Durchsuchen aller BPMN-XML-Texte nach `camunda:decisionRef` erfordern. Eine Löschung kann eine bestehende Prozessdefinition beim nächsten Instanzstart mit `422` fehlschlagen lassen; bereits laufende Instanzen sind unberührt (ihr `workflow_state` enthält die zum Startzeitpunkt geladene Decision bereits vollständig, siehe "State-Persistenz" unten).

**Frontend (`apps/process-designer`, P14-S4)**: der bereits registrierte `CamundaPlatformPropertiesProviderModule` (seit P6-S7/P6-S9 für Signature-/Federation-Tasks im Einsatz) rendert eine "Implementation"-Gruppe mit `Type: DMN`/`Decision reference`/`Binding`/`Tenant ID`/`Result variable` für einen ausgewählten Business Rule Task bereits vollständig, ohne dass dieses Projekt einen eigenen Properties-Panel-Provider dafür schreiben musste (per echtem Playwright-Browser-Test empirisch bestätigt, nicht nur aus der `bpmn-js-properties-panel`-Doku übernommen). Die Entscheidungstabellen selbst werden über eine neue eigenständige Liste + einen eigenen `dmn-js`-Editor bearbeitet (siehe `docs/services/process-designer.md`, [ADR 0021](../adr/0021-bpmn-io-license-watermark.md)-Addendum).

## Geschäftskalender (7.1, seit P14-S5, [ADR 0042](../adr/0042-business-calendar-script-engine-injection.md))

Frei benannte, per CRUD gepflegte Kalender aus zusätzlichen arbeitsfreien Tagen (Feiertagen) - Wochenenden (Sa/So) gelten unabhängig davon IMMER als arbeitsfrei. Wirksam über eine neue, in jeder BPMN-Timer-Dauerangabe aufrufbare Funktion: `business_days(n, calendar_name=None)` liefert eine ISO-8601-Dauer (`"P<x>D"`), die von `n` Werktagen ab "jetzt" auf die entsprechende Anzahl Kalendertage umrechnet - eine BPMN-Datei schreibt z. B. `<bpmn:timeDuration>business_days(3, "de-national")</bpmn:timeDuration>` statt eines statischen `"P3D"`-Literals.

**Technische Grundlage**: SpiffWorkflows `DurationTimerEventDefinition.has_fired()` wertet die Dauerangabe genau einmal aus - beim allerersten Aufruf, sobald der zugehörige Timer-Task `WAITING` wird - über eine per Workflow konfigurierbare `script_engine`. `spiff_adapter.py` konstruiert dafür eine eigene `PythonScriptEngine`-Instanz mit `TaskDataEnvironment(environment_globals={"business_days": ...})` und weist sie sowohl bei `new_workflow()` als auch nach jedem `deserialize()` erneut zu (`wf.script_engine` ist kein Teil des serialisierten Zustands). Dieser Auswertungszeitpunkt ist bereits genau der richtige ("jetzt, wo dieser konkrete Task tatsächlich bereit wird") - kein Vorausberechnen bei Instanzstart nötig, siehe ADR 0042 für die vollständige Begründung.

**Zuordnung (Konzept 7.1: "einem Prozess/einer Installation zuordenbar")**: ein explizit benannter Kalender (`business_days(3, "de-national")`) ist die Prozess-Zuordnung (lebt direkt im BPMN-Modell). Ohne `calendar_name`-Argument greift stattdessen der Installations-Default-Kalender (`is_default=true`), falls einer gepflegt ist, sonst nur die Wochenend-Regel.

**Kein Versionierungsmuster** (anders als `ProcessDefinition`/`DmnDefinition`, ADR 0027) - ein Kalender ist fortlaufend zu pflegende Referenzdatenzeile (z. B. jährlich neue Feiertage nachtragen), `name` bleibt dauerhaft eindeutig, Bearbeiten läuft über `PUT`.

**In-Memory-Cache statt DB-Zugriff aus der Auswertung heraus**: SpiffWorkflows Engine ist durchgehend synchron, ein `async`-DB-Read wäre aus `has_fired()` heraus nicht aufrufbar - `spiff_adapter.py` hält deshalb einen modulweiten Cache (`register_business_calendars()`), den `repository.py` nach jedem Schreibzugriff aktualisiert und `main.py`s Lifespan einmalig beim Service-Start lädt.

## State-Persistenz (ADR 0019)

Jede Prozessinstanz speichert ausschließlich den vollständigen, von `BpmnWorkflowSerializer.serialize_json()` erzeugten JSON-Blob — **keine** separate, normalisierte Task-Tabelle. Begründung/Konsequenzen: siehe [ADR 0019](../adr/0019-workflow-full-state-serialization.md).

## SLA-Poll-Loop (P6-S2, ADR 0020)

Ein asyncio-Hintergrund-Task (`_sla_poll_loop` in `main.py`, gestartet in `lifespan`) prüft alle `sla_poll_interval_seconds` (Default 30s, `DMS_SLA_POLL_INTERVAL_SECONDS`) **jede** Instanz mit `status="running"`: deserialisieren, `spiff_adapter.check_timers()`, Blob neu persistieren, gefeuerte Boundary-Events als `workflow.task.escalated` publizieren. Kein Push-Mechanismus, keine verteilte Sperre bei mehreren `workflow-service`-Replikaten — siehe [ADR 0020](../adr/0020-sla-timer-polling.md) für die vollständige Begründung und die dokumentierten Grenzen. **Seit P6-S6**: prüft vor jedem Tick zusätzlich über den neuen `permission_client.py` (`is_maintenance_active()`, `GET /maintenance-mode` am Permission Service) direkt, ob der systemweite Wartungsmodus (4.8) aktiv ist, und überspringt den Tick dann komplett — kein eingehender Request, an den das Gateway einen `X-DMS-Maintenance-Active`-Header hängen könnte, daher die einzige Stelle in diesem Service mit einer eigenen Polling-Verbindung zum Permission Service statt Header-Auswertung.

## Autorisierung & Wartungsmodus (4.6/4.8, seit P6-S6)

Bewusst begrenzter Retrofit (Nutzerentscheidung: "Admin-Aktionen gaten, Alltagsnutzung offen", siehe [ADR 0024](../adr/0024-not-shutdown-gateway-enforced.md)):

- **Prozessdefinitionen anlegen/löschen** (BPMN-/Script-Task-Upload) erfordern die Capability `admin.object_config` — echter Aufruf gegen den Permission Service über einen neuen, dünnen `permission_client.py` (gleiches Muster wie `auth-service`s Rollen-Client aus P6-S5), `403` ohne die Capability oder ohne `X-DMS-Principal`-Header. `auth-service` legt dafür ein zweites technisches Konto `config-admin`/`config-admin` an (Domäne "Workflow-Konfiguration"). Da Skript-Code ausschließlich über diesen jetzt gegateten Upload ins System gelangt (keine separate Ausführungs-Route), sichert das faktisch auch die Script-Task-Ausführung ab, ohne einen eigenen Check dafür zu brauchen.
- **Instanzstart/Task-Abschluss** respektieren den systemweiten Wartungsmodus (4.8): `503`, solange der vom Gateway injizierte `X-DMS-Maintenance-Active`-Header `"true"` ist. Seit **Post-Roadmap Phase 19 Session 9** ([ADR 0074](../adr/0074-workflow-instance-task-rbac.md)) prüfen beide zusätzlich `workflow.write` über `permission-service` (ersetzt die frühere, bewusst hartkodiert offene P6-S6-Entscheidung "normale Fachnutzung soll keine Domain-Admin-Rolle brauchen" durch eine admin-editierbare "everyone"-Berechtigung mit demselben De-facto-Verhalten).
- **`created_by`/`completed_by` bleiben weiterhin reine, ungeprüfte Strings** — die Gating-Entscheidung betrifft nur, *ob* eine Aktion ausgeführt werden darf, nicht, ob der angegebene Name stimmt (unverändert seit P6-S1).
- **Seit P6-S9**: `POST /federation/inbound`/`.../inbound-result` sind öffentliche Routen (`gateway-service`s `public_routes`, kein `X-DMS-Principal` — der Federation Hub ist kein eingeloggter Nutzer), respektieren aber weiterhin den Wartungsmodus (503-Verhalten müsste ein aufrufender Hub selbst als Zustellungsfehlschlag interpretieren) — bewusst *nicht* in `maintenance_mode_allowed_routes` aufgenommen, da ein föderierter Schritt fachlich Alltagsverarbeitung ist, kein Admin-Vorgang (kein Sonderfall wie bei ADR 0025). Authentisiert wird stattdessen über `X-Federation-Hub-Signature` (ADR 0028).

## BPMN-Import-Review-Gate (Post-Roadmap Phase 21 Session 4, ADR 0087)

`POST /process-definitions` fragt vor der eigentlichen Anlage zusätzlich beim `permission-service` ab, ob der Aktionstyp `workflow.process_definition.import` gerade Genehmigungspflicht hat (`GET /approval-config/{action_type}`, neuer, reiner `approval_client.py`, identisches Muster wie `config_service`s/`document_service`s gleichnamige Klasse). Standardmäßig (keine Genehmigungspflicht konfiguriert) ist das Verhalten **byteidentisch** zu vorher — `201` + `ProcessDefinitionOut`. Ist die Genehmigungspflicht aktiviert, wird stattdessen ein Freigabe-Request beim `permission-service` angelegt (BPMN-Text, Name und optionale `process_id` als `payload`), `202` mit `{status: "pending_approval", approval_request_id}` zurückgegeben — **keine** Anlage, keine BPMN-Validierung an dieser Stelle. Ein neuer, reiner Konsument (`consumer.py`, `ensure_stream=False`, eigener Durable-Name `workflow-service-approval`) reagiert auf das bereits bestehende `permission.approval.approved`-Event, filtert auf diesen Aktionstyp und wendet den zurückgestellten Import über dieselbe `repository.create_process_definition`-Funktion an, die auch der Sofort-Pfad nutzt (inkl. der dort bereits vorhandenen BPMN-Validierung — ein ungültiges BPMN scheitert beim Konsumieren, geloggt statt gemeldet, da kein HTTP-Aufrufer mehr vorhanden ist). `apps/process-designer` erkennt den `202`-Fall (`isPendingApproval()`) und zeigt einen Hinweis statt zur (noch nicht existierenden) Definition zu navigieren. Vollständige Begründung, insbesondere warum der Erfolgsfall bewusst NICHT wie bei `config-service` in eine einheitliche Status-Hülle verpackt wird: [ADR 0087](../adr/0087-bpmn-import-review-gate.md).

## Stellvertretung bei Abwesenheit (4.4a, seit P14-S11)

`POST .../tasks/{id}/complete` verlangt für JEDEN Abschluss seit Post-Roadmap Phase 19 Session 9 die Basis-Berechtigung `workflow.write` (ADR 0074, `completed_by` bleibt trotzdem ein ungeprüftes Freitextfeld, s. o.) — nur wenn der Request zusätzlich `on_behalf_of_principal_id` mitschickt, greift eine weitere, spezifischere Prüfung: `_require_delegation_if_on_behalf_of()` verlangt einen echten `X-DMS-Principal`-Header (`401` sonst, NICHT `completed_by` — sonst könnte jeder Aufrufer eine beliebige Delegation behaupten) und ruft `permission_client.py`s `check_delegation()` gegen `GET /delegations/check` beim Permission Service auf (`403` ohne passende aktive Delegation). Der Prozess-Scope einer Delegation (`scope_process_definition_ids`) wird dabei anhand der `ProcessInstance.process_definition_id` geprüft. Bei Erfolg tragen die publizierten `workflow.task.completed`/`workflow.instance.completed`-Events zusätzlich zum bestehenden `actor` (= `completed_by`) das neue `on_behalf_of`-Feld (= die vertretene Person). Vollständige Architekturbegründung: [ADR 0048](../adr/0048-delegation-lives-in-permission-service-no-task-assignee-retrofit.md).

## Lizenz-Demo-Modus/Sperrverhalten (Konzept 9.3, seit P9-S2)

`workflow-service` ist die einzige heute real existierende, separat lizenzierbare "Applikationskomponente" aus Konzept 9.1 (CMIS-Connector/Migration-Service existieren erst ab Phase 12). Ein neuer, dünner `license_client.py` (`LicenseStatusClient`, Vorbild `permission_client.py`) fragt den eigenen Lizenzstatus beim `registry-service` ab (`GET /license-status/workflow-service`, TTL-Cache 15s, fail-open `"licensed"`) — **nicht** direkt beim `license-service`, die Registry bleibt einzige Vermittlungsstelle (3.2b).

Eine neue `_license_gate(action)`-Dependency (`Depends(...)` statt wie beim Wartungsmodus manuell im Funktionskörper, da hier ein async Cross-Service-Aufruf statt eines simplen Header-Reads nötig ist):

- `"unlicensed"` sperrt vollständig, auch Lesezugriffe (`403`).
- `"demo"` erlaubt nur Lesezugriff (Konzept-Beispiel wörtlich) — schreibende Endpunkte (`POST`/`DELETE /process-definitions*`, `POST .../instances`, `POST .../tasks/{id}/complete`) antworten mit `403`.
- `"licensed"` lässt alles durch.

`/federation/*`-Endpunkte bleiben bewusst ungegatet — Föderation ist ein eigenständiges, in Phase 13 verankertes Thema, keine Vorentscheidung hier.

## Signature Task (3.10, seit P6-S7)

Ein `<bpmn:manualTask>` mit `bpmn:extensionElements/camunda:properties` `taskType=signature`/`requiredLevel=ses|aes|qes` wird als Signature Task erkannt — technisch bleibt es ein gewöhnlicher Manual Task (`.manual is True`, `ready_manual_tasks`/`find_ready_task` unverändert), fachlich verlangt der Abschluss aber eine echte Signatur:

- Die zu signierende `document_id` läuft über die bestehende generische `data`-Prozessvariable (kein neues Schema-Feld — workflow-service kennt kein Dokument-Konzept), z. B. per `initial_data` beim Instanzstart gesetzt.
- `POST .../tasks/{id}/complete` verlangt in diesem Fall `signature_id` im Body. Ein neuer, dünner `signature_client.py` (Muster wie `permission_client.py` aus P6-S6) fragt beim `signature-service` (`GET /signatures/{id}`) nach: die Signatur muss existieren, zum `document_id`-Wert der Task-Daten passen und mindestens `requiredLevel` erreichen (Rangfolge `ses < aes < qes`) — sonst `400`.
- Kein neues BPMN-Element, keine Modeler-Tooling-Änderung nötig — passend zur Konzeptformulierung "technisch eine Sonderform des Manual Task". Beispiel-Fixture: `tests/fixtures/signature_task.bpmn`.
- **Kein Prozess-Designer-Palette-Eintrag** in dieser Session — ein Signature Task muss die Extension-Attribute von Hand im hochgeladenen BPMN-XML setzen. Folgt mit P6-S8.

## Federation (7.4, seit P6-S9)

Zwei weitere Manual-Task-Sonderformen für installationsübergreifende Prozessschritte, vermittelt über einen [Federation Hub](federation-hub-service.md) — technisch bleiben beide gewöhnliche `bpmn:manualTask`-Elemente mit `camunda:properties`, kein neues BPMN-Element, gleiches Grundmuster wie der Signature Task:

- **`taskType=federated`** (Absenderseite): zusätzlich `targetInstallationId`/`targetProcessType`. Sobald bereit, wird der Task **automatisch** dispatcht (`main.py._dispatch_pending_federation_tasks`, aufgerufen nach Instanzstart/Task-Abschluss/SLA-Poll-Tick) — nie von einem Menschen abgeschlossen, ein direkter `.../complete`-Aufruf liefert `409`. Die aktuellen Task-Prozessdaten werden mit dem öffentlichen Schlüssel der Zielinstallation Ende-zu-Ende verschlüsselt (`federation_crypto.py`) und per `federation_client.py` an den Hub übergeben (`POST /handovers`). Der Task bleibt "ready" (fachlich: wartend), bis `POST /federation/inbound-result` ein Ergebnis zurückmeldet und ihn programmatisch abschließt.
- **`taskType=federated_return`** (Empfängerseite): wird ebenfalls automatisch dispatcht, sobald bereit — verschlüsselt die aktuellen Task-Daten für die Ursprungsinstallation (aus dem verknüpften `federation_task`-Datensatz, siehe unten) und schickt sie über den Hub zurück (`POST /handovers/{id}/result`), schließt sich danach selbst ab.
- **Selbstregistrierung** (`main.py._ensure_federation_identity`): opt-in über `Settings.federation_hub_base_url`. Beim allerersten Start mit konfiguriertem Hub wird ein eigenes RSA-2048-Schlüsselpaar erzeugt (`federation_crypto.generate_keypair`), der öffentliche Hub-Schlüssel einmalig abgerufen (Trust-on-First-Use) und die Installation beim Hub registriert (`FederationIdentity`-Singleton, `id=1`, gleiches Muster wie `signature-service`s `InternalCa`) — bei jedem weiteren Start eine idempotente Re-Registrierung (aktualisiert `callback_base_url`/`version`, falls sich Settings geändert haben; ein nicht erreichbarer Hub blockiert den eigenen Start nicht). `callback_base_url` zeigt bewusst auf den **eigenen Gateway** (`{installation_gateway_base_url}/api/workflow-service`), nicht auf die interne Container-Adresse — nur so respektiert eine eingehende Zustellung dieselbe Wartungsmodus-Logik wie jeder andere Request (siehe unten). Der beim Hub gemeldete `display_name` kommt seit P13-S1 aus der geteilten `settings.installation_display_name` (`dms_common.BaseServiceSettings`, 3a) statt einer nur hier bekannten, service-eigenen Einstellung — die zufällig erzeugte Hub-`installation_id` selbst bleibt bewusst unabhängig von der installationsweiten Fleet-/Lizenz-`installation_id` (siehe `docs/services/registry-service.md`). **Seit P13-S4**: jede Registrierung/Re-Registrierung wird zusätzlich mit dem eigenen privaten Schlüssel signiert (`federation_client._signed_headers`, `X-Installation-Signature`) — kein vom Hub ausgegebener `api_key` mehr, siehe "Trust-Härtung" unten.
- **Trust-Härtung/Schlüsselrotation (P13-S4, ADR 0039)**: `federation_client.py` signiert jetzt jede schreibende Anfrage an den Hub (Registrierung, Deregistrierung, Handover-Erzeugung, Ergebnis-Rückmeldung) mit dem eigenen `FederationIdentity.private_key_pem` statt eines vom Hub ausgegebenen `api_key` (der `api_key`-Spalte entfällt vollständig, per Migration entfernt). `POST /federation/rotate-key` (siehe API-Tabelle oben) erlaubt einen kontrollierten Schlüsselwechsel mit Kontinuitätsnachweis. Vollständige Begründung/Konsequenzen (bewusst kein echtes mTLS, Revocation bleibt eine Betreiber-Aktion beim Hub, kein erzwungener Rotationsturnus): siehe [ADR 0039](../adr/0039-federation-trust-hardening-request-signing-over-mtls.md) und [federation-hub-service.md](federation-hub-service.md).
- **`GET`/`PUT /federation/config`** (seit P13-S3): die Versionskompatibilitätsspanne (`version`/`min_compatible_peer_version`) lebt seit dieser Session in einer eigenen `FederationConfig`-DB-Zeile statt direkt in `Settings` - 7.4 verlangt wörtlich, dass sie "Teil des ohnehin schon versionierten Konfigurationsschemas (7.3)" ist. `GET` ist ungegatet (reine Metadaten), `PUT` verlangt dieselbe `admin.object_config`-Capability wie der BPMN-Upload und löst bei aktiver Föderation sofort eine Re-Registrierung beim Hub mit den neuen Werten aus (kein Container-Neustart mehr nötig). Neue `config-service`-Kategorie `federation_config` (siehe `docs/services/config-service.md`) macht diese Spanne über den regulären Konfigurationsimport erreichbar.
- **`GET /federation/installations`**: dünner Proxy auf das Hub-Adressbuch, Grundlage für die Zielinstallations-Auswahl im Process Designer (`apps/process-designer`s `FederatedStepPropertiesProvider`) — leere Liste ohne konfigurierten Hub, keine Auth nötig (wie andere `GET`s).
- **`POST /federation/inbound`**: empfängt eine neue Übergabe. Öffentliche Route (siehe `gateway-service`s `public_routes`) — Authentisierung läuft über `X-Federation-Hub-Signature` (`federation_crypto.verify_body` gegen den beim eigenen Registrieren abgerufenen öffentlichen Hub-Schlüssel), nicht über `X-DMS-Principal`. Löst `targetProcessType` über `Settings.federation_process_type_map` (JSON, `{"<targetProcessType>": "<lokaler process_definition-Name>"}`) auf die **neueste Version** der zugeordneten lokalen Prozessdefinition auf, entschlüsselt den Payload mit dem eigenen privaten Schlüssel und startet eine neue Instanz (`created_by="federation-hub"`). Publiziert zusätzlich `workflow.federation.inbound_received` (siehe Events).
- **`POST /federation/inbound-result`**: empfängt die Rückmeldung eines selbst initiierten Handover, entschlüsselt das Ergebnis und schließt den wartenden `federated`-Task programmatisch ab (`completed_by="federation-hub"`).
- **`FederationIdentity`/`FederationTask`** (neue Tabellen, additiv über `create_all`, keine Alter-Migration nötig): `FederationIdentity` hält das eigene Schlüsselpaar/den Hub-API-Key/den gecachten öffentlichen Hub-Schlüssel. `FederationTask` verknüpft einen lokalen Task/eine Instanz mit einem `handover_id` beim Hub (`direction="outbound"|"inbound"`) — verhindert doppeltes Dispatchen und hält bei einer eingehenden Übergabe fest, an welche `origin_installation_id` ein späterer `federated_return`-Task sein Ergebnis zurückschickt. Eindeutigkeit gilt für `(handover_id, direction)`, nicht `handover_id` allein — beim Selbst-Loopback-Smoke-Test (eine Installation übergibt an sich selbst) landen sonst zwei Zeilen mit demselben `handover_id` in derselben Datenbank (siehe "Erst beim Live-Smoke-Test gefundene Bugs" unten).
- **`handover_id` wird von der Absenderinstallation selbst erzeugt** (`uuid.uuid4()`), nicht vom Hub — ihre eigene `FederationTask`-Zeile wird **vor** dem Hub-Aufruf committet, damit ein verschachtelter Rückruf des Hub bis in dieselbe Installation (Selbst-Loopback) die Zeile bereits sieht (Postgres-Transaktionsisolation). Siehe `docs/services/federation-hub-service.md` für die vollständige Fehleranalyse.
- **Benachrichtigung** (Roadmap-Notiz "Benachrichtigung der Zielinstallation"): `workflow.federation.inbound_received` trägt ein optionales `notify_email`-Feld (aus der Payload der Absenderseite, gleiches Muster wie `escalation_email` beim SLA-Timer) — `notification-service` verschickt bei vorhandenem Wert eine E-Mail, siehe `docs/services/notification-service.md`.
- Kein eigener Palette-Eintrag im Process Designer nötig (wie beim Signature Task) — eine neue Properties-Panel-Gruppe "Föderation" auf Manual Tasks, sichtbar nur wenn der Hub mindestens eine Installation kennt (siehe `docs/services/process-designer.md`).

## Connector-Service-Tasks (7.1 "Auslösen eines Connector-Aufrufs", seit P12-S2)

Anders als Signature Task/Federation (beides Sonderformen des **Manual** Task, da ein Mensch oder ein externer Vermittlungsdienst über den Abschluss entscheidet) ist ein Connector-Service-Task ein echter `bpmn:serviceTask` — läuft **automatisch** wie ein Script Task, ohne auf irgendetwas zu warten. Erster Nutzer ist `migration-service` (7.2), das Muster ist aber bewusst generisch — `workflow-service` kennt `migration-service` nicht.

- **`taskType=connector_call`/`serviceUrl=...`** (`camunda:properties` auf einem `bpmn:serviceTask`): `spiff_adapter.py`s `ConnectorServiceTask`-Spec-Klasse (per `OVERRIDE_PARSER_CLASSES` registriert, SpiffWorkflows eigener dokumentierter Erweiterungspunkt) ruft bei `_execute()` einen modul-weiten, per `register_connector_task_handler()` injizierbaren Callback auf. `main.py` registriert dafür einen Handler, der synchron `httpx.post(serviceUrl, json=dict(task.data))` ausführt (SpiffWorkflow/`do_engine_steps()` ist durchgehend synchron, kein neuer async/sync-Bruch) und die JSON-Antwort in die Prozessdaten zurückmerged. Ein `serviceTask` **ohne** `taskType=connector_call` bleibt unverändert ein echtes No-Op (Rückwärtskompatibilität).
- **`{platzhalter}`-Substitution in `serviceUrl`** (`str.format(**data)` mit den aktuellen Prozessdaten) — erlaubt z. B. eine pro Instanz unterschiedliche `transfer_id` in der URL, ohne die BPMN-Datei pro Instanz individuell erzeugen zu müssen.
- **Real gefundene SpiffWorkflow-Eigenheiten** (nicht offensichtlich aus der Doku): (1) `ServiceTask` ist in keiner Default-Serializer-Konfiguration registriert — `ConnectorServiceTask` muss explizit auf `BpmnTaskSpecConverter` gemappt werden, sonst schlägt die Serialisierung mit "not JSON serializable" fehl. (2) `_execute()` muss `True` zurückgeben, um den Task tatsächlich abzuschließen — ein falsy Rückgabewert (SpiffWorkflows eigener `ServiceTask`-Default) lässt ihn dauerhaft in `STARTED` hängen. (3) Nur `CamundaTaskParser` (nicht die Basis-`TaskParser`) liest `camunda:properties` überhaupt in `task_spec.extensions` ein.

### Resumability: `POST /instances/{id}/retry`

Ein fehlgeschlagener `connector_call` (z. B. Ziel nicht erreichbar) versetzt SpiffWorkflow den Task nach `ERROR` — ein einfaches erneutes `do_engine_steps()` reicht nicht (nur `READY`-Tasks werden verarbeitet). `spiff_adapter.retry_errored_tasks()` nutzt SpiffWorkflows offizielle `reset_branch()`-API, um `ERROR`-Tasks zurück auf `READY`/`FUTURE` zu versetzen (Task-Daten bleiben erhalten), danach lässt `POST /instances/{id}/retry` `do_engine_steps()` erneut laufen.

`start_instance`/`complete_task`/`retry_instance` in `repository.py` persistieren den `workflow_state`-Blob dafür jeweils in einem `try`/`finally` statt erst nach erfolgreichem Abschluss — ohne das gäbe es bei einem Fehlschlag des allerersten automatischen Schritts gar keine Instanz-Zeile mit dem richtigen Zwischenstand zum Fortsetzen (real gefunden). `main.py`s drei betroffene Endpunkte committen aus demselben Grund auch im `except`-Zweig, bevor die Exception weitergereicht wird — sonst würde `get_session()`s Context-Manager den bereits geflushten Zwischenstand beim Schließen der Session zurückrollen.

### Caller-bestimmte Instanz-ID

`ProcessInstanceCreate.instance_id` (optional) lässt den Aufrufer seine eigene Referenz für eine neue Instanz bestimmen, statt eine serverseitig generierte entgegenzunehmen — gleiches Muster wie `federation-hub-service`s `handover_id` (ADR 0028). Wichtig für einen Aufrufer wie `migration-service`, der die ID bereits **vor** dem Start persistieren will: schlägt bereits der erste automatische Schritt fehl, wäre die (dennoch angelegte) Instanz sonst nicht wiederauffindbar für einen späteren `/retry`-Aufruf.

FOR UPDATE`) — ein echter Parallel-Konflikt zweier gleichzeitiger Speicherversuche unter demselben Namen scheitert unbehandelt an der `(name, version)`-Unique-Constraint (`500`), dieselbe bewusste Vereinfachung wie bei document-services Versionsnummern-Vergabe.~~ — **behoben in P25-S1** ([ADR 0096](../adr/0096-workflow-definition-version-race-advisory-lock.md), siehe "Versionierung" oben): ein transaktionsgebundener Postgres-Advisory-Lock auf `name` serialisiert gleichzeitige Speicherversuche derselben Familie, statt einer `SELECT ... - **DMN (P14-S4)**: `DELETE /dmn-definitions/{id}` prüft nicht, ob eine BPMN-Prozessdefinition sie noch per `camunda:decisionRef` referenziert (siehe "DMN-1.3-Entscheidungstabellen" oben) — eine solche Prozessdefinition schlägt beim nächsten Instanzstart mit `422` fehl, statt die Löschung selbst zu blockieren. Jeder BPMN-Parse lädt immer ALLE neuesten DMN-Definitionen (keine statische Analyse, welche `decisionRef`s eine konkrete Datei tatsächlich braucht) — bei sehr vielen DMN-Familien mit entsprechend mehr Parse-Zeit zu revisitieren, für eine Referenzimplementierung unkritisch. Auswertung ist SpiffWorkflows eigene vereinfachte Ausdrucks-Semantik, keine vollständige OMG-FEEL-Implementierung (z. B. keine FEEL-eigenen Datums-/Listenfunktionen über das hinaus, was der zugrundeliegende Python-Ausdruck ohnehin bietet).

Nur eine globale Zeitzone (UTC) für die Wochentagsberechnung, keine installationsspezifische Zeitzone. Keine vorgefertigten Kalender-Vorlagen (z. B. deutsche Feiertage) — bewusst Phase 17 (Konfigurationspakete) vorbehalten.

Ein regulärer, nicht-delegierter Abschluss bleibt weiterhin vollständig ungegatet — die Delegationsprüfung greift ausschließlich, wenn `on_behalf_of_principal_id` explizit gesetzt ist.
