# document-service

**Purpose:** Documents as the core entity (Concept 2.1) — CRUD, permanent versioning (2.1a, no overwriting/discarding), an editing lock for external editing including force-unlock and conflict copy (4.2). Never holds file content itself — every byte access goes through the Storage Service's HTTP API (3.6).

**Concept reference:** 2.1/2.1a/4.2/3.1/3.6/5.2/5.2a (retention/legal hold/forced deletion, since P7-S1)/5.4b (audit depth for forensic trace, since P7-S2c)/5.6 (records disposal lifecycle fields, since P7-S3)/4.2a (public share link, since P14-S10)
**Own Postgres schema:** `document` (tables `document`, `document_version`, `document_lock`, `upload_config`, `legal_hold`, `deletion_register_entry`, `retention_config`, `trash_config`, `audit_trace_config`, `audit_trace_role_override`, `share_link_config`, `share_link`)

## Data Model

- `document`: `id`, `title`, `folder_id`/`object_type_id` (opaque references, see below), `attributes` (JSON, custom fields per object type), `current_version_number` (pointer to the main version), `deleted_at`, `created_by/at/updated_at`, `derived_from_document_id`/`derived_from_version_number`/`originating_case_id` (since P6-S3, editing copies, see below), `retention_until`/`full_deletion`/`pending_deletion_reason`/`deletion_reminder_sent_at`/`reminder_notify_email`/`force_delete_approval_requested_at` (5.2/5.2a, since P7-S1, see below), `deleted_via_folder_id` (5.2, since P7-S1b) — set when this document was deleted not individually but through a cascade via `POST /documents/cascade-trash` (because its folder was moved to the trash); `POST /documents/cascade-restore` uses this to specifically restore only the documents deleted through that cascade, not any independently, individually deleted one. `archive_after`/`archived_at`/`archive_format`/`dehydrated_at` (5.6, since P7-S3, see below).
- `document_version`: `document_id`, `version_number`, `storage_object_key`, `filename`, `content_type`, `size_bytes`, `checksum_sha256`, `is_conflict`, `based_on_version_number`, `comment`, `created_by/at`. Every row remains retrievable forever (2.1a). `storage_object_key` has since P7-S3 also been exposed externally via `GET .../versions/{n}` (`DocumentVersionOut`) — `archival-service` needs the exact live key for dehydration/retrieval.
- `document_lock`: exactly one active row per locked document (`document_id` as PK) — `locked_by`, `session_id`, `based_on_version_number`, `locked_at`, `expires_at`.
- `upload_config`: single row (`id=1`, since P5d-S1) — `allowed_content_types` (JSON list, empty = no restriction), `updated_at`.
- `legal_hold` (5.2, since P7-S1): `id` (UUID PK), `document_id` (FK to `document.id`), `reason` (nullable), `set_by`, `set_at`, `released_by` (nullable), `released_at` (nullable) — active as long as `released_at IS NULL`.
- `deletion_register_entry` (5.2a, since P7-S1): `id` (UUID PK), `document_id` (**deliberately no FK** — the referenced `document` row has already been physically removed by the time of the entry), `trigger` (`"forced_deletion"`\|`"trash_expiry"`), `reason` (nullable), `triggered_by` (nullable), `occurred_at`.
- `retention_config` (5.2/5.2a, since P7-S1): single row (`id=1`, same pattern as `UploadConfig`) — `deletion_reason_required` (boolean), `reminder_lead_days` (integer, nullable).
- `trash_config` (5.2, since P7-S1): single row (`id=1`) — `restore_period_days` (integer, default 30).

`folder_id`/`object_type_id` are opaque references without FK enforcement across service boundaries, but have been actively validated since P3-S3: `folder_id` (if set) must exist at the Folder Service (otherwise 400), `object_type_id` (if set) validates `attributes`+`title` against the Object-Type Service (otherwise 400 with an error list). Since P4-S4 the same validation also applies to `PATCH /documents/{id}`; `object_type_id` itself remains immutable in that case (retyping is a separate operation with different consistency concerns). **`folder_id` is the exception since P12-S1**: `DocumentUpdate.folder_id` (optional) moves the document to a different folder if set and different from the current `folder_id` — a target-existence check like on creation (400 for an unknown target folder), with the object-hierarchy validation (see below) redone against the *new* parent folder. Reason: WebDAV MOVE (`webdav-connector`, see `docs/services/webdav-connector.md`) requires a move operation for documents — `folder-service`'s `PATCH /folders/{id}` has supported `parent_id` changes since P3-S3, this counterpart for documents was completely missing until then.

**Enforced object hierarchy (2.2a, since P5b-S1, ADR 0013)**: The target folder's existence check (`FolderClient.get()`, replacing the earlier plain `exists()`) now returns the full folder body including its `object_type_id` — this, together with `parent_is_root` (`true` if `folder_id` is missing or `"root"`), is passed to `POST /object-types/{id}/validate` so that an `allowedParentTypes` of the document's object type can be enforced. Always relevant on creation (`POST /documents`); for `PATCH /documents/{id}` only if `folder_id` actually triggers a move (see above) — a pure metadata update without a `folder_id` change does not re-validate the hierarchy.

**Ad hoc schema migration**: `attributes` was only added to the existing `document` table in P3-S3. Without Alembic (see `CONTRIBUTING.md`), an `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` in the lifespan startup routine applies this additive, defaulted change idempotently — this only works for exactly this kind of change (a new, nullable/defaulted column), not for renames/type changes/column removal. Once schema changes become more complex, real Alembic tooling will be needed (see "Open Decisions" in `PROGRESS.md`).

## Reference Number Generator (2.2/4.4, since P5e-S2)

Builds on the Object-Type Service (see `docs/services/object-type-service.md` "Reference Number Generator") — this service itself knows no format, but queries `POST /object-types/{id}/next-kennzeichen` (`ObjectTypeClient.next_kennzeichen()`, `404` = no generator configured, in which case `attributes["Kennzeichen"]` simply remains unset) on every document creation with `object_type_id` set. **Since P17-S2** (14.2) this call additionally passes the already-parsed creation attributes (`parsed_attributes`) in the request body — the basis for attribute-based reference-number placeholders such as `{Federführung}` on the object type (see object-type-service.md). If a referenced attribute value is missing (attribute not marked as required), object-type-service returns `422`, which this service passes through as its own `422` to the caller (`MissingKennzeichenAttributeError` in `object_type_client.py`).

- **`Kennzeichen` is a reserved attribute key**: on `POST /documents`, a value sent by the client for this key is always discarded (regardless of whether a generator is configured) — the actual assignment happens exclusively server-side after successful object-type validation.
- **First real role check in the entire system**: `PATCH /documents/{id}` detects a change to `attributes["Kennzeichen"]` by comparing old (`document.attributes`) against new (`payload.attributes`, a full replacement rather than a merge, see below) — if they differ (even omitting the key without comment in an otherwise complete attribute replace counts as a change, since it effectively sets the value to `null`), the gateway-injected `X-DMS-Roles` header (comma-separated) must contain the role from `Settings.kennzeichen_admin_role` (default `"dms-admin"`), otherwise `403`. Until now, **no** service anywhere in the system evaluated this header (see `PROGRESS.md` "Authorization") — the role is created idempotently in the realm by the Auth Service (`ensure_realm_and_client`), assignment to specific users currently happens outside the system, via the Keycloak Admin Console (no own role-management API/UI, see `docs/services/auth-service.md` "Open Points").
- **No format validity check on privileged manual changes**: a `dms-admin` principal can set an arbitrary string, even one that does not match the configured `kennzeichen_format` — deliberately unrestricted, matching the pure role check from the plan (see `PROGRESS.md`).
- **Where `Kennzeichen` is displayed** (before the filename, globally or with per-object-type override) is still open — follows with **P5e-S3**.

## Editing Copies (2.3, since P6-S3)

A process-specific editing copy (classic example: a redaction for file inspection) is, per the concept, **not a new version of the original document**, but a standalone, separately stored document referencing the original document (including a specific source version) and the triggering process/case — and is meant to be "fully audited and versioned just like any other document action".

This session deliberately introduced **no new route** for this, but instead extended `POST /documents` with three optional, nullable form fields: `derived_from_document_id` (references `document.id`, a real FK within the same schema), `derived_from_version_number` (required as soon as `derived_from_document_id` is set — `400` if missing or if the referenced version does not exist per `repository.get_version()`), `originating_case_id` (an opaque reference to a case in the new `case-service`, no existence check — analogous to `folder_id`/`object_type_id`). An editing copy created this way is then a **completely standalone document**: its own `id`, its own version history, running through the same virus-scan/storage-upload/reference-number mechanism as any other document — the three fields are purely provenance metadata with no special handling anywhere else in the service.

`case-service` (P6-S3) is the intended caller (redacting a document referenced in a case), but does not itself call this endpoint yet — creating an editing copy is a manual/process-driven action outside this session's scope; the data model/API extension is the necessary foundation for it.

## Content Storage (3.6 Integration)

Object keys are **content-addressed**: `documents/{document_id}/{sha256}`. This avoids the chicken-and-egg ordering issue of "the upload needs a version number that has not yet been assigned" and automatically deduplicates identical content within the same document (e.g. repeatedly uploading the same file). For this, Document Service talks exclusively to the Storage Service's `PUT`/`GET /objects/{key}` over HTTP — no access to its internals or direct backend usage.

## Content-Type Detection & Format Whitelist (3.1/3.6, since P5d-S1)

The `content_type` stored on every upload is **determined server-side from the
actual magic bytes** (`content_type_sniffer.py`, `python-magic`/
`libmagic`) - no longer taken from the unchecked, browser-sent
`file.content_type` header. Fixes the issue that, e.g., `.txt`/`.json` arrive
with a generic or simply wrong content type depending on the browser/operating
system (user feedback after Phase 5c, see `PROGRESS.md`).
Sniffing runs before the virus scan (no unnecessary scan call for an
already-rejected format) and applies to creation *and* check-in alike.

An admin-editable whitelist (`UploadConfig`, same
single-row pattern as `OcrConfig`/`GuardConfig` of the other services)
allows checking the detected content type against a fixed list - an
unlisted format is rejected with `400` before content/metadata
are written. Empty list (default) = no restriction, identical
behavior to before P5d-S1.

## HTML Preview Hardening (Post-Roadmap Phase 21 Session 3, [ADR 0086](../adr/0086-html-preview-external-subresource-blocking.md))

`user-ui`'s `PreviewPane` renders HTML documents via a `sandbox=""` iframe with `srcDoc` (no `src` pointing to its own origin) - `sandbox=""` blocks script execution/top navigation/forms, but NOT the normal loading of subresources (images, stylesheets, ...), and a CSP header has only limited effect on `srcDoc` content without its own origin. Instead of a CSP header, `document-service` therefore neutralizes external references **server-side, at the source**: `download_current_content`/`download_version_content` check `content_type == "text/html"` (sniffing-based, see above - not the unchecked client header) and, on a match, call `html_preview_guard.rewrite_external_references` before the content is delivered.

The function parses with `BeautifulSoup`/`html.parser` (a new dependency, no existing HTML parsing tool in the project so far - `lxml` exists only for XML/BPMN in other services) and removes any `src`/`href` reference that is not `data:`/`mailto:`/`tel:` or a pure fragment anchor (`#...`) - attribute-driven, not a hardcoded tag set (automatically covers `img`/`script`/`iframe`/`link`/`a`/`audio`/`video`/`source`/`track`/`embed`/`frame` and unusual tags alike). Relative paths are also blocked, since a `srcDoc` document has no safe, resolvable base URL. Directly after each removed reference, a visible marker is inserted (`[Blocked external request: <original-URL>]`) - the visibility in the rendered document required by the plan, instead of a silent removal. An existing `<meta charset>` is normalized to `utf-8` (the function always returns UTF-8 bytes, regardless of the originally declared encoding).

**Deliberately NOT covered** (the plan explicitly names only `src`/`href`): `srcset` (responsive images), `poster` (video thumbnail), `background` (deprecated `<body background>`), as well as `url(...)` within `style` attributes/`<style>` blocks (CSS background images/fonts). A future session could close this if a real leak shows up through it.

## Virus Scan Before Release (10.3, since P5-S1)

Every upload (creation *and* check-in) is checked **synchronously and before any write** against the Virus Scan Service (`VirusScanClient.scan(...)`) — not asynchronously via an event, see [ADR 0010](../adr/0010-virus-scan-synchronous-gating.md) for the reasoning. If the scan comes back positive, the request is rejected with `422` (`{"error": "virus_detected", "threat_name": ...}`) before content lands in the Storage Service or metadata in the service's own DB. If the Virus Scan Service is unreachable, the upload is likewise rejected (`503`, fail-closed instead of silently letting it through). For details on the engine (swappable, the default only detects the EICAR test signature) see `docs/services/virus-scan-service.md`.

## Editing Lock & Conflict Handling (4.2)

- A lock is bound to `locked_by` + `session_id` and automatically expires after a configurable timeout (`default_lock_timeout_seconds`, no background check needed — expiry is evaluated on the next access, analogous to the registry-service pattern).
- **Force-unlock deletes the lock entirely** rather than moving it into a third "supervised" state (a deviation from the literal concept description, see **ADR 0002** for the reasoning). Protection against silent data loss instead comes from an **always-active optimistic conflict detection** at check-in:
  - Every check-in specifies `expected_base_version_number`.
  - If this value matches the current main version → regular check-in, new main version.
  - If it differs (e.g. because someone else has checked in in the meantime after a force-unlock) → **conflict copy**: a standalone, still-retrievable version (`is_conflict=true`, filename `<name>_conflict_<user>_<timestamp>`), the main-version pointer does not move.
- One's own check-in always ends one's own lock (even in the conflict case — the source basis was outdated anyway).
- **Two sibling services automatically check in new versions when their processing actually changes the bytes** (ADR 0025 pattern): `signature-service` after signing a PDF, and, since a round of OCR user feedback, additionally `ocr-service` after embedding an invisible text layer into a previously text-layer-less scan (`created_by="system:ocr-service"`, see `docs/services/ocr-service.md` "Searchable PDF"). Both use exactly the same `expected_base_version_number` mechanism as any other check-in — no special path, no own conflict handling needed.
- **Four-eyes principle (4.3) for force-unlock optionally wired in since P6-S4**: `POST /documents/{id}/lock/force-release` first queries `GET /approval-config/document.force_unlock` at the Permission Service (`approval_client.py`). If approval is enabled, the lock is **not** released immediately, but an approval request is created (response `{status: "pending_approval", approval_request_id}`, lock remains in place) — actual execution happens only via the new `consumer.py` (this service's first NATS consumer at all) once `permission.approval.approved` arrives. Without configuration (default), behavior is unchanged: immediate execution, response `{status: "released", lock}`. For details/the architecture decision see [ADR 0022](../adr/0022-four-eyes-approval-via-events.md) and `docs/services/permission-service.md` "Four-Eyes Approval Mechanism".

## Retention & Legal Hold (5.2, since P7-S1)

A shared pair of fields covers both the regular retention period (5.2) and forced deletion (5.2a): `Document.retention_until` (date) + `full_deletion` (boolean). When `retention_until` is reached without an active legal hold, `full_deletion` decides: `false` → regular trash (existing `deleted_at` logic), `true` → direct physical deletion (see "Forced Deletion & Deletion Register" below).

- **No new BPMN/timer service**: `workflow-service` has no generic "callback after N days" mechanism, only real process instances with timer/boundary events. Instead, this service gets its own `_retention_poll_loop` (`Settings.retention_poll_interval_seconds`, default 3600s) — exactly the same idiom as `workflow-service`'s `_sla_poll_loop` ([ADR 0020](../adr/0020-sla-timer-polling.md)). A BPMN integration remains a later, optional extension; the concept itself explicitly allows direct, process-independent configuration on the object/object type.
- **Default period per object type**: `default_retention_days` on `ObjectType` (see `docs/services/object-type-service.md`) is resolved **once** into a concrete `created_at + default_retention_days` date when a document is created — not looked up repeatedly if the type default later changes. A `retention_until` manually set at creation/via `PUT .../retention` takes precedence.
- **Legal hold overrides any due action** (neither trash nor physical deletion nor a deletion reminder), while it is active (`legal_hold.released_at IS NULL`) — a literal implementation of 5.2. Multiple holds per document are possible; each must be released individually for the document to become "free" again.
- **Deletion reminder** (optional, `RetentionConfig.reminder_lead_days`): no own timer, but a third branch of the same poll loop — detects "within the lead time, reminder not yet sent" (`Document.deletion_reminder_sent_at`) and publishes `document.deletion.reminder` (consumed by `notification-service`, see there).
- **Trash with a restoration period**: `TrashConfig.restore_period_days` (default 30) determines how long `POST /documents/{id}/restore` remains possible after the soft delete (`409` afterward) — expired entries are physically cleaned up by the same poll loop (`trigger="trash_expiry"` in the deletion register, see below), **without** an automatic governance bypass (see there).

## Forced Deletion & Deletion Register (5.2a, since P7-S1)

Complementary to the regular retention period: the reverse scenario, where a document must be **mandatorily physically** deleted after expiry (`full_deletion=true`), including an optional deletion reason and a separate deletion register independent of the deleted object.

- **Deletion reason only transient on the document**: `Document.pending_deletion_reason` is held only between scheduling and actual execution (days/weeks apart is possible). At the actual physical deletion, the reason moves into the persistent `deletion_register_entry` row **and** into a `document.force_deleted` event (audit trail) — the `Document` row itself is completely removed. So the reason "survives" the object only in the register + audit trail, never as a property of a still-existing object.
- **Required/optional configurable**: `RetentionConfig.deletion_reason_required` (installation-wide default) + `ObjectType.deletion_reason_required_override` (tri-state, overrides the global default for individual document classes) — `PUT /documents/{id}/retention` rejects a missing reason with `422` if it is required per resolution.
- **Four-eyes principle (4.3, optional)**: reuses the existing force-unlock precedent 1:1 (`approval_client.py`, `consumer.py`) via the new action type `document.force_delete` — no change to `permission-service` needed other than the configuration row (`PUT /approval-config/document.force_delete`). If approval is enabled, the poll loop creates an approval request instead of immediate execution (`Document.force_delete_approval_requested_at` prevents duplicate requests on every further pass); the actual deletion happens only via a new consumer handler once `permission.approval.approved` arrives with `action_type == "document.force_delete"`.
- **Physical deletion** (`retention_actions.execute_forced_deletion`): deletes every `document_version` via `storage-service` with `bypass_governance=True` — the sanctioned exception to the object-lock protection from 5.1 (see `docs/services/storage-service.md` "Object Lock/WORM", [ADR 0030](../adr/0030-storage-object-lock-governance-mode.md)) —, writes the `deletion_register_entry`, removes the `Document`+`DocumentVersion` rows and publishes `document.force_deleted`. Trash expiry (`trigger="trash_expiry"`), by contrast, runs **without** an automatic bypass (`retention_actions.purge_expired_trash_entry`) — if blocked by a governance lock, the entry remains in place for a later pass, no silent data loss from an unintended bypass.
- **Deletion register not hash-chained** (unlike `audit-service`), **but backup-differentiated since P11-S4**: every row is additionally published as a regular event, which is written both into `audit-service`'s hash-chained ledger **and** into its separate deletion-register ledger, independent of the DB restore cycle (see `docs/services/audit-service.md`, `docs/operations/backup-restore.md`). A deliberately own, immediately queryable `GET /deletion-register` API in this service, instead of a dependency on an `audit-service` filter API.
- **Deletion reconciliation after restore (10.4, P11-S4)**: `POST /documents/{id}/reconcile-restore-deletion` (gate: `X-DMS-Roles` contains `dms-admin`) re-runs `execute_forced_deletion` — for the case where a restore unintentionally brought back an already forcibly deleted document. Referenced by `scripts/restore.sh`'s detection step, but not automatically invoked from there (see `docs/operations/backup-restore.md`).
- **Legal hold role check**: gated by `admin.legal_hold` since Post-Roadmap Phase 19 Session 10 ([ADR 0075](../adr/0075-legal-hold-rbac.md)), see "Open Points".

## Deletion-Request Workflow for Regular Users (5.2, since P7-S1c)

A third, independent retention scenario alongside the regular period and forced deletion: normal users should only be able to **request** a regular trash deletion, not execute it directly — including the requirement that even a privileged person may not delete alone.

- **Own action type `document.delete`**, separate from `document.force_delete` — the latter remains for the retention-triggered, poll-loop-driven forced deletion, `document.delete` instead gates the manual, user-triggered `POST /documents/{id}/trash`. Both independently configurable via `PUT /approval-config/{action_type}`.
- **Gate check directly in the endpoint**, exact same pattern as `force_release_lock` (4.2, P6-S4): `TrashResult{status: "trashed"|"pending_approval", document, approval_request_id}`. Enforced server-side, regardless of which UI path triggered the call.
- **No new self-approval logic needed** — `permission-service` already generically prevents the initiator and approver from being identical (`NotInitiatorAllowedError`). Satisfies "even a deletion admin may not delete alone" without any new role concept.
- **Consumer handler** (`consumer.py`, `_handle_delete_approved`) executes the previously deferred `repository.delete_document` after `permission.approval.approved` with `action_type == "document.delete"` — copy-paste pattern of the existing `document.force_unlock` branch.
- **Approval inbox**: a new, minimal `ApprovalsPane` in the user UI (not the admin UI, since regular users approve each other here) — see `docs/services/user-ui.md`. Deliberately filtered to only `document.delete`/`folder.delete`, no generic all-action-types inbox.

## Trash Family: Personal & Classified-Documents Trash (2.5, since P15-S1)

Full implementation of Concept §2.5's special trash areas (regular/personal/classified-documents trash), built on the already-existing retention/trash infrastructure above. See [ADR 0051](../adr/0051-papierkorb-familie-classification-via-object-type-scoped-global-endpoints.md) for the full architecture reasoning.

- **`deleted_by` column retrofitted**: `repository.delete_document`/`cascade_trash_by_folder_ids` already accepted `deleted_by` as a parameter, but never persisted it (a real gap found in P15-S0) — now a real `Document.deleted_by` column, a prerequisite for the personal trash. Reset to `None` again on `restore_document`/`cascade_restore_by_via_folder_id`.
- **New `scope` query parameter on `GET /documents/deleted`** (`personal`/`admin`/`admin_classified`) — purely additive, without `scope` the previous, folder-scoped, ungated behavior is unchanged (existing callers/tests unaffected). With `scope=personal`, every authenticated caller sees only `deleted_by == X-DMS-Principal` (401 without a principal header). With `scope=admin`/`scope=admin_classified`, the respective role (`trash_hard_delete_admin_role`/`classified_trash_hard_delete_admin_role`, settings, default both `"dms-admin"`) is checked (403 otherwise) — the set of classified documents is resolved once per call via `object_type_client.list_classified_document_type_ids()` (`ObjectTypeClient` method, calls `GET /object-types?applies_to=document&is_classified=true` on `object-type-service` — parameter name unchanged, since P17-S2 internally translated to `classification_level IS NOT NULL`), no N+1 query per document.
- **New `POST /documents/{id}/purge`**: manual, immediate permanent deletion of a document already in the trash (409 otherwise), independent of the automatic `_retention_poll_loop`. Calls the same `retention_actions.purge_expired_trash_entry()` as the poll loop, now extended with optional `trigger`/`triggered_by` parameters (`trigger="manual_purge"` instead of `"trash_expiry"`, `triggered_by` = the real `X-DMS-Principal`) — no second deletion implementation. Role check identical to the `scope` resolution above (classified vs. regular, depending on the affected document's `ObjectType.classification_level` — any set level counts).
- **`DeletionRegisterEntry.trigger`** extended with the value `"manual_purge"` (Pydantic `Literal` + model comment updated).
- **Schema drift found live and fixed**: `object_type_id` still carried `VARCHAR(128)` in this long-lived dev stack (a leftover from an early project phase, `create_all` never changes the type of existing columns) instead of the `Integer` long since declared in the model — unnoticed for equality comparisons, but the new `NOT IN` filter for the classified-documents trash exposed it live (`operator does not exist: character varying <> integer`). A new, guarded migration check in the lifespan (`information_schema.columns` check before `ALTER COLUMN ... TYPE INTEGER`) automatically corrects this on every affected restart, see [ADR 0051](../adr/0051-papierkorb-familie-classification-via-object-type-scoped-global-endpoints.md) "Live Verification Finding".

## Quarantine Area: Internal Creation Path Without Rescanning (2.5/10.3, since P15-S2)

`virus-scan-service`'s release endpoint (`POST /scans/{id}/release`) creates a real document from quarantined bytes on a resolved false positive, bytes that never went through `POST /documents`. Since this endpoint unconditionally scans every creation (10.3, ADR 0010), a repeated call would only reproduce the same (now classified as false positive) finding — especially with the default `eicar` engine, which always detects an EICAR signature as infected, regardless of context. See [ADR 0052](../adr/0052-quarantaene-bereich-internal-creation-endpoint-bypasses-rescan.md) for the full reasoning.

- **`POST /documents/from-quarantine-release`**: a new creation path intended exclusively for `virus-scan-service`. Refactoring: `_prepare_document_fields`/`_persist_new_document` combine the validation/creation logic shared between both endpoints (derivation check, folder/object-type validation, reference number assignment, retention defaults, storage upload, `repository.create_document`, event publication) — only the `virus_scan_client.scan()` call remains exclusive to `POST /documents`.
- **Second, independent role gate**: the `quarantine_release_admin_role` setting (default `dms-admin`) checks `X-DMS-Principal`/`X-DMS-Roles`, forwarded by `virus-scan-service` from the original caller — in addition to the `quarantine_admin_role` already checked there. No internal service auth in this project (see ADR 0052), hence two independent checks instead of one.
- **Own event type `document.created_from_quarantine_release`** (instead of `document.created`) with an additional `source_scan_id` payload field — automatically falls under the already-existing `document.>` wildcard, `audit-service` needed no code change for it.

## Audit Depth for the Forensic Trace (5.4b, since P7-S2c)

The basis for object-related traceability (forensic trace, see `docs/services/reporting-service.md`) includes gapless visibility of read access — until P7-S2c this service published no event at all for this (`GET /documents/{id}` and the content downloads ran completely unaudited). Since this session, this is configurably loggable:

- **Two new event types**: `document.viewed` (only on the single retrieval `GET /documents/{id}`, not on the listing) and `document.downloaded` (both content endpoints) — both fall under the already-existing `document.>` wildcard, `audit-service` needed no code change for it.
- **Base configuration + role overrides**: `AuditTraceConfig` (singleton, `log_viewed`/`log_downloaded`, **default both `true`** — maximum traceability as the factory setting) determines whether logging happens at all. `AuditTraceRoleOverride` (PK `role`, free text with no existence check against `permission-service`/Keycloak — the same existing gap as for every other role name in this system) allows a per-role override per category (`null` = the base applies).
- **Resolution** (`repository.resolve_should_log`, invoked via `main._should_log_document_access`): the caller's roles come from the already gateway-injected `X-DMS-Roles` header (same pattern as `_has_kennzeichen_admin_role` for the reference number generator). **Conflict rule for multiple assigned roles with contradictory overrides**: if any role has an explicit `true` override, logging happens ("log" wins) — only if *all* roles with an override say `false` is nothing logged, otherwise the base applies. Security-first: a role that demands more logging cannot be silently undermined by another role of the same user.
- **The actor** (`actor` in the published event) comes from the gateway-injected `X-DMS-Username` header — if missing (e.g. a direct call not going through the gateway), `actor` stays `null`, but the event is still published (the base default remains authoritative).
- **Configured locally rather than centrally**, deliberately like every other config in this system (`UploadConfig`, `RetentionConfig`, ...) — avoids a synchronous cross-service config lookup on the hot read path (every document click/download).
- **Admin UI**: `/audit-trace-settings/` (`AuditTraceSettings`, see `docs/services/admin-ui.md`).

## Records Disposal & Long-Term Archiving (5.6, since P7-S3)

This service remains the sole authority for the document lifecycle fields (already carrying `retention_until`/`legal_hold`/audit depth), a new `archival-service` handles only the actual transfer mechanics (PDF/A conversion, archive storage, dehydration, retrieval) — the same division of responsibility as `reporting-service` has toward this service.

- **Triggered the same way as `default_retention_days`**: `ObjectType.default_archive_after_days` (see `docs/services/object-type-service.md`) is resolved once into `Document.archive_after` when a document is created. Additionally, a manual trigger: `POST /documents/{id}/archive-request` sets `archive_after=now` if not already set/due — independent of the `retention_until`/`full_deletion` branch (5.2), since records disposal per the concept is explicitly *supplementary* to the regular retention period, not a third branch of the same decision.
- **`archival-service` queries/updates exclusively via the new endpoints** (`GET .../due-for-archival`, `PUT .../archived`, `.../dehydrated`, `.../rehydrated`, `GET .../has-active-hold`) — no direct DB access, same principle as every other service boundary in this system (3.1).
- **"Dehydrating" instead of physical deletion**: the `Document` row remains fully intact on records disposal (`archived_at`/`archive_format`/`dehydrated_at` set, metadata still discoverable via `GET /documents/{id}`, a literal concept requirement) — only the content on the live storage targets is removed by `archival-service` after a configurable transition period. **Since Post-Roadmap Phase 19 Session 11** ([ADR 0076](../adr/0076-root-folder-mail-regex-dehydration-409.md)), `GET /documents/{id}/content` and `.../versions/{n}/content` check `document.dehydrated_at` BEFORE the storage call and return `409` with a retrieval hint instead of a generic `404` that could be mistaken for a real data inconsistency.
- **Legal hold blocks only dehydration, not archiving itself**: `GET /documents/{id}/has-active-hold` (new, reuses the existing `repository.has_active_hold` logic from 5.2) is queried by `archival-service` before every dehydration step — an additional, safe archive copy does no harm, but removing the live copy does.
- **Three new events** (see below) are published by this service, not by `archival-service` itself — consistent with the rule that only the domain owner (`document` stream) publishes `document.*` events.

## License-Limit Block on New Creations (Concept 9.3, since P9-S2)

`POST /documents` checks, as its first action (before any attribute/constraint validation) via a new, thin `license_client.py` (`LicenseLimitClient`, 30s TTL cache, fail-open "not exceeded"), whether `license-service`'s `GET /license/status` reports the `"documents"` dimension in `limits_exceeded` — if so, `403`. Existing documents, new versions (`POST .../versions`), and restoration from the trash remain unaffected ("does not retroactively block existing data, but does prevent new creations", Concept 9.3 verbatim). Direct call to `license-service`, not via registry mediation — that only concerns component license status (`licensed`/`demo`/`unlicensed`), not usage limits.

## Sensors (Concept 10.1, P11-S1)

`document-service` is one of the two sensor pilots (not a full retrofit, see the P11-S0 finding): registers two sensors on self-registration — `document.upload.duration` (histogram, group `performance`, cost `expensive`, literally the Concept 10.1 example name; measured around `POST /documents`, the timer only starts if the sensor is actually active) and `document.count.active_total` (gauge, group `capacity`, cost `cheap`, uses the same `repository.count_active_total` query as `GET /documents/count-active-total`, sampled periodically). ## Public Share Link (4.2a, since P14-S10)

Time-limited, unauthenticated read access to exactly one document, via a `secrets.token_urlsafe(32)` token (also the primary key of the `share_link` table, no separate ID field). Installation-wide switch (`ShareLinkConfig`, `enabled`/`max_validity_days`) — when disabled, all four affected endpoints return `404` instead of `403` ("no API route reachable", the closest approximation without a restart, see ADR 0047) and already-issued links become invalid immediately as well, not only new creations blocked.

**Creation** (`POST /documents/{id}/share-links`) checks — new for this service — a real check against `permission-service` (`permission_client.PermissionServiceClient.check_read`, `GET /check?...&permission=document.read`), whether the requesting person holds `document.read` on the target folder; the first real read-permission check in `document-service`, which until now only knew the four-eyes-principle approval mechanism. `expires_at` must lie in the future and within `max_validity_days`, otherwise `400`.

**Public access** runs via two endpoints without `X-DMS-Principal` (`GET /public/share-links`/`GET /public/share-links/content`), reachable via `gateway-service`'s `public_routes` exception list (see `docs/services/gateway-service.md`) — the token deliberately travels as a query parameter, not as a path segment (see ADR 0047). `PublicShareLinkOut` returns only the minimum (`title`, `content_type`, `size_bytes`, `expires_at`), no `attributes`/`folder_id`/`created_by`. Expired/revoked (but known) links return `410 Gone` with a distinguishable error message — no information leak, since the requesting person already legitimately holds the token.

**Revocation** (`DELETE /share-links/{token}`) is only permitted for the creating person or `X-DMS-Roles: dms-admin` (configurable, `share_link_revoke_admin_role`), idempotent.

## Office Direct Editing: WebDAV Edit Token (Ad hoc Post-Roadmap, see ADR 0061)

A short-lived (`webdav_edit_token_ttl_hours`, default 8h), document-scoped `WebdavEditToken` — structurally modeled on `ShareLink` (`token` as PK), but additionally with `principal_id` (the identity `webdav-connector` uses as the lock holder at check-in). Issuance (`POST /documents/{id}/webdav-edit-tokens`) requires `document.write` (`check_write`, new in `permission_client.py`), not just `document.read` — an edit token grants write access, not merely read access like a share link. `GET /documents/{id}/webdav-edit-tokens` lists active tokens (basis for a later revocation UI, not yet built). `DELETE /webdav-edit-tokens/{token}` is, like the share link, only permitted for the creating person or an admin role.

`GET /internal/webdav-edit-tokens/{token}` is purely east-west (no gateway, no `X-DMS-Principal`, `webdav-connector` calls `document_service_base_url` directly) and resolves a token to `{document_id, principal_id}`, or returns 404/410 on expiry/revocation/an unknown token. Re-checking permissions during an ongoing editing session deliberately does NOT happen — checked only at issuance, the same limitation category as with the share link.

## PDF Export with Export History & Combined Folder Export (Post-Roadmap Phase 28, [ADR 0107](../adr/0107-pdf-export-two-pass-merge-subnumbering.md)/[ADR 0108](../adr/0108-export-history-as-audit-service-query.md))

"Export" alongside "Download": `POST /documents/{id}/export` returns a PDF of the document's current version plus its export history (queried from `audit-service`'s `document.exported` event log, see ADR 0108 — no dedicated storage of its own) in a configurable order. `GET`/`PUT /export-config` (`ExportConfig`, single-row, `history_position: "before"|"after"`, default `"after"`) sets the installation-wide default; an optional `?history_position=` query param overrides it per call. All PDF conversion/merge/stamping happens in `rendering-service` (`POST /render/export/document`, see docs/services/rendering-service.md) — this service only fetches content + history and orchestrates. Publishes `document.exported` unconditionally (not gated by `AuditTraceConfig`, unlike `document.downloaded` — the export history section IS the feature, not an optional trace).

**Combined folder export** (`POST /folders/{id}/export`) creates an async `FolderExportJob` (`202`, poll `GET /folder-exports/{id}` until `completed`/`failed_permanent`, then `GET /folder-exports/{id}/content`) instead of blocking the request — converting every contained document plus merging can take long for a large folder. Same resilience shape as `ArchivalTransfer` (ADR 0078): `attempts`/`next_retry_at` full-jitter backoff, `failed_permanent` as the real terminal state. `_folder_export_poll_loop`/`_run_folder_export_tick` (`main.py`) process due jobs; `list_documents_for_folder_export` (`repository.py`) orders contained documents by `Kennzeichen` (reference number, falling back to title) for a meaningful table of contents — `list_documents_by_folder`'s plain alphabetical-by-title order isn't. Combined-export bytes are stored via the existing `StorageClient.upload()` (key `folder-exports/{job_id}.pdf`), same as any other generated artifact.

`_build_document_export_pdf`/`_run_folder_export_tick` take their `storage`/`rendering_client`/`audit_client` as explicit parameters rather than reading `app.state` (unlike most poll loops in this service) — discovered during testing that httpx clients constructed on one event loop can't be reused from another; matches archival-service's `pipeline.run_active_transfers_tick`'s existing dependency-injection shape.

New settings: `rendering_service_base_url` (default `http://localhost:8011`), `audit_service_base_url` (default `http://localhost:8002`), `max_folder_export_attempts` (5, same as `archival-service`'s `max_archival_attempts`), `folder_export_poll_interval_seconds` (30.0). **Both new base URLs must be set via `DMS_RENDERING_SERVICE_BASE_URL`/`DMS_AUDIT_SERVICE_BASE_URL` in `docker-compose.yml`** — the `Settings` defaults only work outside Docker; a real, live bug (502 with no matching rendering-service log entry at all) was found and fixed during this session's own live verification when this wiring was initially missed.

## Open Points

- **Reference number display in the frontend** (before the filename, globally or overridable per object type) not yet wired up — follows with P5e-S3.
- **`document.viewed`/`document.downloaded` cover only documents** (5.4b, since P7-S2c) — folder read access (`folder-service`) remains unaudited, was not part of the concept text ("read ... documents"). Likewise no existence check of role names in `AuditTraceRoleOverride` against `permission-service`/Keycloak — the same existing gap as for every other role name in the system.
- **No role assignment API/UI**: `dms-admin` currently must be assigned directly via the Keycloak Admin Console (see above, "Reference Number Generator").
- Four-eyes principle for force-unlock optionally available since P6-S4 (see above) — default remains ungated, likewise no feedback channel that notifies `permission-service` of a failed (e.g. meanwhile otherwise resolved) execution.
- **Folders have had their own, parallel retention/legal-hold/forced-deletion pattern since P7-S1b** (`folder-service`, own tables instead of reusing the ones here) — this service is synchronously integrated via the new `cascade-trash`/`cascade-restore`/`count-active` endpoints (see above) when a folder is moved to/restored from the trash, or checked for non-emptiness before forced deletion. See `docs/services/folder-service.md`.
- ~~No legal hold role check (5.2, since P7-S1) — who may set/release a hold is unrestricted~~ — **resolved in Post-Roadmap Phase 19 Session 10** ([ADR 0075](../adr/0075-legal-hold-rbac.md)): new domain-admin role `domain-admin-legal-hold` (`admin.legal_hold`). `GET /legal-holds`/`GET .../has-active-hold` deliberately remain ungated.
- **Deletion register not backup-differentiated** (5.2a) — compensated only via the Audit Service hash chain, see above; real backup separation only arrives with Phase 11.
- **Deletion register/legal hold tables live in this service instead of a dedicated compliance service** — deliberate, to avoid a premature extraction before the need is established across more than one object type (to be re-evaluated once, e.g., cases also need retention, Phase 15).
- **No admin UI toggle for `document.delete`/`document.force_delete`/`document.force_unlock`** (5.2, since P7-S1c) — an identical, already-existing gap, configurable only via the raw `PUT /approval-config/{action_type}` API. A generic "four-eyes principle settings" page for all action types would be a sensible but separate future cut.
- **Approval inbox filtered only for `document.delete`/`folder.delete`** (5.2, since P7-S1c) — not a general replacement for a full deletion-register/restoration cockpit; per user feedback, a precursor to a later-planned "administrative trash" (presumably Phase 15 "special areas").
- **Case references (2.3, since P6-S3)**: the new `case-service` only accesses `current_version_number`/`deleted_at` read-only via `GET /documents/{id}` — nothing needed to change here for that. Editing copies (also 2.3), by contrast, are this session (see above) — no new endpoint, three optional provenance fields on `POST /documents`. Replacement representations (2.4) have been implemented since P5-S2 (see `docs/services/rendering-service.md`), without this service needing any change for it — the Rendering Service consumes the already-existing `document.>` events and calls the already-existing version/content endpoints.
- **No existence check for `originating_case_id`**: an opaque reference to a case in `case-service`, analogous to `folder_id`/`object_type_id` — an unknown value is not rejected.
- Virus-scan gating increases upload latency by the scan time and also scans even when a check-in would be rejected anyway due to an outdated `expected_base_version_number`/lock conflict (unnecessary but not incorrect work) — see ADR 0010 "Consequences".
- No retroactive check and no cycle detection for `allowedParentTypes` (see ADR 0013) — the same limitation as in the Object-Type/Folder Service.
- ~~**`GET /documents/{id}/content` returns a plain `404` after dehydration** (5.6, since P7-S3) instead of a more specific 409 with a retrieval reference~~ — **resolved in Post-Roadmap Phase 19 Session 11** ([ADR 0076](../adr/0076-root-folder-mail-regex-dehydration-409.md)), see "Records Disposal & Long-Term Archiving" above.
- **No existence check that `archival-service` is the calling instance of the internal records-disposal endpoints** (5.6, since P7-S3) — `PUT .../archived`/`.../dehydrated`/`.../rehydrated` are, like most endpoints in this system, ungated, see "Authorization" in `PROGRESS.md`.
- **No rate limiting specific to share link tokens** (4.2a, since P14-S10) beyond the gateway-wide generic IP rate limiting — with ~256 bits of entropy per token, deemed sufficient for a reference implementation, see ADR 0047. `max_validity_days` changes also only affect newly created links, not retroactively already-issued ones (unlike full deactivation).
