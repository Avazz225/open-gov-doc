# 0060 — eGov configuration package part 2: closed four-eyes gaps, circulation-folder process templates, business calendars, extended admin roles

**Status:** accepted
**Context:** P17-S3 (eGov configuration package part 2, concept §14.2), last implementation session of Phase 17

## Decision

Five related decisions:

1. **Real four-eyes enforcement for role assignment and configuration import instead of decorative configuration.** 14.2 literally names "permanent deletion, permission change, configuration import" as the three action types for which the package is supposed to enable four-eyes by default. Before this session, only "permanent deletion" (`document.force_delete`/`folder.force_delete`/`document.force_unlock`) had actual enforcement — for role assignment and configuration import, not a single `action_type="..."` site existed anywhere in the code (confirmed via grep across all `main.py`). Instead of shipping `approval_config` entries that would have had no effect, both gaps were closed in this session:
   - `permission-service`: `POST /role-assignments` now checks `permission.role_assignment.create` via the same generic `_request_approval()` mechanism as scope locks (4.3/4.7) and returns a new `RoleAssignmentActionResult` (`status`/`role_assignment`/`approval_request_id`) instead of the previous flat `RoleAssignmentOut`. Approved assignments are applied in the already-existing self-consumption branch of `approval_consumer.py` (same pattern as scope locks/emergency lock).
   - `config-service`: `POST /config/import` now checks `config.import` via a new `ApprovalClient` (a copy of the `document-service` pattern) and returns `ImportActionResult`. Since `config-service` previously had no event-bus integration at all ("stateless orchestrator", P17-S1), it got a new, **pure consumer** (`ensure_stream=False`, no own stream) for `permission.approval.approved`, which, on an approved `config.import`, calls the same `_apply_config_document()` application logic as the immediate path. `POST /config/fleet-import` deliberately remains ungated (see rationale).
2. **BPMN process templates for the three circulation-folder patterns named in 2.3/7.1** (`packages/egov/workflows/egov_{freigabe,kenntnisnahme,aufgabe}.bpmn`, embedded as the `workflows` category): `Freigabe` (approval) is a single `manualTask` followed by an `exclusiveGateway` that branches on the process variable `entscheidung` (`"Genehmigt"`/default `"Abgelehnt"`); `Kenntnisnahme` (acknowledgment)/`Aufgabe` (task) are each a single linear `manualTask` with no branching. All three were uploaded to and instantiated against the running `workflow-service` and played through to completion before being included in the package (including both gateway branches of `Freigabe`).
3. **Business calendars: one federally uniform default calendar (`DE-Bund`, `is_default: true`) plus 16 state calendars** (`DE-BW` … `DE-TH`, complete per state including the nine nationwide public holidays), with real computed dates for 2026 and 2027 (Gaussian Easter algorithm for all movable holidays, Buß- und Bettag as "Wednesday before November 23"). `BusinessCalendarExport` has no region field (see `workflow_service.models.BusinessCalendar`) — the package therefore ships complete, self-contained date lists per calendar instead of a single calendar with a region parameter.
4. **Two extended, domain-separated admin roles** (`roles` category, permission-service DB roles, not to be confused with the technical `domain-admin-*` system roles from 4.6): `Registratur/Aktenverwaltung` (records administration; `["read", "write"]`) for day-to-day file administration, `Amtsleitung` (office management; `["read", "write", "scope_lock.bypass"]`) for extended oversight/approval authority including access despite an active scope lock. 14.2 names both names explicitly only as an example ("e.g.") — the concrete permission lists are a plausible interpretation made in this session, not a concept quote.
5. **`realm_roles: ["dms-poststelle"]`** — the mail room role already exists in reality (Keycloak realm role, manually created since P15-S3 and enforced by `mail-connector`'s `_require_poststelle()`), but had so far not been included in any configuration package. A fresh installation that imports the eGov package now gets the role created automatically (assignment to specific people remains installation-specific like any realm role, see P17-S1).

## Rationale

- **Why real enforcement instead of pure `approval_config` pre-configuration**: an `approval_config` entry for an `action_type` that no endpoint actually queries would have been pure decoration — `requires_approval: true` could have been imported without changing the system's actual behavior at all. That would have contradicted this project's established pattern of, when implementing a concept section, actually retrofitting genuinely missing but concept-required mechanics rather than simulating them (cf. P17-S1's gateway routing fix, P17-S2's reference number placeholder mechanism).
- **Why `POST /role-assignments` was changed in a response-incompatible way instead of a separate endpoint**: `ForceReleaseResult` (document-service, P6-S4) already establishes the pattern "same endpoint, status envelope response, behavior unchanged when `requires_approval=false`" — a parallel endpoint would have created two paths to the same result and would have been inconsistent with this already repeatedly used pattern (`RoleAssignmentActionResult` instead falls directly in line). The breadth of the impact (practically every service bootstraps its own roles via exactly this endpoint) was checked: all bootstrap callers (`auth-service`, `case-service`, `config-service`, `mail-connector`, `migration-service`, `teamspace-service`, `workflow-service`) only check `response.raise_for_status()`, none parses the response body as a flat object — only two test helper functions (`config-service`/`auth-service`) and two tests within `permission-service` itself accessed `assignment["id"]` and were adjusted accordingly.
- **Why `config-service` gets a pure consumer instead of a full producer+consumer pair**: `config-service` has nothing of its own to publish (see P17-S1: "stateless orchestrator", no own database) — it only reacts to an already-existing event owned by `permission-service`. `ensure_stream=False` thus follows the same two-client principle that `document-service`/`notification-service`/`case-service` already establish for exactly this case (see ADR 0001, "stream ownership").
- **Why `POST /config/fleet-import` was NOT gated**: consistent with ADR 0037's rationale for the RBAC bypass of the fleet-agent path — automated, headless provisioning has no human in the loop who could meaningfully confirm a later pending approval request. A gated but never-answered request would, for this access path, be pure blockage with no security benefit.
- **Why `initiated_by`/`approved_by` for role assignment is `principal_id` (the person who is to receive the role) instead of a separate requester field**: `RoleAssignmentCreate`, like `create_scope_lock` (an older, simpler pattern than the newer delegation endpoints), has no dedicated "who is requesting this" field and deliberately does not read an `X-DMS-Principal` header — `principal_id` is the only available placeholder, the identical trade-off as already documented there.
- **Why three simple, linear/binary-branching BPMN templates instead of more complex processes**: 14.2 explicitly calls for "ready-to-use starting points instead of having to model from scratch", not finished domain processes — every installation models the actual circulation-folder logic (multiple stations, escalation, deadlines) on top of these templates itself, exactly as a real circulation folder is in practice shaped differently case by case. `manualTask` (not `userTask`) used consistently, since `workflow-service`'s task-ready filter (`wf.get_tasks(state=TaskState.READY, manual=True)`) only responds to it (see docstring in `spiff_adapter.py`).
- **Why a default federal calendar plus 16 complete state calendars instead of a single calendar with the "most important" holidays**: 14.2 literally requires "federally uniform as well as, where clearly attributable, state-specific" — an installation must be able to select the calendar actually applicable to its federal state (`workflow-service`'s SLA deadline calculation takes exactly one calendar). Holidays that apply only in individual municipalities (e.g. Assumption of Mary in majority-Catholic Bavarian municipalities, Corpus Christi in parts of Saxony/Thuringia) were deliberately excluded, since they are not "clearly attributable" at the state level — exactly the standard set by the concept text.
- **Why 2026/2027 instead of a recurring pattern or several years**: `non_working_dates` is a plain date list with no repetition rule (see `BusinessCalendarExport`) — two years cover the immediate planning horizon for a fresh installation without unnecessarily bloating the list; an installation adds further years itself as needed (same principle as any other "changeable default" in this package).

## Consequences

- **Breaking response-shape change**: `POST /role-assignments` now returns `{"status", "role_assignment", "approval_request_id"}` instead of a flat `RoleAssignmentOut` — every external client (including outside this repo) must be adjusted. `admin-ui`'s `UserManagement.tsx`/`api.ts` as well as all affected test files were updated accordingly in this session.
- **`scripts/run-tests.sh`'s `CONSUMER_SERVICES` list extended with `config-service`** — the new NATS consumer would otherwise have triggered the same Docker-container-vs-`pytest`-durable conflict that the list already guards against for all other consuming services.
- **`packages/egov/config.json`'s `manifest.version` jumps from `0.1.0` to `1.0.0`** — first complete version of the package (all six components named in 14.2 present). Further changes to this package (e.g. additional state-level differentiation, additional process templates) will regularly increment the version going forward.
- **`packages/egov/workflows/*.bpmn` live as separate source files next to `config.json`**, whose content is embedded 1:1 into the `workflows` category at build time — eases maintenance/diff readability compared to XML-as-a-JSON-string directly in `config.json`, but changes nothing about the format: `config.json` remains the only file actually imported.
- **No automatic realm-role rollback**: if `dms-poststelle` is imported but the installation does not use `mail-connector`, an unused but harmless realm role remains — identical, already-accepted behavior of additive packages elsewhere (14.1).
- **Two real bugs found and fixed during regression testing of this session itself**:
  1. `infra/docker-compose.yml`'s `config-service` block did not set `DMS_NATS_URL` — `BaseServiceSettings` fell back to the default `nats://localhost:4222`, which does not reach the `nats` service inside the container. The new consumer as a result ran in an endless loop of connection errors, without blocking startup itself (not immediately visible via `GET /healthz`) — only the full `POST /config/import` approval round trip during live verification would ever have revealed that the withheld import was never actually applied. Fix: `DMS_NATS_URL: nats://nats:4222` added, along with `depends_on: nats (service_healthy)`, the identical pattern as every other NATS-integrated service.
  2. `scripts/run-tests.sh`'s `CONSUMER_SERVICES` list was initially, mistakenly, extended with `config-service` in this session (see comment there) — the script stopped the container before `config-service`'s own test run, but its tests (unlike the other entries on this list) deliberately run against the real, running container rather than an in-process `TestClient` (see `tests/conftest.py` docstring, P12-S3). Every `config-service` test consequently failed with `Connection refused`. Fix: `config-service` removed from the list again, comment extended with the distinction "needs in-process test client" vs. "tests against real container", so the same mistake is not repeated for a future service.
