# 0039 — Federation trust model hardening: application-layer signatures instead of real mTLS

**Status:** accepted
**Context:** P13-S4 (last session of phase 13, "hardening of the trust model deliberately kept simple in P6-S9", concept 7.4/ADR 0028)

## Decision

The roadmap entry's requirement for "mTLS instead of pure API-key authentication" is **not** implemented as a real transport-layer TLS client certificate, but as a **cryptographically equivalent mechanism at the application layer**: every write request from an installation to the Federation Hub (`POST /installations`, `DELETE /installations/{id}`, `POST /installations/{id}/rotate-key`, `POST /handovers`, `POST /handovers/{id}/result`) must be signed with that same installation's private key (RSA-PSS/SHA-256, `X-Installation-Signature`, with `X-Installation-Id` additionally required on `/handovers`+`/result`), verified against the public key already on file at the hub (`Installation.public_key_pem` - the same key that already exists anyway for end-to-end encryption, ADR 0028). The previous, hub-issued `api_key`/`api_key_hash` model is removed entirely (column dropped via migration, no transition period). Also new: `POST /installations/{id}/rotate-key` (key rotation, signed with the still-current key) and `POST /installations/{id}/revoke` (operator revocation, gated behind a new, independent `DMS_HUB_OPERATOR_KEY` secret).

## Rationale

- **No place in this project for a real PKI**: TLS/mTLS is treated consistently, across the entire rest of the system (concept 10.3: "transport encryption (TLS) between all services"), as a **deployment concern** - not a single other service in this repository terminates TLS itself or verifies client certificates; all internal calls run over plain HTTP inside the Docker Compose network. Introducing real mTLS for the Federation Hub alone (its own certificate issuance/distribution, `ssl_cert_reqs=CERT_REQUIRED` in uvicorn, certificate mounting in `infra/docker-compose.yml`) would be an isolated special case with no reuse value for the rest of the system, and would introduce an entirely new operations/certificate-management discipline that does not exist anywhere else in this project.
- **Cryptographically equivalent property, without this infrastructure**: the actual security goal of mTLS in this context is "the caller must prove possession of a private key that uniquely belongs to its registered identity" - a request signature using the same RSA key pair that every installation already possesses for end-to-end encryption anyway (ADR 0028) delivers exactly that, without needing an additional TLS handshake/certificate store. `sign_body`/`verify_body` already existed for the reverse direction (hub→installation, `X-Federation-Hub-Signature`) - this session merely completes the previously missing opposite direction, which had already been documented as planned since P6-S9 in `federation_crypto.sign_body`'s own docstring ("used for our own calls against the hub").
- **A genuine weakness of the `api_key` model fixed**: an `api_key` is a pure, copyable secret - whoever knows it (e.g. from a log, a compromised backup) can fully impersonate the affected installation without ever possessing its private key. A signature, by contrast, proves actual possession of the private key on every single request - an intercepted API-key-like value (here: a single signature) is not reusable for another request.
- **Self-consistency check on new registration**: `register_or_update_installation()` requires that, for a brand-new `id`, the signature match the `public_key_pem` submitted in the same request - this prevents anyone from registering an arbitrary (foreign or fabricated) public key on behalf of a new installation without possessing its private counterpart.
- **Key change only through a dedicated, narrower path**: a regular re-registration deliberately no longer overwrites `public_key_pem` (a differing value in the payload is ignored) - only `POST /installations/{id}/rotate-key` (signed with the still-current key, a genuine proof of continuity) may change the cryptographic identity. This separates "harmless metadata update" (version, callback URL) from "security-relevant identity change" - a regular re-registration can no longer accidentally (or via an unnoticed foreign call with a correct but outdated understanding) change the key along the way.
- **Revocation is deliberately NOT tied to the affected installation's own signature**: the purpose of revocation is precisely the case where an installation can no longer sign trustworthily (compromised private key) - a self-revocation requirement would be useless in exactly this case. Instead, a separate, independent operator secret (`DMS_HUB_OPERATOR_KEY`, analogous to the already-established pattern from `fleet-management-service`'s `DMS_FLEET_AGENT_API_KEY`, ADR 0037) - `None` by default locks the endpoint entirely, a hub operator must deliberately enable revocation.
- **"Real installation identity instead of a self-chosen `installation_id`"**: the `installation_id` string itself deliberately remains self-chosen (7.4 does not require a globally unique, externally attested identifier, only uniqueness within the given hub's address book, which continues to be enforced by the primary key) - what changes is that the **authenticity** behind this identifier is now cryptographically anchored (whoever can demonstrably prove possession of the private key), instead of hanging off a copyable string. A globally attested identity (e.g. via an external PKI/CA) would be a considerably larger, standalone topic and is not what 3a/7.4 actually require (installations deliberately remain fully autonomous, no central certification regime).

## Consequences

- **Breaking change with no transition period**: `api_key`/`api_key_hash` are removed entirely within the same session (column dropped via `ALTER TABLE ... DROP COLUMN IF EXISTS`), not phased out gradually across several versions - acceptable since this is an early development stage with no production federation participants outside this repo (no rolling-update/coexistence scenario between an old and a new installation to consider). For a genuinely production scenario with foreign, independently operated installations, a transition period (both auth paths accepted in parallel) would have been needed - deliberately not required here.
- **No sensor/monitoring hookup for revocation events** - a hub operator has no proactive way of learning when an installation repeatedly fails `X-Installation-Signature` checks (a potential indicator of an outdated/misconfigured client or an attack attempt). A deliberate limitation of this session, see `docs/services/federation-hub-service.md` "Open Points".
- **No key expiry/enforced periodic rotation** - rotation is purely voluntary/installation-driven. An enforced expiry semantics would have required an additional background process/warning chain (analogous to license-expiry detection, `license-service`) - not part of this session.
- Real transport-layer TLS/mTLS remains purely an operator deployment decision (reverse proxy/ingress with its own certificate management) - unchanged from every other service in this project, see concept 10.3.
