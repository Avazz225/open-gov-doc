# 0039 — Föderations-Vertrauensmodell-Härtung: Anwendungsschicht-Signaturen statt echtem mTLS

**Status:** akzeptiert
**Kontext:** P13-S4 (letzte Session der Phase 13, "Härtung des in P6-S9 bewusst einfach gehaltenen Vertrauensmodells", Konzept 7.4/ADR 0028)

## Entscheidung

Die im Roadmap-Eintrag geforderte "mTLS statt reiner API-Key-Authentifizierung" wird **nicht** als echtes TLS-Client-Zertifikat auf Transportebene umgesetzt, sondern als **kryptografisch gleichwertiger Mechanismus auf Anwendungsebene**: jede schreibende Anfrage einer Installation an den Federation Hub (`POST /installations`, `DELETE /installations/{id}`, `POST /installations/{id}/rotate-key`, `POST /handovers`, `POST /handovers/{id}/result`) muss mit dem privaten Schlüssel derselben Installation signiert sein (RSA-PSS/SHA-256, `X-Installation-Signature`, bei `/handovers`+`/result` zusätzlich `X-Installation-Id`), verifiziert gegen den beim Hub bereits hinterlegten öffentlichen Schlüssel (`Installation.public_key_pem` - derselbe Schlüssel, der ohnehin schon für die Ende-zu-Ende-Verschlüsselung existiert, ADR 0028). Das bisherige, vom Hub ausgegebene `api_key`/`api_key_hash`-Modell entfällt vollständig (Spalte per Migration entfernt, kein Übergangszustand). Zusätzlich neu: `POST /installations/{id}/rotate-key` (Schlüsselrotation, signiert mit dem noch aktuellen Schlüssel) und `POST /installations/{id}/revoke` (Betreiber-Revocation, gegated über ein neues, unabhängiges `DMS_HUB_OPERATOR_KEY`-Geheimnis).

## Begründung

- **Kein Ort für eine echte PKI in diesem Projekt**: TLS/mTLS ist im gesamten restlichen System (Konzept 10.3: "Transportverschlüsselung (TLS) zwischen allen Services") durchgehend als **Deployment-Sache** behandelt - kein einziger anderer Service dieses Repos terminiert TLS selbst oder verifiziert Client-Zertifikate, alle internen Aufrufe laufen über einfaches HTTP innerhalb des Docker-Compose-Netzes. Für den Federation Hub allein echtes mTLS einzuführen (eigene Zertifikatsausstellung/-verteilung, `ssl_cert_reqs=CERT_REQUIRED` in uvicorn, Zertifikats-Mounting in `infra/docker-compose.yml`) wäre ein isolierter Sonderfall ohne Wiederverwendungswert für den Rest des Systems und würde eine vollständig neue, in diesem Projekt bislang nicht existierende Betriebs-/Zertifikatsverwaltungs-Disziplin einführen.
- **Kryptografisch gleichwertige Eigenschaft, ohne diese Infrastruktur**: das eigentliche Sicherheitsziel von mTLS in diesem Kontext ist "der Aufrufer muss den Besitz eines privaten Schlüssels nachweisen, der eindeutig zu seiner registrierten Identität gehört" - genau das leistet eine Anfragesignatur mit demselben RSA-Schlüsselpaar, das jede Installation ohnehin schon für die Ende-zu-Ende-Verschlüsselung besitzt (ADR 0028), ohne einen zusätzlichen TLS-Handshake/Zertifikatsspeicher zu benötigen. `sign_body`/`verify_body` existierten bereits für die umgekehrte Richtung (Hub→Installation, `X-Federation-Hub-Signature`) - diese Session vervollständigt lediglich die bislang fehlende Gegenrichtung, die in `federation_crypto.sign_body`s eigenem Docstring bereits seit P6-S9 als vorgesehen dokumentiert war ("genutzt für eigene Aufrufe gegen den Hub").
- **Echte Schwäche des `api_key`-Modells behoben**: ein `api_key` ist ein reines, kopierbares Geheimnis - wer ihn kennt (z. B. aus einem Log, einem kompromittierten Backup), kann sich vollständig als die betroffene Installation ausgeben, ohne jemals deren privaten Schlüssel zu besitzen. Eine Signatur beweist dagegen den tatsächlichen Besitz des privaten Schlüssels bei jeder einzelnen Anfrage - ein abgefangener API-Key-artiger Wert (hier: eine einzelne Signatur) ist nicht wiederverwendbar für eine andere Anfrage.
- **Selbstkonsistenz-Prüfung bei der Neuregistrierung**: `register_or_update_installation()` verlangt bei einer brandneuen `id`, dass die Signatur zum im selben Request eingereichten `public_key_pem` passt - verhindert, dass irgendjemand einen beliebigen (fremden oder erfundenen) öffentlichen Schlüssel im Namen einer neuen Installation hinterlegt, ohne dessen privaten Gegenpart zu besitzen.
- **Schlüsselwechsel nur über einen dedizierten, engeren Pfad**: eine reguläre Re-Registrierung überschreibt `public_key_pem` bewusst **nicht** mehr (ein abweichender Wert im Payload wird ignoriert) - nur `POST /installations/{id}/rotate-key` (signiert mit dem noch aktuellen Schlüssel, echter Kontinuitätsnachweis) darf die kryptografische Identität ändern. Trennt damit "harmlose Metadaten-Aktualisierung" (Version, Callback-URL) von "sicherheitsrelevanter Identitätsänderung" - eine reguläre Re-Registrierung kann nicht mehr versehentlich (oder durch einen unbemerkten fremden Aufruf mit korrektem, aber veraltetem Verständnis) den Schlüssel mitändern.
- **Revocation bewusst NICHT an die Signatur der betroffenen Installation gebunden**: der Zweck von Revocation ist gerade der Fall, in dem eine Installation nicht mehr vertrauenswürdig signieren kann (kompromittierter privater Schlüssel) - eine Selbst-Revocation-Anforderung wäre in genau diesem Fall nutzlos. Stattdessen ein separates, unabhängiges Betreiber-Geheimnis (`DMS_HUB_OPERATOR_KEY`, analog zum bereits etablierten Muster aus `fleet-management-service`s `DMS_FLEET_AGENT_API_KEY`, ADR 0037) - `None` per Default sperrt den Endpunkt vollständig, ein Hub-Betreiber muss Revocation bewusst aktivieren.
- **"Echte Installations-Identität statt selbst gewählter `installation_id`"**: die `installation_id`-Zeichenkette selbst bleibt bewusst weiterhin selbst gewählt (7.4 verlangt keine global-eindeutige, extern beglaubigte Kennung, nur Eindeutigkeit im Adressbuch des jeweiligen Hub, die weiterhin durch den Primärschlüssel erzwungen wird) - was sich ändert, ist, dass die **Authentizität** hinter dieser Kennung jetzt kryptografisch verankert ist (wer immer nachweislich den privaten Schlüssel besitzt), statt an einem kopierbaren String zu hängen. Eine global beglaubigte Identität (z. B. über eine externe PKI/CA) wäre ein deutlich größerer, eigenständiger Themenkomplex und nicht das, was 3a/7.4 tatsächlich fordern (die Installationen bleiben bewusst vollständig autonom, kein zentrales Zertifizierungsregime).

## Konsequenzen

- **Breaking Change ohne Übergangszeitraum**: `api_key`/`api_key_hash` werden in derselben Session vollständig entfernt (Spalte per `ALTER TABLE ... DROP COLUMN IF EXISTS`), nicht schrittweise über mehrere Versionen abgelöst - vertretbar, da es sich um ein frühes Entwicklungsstadium ohne produktive Föderationsteilnehmer außerhalb dieses Repos handelt (kein Rolling-Update-/Koexistenz-Szenario zwischen alter und neuer Installation zu berücksichtigen). Für ein tatsächlich produktives Szenario mit fremden, unabhängig betriebenen Installationen wäre ein Übergangszeitraum (beide Auth-Wege parallel akzeptiert) nötig gewesen - hier bewusst nicht erforderlich.
- **Kein Sensor-/Monitoring-Anschluss für Revocation-Ereignisse** - ein Hub-Betreiber erfährt nicht proaktiv, wenn eine Installation `X-Installation-Signature`-Prüfungen wiederholt nicht besteht (potenzieller Hinweis auf einen veralteten/falsch konfigurierten Client oder einen Angriffsversuch). Bewusste Grenze dieser Session, siehe `docs/services/federation-hub-service.md` "Offene Punkte".
- **Kein Schlüssel-Ablaufdatum/erzwungene periodische Rotation** - Rotation ist rein freiwillig/installationsgetrieben. Eine erzwungene Ablaufsemantik hätte einen zusätzlichen Hintergrundprozess/eine Warnkette (analog zur Lizenzablauf-Erkennung, `license-service`) erfordert - nicht Teil dieser Session.
- Echtes TLS/mTLS auf Transportebene bleibt weiterhin eine reine Deployment-Entscheidung des Betreibers (Reverse Proxy/Ingress mit eigener Zertifikatsverwaltung) - unverändert gegenüber jedem anderen Service dieses Projekts, siehe Konzept 10.3.
