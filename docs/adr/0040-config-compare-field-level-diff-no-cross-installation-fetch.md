# 0040 — Delta/compare function: field-level diff, manually supplied exports instead of automatic cross-installation fetch

**Status:** accepted
**Context:** P14-S1 (delta/compare function between installations, concept 7.5)

## Decision

A new `POST /config/compare` endpoint in `config-service` compares two already-available `ConfigDocument` exports (7.3) - `compare` is required, `base` is optional (if omitted, the endpoint uses its own current live export, for the use case "what would change if this document were imported"). The comparison operates **field-wise at the top level** per named entry (object type/workflow/role/four-eyes config by name/`action_type`, `sensor_config`/`federation_config` as a singleton), not as a recursive deep diff of nested lists/objects. A configurable **ignore regex** (global via the key `"*"` or per category) normalizes names before the matching step (substring removal via `re.sub`), but affects only the matching - the attribute comparison of the entry thus matched proceeds fully independently of it. This session does **not** build an automated cross-installation fetch (neither directly nor via the Federation Hub) - both exports must already be available to the calling side (admin/CLI), each produced via that installation's own, regularly authenticated `GET /config/export` access.

## Rationale

- **Field-level rather than deep diff already fulfils 7.5 literally**: 7.5 requires a "detail view of which attributes concretely differ" - this is a statement about *which top-level attributes* of an entry differ (e.g. "role `sachbearbeiter` differs in `permissions`"), not a requirement for a recursive patch/diff of nested structures (e.g. individual rows of an object-type layout). A field-level comparison is sufficiently precise for a reference implementation and considerably simpler to implement/understand than a generic tree-diff algorithm - a deliberate, documented simplification, analogous to other "a reference implementation suffices" decisions in this project (e.g. the PAdES-B-B boundary in `signature-service`, ADR 0025).
- **Ignore regex as a pure matching aid, not an attribute filter**: the concept's own example (`100_testobjekt_typ_alpha` vs. `101__testobjekt_typ_alpha`) makes clear that the regex is only meant to influence the question "is this the same object" - the actual name difference is deliberately NOT reported as a differing attribute (it is precisely the accepted, to-be-ignored difference), while all OTHER attributes continue to be compared fully. The display name in the delta report always remains the raw base-instance value, never the normalized one - normalization is an internal matching step, not a display format.
- **No automatic cross-installation fetch in this session - deliberately scoped smaller than 7.5's optional mention**: 7.5 explicitly names a hub-mediated automated fetch as an **option**, not a requirement ("a hub is, however, not a prerequisite for the feature"). Such a fetch would either (a) turn `GET /config/export` into a public, ungated gateway route (the exported configuration contains no secrets, but introducing a new, permanently open attack surface purely for this convenience feature is not justified), or (b) require an entirely new cross-installation authentication scheme for `config-service` (`config-service` is not currently a federation participant like `workflow-service`, ADR 0028/0039 - a dedicated key pair/registration with the hub just for this one convenience feature would be a disproportionately large new trust relationship for a purely read-only diagnostic operation). The honestly scoped variant actually built: both exports are fetched via each installation's own, already-existing authentication (a regular Keycloak login per installation via CLI/admin UI) and then compared locally - this fully satisfies 7.5's core requirement ("the comparison operates on the basis of existing configuration exports") without new infrastructure.
- **CLI first, admin-UI visualization deliberately deferred**: `dms-cli config export`/`config compare` directly and fully satisfy 7.5's second stated access mode ("structured, scriptable output ... relevant e.g. for automated drift checks in a CI/CD pipeline") - `-o json` returns the complete `CompareResult` structure, the table view (default) a compact summary per category. A visual admin-UI presentation is not part of this session (P14-S1 is not on `IMPLEMENTATION_PLAN.md`'s list of sessions with a mandatory browser test) - a deliberate deferral to a later, explicitly planned UI session, consistent with the pattern of building backend/CLI functionality fully first and adding the UI layer separately afterward.
- **`config-service` remains a purely stateless orchestrator**: the comparison changes nothing (7.5: "purely read-only/diagnostic") and stores nothing - `compare.py` consists of pure functions over already-available `ConfigDocument` objects, no new data model, no new table. Consistent with `config-service`'s existing "stateless orchestrator" character (ADR 0035).
- **Installation-specific data (license state, registry reachability) is structurally excluded**, not merely by convention: `ConfigDocument` does not contain these fields at all (they were never part of 7.3's export schema to begin with) - 7.5's explicit exclusion rule is therefore automatically satisfied, with no filtering logic of its own needed.

## Consequences

- **No automated, hub-mediated fetch** - an operator who wants to regularly and automatically compare two installations (e.g. daily drift checks staging↔production) has to build a small script for it themselves (two `dms config export` calls, each with its own login, plus `dms config compare`) instead of a built-in cron job. For the CI/CD use case explicitly named in 7.5, this is sufficient (the pipeline already has credentials for both environments anyway).
- **No admin-UI access to the compare function** in this session - CLI and raw API only. A later UI session would need to build its own view for this (category overview, expandable detail view per differing entry, ignore-regex input field).
- **No deep diff of nested structures** - a change deep inside an object-type layout (`layouts[].rows`) is reported as "the entire `layouts` field differs", not with a row-precise breakdown. For the main use cases named in 7.5 (drift detection, preview before adopting a configuration), "this attribute differs, here are both full values" is sufficient - the actual detailed comparison is left to the viewer.
- `config-service` gets, via `POST /config/compare`, its first endpoint that accepts two complete `ConfigDocument` payloads simultaneously in the request body - with very many object types/workflows the request can become correspondingly large (no dedicated limit set beyond the already-existing FastAPI/gateway limits, the same deliberate simplification as with the existing `POST /config/import`).
