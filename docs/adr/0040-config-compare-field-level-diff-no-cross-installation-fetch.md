# 0040 — Delta-/Vergleichsfunktion: Feld-Ebene-Diff, manuell bereitgestellte Exporte statt automatischem Cross-Installation-Abruf

**Status:** akzeptiert
**Kontext:** P14-S1 (Delta-/Vergleichsfunktion zwischen Installationen, Konzept 7.5)

## Entscheidung

Ein neuer `POST /config/compare`-Endpunkt in `config-service` vergleicht zwei bereits vorliegende `ConfigDocument`-Exporte (7.3) - `compare` ist Pflicht, `base` optional (fehlt es, zieht der Endpunkt den eigenen aktuellen Live-Export heran, Anwendungsfall "was würde sich beim Import dieses Dokuments ändern"). Der Vergleich arbeitet **feldweise auf oberster Ebene** je benanntem Eintrag (Objekttyp/Workflow/Rolle/Vier-Augen-Konfig per Name/`action_type`, `sensor_config`/`federation_config` als Singleton), nicht als rekursiver Tiefendiff verschachtelter Listen/Objekte. Eine konfigurierbare **Ignore-Regex** (global über den Schlüssel `"*"` oder je Kategorie) normalisiert Namen vor dem Zuordnungsschritt (Teilstring-Entfernung per `re.sub`), betrifft aber ausschließlich die Zuordnung - der Attributvergleich des so zugeordneten Eintrags läuft davon unabhängig vollständig weiter. Diese Session baut **keinen** automatisierten Cross-Installation-Abruf (weder direkt noch über den Federation Hub) - beide Exporte müssen der aufrufenden Seite (Admin/CLI) bereits vorliegen, jeweils über den eigenen, regulär authentisierten `GET /config/export`-Zugriff auf die jeweilige Installation erzeugt.

## Begründung

- **Feld-Ebene statt Tiefendiff erfüllt 7.5 bereits wörtlich**: 7.5 verlangt eine "Detailanzeige, welche Attribute konkret abweichen" - das ist eine Aussage über *welche Top-Level-Attribute* eines Eintrags sich unterscheiden (z. B. "die Rolle `sachbearbeiter` unterscheidet sich in `permissions`"), keine Forderung nach einem rekursiven Patch/Diff verschachtelter Strukturen (z. B. einzelner Zeilen eines Objekttyp-Layouts). Ein Feld-Ebene-Vergleich ist für eine Referenzimplementierung ausreichend präzise und deutlich einfacher zu implementieren/zu verstehen als ein generischer Baum-Diff-Algorithmus - bewusste, dokumentierte Vereinfachung, analog zu anderen "Referenzimplementierung genügt"-Entscheidungen in diesem Projekt (z. B. PAdES-B-B-Grenze bei `signature-service`, ADR 0025).
- **Ignore-Regex als reine Zuordnungshilfe, nicht als Attributfilter**: das Konzeptbeispiel selbst (`100_testobjekt_typ_alpha` vs. `101__testobjekt_typ_alpha`) macht deutlich, dass die Regex nur die Frage "ist das dasselbe Objekt" beeinflussen soll - der eigentliche Namensunterschied wird bewusst NICHT als abweichendes Attribut gemeldet (er ist ja gerade der akzeptierte, zu ignorierende Unterschied), während alle ÜBRIGEN Attribute weiterhin vollständig verglichen werden. Der Anzeigename im Delta-Bericht bleibt dabei immer der rohe Basisinstanz-Wert, nicht der normalisierte - die Normalisierung ist ein interner Zuordnungsschritt, kein Anzeigeformat.
- **Kein automatischer Cross-Installation-Abruf in dieser Session - bewusst kleiner geschnitten als 7.5s optionale Erwähnung**: 7.5 nennt einen Hub-vermittelten automatisierten Abruf ausdrücklich als **Option**, nicht als Voraussetzung ("ein Hub ist aber keine Voraussetzung für die Funktion"). Ein solcher Abruf würde entweder (a) `GET /config/export` zu einer öffentlichen, ungegateten Gateway-Route machen (die exportierte Konfiguration enthält zwar keine Geheimnisse, aber eine neue, dauerhaft offene Angriffsfläche allein für diese Komfortfunktion einzuführen ist nicht gerechtfertigt) oder (b) eine komplett neue Cross-Installation-Authentisierung für `config-service` erfordern (`config-service` ist bislang kein Föderationsteilnehmer wie `workflow-service`, ADR 0028/0039 - ein eigenes Schlüsselpaar/eine eigene Registrierung beim Hub nur für diese eine Komfortfunktion wäre eine unverhältnismäßig große neue Vertrauensbeziehung für einen rein lesenden Diagnosevorgang). Die ehrlich geschnittene, tatsächlich gebaute Variante: beide Exporte werden über die jeweils **eigene, bereits bestehende** Authentisierung jeder Installation abgerufen (regulärer Keycloak-Login je Installation über CLI/Admin-UI) und dann lokal verglichen - erfüllt 7.5s Kernanforderung vollständig ("Vergleich arbeitet auf Basis der bestehenden Konfigurationsexporte") ohne neue Infrastruktur.
- **CLI zuerst, Admin-UI-Visualisierung bewusst zurückgestellt**: `dms-cli config export`/`config compare` erfüllen 7.5s zweite genannte Zugriffsart ("strukturierte, skriptfähige Ausgabe ... relevant z. B. für automatisierte Drift-Checks in einer CI/CD-Pipeline") direkt und vollständig - `-o json` liefert die komplette `CompareResult`-Struktur, die Tabellenansicht (Default) eine kompakte Zusammenfassung je Kategorie. Eine visuelle Admin-UI-Aufbereitung ist nicht Teil dieser Session (P14-S1 ist nicht in `IMPLEMENTATION_PLAN.md`s Liste der Sessions mit Browser-Testpflicht) - bewusste Zurückstellung auf eine spätere, explizit als UI-Session geplante Gelegenheit, konsistent mit dem Muster, Backend-/CLI-Funktionalität zuerst vollständig zu bauen und die UI-Schicht separat nachzuziehen.
- **`config-service` bleibt reiner Orchestrator ohne eigenen Zustand**: der Vergleich verändert nichts (7.5: "rein lesend/diagnostisch") und speichert nichts - `compare.py` sind reine Funktionen über bereits vorliegende `ConfigDocument`-Objekte, kein neues Datenmodell, keine neue Tabelle. Passt zum bestehenden "stateless orchestrator"-Charakter von `config-service` (ADR 0035).
- **Installationsspezifische Daten (Lizenzstand, Registry-Erreichbarkeit) sind strukturell ausgeschlossen**, nicht nur per Konvention: `ConfigDocument` enthält diese Felder gar nicht (sie sind ohnehin nie Teil von 7.3s Exportschema) - 7.5s explizite Ausschlussregel ist damit automatisch erfüllt, ohne eigene Filterlogik.

## Konsequenzen

- **Kein automatisierter, Hub-vermittelter Abruf** - ein Betreiber, der zwei Installationen regelmäßig automatisiert vergleichen will (z. B. tägliche Drift-Checks Staging↔Produktion), muss dafür selbst ein kleines Skript bauen (zwei `dms config export`-Aufrufe mit je eigenem Login + `dms config compare`) statt eines eingebauten Cronjobs. Für den in 7.5 explizit genannten CI/CD-Anwendungsfall ist das ausreichend (die Pipeline besitzt ohnehin bereits Zugangsdaten für beide Umgebungen).
- **Kein Admin-UI-Zugang zur Vergleichsfunktion** in dieser Session - nur CLI und rohe API. Eine spätere UI-Session müsste eine eigene Ansicht dafür bauen (Kategorien-Übersicht, aufklappbare Detailanzeige je abweichendem Eintrag, Ignore-Regex-Eingabefeld).
- **Kein Tiefendiff verschachtelter Strukturen** - eine Änderung tief innerhalb eines Objekttyp-Layouts (`layouts[].rows`) wird als "das gesamte `layouts`-Feld weicht ab" gemeldet, nicht mit einer Zeilen-genauen Aufschlüsselung. Für die in 7.5 genannten Hauptanwendungsfälle (Drift-Erkennung, Vorab-Sicht vor einer Konfigurationsübernahme) ist "dieses Attribut weicht ab, hier sind beide vollständigen Werte" ausreichend - der eigentliche Detailvergleich bleibt der Betrachterin/dem Betrachter überlassen.
- `config-service` bekommt durch `POST /config/compare` seinen ersten Endpunkt, der zwei komplette `ConfigDocument`-Payloads gleichzeitig im Request-Body akzeptiert - bei sehr vielen Objekttypen/Workflows kann der Request entsprechend groß werden (kein eigenes Limit über die ohnehin bestehenden FastAPI-/Gateway-Grenzen hinaus gesetzt, gleiche bewusste Vereinfachung wie beim bestehenden `POST /config/import`).
