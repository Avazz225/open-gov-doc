# 0043 — Teamspace: dedicated membership table instead of RBAC extension, supplementary role assignment, no group support

**Status:** accepted
**Context:** P14-S6 (team workspace "teamspace", concept 2.5)

## Decision

A new, standalone service `teamspace-service` models the self-managed, persistent team workspace. The access control that concept 2.5 literally requires to be "independent of the rest of the RBAC model (4.1)" is implemented via a **dedicated, local membership table** (`teamspace_member`), NOT via an extension of `permission-service`'s `Role`/`RoleAssignment` model - every endpoint (except creating a new teamspace) checks directly against this table whether the calling `X-DMS-Principal` is a member. **In addition**, but not as the primary enforcement mechanism, `teamspace-service` creates or removes a resource-scoped `permission-service` role assignment (`teamspace-member`) on the teamspace root folder on every member invite/removal. Members are exclusively individual users (`principal_id` = Keycloak `sub` UUID) - groups are deliberately NOT supported, even though concept 2.5 names them as an option ("members ... or groups").

## Rationale

- **No group concept is actually enforced anywhere in this project**: `permission-service`'s `RoleAssignment.principal_type` does have the comment-documented value `"group"`, but `_collect_effective_roles` never reads `principal_type` anywhere - there is no group-membership expansion. Keycloak groups are also not forwarded by the gateway as a claim (`X-DMS-Principal`/`X-DMS-Username` are both user-scoped). The AD group mapping (4.4) that has been open since P2-S1/P2-S2 is an already-documented, persistently open point - reconstructing teamspace group membership on top of a foundation that does not exist would not be building on existing infrastructure, but an entirely new, standalone undertaking. A deliberate, documented limitation (analogous to the AD group mapping gap itself).
- **A dedicated membership table instead of an RBAC extension fulfils "independent of the RBAC model" most literally**: concept 2.5 explicitly distinguishes teamspace access from "the rest of the RBAC model (4.1)". An implementation purely through `permission-service`'s role/assignment system would have been technically possible (as shown in the anchoring step below), but that is precisely THE RBAC model that teamspace, per the concept, is meant to behave independently of. A separate, local table with its own simple check (`_require_member`/`_require_manager` in `main.py`) is the more direct implementation of the concept's requirement.
- **A supplementary `permission-service` anchoring is still worthwhile and practically free**: `search-service` already genuinely checks `document.read` at folder level today (`POST /check/batch`, empirically verified). Without any `permission-service` anchoring at all, documents inside a teamspace folder would still show up in search results for NON-members (since `folder-service`/`document-service` themselves have no access check of their own, see `docs/architecture.md` "authorization ... still not enforced in several places"). Two additional HTTP calls (get-or-create role + create/remove assignment) per invite/removal are a small extra cost for a genuine, immediately effective security gain, at least for the search path - the already-established get-or-create role pattern from `migration-service`'s `apply_role_assignment` is reused unchanged for this.
- **`GET /users/lookup` (new in `auth-service`) instead of a full user directory**: inviting requires resolving a typed-in username into the Keycloak `sub` UUID actually relevant for `X-DMS-Principal`/`RoleAssignment.principal_id`. The existing `GET /users` is deliberately gated behind `admin.user_management` (admin-UI user management, since P4-S3) - unsuitable for teamspace, since ANY person (not just domain admins) should be able to invite others. The new endpoint is therefore deliberately narrower than `GET /users`: exact name lookup (no enumerating/listing of all accounts), returns only `id`/`username` (no email/name/release status) - not a general-purpose people directory (that is the not-yet-built, installation-wide "contacts" special area from concept 2.5, phase 15), but a minimal, purpose-bound resolution function.
- **A single `can_manage_members` flag instead of separate permission levels** for member management AND deleting the entire teamspace: concept 2.5 itself does not make this distinction ("can delegate this management to further members", without differentiating between "manage members" and "dissolve teamspace"). An additional permission level would be an unrequested increase in complexity.
- **Deleting a teamspace removes only its own metadata, not the root folder with its content**: a genuine folder deletion would be its own, risky feature (retention periods, four-eyes deletion approval, 5.2) - deliberately not built alongside this for a reference implementation. A dissolved teamspace leaves behind an "orphaned" but content-wise intact folder.
- **`teamspace-service` has no document/folder storage of its own**, but creates real `folder-service` folders (`root_folder_id` as an opaque reference) - consistent with the already-established pattern of `case-service` (circulation folder, 2.3), which likewise holds only opaque `document_id` references instead of duplicating its own storage.

## Consequences

- **Two parallel access concepts for the same folder**: the `teamspace_member` table is the actually enforced source of truth for everything running through `teamspace-service` itself (appointments, contacts, member list); the `permission-service` role assignment is only effective wherever another service actually queries it (currently only `search-service`). Direct `folder-service`/`document-service` access to the teamspace folder is NOT protected by teamspace membership - the same gap already documented throughout the project ("authorization ... not enforced"), not newly introduced here, just not closed either.
- **No protection against the last management-capable member removing themselves** - a teamspace can thereby become effectively unmanageable (nobody left who can invite/remove/delete). Deliberately not handled, so as not to overload the session with a rare edge case.
- **`GET /users/lookup` slightly widens `auth-service`'s attack surface**: any authenticated user can now find out whether a given username exists (an existence oracle) - assessed as uncritical for an internal administrative application with a known user population, but a documented deviation from the previous state (user directory fully gated behind `admin.user_management`).
- **Group invitation remains completely unbuilt** - a later implementation would first need the long-open AD/Keycloak group integration (4.4), not a teamspace-specific extension on its own.
- No new `docs/adr` entry is needed for the "dedicated service instead of extending an existing one" question - the pattern (new, lean service with its own Postgres schema plus cross-service references) is already established by `favorite-service` (P7-S1d) and `case-service` (P6-S3).
