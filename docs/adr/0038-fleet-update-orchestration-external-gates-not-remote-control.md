# 0038 — Fleet update orchestration: declarative coordination with external gates instead of remote-controlling foreign security primitives

**Status:** accepted
**Context:** P13-S2b (fleet update orchestration, concept 3a extension "as an extension of the fleet/license management service already planned anyway")

## Decision

Fleet update orchestration is built as an extension of `fleet-management-service` (P13-S2), not as its own service: named installation groups (`InstallationGroup`), versioned update plans with ordered, named steps (`UpdatePlan.steps`), and waves (`Rollout` = a plan applied to a set of installations resolved via group/`include`/`exclude`, must be started explicitly). Every plan step has exactly one of two types:

- **`verify`** — automatic: `fleet-management-service` itself queries the already-existing `_fetch_status()` path (P13-S2, via the target installation's gateway) and translates the result into success/`retry_later`/`recoverable_failed`.
- **`gate`** — externally/manually confirmed (`POST .../mark-done`): stands for any action whose actual execution lies **outside** this service - setting a scope lock/maintenance mode on the target installation (4.7/4.8), performing the actual rolling update (10.5), taking a backup (10.4), final release. `fleet-management-service` **does not itself trigger these actions via HTTP on a foreign installation** - the operator who performed the action (a human, or their CI/automation) confirms it via the fleet console.

The concept's five error-outcome decisions (`retry_later`/`wait_external`/`manual_required`/`recoverable_failed`/`fatal_contract`) are the `status` of an `InstallationRun` - `wait_external` is the default waiting state of any step not yet confirmed (whether "external" means a human or an automated system is irrelevant to the state). Four-eyes (4.3) for `requires_approval` steps is implemented as a **structural** propose-then-approve flow (two separate API calls, `approve` requires `actor != proposed_by`) within `fleet-management-service` itself, not by calling into `permission-service`'s actual 4.3 mechanism on a target installation.

## Rationale

- **Isolation (3a) structurally forbids a central trust anchor for write actions like locks/maintenance mode**: `permission-service`'s `POST /scope-locks`/`POST /maintenance-mode/trigger` are today protected exclusively by the caller already holding a valid Keycloak token for the given installation (no additional RBAC capability gate on scope locks; `maintenance-mode/trigger` even requires a specific capability granted per installation, and `maintenance-mode/lift` literally requires the identity of that one installation's **currently active superuser**). `fleet-management-service` structurally **never** has a valid principal for a foreign installation (3a: "fully isolated", separate user management/separate Keycloak realm per installation) - there is no safe way to remote-control these two endpoints without either (a) introducing a hitherto nonexistent, dedicated RBAC exception in `permission-service` that would simultaneously risk breaking every already-existing, currently ungated internal caller (e.g. `migration-service`'s direct `/scope-locks` call without any header), or (b) bypassing `permission-service`'s deliberately strict superuser binding on `maintenance-mode/lift` - both are their own, significant security-relevant decisions that this session should not make in passing.
- **`license-service`/`config-service`'s P13-S2 bypass is not a transferable pattern for locks/maintenance mode**: those two endpoints already had a narrow, clearly scoped RBAC check (`admin.license`/`admin.object_config`) that could be extended with a single additional bypass path without affecting existing callers. Scope locks/maintenance mode do not have this property (see above) - the P13-S2 approach cannot be mechanically repeated here.
- **10.4 (backup) and 10.5 (rolling update) are already deliberately scripts, not services** (P10-S3/P11-S3 decisions: "operational scripts instead of a service"). So there is **no HTTP endpoint at all** that `fleet-management-service` could remote-control for the actual update/backup execution - these steps would be external/manual regardless of the scope-lock question. The decision made here, to treat `lock`/`maintenance_mode` steps **likewise** as external gates rather than remote control, makes the model uniform across all four "prepare/update/backup/release" step types, instead of maintaining two different mechanics (two real remote calls plus two external gates).
- **Honestly scoped coordination, not a remote-control claim**: concept 3a explicitly describes this layer as a "coordination layer ... that triggers 10.5 per installation in a targeted way" - "triggers" is understood here as "determines the order/timing and tracks the outcome", not as "itself holds privileged remote access to every managed installation". A genuine remote-control model would be a separate, standalone security design (e.g. a second, even more narrowly scoped action-specific key per installation and action type) - deliberately not part of this session, see "Open Points" in `docs/services/fleet-management-service.md`.
- **Four-eyes as a structural rather than cryptographic two-person flow**: `fleet-management-service` has no user management of its own (like `migration-service`'s own admin endpoints already, which are protected only via `license_gate` rather than RBAC - a precedent for "simpler protection on a deliberately narrower attack surface"). A genuine approval enforced by two distinct authenticated identities would require its own user management for the fleet layer - 3a does not require that and it is not part of this session. The enforced `actor != proposed_by` check is a real, if weaker, protection (it at least prevents the same API caller/the same typed-in identifier, no protection against one person with two aliases).

## Consequences

- No new NATS consumer/no new cross-installation event-bus connection is needed - `fleet-management-service` remains (like `federation-hub-service`) without its own event bus, since 4.3's generic approval mechanism is **not** literally reused (see above), only its underlying principle.
- The effectiveness of `gate` steps depends entirely on the honesty of the reporting operator/their automation - `fleet-management-service` does not verify that a scope lock/a backup/a rolling update actually happened before `mark-done` marks the step as complete (except for the `verify` step type, which does actually check automatically). Documented as a deliberate limitation, not a silent one.
- A later, tighter form of remote control (e.g. a dedicated, action-/installation-specific token that would let `fleet-management-service` trigger specifically ONLY `POST /scope-locks` with a fixed `resource_id="root"` and ONLY for the duration of an active rollout) remains a possible future extension, but is its own security feature to be designed in detail - not part of this session.
