# 0096 — Workflow Service: Postgres-Advisory-Lock gegen die Versions-Race-Condition bei Prozess-/DMN-Definitionen

**Status:** akzeptiert
**Kontext:** P25-S1. `repository.create_process_definition`/`create_dmn_definition` berechneten die nächste Version einer Familie unlocked (`SELECT max(version) WHERE name = ...` gefolgt von einem separaten `INSERT`) — ein bereits in [ADR 0027](0027-workflow-process-definition-versioning.md) "Konsequenzen" bewusst akzeptierter offener Punkt: zwei echt gleichzeitige Speicherversuche unter demselben `name` konnten denselben `next_version` berechnen und kollidierten dann unbehandelt an der `(name, version)`-Unique-Constraint (`IntegrityError`/`500`, statt automatisch aufgelöst zu werden). P25-S1 macht diesen offenen Punkt zu, da er inzwischen real den "Speichern"-Fluss des Process Designer (ADR 0027) betreffen kann, sobald mehrere Personen gleichzeitig an derselben Prozessfamilie arbeiten.

Dieses Projekt kennt bereits zweimal ein etabliertes Muster für genau dieses Problem: `object_type_service.repository._next_sequence_number` und `case_service.repository._next_case_sequence_number` legen per `INSERT ... ON CONFLICT DO NOTHING` eine persistente Zähler-Zeile an (falls noch nicht vorhanden) und sperren sie danach mit `SELECT ... FOR UPDATE`, bevor sie hochgezählt wird.

## Entscheidung

**Kein neues Zähler-Tabellen-Muster für `ProcessDefinition`/`DmnDefinition`.** Stattdessen ein transaktionsgebundener Postgres-Advisory-Lock (`pg_advisory_xact_lock(key1, key2)`) auf den Familien-`name`, direkt vor dem `SELECT max(version)` in beiden `create_*`-Funktionen — freigegeben automatisch bei COMMIT/ROLLBACK der jeweiligen Transaktion, kein manuelles Unlock nötig. `key1` ist je Funktion ein fester Namespace-Integer (`_PROCESS_DEFINITION_LOCK_NAMESPACE = 1`, `_DMN_DEFINITION_LOCK_NAMESPACE = 2`), `key2` ist `hashtext(name)` — getrennte Namespaces verhindern, dass eine Prozess- und eine DMN-Familie mit zufällig demselben `name`-String sich gegenseitig sperren, obwohl sie unabhängig versioniert werden.

**Bewusst NICHT das etablierte `_next_sequence_number`-Muster übernommen**, obwohl es an zwei Stellen dieses Projekts bereits existiert: `ProcessDefinition`/`DmnDefinition` haben (anders als `ObjectTypeSequence`/`CaseSequence`) keine eigene, immer schon existierende Zähler-Zeile je Familie — sie WÄRE die Zeile mit der höchsten `version`. Ein `SELECT ... FOR UPDATE` auf `ProcessDefinition WHERE name = ...` sperrt aber unter Postgres' Standard-Isolationsstufe (READ COMMITTED, kein Predicate Locking) nur tatsächlich zurückgegebene Zeilen — für eine brandneue Familie (noch keine einzige Zeile mit diesem `name`) gibt es nichts zu sperren, zwei gleichzeitige Erstanlagen derselben neuen Familie würden also weiterhin beide `next_version = 1` berechnen und kollidieren. Das etablierte Muster vollständig zu übernehmen hätte eine zusätzliche `ProcessDefinitionSequence`/`DmnDefinitionSequence`-Tabelle samt Migration gebraucht, nur um dieselbe Garantie zu erreichen, die ein Advisory-Lock ohne zusätzlichen Tabellenzustand liefert.

## Begründung

- **Advisory-Lock deckt sowohl Erst- als auch Folgeversionen ab** — unabhängig vom aktuellen Zeilenbestand, da er rein über den `name`-Hash sperrt, nicht über konkrete Zeilen.
- **Kein zusätzlicher Tabellenzustand/keine Migration nötig** — im Gegensatz zu einer neuen Zähler-Tabelle je Definitionstyp. Der Lock existiert nur für die Dauer der Transaktion, kein persistenter Zeilenbestand, um den sich Aufräum-/Migrations-Logik kümmern müsste.
- **Dieses Projekt ist durchgängig Postgres-spezifisch entwickelt** (z. B. `DISTINCT ON` in `list_process_definitions`, `INSERT ... ON CONFLICT DO NOTHING` im Kennzeichengenerator, siehe ADR 0027 "Begründung") — ein weiteres Postgres-natives Primitiv fügt sich in dieses bestehende Muster ein, statt eine DB-agnostische Abstraktion vorzutäuschen, die es im restlichen Projekt ohnehin nicht gibt.
- **Getrennte Namespaces (`key1`) statt eines einzelnen globalen Locks** — verhindert unnötige Serialisierung zwischen unabhängigen Prozess-/DMN-Familien mit rein zufällig gleichem Namen; jede Familie sperrt nur gegen sich selbst.

## Konsequenzen

- **Löst den in ADR 0027 "Konsequenzen" akzeptierten offenen Punkt vollständig auf** — `docs/services/workflow-service.md` "Offene Punkte" wird entsprechend aktualisiert (durchgestrichen, wie bei anderen in späteren Sessions geschlossenen Punkten).
- **`hashtext()` ist eine Postgres-interne, nicht offiziell für Cross-Major-Version-Stabilität dokumentierte Funktion** — für einen rein innerhalb einer einzelnen Transaktion verwendeten Lock-Schlüssel unkritisch (keine Persistenz über einen Postgres-Versionswechsel hinweg nötig, anders als z. B. bei einem gespeicherten Hash-Wert).
- **Kein Schutz gegen eine künftige Wiederverwendung derselben `AsyncSession` für mehrere nebenläufige Aufrufe** — Advisory-Locks sind an die Datenbank-Session/-Verbindung gebunden, nicht an den Python-`asyncio`-Task; das ist hier unkritisch, da `AsyncSession` in diesem Projekt ohnehin nie nebenläufig von mehreren Tasks gleichzeitig verwendet wird (siehe Test-Fixtures), aber ein künftiger Verstoß gegen diese Konvention würde sich nicht mehr wie erwartet gegenseitig sperren.
- **`create_dmn_definition`s bereits bestehende `DuplicateDecisionIdError`-Prüfung gegen ANDERE Familien bleibt unverändert ungeschützt gegen ihre eigene, analoge Race Condition** (zwei gleichzeitige Erstanlagen unterschiedlicher Familien mit kollidierender `decision_id`) — aus Scope-Gründen nicht Teil dieser Session, da es sich um ein eigenständiges Datenintegritätsproblem handelt (Cross-Familie), nicht um die hier behandelte Versionsvergabe-Race-Condition innerhalb einer Familie.
