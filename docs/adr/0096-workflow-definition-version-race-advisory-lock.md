# 0096 — Workflow Service: Postgres advisory lock against the version race condition for process/DMN definitions

**Status:** accepted
**Context:** P25-S1. `repository.create_process_definition`/`create_dmn_definition` computed the next version of a family unlocked (`SELECT max(version) WHERE name = ...` followed by a separate `INSERT`) — an open point already deliberately accepted in [ADR 0027](0027-workflow-process-definition-versioning.md) "Consequences": two genuinely concurrent save attempts under the same `name` could compute the same `next_version` and then collide unhandled against the `(name, version)` unique constraint (`IntegrityError`/`500`, instead of being resolved automatically). P25-S1 closes this open point, since it can now realistically affect the "save" flow of the Process Designer (ADR 0027) as soon as multiple people work on the same process family concurrently.

This project already has an established pattern for exactly this problem, used twice: `object_type_service.repository._next_sequence_number` and `case_service.repository._next_case_sequence_number` create a persistent counter row via `INSERT ... ON CONFLICT DO NOTHING` (if not already present) and then lock it with `SELECT ... FOR UPDATE` before incrementing it.

## Decision

**No new counter-table pattern for `ProcessDefinition`/`DmnDefinition`.** Instead, a transaction-scoped Postgres advisory lock (`pg_advisory_xact_lock(key1, key2)`) on the family `name`, taken directly before the `SELECT max(version)` in both `create_*` functions — released automatically on COMMIT/ROLLBACK of the respective transaction, no manual unlock needed. `key1` is a fixed namespace integer per function (`_PROCESS_DEFINITION_LOCK_NAMESPACE = 1`, `_DMN_DEFINITION_LOCK_NAMESPACE = 2`), `key2` is `hashtext(name)` — separate namespaces prevent a process family and a DMN family that happen to share the same `name` string from locking each other out, even though they are versioned independently.

**Deliberately did NOT adopt the established `_next_sequence_number` pattern**, even though it already exists in two places in this project: unlike `ObjectTypeSequence`/`CaseSequence`, `ProcessDefinition`/`DmnDefinition` have no dedicated, always-already-existing counter row per family — it WOULD be the row with the highest `version`. But a `SELECT ... FOR UPDATE` on `ProcessDefinition WHERE name = ...` only locks rows actually returned, under Postgres' default isolation level (READ COMMITTED, no predicate locking) — for a brand-new family (not a single row with this `name` yet), there is nothing to lock, so two concurrent first-time creations of the same new family would still both compute `next_version = 1` and collide. Fully adopting the established pattern would have required an additional `ProcessDefinitionSequence`/`DmnDefinitionSequence` table plus a migration, just to achieve the same guarantee an advisory lock provides with no additional table state.

## Rationale

- **The advisory lock covers both first and subsequent versions** — regardless of the current row population, since it locks purely on the `name` hash, not on concrete rows.
- **No additional table state/no migration needed** — unlike a new counter table per definition type. The lock exists only for the duration of the transaction, no persistent row population that cleanup/migration logic would need to manage.
- **This project is consistently developed Postgres-specific** (e.g. `DISTINCT ON` in `list_process_definitions`, `INSERT ... ON CONFLICT DO NOTHING` in the reference-number generator, see ADR 0027 "Rationale") — another Postgres-native primitive fits into this existing pattern, rather than pretending a DB-agnostic abstraction that doesn't exist elsewhere in the project anyway.
- **Separate namespaces (`key1`) instead of a single global lock** — avoids unnecessary serialization between independent process/DMN families that happen to share a name; each family only locks against itself.

## Consequences

- **Fully resolves the open point accepted in ADR 0027 "Consequences"** — `docs/services/workflow-service.md` "Open Points" is updated accordingly (struck through, as with other points closed in later sessions).
- **`hashtext()` is a Postgres-internal function not officially documented as stable across major versions** — uncritical for a lock key used purely within a single transaction (no persistence across a Postgres version change needed, unlike, e.g., a stored hash value).
- **No protection against a future reuse of the same `AsyncSession` across multiple concurrent calls** — advisory locks are bound to the database session/connection, not to the Python `asyncio` task; this is uncritical here since `AsyncSession` is never used concurrently by multiple tasks in this project anyway (see test fixtures), but a future violation of this convention would no longer lock against each other as expected.
- **`create_dmn_definition`'s existing `DuplicateDecisionIdError` check against OTHER families remains unprotected against its own, analogous race condition** (two concurrent first-time creations of different families with a colliding `decision_id`) — out of scope for this session, since it's a standalone data-integrity issue (cross-family), not the within-family version-assignment race condition addressed here.
