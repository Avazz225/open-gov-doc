# 0056 — Struktur-Vorlagen: direkt in folder-service, JSON-Baum ohne Attributwerte

**Status:** akzeptiert
**Kontext:** P15-S6 (Vorlagen, Konzept §2.5/7.3), letzte Session der Phase 15

## Entscheidung

Vier zusammenhängende Entscheidungen:

1. **Neue Fähigkeit direkt in `folder-service`, NICHT auf `config-service`s bestehendem 7.3-Export aufgebaut** — bereits bei P15-S0 korrigiert (siehe `PROGRESS.md` "Bereichsstruktur: Sonderbereiche — Phasen-Kickoff"): `config-service`s JSON-Struktur-Ex-/Import exportiert ausschließlich Schema-/Konfigurationskategorien (Objekttypen, Workflows, DMN, Geschäftskalender, Rollen, ...), keine echten Ordnerbaum-Dateninstanzen.
2. **Vorlage = verschachtelter JSON-Baum in einer neuen `folder_template`-Tabelle**, nicht ein Satz "toter" `Folder`-Zeilen ohne `parent_id` — ein Teilbaum wird beim Erfassen (`POST /folder-templates`) rekursiv über die bereits bestehende `list_children` gewalkt und als `{"name", "object_type_id", "children"}`-Baum persistiert. Eine Vorlage bleibt dadurch unabhängig vom Fortbestehen ihres ursprünglichen Quellordners gültig (kein FK auf `Folder`).
3. **Nur Struktur (Name + Objekttyp je Knoten), bewusst KEINE Attributwerte** — ein "Aktenplan-Rohbau" (Konzept-Wortlaut) ist per Definition unvollständig; Attributwerte sind Instanzdaten, keine Struktur.
4. **Anwenden überspringt bewusst die object-type-Validierung** (`main.py`s `_validate_against_object_type`, u. a. Pflichtattribut-Prüfung) — `repository.apply_template` ruft `repository.create_folder` direkt auf, nicht den validierenden `POST /folders`-Endpunkt-Code-Pfad.

## Begründung

- **Warum `folder-service` statt `config-service`**: `folder-service` besitzt den Ordnerbaum bereits vollständig (Hierarchie, `object_type_id`, `list_children`) — eine sechste `config-service`-Kategorie hätte diesen Zustand dupliziert oder einen Cross-Service-Read erfordert (in diesem Projekt durchgängig vermieden, jeder Service bleibt alleinige Autorität für sein eigenes Schema).
- **Warum ein eigener JSON-Baum statt "toter" Folder-Zeilen**: eine Vorlage muss unabhängig existieren können, auch nachdem der ursprüngliche Quellordner verschoben, umbenannt oder gelöscht wurde — ein JSON-Snapshot in einer eigenen Tabelle trennt "Vorlage" sauber von "aktiver Ordnerbaum", ohne eine zweite, parallele `Folder`-Population mit eigenem Lebenszyklus/eigenen Papierkorb-/Aufbewahrungsregeln zu benötigen (die für Vorlagen-Knoten ohnehin sinnlos wären).
- **Warum keine Attributwerte**: Konzept 2.5/7.3 nennt wörtlich "Aktenplan-**Rohbau**" — ein Rohbau wird nach dem Anwenden erst befüllt. Attributwerte mitzuerfassen würde eine Vorlage faktisch zu einer Kopiervorlage für konkrete Falldaten machen, nicht für Struktur — ein anderes, hier nicht verlangtes Feature.
- **Warum die object-type-Validierung beim Anwenden übersprungen wird**: `object_type_service.validate()` prüft u. a. Pflichtattribute — ein frisch aus einer Struktur-Vorlage angelegter Ordner hat naturgemäß `attributes={}`. Würde die Validierung greifen, würde das Anwenden einer Vorlage mit einem pflichtattributierten Objekttyp fehlschlagen (oder mitten im Teilbaum abbrechen, ein inkonsistenter Halbzustand). Da object-type-service keinen Modus "nur Struktur-, keine Attributprüfung" anbietet und ein solcher Modus für diese eine Session unverhältnismäßig wäre, wird die Validierung beim Anwenden komplett übersprungen — Pflichtattribute werden ganz regulär beim späteren Ausfüllen über `PATCH /folders/{id}` geprüft (dort läuft `_validate_against_object_type` unverändert weiter, da `update_folder`'s Attribut-Pfad hiervon nicht betroffen ist). Damit werden auch etwaige Eltern-Kind-Objekttyp-Nestingregeln (2.2b) beim Anwenden nicht geprüft — bewusst dokumentierte Grenze, siehe "Konsequenzen".
- **Warum rohe Ordner-ID-Texteingaben statt eines Baum-Pickers im Frontend**: identisches, bereits etabliertes Muster wie `QuarantinePane`s Zielordner-Feld (P15-S2) und `PoststellePane`s Zielordner-Override (P15-S3) — ein waschechter Ordnerbaum-Picker wäre ein eigenständiges, größeres UI-Feature, für das es keinen bestehenden Baustein gibt und das für eine Referenzimplementierung dieser Session unverhältnismäßig ist.
- **Warum `created_by` weiterhin client-seitig im Body statt aus `X-DMS-Principal`**: `folder-service` nutzt dieses Muster bereits durchgängig für ALLE bestehenden Schreiboperationen (`FolderCreate.created_by`, `TrashRequest.deleted_by`) — eine neue, abweichende Konvention nur für die Vorlagen-Endpunkte hätte die Inkonsistenz innerhalb desselben Service vergrößert statt verkleinert. Die allgemeine, projektweite "kein client-gefälschter Urheber"-Härtung (siehe z. B. mail-connector, P15-S3) ist eine für `folder-service` insgesamt noch offene, nicht in dieser Session behobene Alt-Lücke.

## Konsequenzen

- **`GET /folder-templates`/`.../{id}`/`POST .../apply`/`DELETE .../{id}` sind ungegated** — identisches Muster wie `POST /folders` selbst (kein Rollen-Check in `folder-service` für reguläre Ordneroperationen). Keine Konzeptvorgabe verlangt hier eine Einschränkung, anders als bei Aussonderung (P15-S5) oder Quarantäne (P15-S2).
- **Eltern-Kind-Objekttyp-Nestingregeln (2.2b) werden beim Anwenden nicht geprüft** — eine Vorlage kann theoretisch einen Objekttyp unter einem strukturell unpassenden Elternobjekttyp anlegen. Bewusst akzeptierte Grenze dieser Session (siehe "Begründung"), nicht rückwirkend über eine neue Teil-Validierung in object-type-service geschlossen.
- **`object_type_id` ist eine opake, ungeprüfte Referenz** wie überall sonst in diesem Projekt — wird der Objekttyp zwischen Erfassen und Anwenden gelöscht, entsteht ein Ordner mit einer nicht mehr auflösbaren `object_type_id`, keine Sonderbehandlung dafür.
- **Anwenden ist eine reine Kopie, keine lebendige Verknüpfung** — nach dem Anwenden gibt es keine Rückreferenz von den erzeugten Ordnern zur Vorlage; eine spätere Änderung der Vorlage wirkt sich nicht auf bereits angewendete Strukturen aus (erwartetes Verhalten für eine "Vorlage", nicht für eine "Verknüpfung").
- **`folder.resource.created` wird für JEDEN erzeugten Ordner einzeln publiziert** (main.py, nach dem Commit) — identisches Event/Payload wie bei einer einzelnen `POST /folders`, damit `permission-service`s `ResourceNode`-Baum synchron bleibt. Live verifiziert (siehe PROGRESS.md).
