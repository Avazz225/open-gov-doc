# 0056 — Structure templates: directly in folder-service, JSON tree without attribute values

**Status:** accepted
**Context:** P15-S6 (structure templates, concept §2.5/7.3), last session of Phase 15

## Decision

Four related decisions:

1. **New capability directly in `folder-service`, NOT built on `config-service`'s existing 7.3 export** — already corrected at P15-S0 (see `PROGRESS.md` "Area structure: special areas — phase kickoff"): `config-service`'s JSON structure export/import exports exclusively schema/configuration categories (object types, workflows, DMN, business calendars, roles, ...), no real folder-tree data instances.
2. **Template = nested JSON tree in a new `folder_template` table**, not a set of "dead" `Folder` rows without `parent_id` — a subtree is walked recursively via the already-existing `list_children` when captured (`POST /folder-templates`) and persisted as a `{"name", "object_type_id", "children"}` tree. A template thereby remains valid independently of whether its original source folder continues to exist (no FK on `Folder`).
3. **Structure only (name + object type per node), deliberately NO attribute values** — an "outline file plan" (concept wording) is by definition incomplete; attribute values are instance data, not structure.
4. **Applying deliberately skips object-type validation** (`main.py`'s `_validate_against_object_type`, including required-attribute checks) — `repository.apply_template` calls `repository.create_folder` directly, not the validating `POST /folders` endpoint code path.

## Rationale

- **Why `folder-service` instead of `config-service`**: `folder-service` already owns the folder tree completely (hierarchy, `object_type_id`, `list_children`) — a sixth `config-service` category would have duplicated this state or required a cross-service read (avoided consistently throughout this project, every service remains sole authority for its own schema).
- **Why a dedicated JSON tree instead of "dead" Folder rows**: a template must be able to exist independently, even after the original source folder has been moved, renamed, or deleted — a JSON snapshot in its own table cleanly separates "template" from "active folder tree", without needing a second, parallel `Folder` population with its own lifecycle/trash/retention rules (which would be meaningless for template nodes anyway).
- **Why no attribute values**: concept 2.5/7.3 literally says "**outline** file plan" — an outline is only filled in after being applied. Capturing attribute values as well would effectively turn a template into a copy template for concrete case data, not for structure — a different feature, not requested here.
- **Why object-type validation is skipped when applying**: `object_type_service.validate()` checks, among other things, required attributes — a folder freshly created from a structure template naturally has `attributes={}`. If validation applied, applying a template with a required-attribute object type would fail (or abort mid-subtree, an inconsistent half-state). Since object-type-service offers no "structure-only, no attribute check" mode, and such a mode would be disproportionate for this one session, validation is skipped entirely when applying — required attributes are checked entirely normally later, when filling them in via `PATCH /folders/{id}` (where `_validate_against_object_type` continues to run unchanged, since `update_folder`'s attribute path is unaffected by this). This also means parent-child object-type nesting rules (2.2b) are not checked when applying — a deliberately documented boundary, see "Consequences".
- **Why raw folder-ID text input instead of a tree picker in the frontend**: identical, already-established pattern as `QuarantinePane`'s target-folder field (P15-2) and `PoststellePane`'s target-folder override (P15-S3) — a full-fledged folder-tree picker would be its own, larger UI feature, for which no existing building block exists and which is disproportionate for this session's reference implementation.
- **Why `created_by` remains client-side in the body instead of coming from `X-DMS-Principal`**: `folder-service` already consistently uses this pattern for ALL existing write operations (`FolderCreate.created_by`, `TrashRequest.deleted_by`) — a new, deviating convention only for the template endpoints would have increased the inconsistency within the same service rather than reducing it. The general, project-wide "no client-forged authorship" hardening (see e.g. mail-connector, P15-S3) is a still-open legacy gap for `folder-service` overall, not fixed in this session.

## Consequences

- **`GET /folder-templates`/`.../{id}`/`POST .../apply`/`DELETE .../{id}` are ungated** — identical pattern to `POST /folders` itself (no role check in `folder-service` for regular folder operations). No concept requirement calls for a restriction here, unlike records disposal (P15-S5) or quarantine (P15-S2).
- **Parent-child object-type nesting rules (2.2b) are not checked when applying** — a template could in theory create an object type under a structurally unsuitable parent object type. Deliberately accepted boundary of this session (see "Rationale"), not retroactively closed via a new partial validation in object-type-service.
- **`object_type_id` is an opaque, unvalidated reference** as everywhere else in this project — if the object type is deleted between capture and applying, a folder is created with a no-longer-resolvable `object_type_id`, no special handling for this.
- **Applying is a pure copy, not a live link** — after applying, there is no back-reference from the created folders to the template; a later change to the template does not affect already-applied structures (expected behavior for a "template", not a "link").
- **`folder.resource.created` is published individually for EVERY folder created** (main.py, after the commit) — identical event/payload as for a single `POST /folders`, so that `permission-service`'s `ResourceNode` tree stays in sync. Live verified (see PROGRESS.md).
