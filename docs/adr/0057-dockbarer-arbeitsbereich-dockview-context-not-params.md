# 0057 — Dockable workspace: `dockview-react`, React context instead of panel params for frequently-changing data

**Status:** accepted
**Context:** P16-S1 (dockable workspace scaffolding, concept §8), library choice already made at P16-S0

## Decision

Four related decisions:

1. **`dockview-react` as the docking library** (chosen at P16-S0, implemented here) — MIT-licensed, covers the full required feature set, zero runtime dependencies, React 19 bindings.
2. **New `DockableDocumentArea` component** fully replaces the previous, fixed three-column `Splitter` layout for the document view — explorer, document tabs+preview, and metadata become dockview panels; the earlier hand-built tab strip in `ExplorerPane` is removed (dockview's own tab strip per panel group takes over).
3. **Panel content reads frequently-changing data via a React context, not via dockview's `params`** — `params` is used only for values fixed at panel-creation time (a preview panel's `documentId`); everything else (folder contents, open documents, active document, handlers) flows through a shared `WorkspaceContext` provided by `DockableDocumentArea`.
4. **`DockableDocumentArea` always stays mounted**, only hidden via CSS when an IconRail special area is active — not conditionally rendered like the other special-area panes.

## Rationale

- **Why context instead of `params`**: dockview's `params` mechanism is intended for values that rarely change over a panel's lifetime (here: which document a preview panel shows) — every change would otherwise need to be explicitly propagated via `panel.api.updateParameters()`. Folder contents/open documents/active document, on the other hand, change on practically every user interaction; a shared context that each panel component reads via a hook instead stays automatically up to date on every render, without needing a second, parallel synchronization layer.
- **Why `DockableDocumentArea` always stays mounted**: conditionally mounting/unmounting it on switching to an IconRail special area (as with the other panes) would discard both the user-configured dockview layout and all open document panels, requiring them to be rebuilt on switching back — a noticeable break of concept 8's "layout is a pure, persistent display preference" requirement. Pure CSS hiding preserves both without loss.
- **Why "which documents are open" (`openDocuments`) stays in `DocumentWorkspace`, not in `DockableDocumentArea` itself**: for the same reason as above — since `DockableDocumentArea` itself stays permanently mounted, moving it there would have been harmless, but the separation makes explicit that "which documents are open" is business state (also set from search/favorites/teamspaces), while "how they are currently arranged" is pure UI state of `DockableDocumentArea`.
- **Why a single, shared "open document" entry point** (`DocumentWorkspace.openDocumentTab`, called equally from explorer/search/favorites/teamspaces via a `useImperativeHandle` ref on `DockableDocumentArea`): now always switches to the document view. Previously, a document opened from search remained unnoticed in the background (the preview was only visible within the document view) — a UX break that already existed before P16-S1, incidentally fixed by the switch to a single entry point.
- **Why the dockview tab title shows the raw document title, not the reference-number-formatted display** (`formatDocumentTitle`, `@/lib/kennzeichen`): this formatting needs `documentTypeById`/`kennzeichenShowByDefault`, which so far are loaded exclusively within `ExplorerPane`. Lifting them additionally into `DockableDocumentArea` or loading them there a second time would be disproportionate for a scaffolding session — `PreviewPane`'s own heading has always shown the raw title, the same, already-accepted simplification now also applies to the tab.

## Consequences

- **"Multiple documents simultaneously visible and arrangeable" (concept 8) is achieved via dockview's own drag & drop/splitting**, not via custom code when opening a document — a newly opened document initially lands as another tab in the same preview group (browser-tab-like, only the active tab of a group renders its content); only actually dragging one out into its own group (by the user, via drag) shows two documents truly simultaneously. This is dockview's intended interaction model (identical to VS Code) and needs no additional code.
- **Open point, not conclusively verifiable live in this session**: during testing, a jsdom-specific effect was found — when `DockableDocumentArea.resetLayout()` is called while a document is already open, dockview's own built-in model (checked via `api.panels`/`api.toJSON()`) correctly reports exactly the expected panels (`explorer`, `doc:<id>`, `metadata`), but the associated React portal content of the reused `doc:<id>` panel does not reliably re-render within jsdom (the tab itself AND the model are correct, only the panel CONTENT stays empty in the test environment). No indication of a real model bug — presumably an interaction between dockview's React portal rendering and jsdom's lack of a real layout/animation-frame cycle for a panel ID reused WITHIN the same synchronous tick. The Vitest suite therefore additionally checks the persisted dockview layout (`localStorage`) for exactly this case instead of relying solely on the rendered DOM content. **No browser available in this session environment** (neither `chromium-cli` nor `playwright` installed) — actual behavior in a real browser remains unverified and should be confirmed by a human before production use (identical limitation of this development environment, already documented at P15-S2/S3/S4).
- **`dockview-react` brings its own CSS** (`dockview-react/dist/styles/dockview.css`), whose `--dv-*` variables are deliberately NOT set via one of the bundled preset themes (abyss/gh/mocha/...), but mapped directly onto the already-existing `--dms-*` tokens (ADR 0009) — a single mapping in `globals.css` covers all four color schemes (light/dark/high-contrast/automatic), since the dockview variables are only resolved against the app's own ones at use time.
- **Bundle size**: the start page grew from ~19.6 kB to ~106 kB initial load size (dockview + splitting/grid logic) — an expected, acceptable price for a real docking library compared to the previous ~250-line hand-built version (`Splitter.tsx`, kept as an unused component, no other consumers in the project).
- **`Splitter.tsx` is no longer used, but deliberately not deleted** (no compelling reason to remove a working component just because its only caller — `DocumentWorkspace` — no longer needs it) — should a future need for a simple two-way split outside the dockable area arise, it remains available. No dedicated component test exists (was also not the case before), so no orphaned tests to remove.
