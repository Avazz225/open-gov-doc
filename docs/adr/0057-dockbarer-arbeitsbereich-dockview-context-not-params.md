# 0057 — Dockbarer Arbeitsbereich: `dockview-react`, React-Context statt Panel-Params für wechselnde Daten

**Status:** akzeptiert
**Kontext:** P16-S1 (Dockbares Arbeitsbereich-Grundgerüst, Konzept §8), Bibliothekswahl bereits bei P16-S0 getroffen

## Entscheidung

Vier zusammenhängende Entscheidungen:

1. **`dockview-react` als Docking-Bibliothek** (Auswahl bei P16-S0, hier umgesetzt) — MIT-lizenziert für den vollständigen benötigten Funktionsumfang, null Laufzeit-Abhängigkeiten, React-19-Bindings.
2. **Neue Komponente `DockableDocumentArea`** ersetzt das bisherige, feste `Splitter`-Dreispaltenlayout für die Dokumentenansicht vollständig — Explorer, Dokumenttabs+Vorschau und Metadaten werden zu dockview-Panels; die frühere handgebaute Tableiste in `ExplorerPane` entfällt (dockviews eigener Tab-Strip je Panelgruppe übernimmt das).
3. **Panel-Inhalte lesen häufig wechselnde Daten über einen React-Context, nicht über dockviews `params`** — `params` wird nur für zur Panel-Erzeugungszeit feste Werte verwendet (die `documentId` eines Vorschau-Panels); alles andere (Ordnerinhalt, offene Dokumente, aktives Dokument, Handler) fließt über einen gemeinsamen `WorkspaceContext`, den `DockableDocumentArea` bereitstellt.
4. **`DockableDocumentArea` bleibt immer gemountet**, nur per CSS ausgeblendet, wenn ein IconRail-Sonderbereich aktiv ist — nicht bedingt gerendert wie die übrigen Sonderbereich-Panes.

## Begründung

- **Warum Context statt `params`**: dockviews `params`-Mechanismus ist für Werte gedacht, die sich über die Lebensdauer eines Panels kaum ändern (hier: welches Dokument ein Vorschau-Panel zeigt) - jede Änderung müsste sonst explizit über `panel.api.updateParameters()` nachgezogen werden. Ordnerinhalt/offene Dokumente/aktives Dokument ändern sich dagegen bei praktisch jeder Nutzerinteraktion; ein gemeinsamer Context, den jede Panel-Komponente per Hook liest, bleibt dagegen automatisch mit jedem Render aktuell, ohne eine zweite, parallele Synchronisationsschicht zu benötigen.
- **Warum `DockableDocumentArea` immer gemountet bleibt**: ein bedingtes Mounten/Unmounten beim Wechsel zu einem IconRail-Sonderbereich (wie bei den übrigen Panes) würde sowohl die vom Nutzer eingestellte dockview-Anordnung als auch alle offenen Dokument-Panels verwerfen und beim Zurückwechseln neu aufbauen müssen - ein spürbarer Bruch der "Anordnung ist eine reine, dauerhafte Anzeigepräferenz"-Vorgabe aus Konzept 8. Reines CSS-Ausblenden erhält beides verlustfrei.
- **Warum "welche Dokumente offen sind" (`openDocuments`) in `DocumentWorkspace` bleibt, nicht in `DockableDocumentArea` selbst**: aus demselben Grund wie oben - da `DockableDocumentArea` selbst dauerhaft gemountet bleibt, wäre eine Verlagerung dorthin unschädlich gewesen, aber die Trennung macht explizit, dass "welche Dokumente sind offen" fachlicher Zustand ist (auch von Suche/Favoriten/Teamspaces aus gesetzt), während "wie sind sie gerade angeordnet" reiner UI-Zustand von `DockableDocumentArea` ist.
- **Warum ein einziger, gemeinsamer "Dokument öffnen"-Einstiegspunkt** (`DocumentWorkspace.openDocumentTab`, aufgerufen von Explorer/Suche/Favoriten/Teamspaces gleichermaßen über einen `useImperativeHandle`-Ref auf `DockableDocumentArea`): schaltet jetzt immer auf die Dokumentenansicht um. Vorher blieb ein aus der Suche geöffnetes Dokument unbemerkt im Hintergrund offen (die Vorschau war nur innerhalb der Dokumentenansicht sichtbar) - ein bereits vor P16-S1 bestehender UX-Bruch, der durch die Umstellung auf einen einzigen Einstiegspunkt nebenbei mitbehoben wurde.
- **Warum der dockview-Tab-Titel den rohen Dokumenttitel zeigt, nicht die Kennzeichen-formatierte Anzeige** (`formatDocumentTitle`, `@/lib/kennzeichen`): diese Formatierung braucht `documentTypeById`/`kennzeichenShowByDefault`, die bislang ausschließlich innerhalb von `ExplorerPane` geladen werden. Sie zusätzlich nach `DockableDocumentArea` zu heben oder dort ein zweites Mal zu laden, wäre für ein Grundgerüst unverhältnismäßig - `PreviewPane`s eigene Überschrift zeigte den rohen Titel schon immer, dieselbe, bereits akzeptierte Vereinfachung gilt jetzt auch für den Tab.

## Konsequenzen

- **"Mehrere Dokumente gleichzeitig sicht- und anordenbar" (Konzept 8) wird durch dockviews eigenes Drag&Drop/Splitten erreicht**, nicht durch eigenen Code beim Öffnen eines Dokuments - ein neu geöffnetes Dokument landet zunächst als weiterer Tab in derselben Vorschau-Gruppe (Browser-Tab-artig, nur der aktive Tab einer Gruppe rendert seinen Inhalt); erst ein tatsächliches Herausziehen in eine eigene Gruppe (durch die Nutzerin/den Nutzer, per Ziehen) zeigt zwei Dokumente wirklich gleichzeitig. Das ist die von dockview vorgesehene Bedienweise (identisch zu VS Code) und braucht keinen zusätzlichen Code.
- **Offener Punkt, in dieser Session live nicht abschließend verifizierbar**: beim Testen wurde ein jsdom-spezifischer Effekt gefunden - wird `DockableDocumentArea.resetLayout()` aufgerufen, während bereits ein Dokument offen ist, meldet dockviews eigenes eingebautes Modell (per `api.panels`/`api.toJSON()` geprüft) korrekt genau die erwarteten Panels (`explorer`, `doc:<id>`, `metadata`), der zugehörige React-Portal-Inhalt des wiederverwendeten `doc:<id>`-Panels rendert innerhalb von jsdom aber nicht zuverlässig neu (der Tab selbst UND das Modell sind korrekt, nur der Panel-INHALT bleibt in der Testumgebung leer). Kein Hinweis auf einen echten Modellfehler - vermutlich eine Interaktion aus dockviews React-Portal-Rendering mit jsdoms fehlendem echten Layout-/Animationsframe-Zyklus bei einer INNERHALB DESSELBEN synchronen Ticks wiederverwendeten Panel-ID. Die Vitest-Suite prüft deshalb für genau diesen Fall zusätzlich das persistierte dockview-Layout (`localStorage`) statt ausschließlich den gerenderten DOM-Inhalt. **In dieser Session-Umgebung kein Browser verfügbar** (weder `chromium-cli` noch `playwright` installiert) - das tatsächliche Verhalten in einem echten Browser bleibt unverifiziert, sollte vor Produktivnutzung von einem Menschen nachvollzogen werden (identische, bereits bei P15-S2/S3/S4 dokumentierte Einschränkung dieser Entwicklungsumgebung).
- **`dockview-react` bringt eigenes CSS mit** (`dockview-react/dist/styles/dockview.css`), dessen `--dv-*`-Variablen bewusst NICHT über eines der mitgelieferten Preset-Themes (abyss/gh/mocha/...) gesetzt werden, sondern direkt auf die bereits bestehenden `--dms-*`-Tokens (ADR 0009) abgebildet sind - eine einzige Zuordnung in `globals.css` reicht für alle vier Farbschemata (hell/dunkel/hoher Kontrast/automatisch), da die dockview-Variablen erst zur Verwendungszeit über die App-eigenen aufgelöst werden.
- **Bundle-Größe**: die Startseite wuchs von ~19,6 kB auf ~106 kB Erstladegröße (dockview + Splitting-/Grid-Logik) - erwarteter, vertretbarer Preis für eine echte Docking-Bibliothek gegenüber dem vorherigen ~250-Zeilen-Handbau (`Splitter.tsx`, bleibt als ungenutzte Komponente erhalten, keine weiteren Verwender im Projekt).
- **`Splitter.tsx` wird nicht mehr verwendet**, aber bewusst nicht gelöscht (kein zwingender Grund, eine funktionierende Komponente zu entfernen, nur weil ihr einziger Aufrufer - `DocumentWorkspace` - sie nicht mehr braucht) - falls ein künftiger Bedarf für eine einfache Zwei-Wege-Teilung außerhalb des dockbaren Bereichs entsteht, ist sie weiterhin vorhanden. Kein eigener Komponententest vorhanden (war es auch vorher nicht), daher keine verwaisten Tests zu entfernen.
