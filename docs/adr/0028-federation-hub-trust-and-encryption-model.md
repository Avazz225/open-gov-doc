# 0028 — Federation Hub: Vertrauens- und Verschlüsselungsmodell (Grundgerüst)

**Status:** akzeptiert
**Kontext:** P6-S9 (Federation Hub Grundgerüst, Konzept 7.4), vorgezogen von P13-S3/S4 nach der P6-S8-Planfreigabe (siehe `PROGRESS.md` "Process Designer / Prozess-Versionierung"). Konzept 7.4 verlangt, dass der Federation Hub übertragene Dokumente/Daten Ende-zu-Ende zwischen den beteiligten Installationen verschlüsselt sieht — "der Hub selbst kann die Inhalte nicht einsehen, nur vermitteln". Die dafür eigentlich vorgesehene Grundlage (eine echte, systemweite Installations-Identität/PKI) entsteht aber laut Roadmap erst in P13-S1 (Mehrfachinstallations-Grundlagen), lange nach dieser Session. Bei der Plan-Rückfrage entschied der Nutzer, echte Ende-zu-Ende-Verschlüsselung trotzdem **jetzt** umzusetzen, mit bewusst einfachem, aber echtem Schlüsselmanagement statt eines reinen Klartext- oder Nur-Transport-Ansatzes.

## Entscheidung

**Jede Installation erzeugt bei erster Konfiguration ein eigenes RSA-2048-Schlüsselpaar** (`cryptography`, gleiche Bibliothek/Serialisierung wie `signature-service`s interne CA, ADR 0025) und meldet sich damit beim Hub an (`public_key_pem` im Adressbuch). Ein Handover-Payload wird **hybrid verschlüsselt** (frischer AES-256-GCM-Schlüssel für die Nutzdaten, RSA-OAEP verschlüsselt diesen Schlüssel mit dem öffentlichen Schlüssel der Zielinstallation) — der Hub leitet das Ergebnis nur als opaken, base64-kodierten String weiter und persistiert ihn nicht (`federation_hub_service.models.Handover` hat kein Payload-Feld).

**Vertrauen zwischen Hub und Installationen läuft über zwei unterschiedliche, jeweils passende Mechanismen statt eines einzigen geteilten Geheimnisses:**
- *Installation → Hub*: ein bei der Registrierung einmalig ausgegebener, zufälliger API-Key (`secrets.token_urlsafe(32)`), den der Hub nur **gehasht** speichert (SHA-256 — bewusst kein langsames Passwort-Hashing wie bcrypt/argon2, da der Key selbst bereits hochentropisch zufällig ist, kein von Menschen gewähltes, erratbares Geheimnis).
- *Hub → Installation*: der Hub erzeugt beim eigenen ersten Start **ebenfalls** ein RSA-2048-Schlüsselpaar (`hub_identity`, gleiches Singleton-Muster) und **signiert** jede an eine Installation zugestellte Nachricht damit (RSA-PSS/SHA-256, Header `X-Federation-Hub-Signature`). Jede Installation ruft den öffentlichen Hub-Schlüssel einmalig beim eigenen Registrieren ab (`GET /public-key`, Trust-on-First-Use) und verifiziert damit jede spätere Zustellung.

Diese Aufteilung vermeidet, dass der Hub **irgendein** Geheimnis im Klartext speichern müsste, das er später erneut verwenden können muss (ein ursprünglich erwogener Entwurf — der Hub liefert eingehende Zustellungen mit dem eigenen, ihm bekannten API-Key der Zielinstallation aus — hätte genau das erfordert; wurde während der Implementierung zugunsten des Signatur-Modells verworfen).

**Versionskompatibilität**: einfache `(major, minor)`-Zahlenpaare statt einer SemVer-Bibliothek — der Hub prüft bei `POST /handovers` beidseitig, ob `version`/`min_compatible_peer_version` der beiden beteiligten Installationen zueinander passen, sonst `409`.

## Begründung

- **Echte E2E-Verschlüsselung ohne P13-S1 abzuwarten**: das Schlüsselpaar-pro-Installation-Modell braucht keine systemweite Installations-ID-Infrastruktur — jede Installation verwaltet ihre eigene Identität selbst, das Adressbuch des Hub ist bereits der einzige Ort, an dem sich Installationen überhaupt kennenlernen. Erfüllt "Hub kann Inhalte nicht einsehen" wörtlich, ab dieser Session.
- **Signatur statt geteiltem API-Key für Hub→Installation-Zustellungen**: Standardmuster für Webhook-artige Zustellungen (vergleichbar mit signierten Webhooks anderer Systeme), verlangt vom Hub nur, dass er seinen **eigenen** privaten Schlüssel kennt — nie den einer fremden Installation. Sicherheitshygienisch sauberer als eine "Klartext-Key-Weitergabe", die bei einem DB-Kompromiss des Hub sofort alle Installationen kompromittiert hätte.
- **Schnelles statt langsames Hashing für API-Keys**: bcrypt/argon2 sind für von Menschen gewählte, niedrigentropische Passwörter gedacht (Schutz gegen Offline-Brute-Force). Ein 32-Byte-`secrets.token_urlsafe`-Wert hat bereits genug Entropie, dass ein schneller Hash (SHA-256) für den hier relevanten Bedrohungsfall (reiner DB-Auszugsdiebstahl) ausreicht — kein Grund, eine zusätzliche Abhängigkeit (`passlib`/`bcrypt`) nur für dieses eine Feld einzuführen.
- **Kein neues BPMN-Element für föderierte Schritte**: wie beim Signature Task (P6-S7, ADR-lose Konvention) bleibt ein föderierter Schritt technisch ein `bpmn:ManualTask` mit `camunda:properties` — reproduziert das bewährte Muster statt ein neues UI-/Backend-Konzept zu erfinden.

## Konsequenzen

- **Kein mTLS, keine echte Installations-Identität, keine Schlüsselrotation/-Revocation** — bewusste Grenzen eines Grundgerüsts. Ein Betreiber, der einen fremden Hub nutzt, muss dessen Betreiber vertrauen, keine Zustellungen an eine falsche/kompromittierte `callback_base_url` umzuleiten (der Hub selbst könnte theoretisch eine falsche `to_installation`-Zuordnung vornehmen — das TLS-/mTLS-Sicherheitsniveau zwischen Hub und Installationen ist Deployment-Sache, nicht Teil dieser Anwendungsschicht-Absicherung). Wird verfeinert, sobald die Installations-ID-Grundlagen aus P13-S1 existieren (P13-S4).
- **Selbst-Loopback als Test-Methodik dieser Session**: die einzige verfügbare Dev-Umgebung hat nur eine laufende `workflow-service`-Installation. Der Live-Smoke-Test lässt diese Installation einen föderierten Schritt an **sich selbst** übergeben (eigene `installation_id` als Ziel) — der komplette Rundlauf (Verschlüsselung, Hub-Vermittlung, Signaturprüfung, Empfang, neue lokale Instanz, Rückmeldung) läuft dadurch real durch, ohne eine zweite Installation simulieren zu müssen. Ein echter Zwei-Installationen-Test steht aus, bis eine zweite Umgebung verfügbar ist.
- **Keine Durchsetzung von `supported_process_types`/`supported_document_types`** — der Hub speichert sie, prüft aber nicht, ob ein Handover tatsächlich zu einem deklarierten Typ passt (siehe `docs/services/federation-hub-service.md` "Offene Punkte").
- **Synchrone Zustellung ohne Retry-Warteschlange** — ein vorübergehend nicht erreichbares Ziel führt sofort zu `delivery_failed`, keine spätere automatische Nachzustellung.

## Nachtrag: zwei reale Bugs, erst beim Selbst-Loopback-Smoke-Test gefunden

Die synchrone Zustellung (siehe oben) reicht im Selbst-Loopback-Fall bis zurück in dieselbe Installation/denselben Prozess — das deckte zwei Probleme auf, die mit reiner Unit-Testabdeckung (gemockte/gestubbte Gegenstellen) unsichtbar geblieben wären:

1. **Postgres-Transaktionsisolation**: `POST /handovers` committete die neu angelegte Handover-Zeile ursprünglich erst *nach* dem Zustellversuch. Im Selbst-Loopback ruft die Zielinstallation aber synchron zurück in den Hub (`POST .../result`), bevor die ursprüngliche Transaktion committet ist — die neue, separate Anfrage sah die Zeile noch nicht (`404 handover_id unbekannt`). Fix: `session.commit()` direkt nach dem Anlegen der Zeile, **vor** dem eigentlichen Zustellversuch.
2. **Zirkuläre Abhängigkeit bei serverseitig generierter `handover_id`**: der Hub generierte `handover_id` ursprünglich selbst und gab sie erst in der `POST /handovers`-Antwort zurück. Im Selbst-Loopback braucht aber bereits die *eigene, lokale* Buchführung der Absenderinstallation (ihre `FederationTask`-Zeile, verhindert doppeltes Dispatchen) diese ID, bevor der verschachtelte Rückruf sie dort nachschlagen kann — zum Zeitpunkt des Rückrufs war die Antwort mit der ID aber noch gar nicht zurückgeliefert worden. Fix: **Protokolländerung** — die Absenderinstallation erzeugt `handover_id` selbst (`uuid.uuid4()`) und schickt sie im `POST /handovers`-Body mit; sie committet ihre eigene `FederationTask`-Zeile lokal, **bevor** sie den Hub überhaupt aufruft. Nebeneffekt: ein sauberes, idempotenzschlüsselartiges Protokoll (der Aufrufer legt seine eigene Referenz fest, statt auf eine serverseitig generierte ID warten zu müssen) — kein reiner Testworkaround, sondern eine Verbesserung, die auch echten Zwei-Installationen-Szenarien zugutekommt.

Damit einhergehend musste `models.FederationTask`s Eindeutigkeit von `handover_id` allein auf `(handover_id, direction)` gelockert werden — im Selbst-Loopback landen sonst zwei Zeilen (`outbound` und `inbound`) mit demselben `handover_id` in derselben Datenbank, was mit der alten Constraint sofort einen `IntegrityError` ausgelöst hätte. `repository.get_federation_task_by_handover` bekam dafür einen `direction`-Parameter (Default `"outbound"`, passend zum einzigen tatsächlichen Aufrufer `POST /federation/inbound-result`).

Für ein echtes Zwei-Installationen-Szenario (keine Selbst-Referenz) wären beide Probleme nie aufgetreten, da dort zwei komplett getrennte Prozesse/Datenbanken beteiligt sind — sie sind eine direkte, aber lehrreiche Konsequenz der in dieser Session gewählten Selbst-Loopback-Test-Methodik.

## Nachtrag (P13-S3): Versionsformat-Validierung bei der Registrierung, Versionskompatibilität als 7.3-Kategorie

Zwei Ergänzungen im Rahmen der P13-S3-Prüfung ("Anpassung an die Mehrfachinstallations-/Fleet-Grundlagen aus P13-S1/S2/S2b, falls sich Lücken zeigen"):

- **Realer Bug gefunden und behoben**: `POST /installations` akzeptierte bislang jeden beliebigen `version`/`min_compatible_peer_version`-String anstandslos. `repository.is_version_compatible()`s naive `(major, minor)`-Zahlenparsung (`_parse_version`) warf bei einem nicht-numerischen Wert einen unbehandelten `ValueError` - nicht beim fehlerhaften `POST /installations` selbst, sondern **erst bei einer späteren, völlig anderen** `POST /handovers`-Vermittlung, sobald die betroffene Installation an EINEM Handover beteiligt war (500 statt einer aussagekräftigen Fehlermeldung an der Stelle, an der das Problem tatsächlich entsteht). Fix: die Parsing-Logik wandert in eine neue, gemeinsame `version_utils.py` (`parse_version`, wirft jetzt `InvalidVersionFormatError`) und wird über einen Pydantic-`field_validator` auf `InstallationRegister` bereits bei der Registrierung erzwungen (`422` mit klarer Meldung statt eines späteren 500 bei einer fremden Vermittlung). Gefunden durch eigene Testdaten mit einem hex-artigen Versionswert - kein Fund an echten Installationen.
- **Versionskompatibilitätsspanne ist jetzt tatsächlich Teil des 7.3-Konfigurationsschemas**: 7.4 verlangt wörtlich "Diese Kompatibilitätsspanne ist Teil des ohnehin schon versionierten Konfigurationsschemas (7.3)" - vor P13-S3 lebte sie ausschließlich in `workflow-service`s `Settings` (`installation_version`/`installation_min_compatible_peer_version`, nur per Container-Neustart änderbar, nie über den regulären Konfigurationsimport erreichbar). Neu: `workflow-service` bekam eine `FederationConfig`-DB-Zeile plus `GET`/`PUT /federation/config` (gegated hinter derselben `admin.object_config`-Capability wie der BPMN-Upload; ein `PUT` löst sofort eine Re-Registrierung beim Hub aus, kein Neustart mehr nötig), `config-service` bekam die neue Kategorie `federation_config`. Kein Adressbuch-Gap gefunden - die Trennung zwischen Fleet-/Lizenz-`installation_id` (P13-S1) und der Hub-eigenen, bewusst unabhängigen Installationskennung bleibt unverändert bestehen (siehe ADR 0037).
