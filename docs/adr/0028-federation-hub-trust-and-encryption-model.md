# 0028 — Federation Hub: Trust and Encryption Model (basic framework)

**Status:** accepted
**Context:** P6-S9 (Federation Hub basic framework, Concept 7.4), brought forward from P13-S3/S4 following the P6-S8 plan approval (see `PROGRESS.md` "Process Designer / Process Versioning"). Concept 7.4 requires that documents/data transferred via the Federation Hub be encrypted end-to-end between the participating installations — "the hub itself cannot inspect the content, only mediate." However, the foundation actually intended for this (a real, system-wide installation identity/PKI) is not scheduled to exist until P13-S1 (multi-installation foundations) per the roadmap, long after this session. During the plan check-in, the user decided to implement real end-to-end encryption **now** regardless, with deliberately simple but real key management instead of a plain-text or transport-only approach.

## Decision

**Each installation generates its own RSA-2048 key pair on first configuration** (`cryptography`, same library/serialization as `signature-service`'s internal CA, ADR 0025) and registers with the hub using it (`public_key_pem` in the address book). A handover payload is **hybrid-encrypted** (a fresh AES-256-GCM key for the payload, RSA-OAEP encrypts this key with the target installation's public key) — the hub only forwards the result as an opaque, base64-encoded string and does not persist it (`federation_hub_service.models.Handover` has no payload field).

**Trust between hub and installations runs over two different, purpose-matched mechanisms instead of a single shared secret:**
- *Installation → Hub*: a random API key issued once at registration (`secrets.token_urlsafe(32)`), which the hub stores only **hashed** (SHA-256 — deliberately not slow password hashing like bcrypt/argon2, since the key itself is already high-entropy random, not a human-chosen, guessable secret).
- *Hub → Installation*: the hub **also** generates an RSA-2048 key pair on its own first startup (`hub_identity`, same singleton pattern) and **signs** every message delivered to an installation with it (RSA-PSS/SHA-256, header `X-Federation-Hub-Signature`). Each installation retrieves the hub's public key once, at its own registration (`GET /public-key`, trust-on-first-use), and uses it to verify every subsequent delivery.

This split avoids the hub ever having to store **any** secret in plain text that it would later need to reuse (an originally considered design — the hub delivers incoming deliveries using its own, known API key of the target installation — would have required exactly that; it was discarded during implementation in favor of the signature model).

**Version compatibility**: simple `(major, minor)` number pairs instead of a SemVer library — the hub checks at `POST /handovers`, on both sides, whether `version`/`min_compatible_peer_version` of the two participating installations match each other, otherwise `409`.

## Rationale

- **Real E2E encryption without waiting for P13-S1**: the key-pair-per-installation model needs no system-wide installation-ID infrastructure — each installation manages its own identity itself, and the hub's address book is already the only place where installations get to know each other at all. Fulfills "hub cannot inspect content" literally, starting with this session.
- **Signature instead of a shared API key for hub→installation deliveries**: standard pattern for webhook-style deliveries (comparable to signed webhooks in other systems), requiring the hub to know only its **own** private key — never that of a foreign installation. Security-hygienically cleaner than a "plain-text key handoff," which would immediately compromise all installations upon a DB compromise of the hub.
- **Fast rather than slow hashing for API keys**: bcrypt/argon2 are designed for human-chosen, low-entropy passwords (protection against offline brute-force). A 32-byte `secrets.token_urlsafe` value already has enough entropy that a fast hash (SHA-256) suffices for the relevant threat case here (pure DB-dump theft) — no reason to introduce an additional dependency (`passlib`/`bcrypt`) for this one field alone.
- **No new BPMN element for federated steps**: as with the Signature Task (P6-S7, ADR-less convention), a federated step technically remains a `bpmn:ManualTask` with `camunda:properties` — reproduces the proven pattern instead of inventing a new UI/backend concept.

## Consequences

- **No mTLS, no real installation identity, no key rotation/revocation** — deliberate limits of a basic framework. An operator using a foreign hub must trust that hub's operator not to redirect deliveries to a wrong/compromised `callback_base_url` (the hub itself could theoretically make a wrong `to_installation` mapping — the TLS/mTLS security level between hub and installations is a deployment matter, not part of this application-layer safeguard). Will be refined once the installation-ID foundations from P13-S1 exist (P13-S4).
- **Self-loopback as this session's test methodology**: the only available dev environment has just one running `workflow-service` installation. The live smoke test has this installation hand over a federated step to **itself** (its own `installation_id` as target) — the complete round trip (encryption, hub mediation, signature verification, receipt, new local instance, response) runs through for real, without needing to simulate a second installation. A real two-installation test remains pending until a second environment is available.
- **No enforcement of `supported_process_types`/`supported_document_types`** — the hub stores them but does not check whether a handover actually matches a declared type (see `docs/services/federation-hub-service.md` "Open Points").
- **Synchronous delivery without a retry queue** — a temporarily unreachable target immediately results in `delivery_failed`, with no later automatic redelivery.

## Addendum: two real bugs found only during the self-loopback smoke test

Synchronous delivery (see above) loops all the way back into the same installation/the same process in the self-loopback case — this exposed two problems that would have remained invisible with pure unit-test coverage (mocked/stubbed counterparts):

1. **Postgres transaction isolation**: `POST /handovers` originally committed the newly created handover row only *after* the delivery attempt. In self-loopback, however, the target installation synchronously calls back into the hub (`POST .../result`) before the original transaction has committed — the new, separate request did not yet see the row (`404 handover_id unknown`). Fix: `session.commit()` directly after creating the row, **before** the actual delivery attempt.
2. **Circular dependency from a server-generated `handover_id`**: the hub originally generated `handover_id` itself and returned it only in the `POST /handovers` response. In self-loopback, however, the sending installation's *own, local* bookkeeping (its `FederationTask` row, preventing duplicate dispatch) already needs this ID before the nested callback can look it up there — but at the time of the callback, the response containing the ID had not yet been delivered. Fix: **protocol change** — the sending installation generates `handover_id` itself (`uuid.uuid4()`) and sends it in the `POST /handovers` body; it commits its own `FederationTask` row locally **before** even calling the hub. Side effect: a clean, idempotency-key-like protocol (the caller sets its own reference instead of having to wait for a server-generated ID) — not a pure test workaround, but an improvement that also benefits real two-installation scenarios.

Related to this, `models.FederationTask`'s uniqueness on `handover_id` alone had to be relaxed to `(handover_id, direction)` — in self-loopback, two rows (`outbound` and `inbound`) with the same `handover_id` otherwise end up in the same database, which would have immediately triggered an `IntegrityError` under the old constraint. `repository.get_federation_task_by_handover` got a `direction` parameter for this (default `"outbound"`, matching the only actual caller `POST /federation/inbound-result`).

For a real two-installation scenario (no self-reference), neither problem would ever have occurred, since two completely separate processes/databases are involved there — they are a direct, but instructive, consequence of the self-loopback test methodology chosen in this session.

## Addendum (P13-S3): version-format validation at registration, version compatibility as a 7.3 category

Two additions from the P13-S3 review ("adaptation to the multi-installation/fleet foundations from P13-S1/S2/S2b, where gaps appear"):

- **Real bug found and fixed**: `POST /installations` previously accepted any arbitrary `version`/`min_compatible_peer_version` string without complaint. `repository.is_version_compatible()`'s naive `(major, minor)` number parsing (`_parse_version`) threw an unhandled `ValueError` for a non-numeric value — not at the faulty `POST /installations` call itself, but **only during a later, completely unrelated** `POST /handovers` mediation, as soon as the affected installation was involved in ANY handover (500 instead of a meaningful error message at the point where the problem actually originates). Fix: the parsing logic moves into a new, shared `version_utils.py` (`parse_version`, now raises `InvalidVersionFormatError`) and is enforced via a Pydantic `field_validator` on `InstallationRegister` already at registration time (`422` with a clear message instead of a later 500 during an unrelated mediation). Found via the team's own test data with a hex-like version value — not a finding on real installations.
- **Version-compatibility range is now actually part of the 7.3 configuration schema**: 7.4 literally requires "This compatibility range is part of the already-versioned configuration schema (7.3)" — before P13-S3 it lived exclusively in `workflow-service`'s `Settings` (`installation_version`/`installation_min_compatible_peer_version`, changeable only via container restart, never reachable through the regular configuration import). New: `workflow-service` got a `FederationConfig` DB row plus `GET`/`PUT /federation/config` (gated behind the same `admin.object_config` capability as the BPMN upload; a `PUT` immediately triggers a re-registration at the hub, no more restart needed), `config-service` got the new category `federation_config`. No address-book gap found — the separation between the fleet/license `installation_id` (P13-S1) and the hub's own, deliberately independent installation identifier remains unchanged (see ADR 0037).
