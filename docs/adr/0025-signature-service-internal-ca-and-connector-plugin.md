# 0025 — Signature Service: Internal CA + Connector Plugin Principle + Signature Task via Camunda Extensions

**Status:** accepted
**Context:** P6-S7 (Concept 3.10, "Signature Integration"). Electronic signature as a broker in front of external, accredited trust service providers (QTSPs): interchangeable signature provider connectors (plugin principle like CMIS/WebDAV, 3.3), signature levels SES/AES/QES configurable per object type, binding to a specific document version (2.1a), a new BPMN task type "Signature Task" (7.1, technically a special form of Manual Task), verifiability at any time. Recommended scope per `IMPLEMENTATION_PLAN.md`: build the basic framework + connector abstraction, only implement/test SES/AES for real with system-internal/self-signed keys — a genuine accredited QTSP for QES requires an external business relationship and is not an automation/test case for this session.

## Decision

**New `services/signature-service/`** (port 8017, its own Postgres schema `signature`), scaffolded after the established `notification-service` pattern (FastAPI lifespan, registry self-registration, `*_client.py` HTTP clients against sibling services, `conftest.py` test pattern with real calls instead of mocking).

**Signature provider connector abstraction, mapped 1:1 onto the storage backend pattern (3.6, ADR 0017)**: `SignatureProviderConnector` (ABC) with `sign()`/`verify()`, factory dispatch in `connectors/__init__.py` on `type` with a stable `id` mapping. Config via `DMS_SIGNATURE_PROVIDERS` (JSON list), default seed a single entry `{id: "internal", type: "internal", levels: ["ses","aes"]}`. `type: "qtsp"` is provided for in the Pydantic schema, but the factory throws a clear error on any attempt to configure it — the same "abstraction now, second/real connector later" discipline as with the documented but unimplemented Azure Blob backend in storage-service.

**Internal, self-signed root CA instead of an external dependency**: new singleton table `internal_ca` (`id=1`, same pattern as `OcrConfig`/`SystemMaintenanceMode`), generated via `cryptography` on first startup (RSA 2048, 20-year validity) and idempotently reused thereafter. `InternalSelfSignedConnector.sign()` issues **a new leaf certificate per signing operation**, signed by this root: for `level="ses"` with a generic subject (`CN=DMS System (SES)`, no binding to a person — "simple electronic confirmation"), for `level="aes"` with a person-bound subject (`CN=<display name>`, `emailAddress=<email>`, from a real `auth-service` account check) — this makes AES "uniquely attributable to a person" without an external provider. Leaf certificates are deliberately valid for multiple years (5 years) rather than short-lived, since this session implements PAdES-**B-B** (no timestamp authority countersigning, no PAdES-B-LTA) — a short leaf lifetime would artificially mark every later verification as "expired," even though the signing operation itself was valid at the time of signing.

**pyHanko handles the PDF-side work**: `SimpleSigner.load()` (PEM files from `tempfile`) + `async_sign_pdf()` (not the sync `sign_pdf()` variant — it internally calls `asyncio.run()` and collides with the already-running event loop of the FastAPI handler, see Consequences) for PAdES-B-B embedding; `async_validate_pdf_signature()` (same async reasoning) with a `ValidationContext(trust_roots=[<internal CA>], allow_fetching=False, revocation_mode="soft-fail")` for verification — no OCSP/CRL revocation checking possible, since the internal CA does not operate real revocation-list infrastructure.

**Signing produces a new document version instead of replacing the existing one**: `POST /signatures {document_id, level, signer_principal_id, version_number?, reason?}` loads the current (or explicitly specified) version via document-service, rejects `content_type != application/pdf` with `400` (PAdES is PDF-specific, dictated by pyHanko itself), signs it, checks in the signed bytes as a **new version** at document-service (`POST /documents/{id}/versions`, `expected_base_version_number = the signed source version`) and creates a `Signature` record that references `document_id` + the new `version_number` + `source_version_number` + certificate metadata. If a version other than the current main version is signed, document-service's existing optimistic conflict detection (4.2) automatically produces a conflict copy instead of the main version being moved — no special handling needed on the signature-service side.

**Minimum signature level per object type**: additive column `object_type.required_signature_level` (`ses`/`aes`/`qes`/`NULL`, only for `applies_to="document"`, ad-hoc migration like `document.attributes`), enforced at the signing operation itself (`400` if the level is too low).

**Signer identity self-reported but verified against real accounts**: `signer_principal_id` remains a body field (consistent with `triggered_by`/`approved_by`/`completed_by`/`lifted_by` across the whole project), but — continuing the P6-S6 retrofit pattern used at notification-service — is checked against `auth-service` (`GET /users`, technical `users-admin` account); this supplies the display name/email for the AES certificate, `400` for an unknown principal.

**Signature Task in the workflow (7.1) via Camunda extension attributes, no new BPMN element**: `spiff_adapter.py` switches the parser from `SpiffWorkflow.bpmn.parser.BpmnParser` to `SpiffWorkflow.camunda.parser.CamundaParser` (still maps `manualTask` to `ManualTask` — `.manual is True` unchanged, `ready_manual_tasks`/`find_ready_task` need no changes), but additionally populates `task_spec.extensions` from `bpmn:extensionElements/camunda:properties`. A `<bpmn:manualTask>` with `taskType=signature`/`requiredLevel=aes` thereby becomes recognizable as a Signature Task, while technically remaining an ordinary Manual Task — no modeler tooling break, no new process-designer palette entry needed (that is explicitly the subject of P6-S8, which follows directly after). The `document_id` to be signed runs through the existing generic `data` process variable, since workflow-service has no concept of a document. `TaskCompleteRequest` gets a new optional `signature_id` field; if the task is a Signature Task according to the extension, `POST .../tasks/{id}/complete` requires a valid signature matching the expected document with sufficient level (new, thin `signature_client.py`, pattern like `permission_client.py` from P6-S6) — otherwise `400`.

**Serializer config had to be updated as well**: `CamundaParser` maps `<bpmn:userTask>` to Camunda's own `UserTask` spec class instead of the BPMN default class — without the matching converter (`SpiffWorkflow.camunda.serializer.config.CAMUNDA_CONFIG` instead of `BpmnWorkflowSerializer.configure()`), JSON serialization of already-existing fixtures with `userTask` elements (e.g. the P6-S2 boundary timer test) fails.

**Emergency-shutdown interaction (4.8)**: `POST /signatures` is not on the gateway allow-list — during maintenance mode the gateway blocks this endpoint like any other automatically (default-deny, no gateway code change needed).

**Auditing**: new event `signature.created`, `audit-service` gets `signature.>` as a new entry in the `subjects` list (like every previous new domain).

## Rationale

- **Connector abstraction adopted 1:1 from the storage backend pattern rather than reinvented**: the same `id`-not-`type` keying, the same factory dispatch structure — a developer familiar with storage-service will recognize the pattern immediately.
- **Internal CA instead of a placeholder certificate**: a real, if self-signed, PKI is the only variant that actually produces and verifies working PAdES signatures — a pure placeholder (e.g. a dummy hash instead of real cryptography) would have missed 3.10's core requirement ("cryptographic proof").
- **Signing produces a new version instead of an in-place change**: a PAdES signature inevitably alters the PDF bytes (that is the whole point of the cryptographic binding) — storing it as a new, permanently retained version is the only variant consistent with 2.1a ("nothing is ever discarded") and the concept's statement that "a subsequent alteration of the signed content is made detectable by the signature itself").
- **Camunda extension attributes instead of a new BPMN element for the Signature Task**: the least invasive implementation consistent with the researched Spiff API (`manualTask`→`ManualTask` remains unchanged) and requiring no modeler tooling change — matching the concept's wording "technically a special form of Manual Task."
- **`async_sign_pdf`/`async_validate_pdf_signature` instead of the sync variants**: pyHanko's `sign_pdf`/`validate_pdf_signature` internally call `asyncio.run()`, which in an already-running FastAPI async handler leads to `RuntimeError: asyncio.run() cannot be called from a running event loop` — verified for real against the installed pyHanko version (0.36.2), not just taken from the documentation.
- **Multi-year rather than short-lived leaf certificates**: consistent with the deliberately chosen PAdES-B-B scope (no timestamp authority countersigning) — a short lifetime would have made verification artificially unreliable without any real benefit.

## Consequences

- **QES remains completely unimplemented** — both the connector type (`type: "qtsp"`) and a check mechanism for external trust service providers exist only as schema placeholders. A signing attempt with `level="qes"` fails with `400` ("no connector configured"), regardless of object type.
- **No OCSP/CRL revocation checking** — `GET /signatures/{id}/verify` only checks integrity (content unchanged since signing) and certificate validity period, not certificate revocation. For a self-signed internal CA without real revocation-list infrastructure this is the only honest depth of verification.
- **No PAdES-B-LTA/long-term archiving** — 3.10 explicitly names B-LTA as important for records disposal (5.6); this session delivers only B-B. A future retrofit would need a real timestamp authority.
- **No process-designer palette entry for Signature Tasks** — BPMN modeling remains raw XML upload, a Signature Task requires setting the extension attributes by hand in the XML. Follows with P6-S8.
- **The `CamundaParser` switch affects all BPMN processing of the Workflow Service**, not just new Signature Tasks — existing fixtures/processes continue to run unchanged (verified: all 52 previous workflow-service tests remain green), but any future session that touches SpiffWorkflow directly must be aware of this parser/serializer switch.
- **Another technical account (`users-admin`) is reused for a third foreign domain** — Signature Service authenticates for the signer existence check as `users-admin`, like notification-service, instead of introducing its own account (already noted in ADR 0023/0024 as a pattern worth revisiting).
