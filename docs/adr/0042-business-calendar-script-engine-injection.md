# 0042 — Business calendar: dedicated SpiffWorkflow script engine instead of precomputation, fixed weekend rule, no versioning pattern

**Status:** accepted
**Context:** P14-S5 (regional business calendars for SLA deadline calculation, concept 7.1)

## Decision

A new `BusinessCalendar` data type in `workflow-service` (a named list of non-working days, `PUT`-based update-in-place instead of versioning, at most one calendar `is_default` at a time) takes effect via a new function `business_days(n, calendar_name=None)` callable within a BPMN timer duration expression - a BPMN file writes, e.g., `business_days(3, "de-national")` instead of a static `"P3D"` literal. Technical basis: `spiff_adapter.py` constructs its own `SpiffWorkflow.bpmn.script_engine.PythonScriptEngine` instance with `TaskDataEnvironment(environment_globals={"business_days": ...})` and assigns it explicitly both in `new_workflow()` and after every `deserialize()` (`wf.script_engine = ...`, a public, settable property). Weekends (Sat/Sun) are **always** treated as non-working, regardless of any specific calendar - a calendar itself only holds the additional, calendar-specific days (holidays). Without a `calendar_name` argument, the installation's default calendar applies if one is maintained as `is_default`, otherwise only the weekend rule applies.

## Rationale

- **Evaluation happens only at the actual moment the timer starts running, rather than a precomputation at instance start**: `DurationTimerEventDefinition.has_fired()` (installed SpiffWorkflow version, verified via `inspect`) evaluates the duration expression exactly once - on the very first `has_fired()` call, as soon as the associated timer task becomes `WAITING`, via `my_task.workflow.script_engine.evaluate(...)`. For a boundary timer on a task that is only reached partway through the process (e.g. after a preceding approval step lasting several days), exactly THIS moment is "now" in the sense of 7.1's "3 business days deadline" - computing this at instance start would ignore the actual waiting time until this task is reached, and would simply be wrong for most realistic process flows. Since SpiffWorkflow already picks this evaluation point correctly on its own, `business_days()` only needs to hook in at exactly this point, with no precomputation/caching logic of its own needed.
- **`environment_globals` is SpiffWorkflow's own designated extension point** for additional functions callable within any script/expression (`TaskDataEnvironment.__init__`, verified) - not a private workaround of the library. A name collision with a process variable of the same name already triggers its own clear `ValueError` there (`check_for_overwrite`), so no collision check of our own is needed.
- **`wf.script_engine` must be re-set after every `deserialize()`** - `BpmnWorkflowConverter.from_dict()` (SpiffWorkflow's deserializer) always creates a new, generic `BpmnWorkflow` instance without a `script_engine` argument when restoring (verified by reading the source), `script_engine` is not part of the serialized JSON state. Without this re-assignment, any instance loaded via `repository.deserialize()` and already running would lose the ability to resolve `business_days(...)` as soon as a not-yet-reached timer task first becomes ready (e.g. after `complete_task()`/`retry_instance()`/the SLA poll tick) - reproduced in practice as a test case (`test_business_days_timer_survives_serialize_deserialize_roundtrip`).
- **Weekends are hardcoded rather than part of the calendar data**: 7.1 itself phrases the requirement as "does not run through a stored weekend/holiday" - "business day" by definition already excludes weekends; a calendar does not need to encode this obvious fact as data rows every time (which would only generate unnecessarily many, annually recurring entries). `business_days()` therefore already means, by its very name, at minimum "business days instead of calendar days" - even with no specific calendar at all (`calendar_name=None`, no default maintained), the weekend remains excluded. This does NOT contradict 7.1's principle "without a configured calendar, existing behavior remains the default": the existing behavior (a pure `"P3D"` literal) remains fully unchanged for any BPMN file that does not call `business_days()` at all - the principle refers to already-existing process definitions, not to the weekend semantics of the new function itself.
- **The `calendar_name` argument = process assignment, the `is_default` flag = installation assignment**: 7.1 requires a calendar "assignable to a process/an installation". A calendar explicitly named in the BPMN file (`business_days(3, "de-national")`) already IS the process assignment - it lives directly in the model, no additional assignment table needed. The installation default (`is_default=true`, applies only without an explicit argument) covers the second named case, without introducing another configuration layer (e.g. a separate "installation → default calendar" singleton table) - a boolean flag on the existing calendar row is enough.
- **No versioning pattern like `ProcessDefinition`/`DmnDefinition`** ([ADR 0027](0027-workflow-process-definition-versioning.md)): a business calendar is continuously maintained reference data (e.g. adding new holidays annually), not immutable, versioned execution logic - a new "version" on every annual maintenance update would be pure data noise with no domain value. Instead, normal update-in-place (`PUT`) like `SensorConfig`/`ApprovalConfig`, `name` remains permanently unique.
- **An in-memory cache instead of a synchronous DB access from within `has_fired()`**: SpiffWorkflow's engine (including `script_engine.evaluate()`) is entirely synchronous, an `async` DB read would not be callable at this point (the same limitation as the already-existing connector service tasks, P12-S2 - though there an injectable, genuinely HTTP-calling handler exists; here a pure cache is deliberately used instead, since calendar data changes rarely and synchronous reloading would be disproportionate for a reference implementation). `repository.py` keeps the cache current after every write access (create/update/delete), `main.py`'s lifespan loads it once at service startup.

## Consequences

- **A single global time zone (UTC) only** - like the rest of the project (`datetime.now(UTC)` used throughout) - no installation-specific time zone for the weekday calculation. For an internationally distributed installation, the weekday change could therefore deviate by up to ±12h from local perception; accepted for a reference implementation, a documented limitation.
- **`business_days()` is NOT part of a complete OMG FEEL implementation** - a plain Python function defined in this module, callable from any BPMN script/expression context (not just timer duration expressions), since `environment_globals` applies globally to the whole engine instance.
- **No retroactive check when deleting a calendar** - if a BPMN file references a `calendar_name` that has since been deleted, the affected instance fails with an `UnknownBusinessCalendarError` (propagated as a `WorkflowTaskException` from SpiffWorkflow's engine) only the next time the timer task is reached, rather than the deletion itself being blocked - the same deliberate simplification as deleting a DMN decision table ([concept 7.1 implementation P14-S4](../services/workflow-service.md)).
- **No pre-built calendar templates (e.g. German holidays) in this session** - concept section 12.2/17 explicitly names a "prepared business calendar with national and state-specific holidays" as part of a future, curated **configuration package** (phase 17), not this scaffolding session - every installation starts with zero calendars, pure, immediately usable CRUD management.
