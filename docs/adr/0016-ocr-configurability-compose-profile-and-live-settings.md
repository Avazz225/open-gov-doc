# 0016 — OCR-Konfigurierbarkeit: Compose-Profil für `ocrEnabled`, DB-Zeile für Wortobergrenze/Batch-Size

**Status:** akzeptiert
**Kontext:** Konzept 3.9, Session P5b-S5

## Entscheidung

Die drei in 3.9 geforderten Konfigurationspunkte werden **nicht** einheitlich über einen einzigen Mechanismus umgesetzt, sondern bewusst aufgeteilt:

- **`ocrEnabled`** wird als **Docker-Compose-Profil** (`profiles: ["ocr"]` am `ocr-service`-Container) umgesetzt, aktiviert über `COMPOSE_PROFILES=ocr` (Default: an, wie vor dieser Session). Ist das Profil nicht aktiv, wird der Container bei einem bloßen `docker compose up` gar nicht erst betrachtet - explizites `docker compose up ocr-service` funktioniert weiterhin (Compose aktiviert das Profil eines explizit benannten Service automatisch). Es gibt **keinen** Laufzeit-Schalter dafür in der Admin-UI - nur einen Status ("erreichbar" vs. "nicht erreichbar").
- **Maximale Wortobergrenze** und **Verarbeitungs-Batch-Size** werden als neue, einzeilige `OcrConfig`-Tabelle (`ocr_config`, feste `id=1`) im ocr-service persistiert, über `GET`/`PUT /config` von der Admin-UI aus editierbar, und bei **jedem verarbeiteten Dokument frisch aus der DB gelesen** - keine Neustart nötig, damit eine Änderung wirkt.

## Begründung

- **3.9 selbst widerspricht sich hier leicht**: Es fordert einerseits "`ocrEnabled: false` - der OCR Service muss selbst nicht deployt werden", andererseits "alle drei Einstellungen sind Admin-UI-Konfiguration, keine Code-/Deployment-Änderung". Beides gleichzeitig ist unmöglich - ein nicht deployter Container kann keine Admin-UI-Anfrage entgegennehmen, um sich selbst zu deployen. Da IMPLEMENTATION_PLAN.md für diese Session bereits konkret "Docker-Compose-Profil-Opt-out" für `ocrEnabled` festlegt, wird dieser Teil wörtlich so umgesetzt; die verbleibenden zwei Einstellungen bekommen dafür die volle "keine Deployment-Änderung nötig"-Eigenschaft, die 3.9 für sie explizit verlangt.
- **Kein Vorbild für DB-gestützte Admin-UI-Einstellungen in diesem Repo** (geprüft): Jede bisherige Konfiguration ist entweder eine pydantic-`Settings`-Umgebungsvariable (nur bei Neustart wirksam, z. B. `DMS_SCAN_ENGINE`, `DMS_REDUNDANCY_ENABLED`) oder ein Keycloak-User-Attribut (`ThemePreference`, personenbezogen, nicht service-weit). Eine echte, service-weite, laufzeitveränderliche Einstellung ist in P5b-S5 die erste ihrer Art - `OcrConfig` ist bewusst eine eigenständige, einzeilige Tabelle statt eine der beiden bestehenden Formen zu verbiegen.
- **Kein Compose-Profil-Präzedens** (geprüft): Weder virus-scan-service (austauschbare Engine über `DMS_SCAN_ENGINE`, aber immer deployt) noch storage-service (`DMS_REDUNDANCY_ENABLED`, ein In-Prozess-Verhalten, kein Container-Opt-out) nutzen `profiles:`. Diese Session führt das Muster im Repo neu ein.
- **`rendering-service`/`search-service` hängen bewusst nicht per `depends_on` an `ocr-service`**: Mit aktivem Profil-Opt-out würde ein `depends_on` auf einen nicht in die Auflösung einbezogenen Service den Compose-Start von `rendering-service`/`search-service` verhindern. Beide rufen `ocr-service` ohnehin nur asynchron per HTTP nach einem `ocr.completed`-Event auf (nie zwingend beim eigenen Start) - ihre Nichterreichbarkeit ist bereits ein normaler Fall (OCR noch nicht fertig, jetzt zusätzlich: OCR nie geplant). `search-service` fing das bereits vor dieser Session über ein generisches `except Exception` ab; `rendering-service`s `consumer.py` bekam in dieser Session dieselbe Behandlung ergänzt (vorher ungefangen, siehe Konsequenzen).
- **Wortobergrenze wird geschätzt, nicht exakt gezählt** (3.9 nennt die Schätzmethode selbst als Implementierungsdetail, Konzept-Fußnote bestätigt das nochmal explizit für diese Session): eine echte Wortzählung würde bei Scans/Bildern dieselbe teure Tesseract-Arbeit voraussetzen, die die Obergrenze gerade vermeiden soll. Gewählt: `Seitenzahl × 250` (PyMuPDFs `page_count`, ohnehin ohne Rendern verfügbar) - Rasterbilder zählen dabei immer als eine Seite (kein Seitenzahl-Konzept für Einzelbilder).
- **Batch-Size = Nebenläufigkeitsgrenze, nicht Pull-Batching**: Der Event-Bus liefert push-basiert und verarbeitet bisher grundsätzlich sequentiell (ein Callback pro NATS-Subscription, erst nach dessen Abschluss wird das nächste zugestellt) - es gibt kein Pull-/Fetch-Muster, dessen Batch-Größe konfigurierbar wäre. `NatsEventBusClient.subscribe()` bekam deshalb einen neuen, **optionalen** `max_concurrency`-Parameter (Default `1` = exakt das bisherige Verhalten, für alle anderen Konsumenten unverändert); `ocr-service` reicht dafür ein Callable durch, das `OcrConfig.batch_size` bei jeder Nachricht live nachliest. Ein fehlschlagender Handler gibt seine Kapazität trotzdem frei und bestätigt (ackt) die Nachricht **nicht** - dieselbe Redelivery-Semantik wie im unveränderten sequentiellen Pfad.
- **Kein eigener `ocr_enabled`-Spalte in `OcrConfig`**: Ein Laufzeit-Soft-Flag zusätzlich zum Compose-Profil hätte zwei sich potenziell widersprechende "aus"-Zustände erzeugt (Container läuft, aber Flag sagt "aus" - wer gewinnt?). Da 3.9 nur einen einzigen `ocrEnabled`-Punkt nennt und dieser bereits das Compose-Profil ist, bleibt es dabei.

## Konsequenzen

- Ein neuer Status `"skipped"` ergänzt `OcrResult.status` (`ready`/`needs_review`/`failed`/`skipped`) und ein neues Event `ocr.skipped` - eine wegen der Wortobergrenze übersprungene Verarbeitung ist im Audit-Trail sichtbar, nicht von "noch nicht verarbeitet" zu unterscheiden.
- `docker-compose.yml`: `ocr-service` trägt jetzt `profiles: ["ocr"]`; `.env`/`.env.example` setzen `COMPOSE_PROFILES=ocr` als Default (unverändertes Verhalten beim bloßen `cp .env.example .env`). Zum echten Opt-out muss `ocr` aus `COMPOSE_PROFILES` entfernt werden.
- `rendering-service/consumer.py` fängt jetzt auch Verbindungsfehler beim OCR-Nachladen ab (vorher ungefangen - hätte ein `ocr.completed`-Alt-Event nach nachträglichem OCR-Opt-out endlos redeliver-t, ohne je verarbeitbar zu sein).
- Admin-UI bekommt eine neue "OCR-Einstellungen"-Seite (`/ocr-settings/`), die bei nicht erreichbarem `ocr-service` einen erklärenden Leerzustand statt eines Fehlers zeigt - das ist die einzige Sichtbarkeit von `ocrEnabled=false` in der UI, kein Schalter.
- Die Batch-Size-Nebenläufigkeit ist **grob**, nicht exakt planbar (kein Vorrang/Priorisierung zwischen Dokumenten, keine Begrenzung des Speicherbedarfs pro gleichzeitig laufender Tesseract-Instanz selbst) - für den in 3.9 verlangten Zweck ("Stellschraube für Durchsatz vs. Ressourcenverbrauch") ausreichend, aber kein Ersatz für einen echten Worker-Pool mit Ressourcen-Accounting.
- Die geschätzte Wortobergrenze kann bei sehr textarmen mehrseitigen PDFs (z. B. viele fast leere Seiten) zu früh greifen und bei sehr textdichten Einzelbildern nie greifen - akzeptierte Ungenauigkeit einer bewusst günstigen Heuristik (siehe `docs/services/ocr-service.md`, Offene Punkte).
