# 0016 — OCR configurability: compose profile for `ocrEnabled`, DB row for word ceiling/batch size

**Status:** accepted
**Context:** Concept 3.9, Session P5b-S5

## Decision

The three configuration points required in 3.9 are **not** implemented uniformly through a single mechanism, but deliberately split:

- **`ocrEnabled`** is implemented as a **Docker Compose profile** (`profiles: ["ocr"]` on the `ocr-service` container), activated via `COMPOSE_PROFILES=ocr` (default: on, as before this session). If the profile is not active, the container is not even considered on a plain `docker compose up` - an explicit `docker compose up ocr-service` still works (Compose automatically activates the profile of an explicitly named service). There is **no** runtime toggle for this in the Admin UI - only a status ("reachable" vs. "not reachable").
- **Maximum word ceiling** and **processing batch size** are persisted as a new, single-row `OcrConfig` table (`ocr_config`, fixed `id=1`) in ocr-service, editable from the Admin UI via `GET`/`PUT /config`, and **read fresh from the DB for every document processed** - no restart needed for a change to take effect.

## Rationale

- **3.9 slightly contradicts itself here**: it demands, on the one hand, "`ocrEnabled: false` - the OCR Service does not itself need to be deployed", and on the other, "all three settings are Admin UI configuration, no code/deployment change". Both at once is impossible - a container that is not deployed cannot receive an Admin UI request to deploy itself. Since `IMPLEMENTATION_PLAN.md` already concretely specifies a "Docker Compose profile opt-out" for `ocrEnabled` for this session, this part is implemented literally as stated; the remaining two settings in return get the full "no deployment change needed" property that 3.9 explicitly demands for them.
- **No precedent for DB-backed Admin UI settings in this repo** (checked): every existing configuration is either a pydantic `Settings` environment variable (effective only on restart, e.g. `DMS_SCAN_ENGINE`, `DMS_REDUNDANCY_ENABLED`) or a Keycloak user attribute (`ThemePreference`, personal, not service-wide). A genuine, service-wide, runtime-changeable setting is the first of its kind in P5b-S5 - `OcrConfig` is deliberately a standalone, single-row table rather than bending one of the two existing forms.
- **No Compose profile precedent** (checked): neither virus-scan-service (swappable engine via `DMS_SCAN_ENGINE`, but always deployed) nor storage-service (`DMS_REDUNDANCY_ENABLED`, an in-process behavior, not a container opt-out) use `profiles:`. This session introduces the pattern into the repo for the first time.
- **`rendering-service`/`search-service` deliberately do not depend on `ocr-service` via `depends_on`**: with the profile opt-out active, a `depends_on` on a service not included in resolution would prevent `rendering-service`/`search-service` from starting via Compose. Both call `ocr-service` only asynchronously via HTTP after an `ocr.completed` event anyway (never mandatorily at their own startup) - their unreachability is already a normal case (OCR not yet finished, now additionally: OCR never scheduled). `search-service` already caught this before this session via a generic `except Exception`; `rendering-service`'s `consumer.py` got the same handling added in this session (previously uncaught, see Consequences).
- **The word ceiling is estimated, not exactly counted** (3.9 itself names the estimation method as an implementation detail, and a concept footnote explicitly confirms this again for this session): an actual word count would, for scans/images, require the same expensive Tesseract work that the ceiling is meant to avoid in the first place. Chosen: `page count × 250` (PyMuPDF's `page_count`, available without rendering anyway) - raster images always count as one page (no page-count concept for single images).
- **Batch size = concurrency limit, not pull batching**: the event bus delivers push-based and has so far always processed sequentially (one callback per NATS subscription, the next is only delivered after it completes) - there is no pull/fetch pattern whose batch size would be configurable. `NatsEventBusClient.subscribe()` therefore got a new, **optional** `max_concurrency` parameter (default `1` = exactly the previous behavior, unchanged for all other consumers); `ocr-service` passes in a callable for this that re-reads `OcrConfig.batch_size` live on every message. A failing handler still releases its capacity but does **not** acknowledge (ack) the message - the same redelivery semantics as in the unchanged sequential path.
- **No dedicated `ocr_enabled` column in `OcrConfig`**: a runtime soft flag in addition to the Compose profile would have created two potentially contradictory "off" states (container running, but flag says "off" - who wins?). Since 3.9 names only a single `ocrEnabled` point, and that is already the Compose profile, it stays that way.

## Consequences

- A new status `"skipped"` extends `OcrResult.status` (`ready`/`needs_review`/`failed`/`skipped`) and a new event `ocr.skipped` - processing skipped due to the word ceiling is visible in the audit trail, distinguishable from "not yet processed".
- `docker-compose.yml`: `ocr-service` now carries `profiles: ["ocr"]`; `.env`/`.env.example` set `COMPOSE_PROFILES=ocr` as default (unchanged behavior for a plain `cp .env.example .env`). For an actual opt-out, `ocr` must be removed from `COMPOSE_PROFILES`.
- `rendering-service/consumer.py` now also catches connection errors when reloading OCR (previously uncaught - would have caused a stale `ocr.completed` event to be redelivered endlessly after a later OCR opt-out, without ever being processable).
- Admin UI gains a new "OCR Settings" page (`/ocr-settings/`), which shows an explanatory empty state instead of an error when `ocr-service` is unreachable - this is the only visibility of `ocrEnabled=false` in the UI, not a toggle.
- Batch-size concurrency is **coarse**, not exactly plannable (no precedence/prioritization between documents, no limit on memory footprint per concurrently running Tesseract instance itself) - sufficient for the purpose required in 3.9 ("a lever for throughput vs. resource consumption"), but no substitute for a real worker pool with resource accounting.
- The estimated word ceiling can trigger too early for very text-sparse multi-page PDFs (e.g. many nearly empty pages) and never trigger for very text-dense single images - an accepted inaccuracy of a deliberately cheap heuristic (see `docs/services/ocr-service.md`, Open Points).
