# 0046 — LibreOffice/OpenOffice extension: Writer only, dialog hub instead of sidebar, `loadComponentFromURL` instead of in-place replacement

**Status:** accepted
**Context:** Concept 3.3a, session P14-S9 (office integration part 2, shared backend interface with P14-S8/[ADR 0045](0045-office-addin-word-only-reused-endpoints-settings-linking.md))

## Decision

A new `.oxt` extension package (`apps/libreoffice-addin`) implements the same 3.3a functionality as the Microsoft Office add-in (P14-S8) for **LibreOffice/OpenOffice Writer only**, as a pure Python UNO script (no Basic, no compiled C++/Java service) — registered via `Addons.xcu` as a single menu entry ("Tools > Open OG Doc..."), which opens a "hub" dialog with buttons for each action. As in P14-S8, **no new backend endpoint** is called — the same gateway, the same `document-service`/`workflow-service`/`object-type-service`/`folder-service`/`search-service` endpoints, reimplemented in `python/dms_client.py` (pure standard library, no `pip install requests`).

## Rationale

- **Writer only, no Calc/Impress**: the central "load DMS content into the current document" capability is based on `Desktop.loadComponentFromURL()` (see below) — technically usable across hosts, but the finer control over title/metadata editing, saving via `storeToURL`, and the add-in's fundamental focus on text documents (concept examples: contracts, templates) justify the same Word-only-style restriction as P14-S8/ADR 0045, for consistency between the two extensions. Calc/Impress support would be a separate, later extension.
- **A dialog hub instead of a persistent sidebar panel**: UNO technically has a sidebar-deck API (`XSidebarPanel`/`XUIElementFactory`), but its implementation is practically documented/common only in Java/C++ - a Python-based sidebar implementation is barely documented and considerably more fragile than the pattern chosen here, which is well-established: a single, programmatically assembled (not via an `.xdl` resource file) `UnoControlDialog` that, as needed, opens further focused dialogs (login, open, template, metadata, workflow). This is the realistic implementation of "as far as the respective platform allows" (concept wording) for UNO, not a convenience compromise.
- **`loadComponentFromURL()` instead of in-place replacement of the currently open document**: Word JS's `insertFileFromBase64(..., replace)` has no 1:1 equivalent of comparable robustness in the Writer API. The more idiomatic, more natural approach for a desktop program is instead a genuine "open file": downloaded bytes are written to a local temporary file, `Desktop.loadComponentFromURL(url, "_blank", 0, props)` opens it as a NEW window. For "new from template", `AsTemplate=True` is additionally set - LibreOffice's OWN "new document from template" loading option, a genuine advantage of this platform, even superior to the Word add-in's approach (no need to rebuild template semantics from scratch).
- **Document linking via `UserDefinedProperties`**, the same principle as Office.js' `document.settings` (ADR 0045): `document.getDocumentProperties().UserDefinedProperties` is UNO's equivalent - add-in-owned state stored inside the file itself (ODF `meta.xml`/OOXML core properties), surviving close/reopen.
- **Saving via `storeToURL()` instead of slice-based `getFileAsync`**: since the add-in runs with direct filesystem access (no sandboxing like a web task pane), reading the current bytes is even simpler than with Office.js - `doc.storeToURL(temp_url, (FilterName=...,))` reliably exports the current editing state to a temporary file, regardless of whether the user has already saved locally.
- **The content type is stored together with the document link (a third `UserDefinedProperties` property `ogdoc_content_type`)** - a real bug found before this session's live test: an initial version always saved as ODF (`writer8` filter) when "saving to OG Doc", regardless of the originally opened format (e.g. DOCX) - a document would have been silently converted. Fixed by storing the content type actually observed when opening/loading a template (from the HTTP `Content-Type` header of `GET .../content`) together with the link, and reusing it on save.
- **`OpenOffice.org-minimal-version` checks against `ReferenceOOoMajorMinor`, not the real product version** - a real stumbling block found during this session's live installation: an initially entered value `value="7.0"` caused `unopkg add` to fail with "unsatisfied dependencies", even though a real, newer LibreOffice 26.2 instance was installed - LibreOffice internally still keeps a stable compatibility value for the dependency check (`ReferenceOOoMajorMinor=4.1` in `program/versionrc`, independent of the actual, now date-based version numbering). Fixed by setting `value="4.1"`, while keeping the still-readable `d:name="LibreOffice/OpenOffice 7.0 or newer"`.

## Verification (see also PROGRESS.md "LibreOffice add-in")

Unlike P14-S8 (Word), this development environment actually has a **real, functional LibreOffice 26.2 installation with a Python-UNO binding** (`/opt/libreoffice26.2`) - a genuine verification opportunity that does not exist for Word. What was exploited:

1. **A real `.oxt` installation via `unopkg add`**: exit 0, `unopkg list --verbose` confirms "is registered: yes" for the package AND for `Addons.xcu`, all four `python/*.py` files end up correctly, after installation, in the directory expected by LibreOffice's `ScriptProviderForPython` convention (confirmed by filesystem inspection after installation). Subsequently cleanly uninstalled (`unopkg remove`).
2. **30 real `unittest` tests** (`python3 -m unittest discover`) - pure business logic with no UNO dependency (status texts, attribute filtering, file-extension detection, `dms_client`'s multipart/error handling) AND real UNO property-container logic against a hand-written fake of `UserDefinedProperties`/`PropertySetInfo` (`tests/uno_mock.py`) - including an import of the complete `ogdoc_addin.py` module, which would have surfaced any reference error (typo in function/variable names).
3. **No working headless UNO script-bridge access** (`soffice --accept=...`) - actually tried (both TCP-socket AND Unix-pipe transport, both failing identically: a clean, controlled process exit with code 81 directly after the internal IPC bootstrap, confirmed via `strace` to be no crash/signal). Presumably an incomplete "base" package selection of this particular installation (separate `libobasis26.2-*` packages instead of the usual `libreoffice-core`/`-writer` Debian packages) is missing a component needed for the external listener - **not** a sandbox network restriction of this environment (a real TCP `bind`/`listen` on the same port was tested successfully in isolation). As a result, actually invoking `open_ogdoc()` via the real script-provider mechanism was NOT possible - the dialog-building/action functions themselves (`_show_hub_dialog`, `_handle_*`) are therefore only import-/wiring-checked, not behavior-tested against real `UnoControlDialog` objects.

## Consequences

- **No real sideload/click-through test in Writer possible** in this environment (see point 3 above) - a human should actually install (`unopkg add` or the Extension Manager UI) and click through `apps/libreoffice-addin/OgDocAddin.oxt` (produced via `python3 build.py`) before production use.
- **The dialog UI is deliberately functional-plain** (programmatic AWT controls, no `.xdl` resources, no type-specific attribute widgets) - the identical, documented simplification as `apps/office-addin`'s `MetadataForm` (P14-S8).
- **Opening ALWAYS creates a new window instead of replacing the currently open one** - a deliberate, platform-driven difference from Word (see rationale above), tracked transparently in the hub state via `_STATE["working_doc"]` (subsequent actions like metadata/save/workflow act on the NEWLY opened window).
- **Template library identical to P14-S8**: the same convention-based root folder "Vorlagen", the same automatic role-basedness via existing folder read permissions - no second implementation of this concept needed.
- **The `ReferenceOOoMajorMinor` pitfall affects any future version of this package** - if the minimum version is genuinely raised in the future (e.g. if `insertFileFromBase64`-like newer APIs turn out to be needed), the check must continue to be made against the `4.x` compatibility value, not against the real LibreOffice version number.
