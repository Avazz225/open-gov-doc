# 0017 — Storage device identity: target list instead of fixed slots, DB reference value instead of trusting the backend itself

**Status:** accepted
**Context:** Concept 3.6 ("storage device swap sensitivity" + "arbitrarily many backend instances of the same type"), Session P5b-S6 — last session of Phase 5b

## Decision

Two previously separate but related retrofits to `storage-service`:

1. **The target set becomes a real list** (`Settings.targets: list[BackendTargetConfig]`, each entry with `id`+`type`+its own credentials) instead of the previous fixed two-slot structure (`backend`/`secondary_backend`, [ADR 0004](0004-storage-redundancy-scope.md)). `id` — not `type` — is the unique key, which makes arbitrarily many instances of the same type (e.g. two S3 providers) possible within the same target set.
2. **Storage device swap guard**: on first use, each target gets a generated device ID, stored as a marker object under a reserved key (`__dms_storage_identity__`) via the existing `StorageBackend.write`/`read` interface — no new backend methods. The **reference value** ("what was last known") additionally lives in a new `backend_identity` table in the shared DB, not only in the backend itself. On every startup, the service compares, for each target, the marker file against the DB reference value; on mismatch/absence, startup is refused by default (`RuntimeError` before `yield`, the same pattern as the existing `_validate_settings`). A new, DB-backed `GuardConfig.allow_degraded_start` flag (Admin-UI-editable, `GET`/`PUT /guard-config`) permits a degraded start, provided at least one target is verifiably unchanged — in that case, all `object_copy` rows of the affected targets are automatically reset to `pending`, so that the already-existing retry queue (`POST /replication/process-pending`) catches them up.

## Rationale

- **3.6 literally contradicts itself**: it demands, on one hand, "`ocrEnabled`-style" Admin UI configurability for the override, but on the other, an already-running service that *refuses to start* because of a detected device swap must somehow be able to receive this authorization without itself being reachable. Resolution: the override is a **proactively set standing policy** ("if a swap is ever detected, start degraded"), not an authorization granted at the moment of refusal — Postgres (where `GuardConfig` lives) is independent of a broken storage backend and already available before the backends themselves (see `main.py`'s lifespan ordering: DB engine first, backends afterward), which makes reading this setting at startup mechanically unproblematic.
- **The reference value must not live exclusively in the backend itself**: a swapped/reset target precisely has *no* marker file left in the failure case — comparing only "does the backend have a marker file, and does it match itself" would be trivially always true or always a first-start case, never a detectable regression. The new `backend_identity` table is therefore the actual source of truth, with the marker file in the backend serving only as the value to check against.
- **No new backend interface needed**: the marker file is stored via the already-existing `write()`/`read()` under a reserved key, exactly like a normal object — avoiding a second, parallel backend capability just for this one purpose. The reserved key (`__dms_storage_identity__`, no slash) does not collide with real, always-segmented document/OCR/rendition keys (`type/id/...`) — a documented namespace reservation, not a technically enforced lock.
- **Using `id` instead of `type` as the key also directly resolves the multiple-devices requirement**: `replication.py` was, per ADR 0004, already fully generic with respect to arbitrary target `id` strings (confirmed by its own tests, which always used freely chosen IDs such as `"a"`/`"b"` rather than backend type names) — the restriction to "exactly two targets, one of each type" sat exclusively in `Settings`/`backends/__init__.py`. This session removes that restriction there, without touching `replication.py`.
- **No renaming/migration effort for existing data**: `ObjectMetadata.backend`/`ObjectCopy.backend_id` have always been free strings with no FK to a type table — from this session on they mean "target `id`" instead of "backend type", which for the unchanged default (a single target with `id="local"`) yields exactly the same value as before.
- **A new, dedicated env-var form (`DMS_TARGETS` as a JSON list) instead of continuing the flat-var structure**: `pydantic-settings` natively supports JSON decoding of complex field types (including nested Pydantic models) from a single environment variable (empirically confirmed) — the same principle that `gateway-service` already uses for `CORS_ALLOWED_ORIGINS` (a simple `list[str]`), extended here to a list of objects. A numbered env-var form (`DMS_TARGETS__0__TYPE=...`) or a separate config file would have been alternatives, but without existing precedent in this repo and without a discernible advantage over the already-proven JSON form.
- **Mandatory background replication remains on the existing retry-queue mechanism** (ADR 0004: explicit `POST /replication/process-pending` endpoint instead of an in-process background task) rather than a new automatic execution mechanism — consistent with the already-documented, still-open gap "no automatic periodic execution" (waiting on the Plugin Orchestration Service, Phase 10). This session does not change that, but makes the need for a scheduler soon more visible (a degraded start otherwise stays permanently degraded).

## Consequences

- `Settings.backend`/`secondary_backend`/`redundancy_enabled`/`local_storage_base_path`/`s3_*` are removed without replacement in favor of `Settings.targets` — no backward-compatibility shim, since `docker-compose.yml`/`.env`/`.env.example` were updated in the same commit (default behavior for `cp .env.example .env` remains unchanged: a single local target, no redundancy).
- `main.py`'s lifespan for the first time opens a DB session **before** `yield`, outside the otherwise universally used `Depends(get_session)` request flow (`app.state.session_factory()` directly) — a new but necessary pattern for this service, since the guard must decide before the first request.
- A target newly added to the target set is automatically "stamped" on first start (bootstrap, not a failure). **Since P5c-S2**: the same first-start bootstrap additionally marks all already-existing objects that do not yet have a copy on this target as `pending` (`repository.seed_pending_copies_for_new_target`) — the existing retry queue (`POST /replication/process-pending`) catches them up. No new trigger mechanism needed, since a target-set change requires a restart anyway (settings are only read at startup).
- The word-ceiling/batch-size-style split "deployment vs. Admin UI" from [ADR 0016](0016-ocr-configurability-compose-profile-and-live-settings.md) deliberately repeats itself here analogously: target set = deployment (`DMS_TARGETS`), guard override = Admin UI (`GuardConfig`) — the same categorization logic, applied a second time in the same repo.
- `GET /guard-status` is purely read-only/informational (device ID + count of open copies per target). **Since P5c-S2**: `POST /guard-status/{target_id}/reidentify` accepts an intended device swap at runtime (no restart needed) — it takes over an already-existing marker file of the new device or stamps a new one (same logic as the first-start bootstrap), resets all previous copies of the target to `pending` via `reset_copies_for_backend` (the same retry queue as with the automatic degraded start), and thereby replaces the direct correction in `backend_identity` that was previously necessary.
