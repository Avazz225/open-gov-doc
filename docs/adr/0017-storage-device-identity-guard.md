# 0017 — Storage-Datenträger-Identität: Ziel-Liste statt fester Slots, DB-Referenzwert statt Vertrauen ins Backend selbst

**Status:** akzeptiert
**Kontext:** Konzept 3.6 ("Datenträger-Wechsel-Sensibilität" + "beliebig viele gleichartige Backend-Instanzen"), Session P5b-S6 — letzte Session der Phase 5b

## Entscheidung

Zwei bislang getrennte, aber zusammenhängende Retrofits an `storage-service`:

1. **Ziel-Set wird eine echte Liste** (`Settings.targets: list[BackendTargetConfig]`, je Eintrag `id`+`type`+eigene Zugangsdaten) statt der bisherigen festen Zwei-Slot-Struktur (`backend`/`secondary_backend`, [ADR 0004](0004-storage-redundancy-scope.md)). `id` — nicht `type` — ist der eindeutige Schlüssel, wodurch beliebig viele gleichartige Instanzen (z. B. zwei S3-Provider) im selben Ziel-Set möglich sind.
2. **Datenträger-Wechsel-Wächter**: Jedes Ziel bekommt bei erstmaliger Nutzung eine generierte Geräte-ID, hinterlegt als Marker-Objekt unter einem reservierten Key (`__dms_storage_identity__`) über das bestehende `StorageBackend.write`/`read`-Interface — keine neuen Backend-Methoden. Der **Referenzwert** ("was war zuletzt bekannt") liegt zusätzlich in einer neuen `backend_identity`-Tabelle in der Shared DB, nicht nur im Backend selbst. Bei jedem Start vergleicht der Service für jedes Ziel Marker-Datei gegen DB-Referenzwert; bei Abweichung/Fehlen wird der Start standardmäßig verweigert (`RuntimeError` vor `yield`, gleiches Muster wie das bestehende `_validate_settings`). Ein neues, DB-gestütztes `GuardConfig.allow_degraded_start`-Flag (Admin-UI-editierbar, `GET`/`PUT /guard-config`) erlaubt einen degradierten Start, sofern mindestens ein Ziel nachweislich unverändert ist — in diesem Fall werden alle `object_copy`-Zeilen der betroffenen Ziele automatisch auf `pending` zurückgesetzt, sodass die bereits bestehende Retry-Queue (`POST /replication/process-pending`) sie nachzieht.

## Begründung

- **3.6 widerspricht sich selbst, wörtlich genommen**: Es fordert einerseits "`ocrEnabled`-artige" Admin-UI-Konfigurierbarkeit für den Override, andererseits muss ein bereits laufender Service, der wegen eines erkannten Datenträger-Wechsels *nicht startet*, diese Freigabe irgendwie entgegennehmen können, ohne selbst erreichbar zu sein. Auflösung: der Override ist eine **proaktiv gesetzte Standing-Policy** ("falls je ein Wechsel erkannt wird, degradiert starten"), keine Freigabe im Moment der Verweigerung — Postgres (wo `GuardConfig` liegt) ist von einem defekten Storage-Backend unabhängig und bereits vor den Backends selbst verfügbar (siehe `main.py`s Lifespan-Reihenfolge: DB-Engine zuerst, Backends danach), weshalb das Lesen dieser Einstellung beim Start mechanisch unproblematisch ist.
- **Referenzwert darf nicht ausschließlich im Backend selbst liegen**: Ein ausgetauschtes/zurückgesetztes Ziel hat im Fehlerfall gerade *keine* Marker-Datei mehr — vergliche man nur "hat das Backend eine Marker-Datei, und stimmt sie mit sich selbst überein", wäre das trivial immer wahr oder immer ein Erststart-Fall, nie ein erkennbarer Rückfall. Die neue `backend_identity`-Tabelle ist deshalb die eigentliche Quelle der Wahrheit, die Marker-Datei im Backend nur der zu prüfende Gegenwert.
- **Kein neues Backend-Interface nötig**: Die Marker-Datei wird über das bereits bestehende `write()`/`read()` unter einem reservierten Key abgelegt, exakt wie ein normales Objekt — vermeidet eine zweite, parallele Backend-Fähigkeit nur für diesen einen Zweck. Der reservierte Key (`__dms_storage_identity__`, kein Schrägstrich) kollidiert nicht mit echten, stets segmentierten Dokument-/OCR-/Rendition-Keys (`typ/id/...`) — ein dokumentierter Namensraum-Vorbehalt, keine technisch erzwungene Sperre.
- **`id` statt `type` als Schlüssel löst die Mehrfach-Devices-Anforderung direkt mit**: `replication.py` war laut ADR 0004 bereits vollständig generisch gegenüber beliebigen Ziel-`id`-Strings (bestätigt durch dessen eigene Tests, die schon immer mit frei gewählten IDs wie `"a"`/`"b"` statt Backend-Typnamen arbeiteten) — die Beschränkung auf "genau zwei Ziele, je ein Typ" saß ausschließlich in `Settings`/`backends/__init__.py`. Diese Session löst sie dort auf, ohne `replication.py` anzufassen.
- **Kein Umbenennungs-/Migrationsaufwand für bestehende Daten**: `ObjectMetadata.backend`/`ObjectCopy.backend_id` sind schon immer freie Strings ohne FK auf eine Typ-Tabelle — sie bedeuten ab dieser Session "Ziel-`id`" statt "Backend-Typ", was für den unveränderten Default (ein einzelnes Ziel mit `id="local"`) exakt denselben Wert ergibt wie zuvor.
- **Eigene, neue Env-Var-Form (`DMS_TARGETS` als JSON-Liste) statt fortgeführter Flat-Var-Struktur**: `pydantic-settings` unterstützt JSON-Dekodierung komplexer Feldtypen (inkl. verschachtelter Pydantic-Modelle) aus einer einzelnen Umgebungsvariable nativ (empirisch bestätigt) — dasselbe Prinzip, das `gateway-service` bereits für `CORS_ALLOWED_ORIGINS` (eine einfache `list[str]`) nutzt, hier auf eine Liste von Objekten erweitert. Eine nummerierte Env-Var-Form (`DMS_TARGETS__0__TYPE=...`) oder eine separate Config-Datei wären Alternativen gewesen, aber ohne bestehendes Vorbild in diesem Repo und ohne erkennbaren Vorteil gegenüber der bereits bewährten JSON-Form.
- **Zwingende Hintergrund-Replikation bleibt auf dem bestehenden Retry-Queue-Mechanismus** (ADR 0004: expliziter `POST /replication/process-pending`-Endpunkt statt In-Prozess-Hintergrundtask) statt eines neuen automatischen Ausführungsmechanismus — konsistent mit der bereits dokumentierten, weiterhin offenen Lücke "keine automatische periodische Ausführung" (wartet auf den Plugin Orchestration Service, Phase 10). Diese Session ändert daran nichts, macht die Notwendigkeit eines baldigen externen Schedulers aber sichtbarer (ein degradierter Start bleibt sonst dauerhaft degradiert).

## Konsequenzen

- `Settings.backend`/`secondary_backend`/`redundancy_enabled`/`local_storage_base_path`/`s3_*` entfallen ersatzlos zugunsten von `Settings.targets` — kein Rückwärtskompatibilitäts-Shim, da `docker-compose.yml`/`.env`/`.env.example` im selben Commit mitaktualisiert wurden (Default-Verhalten für `cp .env.example .env` bleibt unverändert: ein einzelnes lokales Ziel, keine Redundanz).
- `main.py`s Lifespan öffnet erstmals eine DB-Session **vor** `yield`, außerhalb des sonst überall genutzten `Depends(get_session)`-Requestflusses (`app.state.session_factory()` direkt) — ein neues, aber notwendiges Muster für diesen Service, da der Wächter vor der ersten Anfrage entscheiden muss.
- Ein neu zum Ziel-Set hinzugefügtes Ziel wird beim ersten Start automatisch "geprägt" (Bootstrap, kein Fehlschlag) — es bekommt aber **keine** automatische Kopie bestehender Objekte (Rebalancing bleibt weiterhin ein eigener, noch offener Punkt seit ADR 0004).
- Die Wortobergrenze/Batch-Size-artige Trennung "Deployment vs. Admin-UI" aus [ADR 0016](0016-ocr-configurability-compose-profile-and-live-settings.md) wiederholt sich hier bewusst analog: Ziel-Set = Deployment (`DMS_TARGETS`), Wächter-Override = Admin-UI (`GuardConfig`) — dieselbe Kategorisierungslogik, zweite Anwendung im selben Repo.
- `GET /guard-status` ist rein lesend/informativ (Geräte-ID + Anzahl offener Kopien je Ziel) — kein Mechanismus, um eine falsch als "unverändert" erkannte Geräte-ID manuell zurückzusetzen (z. B. nach einem legitimen, beabsichtigten Datenträgertausch); das müsste aktuell direkt in der `backend_identity`-Tabelle korrigiert werden. Als offener Punkt dokumentiert.
