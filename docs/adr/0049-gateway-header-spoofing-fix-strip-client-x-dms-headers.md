# 0049 — Gateway: client-supplied X-DMS-\* headers are now stripped before proxying (security finding + fix)

**Status:** accepted
**Context:** Discovered during live verification of P14-S11 (delegation on absence, 4.4a) — unrelated to the actual session mandate, but directly security-relevant to its design.

## Decision

`gateway_service.upstream.filter_headers()` now additionally strips **every client-supplied `X-DMS-*` header**, on top of the existing hop-by-hop headers, before the identity headers derived by the gateway itself from the validated JWT (`X-DMS-Principal`, `X-DMS-Username`, `X-DMS-Roles`) as well as `X-DMS-Maintenance-Active` are set.

## Rationale

- **The finding**: during live verification of `GET /delegations/check` (P14-S11), it was noticed that a self-supplied `X-DMS-Principal` header arrived at the downstream service (`permission-service`) despite a valid bearer token — not the real value derived from the JWT. Reproduced with a minimal Python snippet against Starlette's real `Headers` class: `proxy()`'s `headers = filter_headers(request.headers)` returns a `dict` whose keys take on exactly the ASGI-normalized (lowercased) casing of the incoming headers (e.g. `"x-dms-principal"`), while `identity_headers = {"X-DMS-Principal": ...}` is capitalized in the source code. `headers.update(identity_headers)` on a Python `dict` only overwrites keys with an exactly matching spelling — `"x-dms-principal"` and `"X-DMS-Principal"` are two **different** keys. Both consequently ended up as two separate header lines in the upstream request; which value actually "won" at the receiver depended on the respective HTTP parser — empirically verified: the client-sent (spoofed) value prevailed.
- **Impact**: any authenticated principal (given a valid bearer token — the token requirement itself could NOT be bypassed, the absence of a token still correctly resulted in `401`) could thereby impersonate **any other person or any set of roles** toward any backend service that evaluates `X-DMS-Principal`/`X-DMS-Roles`. Affected: P5e-S2 (reference number admin role check), P14-S6 (teamspace membership check), P14-S10 (share link creator/admin revocation), P14-S11 (delegation check/revocation) — every place in the system that has progressively built trust on these headers since P5e-S2. The bearer token requirement itself (authentication) remained intact — the finding concerns exclusively the downstream **identity propagation** (authorization), not login protection.
- **The fix**: `filter_headers()` discards any incoming header whose lowercased name starts with `"x-dms-"` — regardless of exact casing (`X-DMS-Principal`, `x-dms-principal`, `X-Dms-Principal`, ...). Since `X-DMS-*` headers are exclusively intended for the internal trust chain set by the gateway itself (no legitimate client ever sends them), a blanket removal without an exception list is both safe and future-proof — even an `X-DMS-*` header added later would automatically be protected, without needing to adjust the filter again.
- **Why not instead merge `identity_headers` keys case-insensitively**: that would only be safe for the three/four headers known today, a later new `X-DMS-*` header would need to be added explicitly — the blanket prefix filtering in the `filter_headers()` step is the more robust, more generic solution and fits the already-existing purpose of this function ("what is allowed to come from the client").
- **Live verified**: the same spoofing attempt that succeeded before the fix demonstrably returns the real, JWT-derived identity instead of the spoofed value after rebuilding/restarting the `gateway-service` container (`permission-service`'s `POST /delegations` used as a genuine "echo" target, no mock).

## Consequences

- **No known case of actual abuse** in this development environment — the finding arose from routine live verification, not from an incident report. Since this project is a reference implementation in a sandbox development environment (no real production installation with external users), a retroactive forensic review is not warranted — the fix closes the gap going forward.
- **All prior sessions that described `X-DMS-Principal`/`X-DMS-Roles` as "trustworthy because injected by the gateway"** (P5e-S2, P14-S6, P14-S10, P14-S11) were correct in their description of the INTENDED architecture — the actual implementation of the gateway itself had the gap, not the respective consumer logic in the backend services. None of these sessions need to be revised in substance.
- **Direct access to a backend service bypassing the gateway** (e.g. `curl` directly against a service's port exposed on the host in this dev environment) remains unprotected against header spoofing — this is the already-documented, deliberate boundary in many places ("authorization ... still not enforced in several places", `docs/architecture.md`) and lies outside what a gateway fix can solve. The finding fixed here concerned exclusively the path **through** the gateway, which had previously been incorrectly considered fully trustworthy.
- **Response path also hardened**: `filter_headers()` is also applied to the response coming back from upstream (`filter_headers(upstream_response.headers)`) — a backend service therefore also cannot pass an `X-DMS-*` header through to the original caller on the response path, although no concrete attack scenario is known for this (purely defensive, same function, no extra effort).
