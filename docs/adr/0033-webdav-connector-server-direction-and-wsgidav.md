# 0033 — WebDAV Connector: server direction, `wsgidav`+`WsgiToAsgi`, synchronous connector SDK

**Status:** accepted
**Context:** P12-S1 (Concept 3.3, "Connector Architecture"). P12-S0 decided, upon check-in, on WebDAV over CMIS as the first reference connector (CMIS follows as its own session, P12-S4). Concept 3.3/3.7/3.8/9/12 are ambiguous as to whether a connector opens the DMS *up to* external programs or, conversely, taps into an external repository — this had to be clarified before any implementation, since the two directions imply completely different architectures.

## Decision

**Direction: WebDAV server, not client.** Two concrete concept/ADR passages resolve the ambiguity: Concept 4.2 ("If a user opens a document from within an application, e.g. Word via WebDAV/CMIS integration, for editing, an edit lock is automatically set") and [ADR 0002](0002-document-locking-optimistic-conflict-detection.md) ("Corresponds to the established optimistic-concurrency/ETag pattern from WebDAV/CMIS, which the document is addressed through by external applications anyway") — both describe the DMS as the system addressed via WebDAV, not as a client of a foreign repository. `webdav-connector` therefore makes `folder-service`/`document-service` themselves addressable via WebDAV (mountable like a network drive in Explorer/Finder/Word).

**Protocol engine: `wsgidav` (MIT) instead of a custom build.** Building WebDAV from scratch, including correct Windows Explorer/Finder compatibility (Depth header, If header, lock-token semantics, many client-specific quirks), is a substantial, error-prone project in its own right. `wsgidav` has a documented, officially supported extension point for non-filesystem backends (`DAVProvider`/`DAVCollection`/`DAVNonCollection`, with real examples for MongoDB/MySQL/Mercurial backends in the bundled `virtual_dav_provider.py`) — the right place to hook `folder-service`/`document-service` in behind it, without reinventing the protocol. `"lock_storage": True` additionally provides a complete, RFC-4918-compliant in-process lock manager (opaque tokens, timeouts, If-header checking) — no custom WebDAV LOCK/UNLOCK protocol mechanics needed.

**WSGI-in-ASGI: `asgiref.wsgi.WsgiToAsgi` mounts `wsgidav` under `/webdav` in a normal FastAPI app.** `app.mount(settings.webdav_mount_path, WsgiToAsgi(WsgiDAVApp(config)))` keeps the service outwardly consistent with the standard service template (`/healthz`, `BaseServiceSettings`, registry self-registration, license checking run as normal FastAPI routes) — only the actual WebDAV traffic under `/webdav/*` passes through the bridged wsgidav engine. **Important**: `WsgiToAsgi` mounts only the ASGI transport; wsgidav itself knows nothing about the mount prefix — the `"mount_path"` config key in the `WsgiDAVApp` config dict must be set explicitly to the same value, otherwise wsgidav returns hrefs relative to its own root instead of the actual public URL (see Consequences).

**DMS tree translation lives in its own, reusable library (`libs/dms-connector-sdk`), not in the connector itself.** Concept 3.3 explicitly requires a reusable SDK, not just a connector. `DmsTreeClient` (path resolution, CRUD, move, lock wrapper) and `ConnectorCapability`/`ConnectorDescriptor` (capability description `read`/`write`/`metadata`/`locking`/`versioning`, taken verbatim from 3.3) live there — the future CMIS connector (P12-S4) needs the same DMS-side logic, only a different protocol layer on top.

**`DmsTreeClient` is deliberately synchronous (`httpx.Client`, not `AsyncClient`).** wsgidav's `DAVProvider` interface is itself synchronous (WSGI) — an async variant would have needed an async/sync bridge (`asgiref.async_to_sync`) inside the provider across multiple nested thread/loop boundaries, a known fragile pattern. A future FastAPI-based connector (CMIS, P12-S4) can still safely use the library: FastAPI runs normal `def` endpoints (not `async def`) automatically in its own thread pool.

**WebDAV LOCK/UNLOCK is mapped onto `document-service`'s existing lock endpoints**, not onto a second, dedicated lock system — a file locked via WebDAV is server-side the same lock the user UI also sees (4.2). **Deliberate limit**: the document-service lock is held only for the duration of each individual write operation (`end_write()` acquires/releases it around the upload), not for the entire editing duration of an externally opened document — a WebDAV Basic Auth session has no native session concept, unlike a browser login, that could carry a persistent lock.

**Real additional fix found during implementation, in `document-service`**: `DocumentUpdate` got a new optional `folder_id` field; `PATCH /documents/{id}` moves the document if it differs from the current value (with the same target-existence/object-hierarchy validation as at creation). `folder-service`'s `PATCH /folders/{id}` already supported `parent_id` changes since P3-S3 — the counterpart for documents was completely missing, but was strictly necessary for WebDAV MOVE (a mandatory method).

## Rationale

- **Server instead of client is the only direction consistent with ADR 0002/Concept 4.2** — a client implementation (DMS pulls content from a foreign WebDAV server) would have ignored both passages and would have surfaced as a wrong decision at the next concept review.
- **`wsgidav` instead of a custom build**: the alternative would be implementing RFC 4918, including all practically relevant client quirks (Windows Explorer/macOS Finder), from scratch — a standalone project outside this session's scope, with no advantage over an actively maintained, established library.
- **Own SDK library instead of code directly in the connector**: without this separation, P12-S4 (CMIS) would either have to import code from `webdav-connector` (an unclean cross-service import) or duplicate the DMS tree logic — both worse than the SDK separation already required by Concept 3.3 anyway.
- **Synchronous SDK instead of async+bridge**: a nested `asgiref.async_to_sync` bridge inside wsgidav's own synchronous callback context is a documented fragile pattern (potential deadlocks/thread-pool exhaustion with nested event loops) — the synchronous variant is both simpler and, for the given use case (no high-concurrency target for a reference implementation), without any downside.
- **Lock mapping onto document-service instead of a dedicated lock system**: two parallel, unsynchronized lock systems for the same document would be an immediate consistency break (a document locked via WebDAV could still appear free in the user UI) — unacceptable for 4.2's core promise.

## Consequences

- **The `mount_path` configuration trap is real and remains relevant for any future WSGI-in-ASGI mount**: without the `"mount_path"` key, wsgidav returns technically valid but, for the client, wrong hrefs — WebDAV clients that determine the resource name by stripping the mount prefix from the href (e.g. `webdav4`) end up with **mangled rather than erroring** names, a particularly insidious silent failure (no crash, no error message, just wrong data). Every future connector that mounts `WsgiToAsgi` under a subpath must apply the same pattern.
- **An additional HTTP round trip per document in every directory listing**: `document-service`'s `DocumentOut` carries no file metadata (size/content type/checksum, which live only on `DocumentVersionOut`) — `DmsTreeClient` must fetch these separately for every `TreeDocument` construction. Accepted for a reference implementation; a possible optimization point at a future performance session (e.g. for very large folders) (e.g. denormalization on the `document-service` side or a batch endpoint).
- **Only one WebDAV connector instance can reasonably run at a time**: wsgidav's lock manager is in-process (`lock_storage: True`), analogous to `gateway-service`'s `RateLimiter` (ADR 0005) — with multiple instances behind a load balancer, WebDAV LOCKs would not be visible across instances (the document-service lock itself would be unaffected, since it is managed centrally there).
- **Real Windows Explorer/macOS Finder compatibility is untested** — this session's sandboxed test environment had no GUI client available; testing was done exclusively via a real WebDAV client (`webdav4`) at the protocol level. `wsgidav` is the engine actually used/tested in practice for this — a human should mount it for real once before production use.
