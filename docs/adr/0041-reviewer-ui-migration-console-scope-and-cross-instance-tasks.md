# 0041 — Reviewer/approval UI + migration console: two new frontend apps, new cross-instance task list, no new authorization layer

**Status:** accepted
**Context:** P14-S2 (reviewer/approval UI + migration console, concept 8)

## Decision

Two new, standalone Next.js static-export frontend applications (identical scaffolding to `apps/user-ui`/`apps/admin-ui`/`apps/process-designer`, ADR 0006), port 3005 and 3004 respectively:

- **`apps/reviewer-ui`** — "a slim focus on approval tasks only, including four-eyes cases" (8, verbatim). Two areas: a task inbox for ready BPMN manual/signature tasks across **all** running `workflow-service` instances, and a generic four-eyes approval inbox across **all** `action_type`s from `permission-service`'s `GET /approval-requests`.
- **`apps/migration-console`** — a console for `migration-service` transfer operations (7.2/8, verbatim "migration console for transfer operations"): managing installation pairing, starting/observing transfers (dry run, deletion deadline, four-eyes hint, phase timeline, polling).

A new `GET /tasks` endpoint in `workflow-service` (closing a previously missing gap: only the instance-scoped `GET /instances/{id}/tasks` existed) collects the ready tasks of all `running` instances and filters out `federated`/`federated_return` tasks (which resolve exclusively and automatically via the Federation Hub, 7.4). No new authorization layer for either app - both backends (`workflow-service`'s task endpoints, `permission-service`'s approval endpoints, `migration-service`'s transfer/pairing endpoints) were already open to every authenticated principal, or gated only by their respective own license check; no domain-separated admin role is needed.

## Rationale

- **First generic consumer of `permission-service`'s approval API**: previously there were three independent consumers, each narrowly filtered to a single `action_type` (`admin-ui`'s `ManipulationSection` for only the three curated query-manipulation actions, `admin-ui`'s `SuperuserBreakGlass` for only `auth.superuser.activate`, `user-ui`'s `ApprovalsPane` for only `document.delete`/`folder.delete`) - even though the backend API itself was fully generic over arbitrary `action_type`s from the start. `reviewer-ui`'s approvals area is the first UI to consume `GET /approval-requests` **unfiltered**, making every four-eyes request in the system actually visible, regardless of which service generated it (`migration.transfer.start`, `permission.scope_lock.create`, future action types with no code change to this UI). The three existing, narrowly filtered consumers remain unchanged - they continue to serve their own, context-specific purpose (e.g. the approval link right next to the affected query manipulation); `reviewer-ui` is an additional, complete overview, not a replacement.
- **`GET /tasks` as a generic, reusable primitive rather than reviewer-ui-specific logic**: the obvious alternative (doing the cross-instance aggregation client-side in `reviewer-ui` itself, e.g. `GET /instances?status=running` followed by N calls to `GET /instances/{id}/tasks`) would have generated considerably more requests on one hand, and on the other would have pushed pure backend logic (which task types are even completable by a human) into the frontend layer - that logic would have been duplicated by a future second consumer (e.g. a mobile app or a CLI command). The new endpoint instead joins the already-existing cross-instance `GET /instances` endpoints, following exactly the same iteration pattern as the already-existing `_sla_poll_loop` (iterate over all `running` instances).
- **No new authorization layer for task completion/approval decisions**: `workflow-service`'s task completion was already deliberately open to every authenticated principal (P6-S6 decision, "everyday use should not require a domain admin role", see ADR 0024), `permission-service`'s approval endpoints already optionally check a `required_permission` per action type as well as, structurally, that initiator and decider are not identical (the core four-eyes rule) - both already sufficiently granular. A further, app-specific access check just for `reviewer-ui`/`migration-console` would have duplicated this already-existing, service-side enforcement without real added value.
- **`migration-console` maps only the three source-side relevant endpoints** (`POST/GET /paired-installations`, `POST/GET /transfers`) - the `.../steps/*` endpoints are targets of automatic `connector_call` service tasks (P12-S2) and the `/inbound/*` endpoints are called by the **paired counterpart**, never by local operating staff - both deliberately not wired up in the console, as they are purely internal workflow/protocol mechanics.
- **Lightweight polling (5s) instead of push in `migration-console`**: a transfer automatically progresses through several phases in the background (the associated `workflow-service` instance advances itself via `connector_call` service tasks) - without repeated reloading, the console would stay stuck at the state of the last page load. Identical, already-established pattern to `MaintenanceBanner`'s 30s poll in all frontend apps - no new WebSocket/SSE mechanism for a reference implementation.
- **Two new ports (3004/3005) instead of the originally obvious 3003/3004**: `3003` is already occupied by `GRAFANA_PORT` (10.1) - actually noticed while setting up the compose blocks, before it caused a startup conflict. Along the way, a second, independent finding: the CORS-origin default in `docker-compose.yml` (`DMS_CORS_ALLOWED_ORIGINS`) had never included `PROCESS_DESIGNER_PORT` (3002) since P6-S8 - `.env.example`'s own default was correct, but `docker-compose.yml`'s built-in fallback (used when there's no `.env` file) was not. Both gaps fixed together in the same line, since they were directly adjacent to the change already needed.

## Consequences

- **No rejection-form convenience beyond `window.prompt`** in `reviewer-ui`'s approval rejection - sufficient for a reference implementation, a dedicated dialog form would be pure UI polish with no new domain logic.
- **No server push/notification to reviewers/migration owners** - both apps are pure pull interfaces (the task list must be actively opened, transfer progress actively watched). Already documented elsewhere as a deliberate limitation (`permission-service`'s ADR 0022: "no notification to approvers"), structurally identical here for tasks/transfers.
- **`GET /tasks` returns tasks from all process families unfiltered** - no role-/lane-based preselection ("only my tasks"), since `workflow-service` does not enforce lane assignments anywhere yet (an already-documented limitation, see `docs/services/workflow-service.md` "Open Points"). `reviewer-ui` accordingly shows every logged-in principal the same complete list.
