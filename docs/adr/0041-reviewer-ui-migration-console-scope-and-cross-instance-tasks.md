# 0041 — Reviewer/Approval-UI + Migrations-Konsole: zwei neue Frontend-Apps, neue Cross-Instanz-Aufgabenliste, keine neue Autorisierungsschicht

**Status:** akzeptiert
**Kontext:** P14-S2 (Reviewer/Approval-UI + Migrations-Konsole, Konzept 8)

## Entscheidung

Zwei neue, eigenständige Next.js-Static-Export-Frontend-Anwendungen (identisches Grundgerüst wie `apps/user-ui`/`apps/admin-ui`/`apps/process-designer`, ADR 0006), Port 3005 bzw. 3004:

- **`apps/reviewer-ui`** — "schlanker Fokus nur auf Freigabeaufgaben, auch für Vier-Augen-Fälle" (8, wörtlich). Zwei Bereiche: eine Aufgaben-Inbox für bereite BPMN-Manual-/Signature-Tasks über **alle** laufenden `workflow-service`-Instanzen hinweg, und eine generische Vier-Augen-Freigabe-Inbox über **alle** `action_type`s von `permission-service`s `GET /approval-requests`.
- **`apps/migration-console`** — Konsole für `migration-service`-Transfer-Vorgänge (7.2/8, wörtlich "Migrations-Konsole für Transfer-Vorgänge"): Installations-Paarung verwalten, Transfers starten/beobachten (Dry-Run, Löschfrist, Vier-Augen-Hinweis, Phasen-Zeitverlauf, Polling).

Neuer Endpunkt `GET /tasks` in `workflow-service` (schließt eine bislang fehlende Lücke: es gab nur die instanzgebundene `GET /instances/{id}/tasks`) sammelt die bereiten Tasks aller `running`-Instanzen ein und filtert `federated`/`federated_return`-Tasks heraus (die schließen sich ausschließlich automatisch über den Federation Hub ab, 7.4). Keine neue Autorisierungsschicht für beide Apps - beide Backends (`workflow-service`s Task-Endpunkte, `permission-service`s Approval-Endpunkte, `migration-service`s Transfer-/Paarungs-Endpunkte) waren bereits für jeden authentifizierten Principal offen bzw. nur über die jeweils eigene Lizenzprüfung gegated, keine domänengetrennte Admin-Rolle nötig.

## Begründung

- **Erster generischer Konsument von `permission-service`s Approval-API**: bislang gab es drei unabhängige, jeweils eng auf einen einzigen `action_type` gefilterte Konsumenten (`admin-ui`s `ManipulationSection` nur für die drei kuratierten Query-Manipulationsaktionen, `admin-ui`s `SuperuserBreakGlass` nur für `auth.superuser.activate`, `user-ui`s `ApprovalsPane` nur für `document.delete`/`folder.delete`) - obwohl die Backend-API selbst von Anfang an vollständig generisch über beliebige `action_type`s war. `reviewer-ui`s Freigaben-Bereich ist die erste UI, die `GET /approval-requests` **ungefiltert** konsumiert und damit tatsächlich jede Vier-Augen-Anfrage im System sichtbar macht, unabhängig davon, welcher Service sie erzeugt hat (`migration.transfer.start`, `permission.scope_lock.create`, künftige Aktionstypen ohne Codeänderung an dieser UI). Die drei bestehenden, eng gefilterten Konsumenten bleiben unverändert bestehen - sie erfüllen weiterhin ihren jeweils eigenen, kontextspezifischen Zweck (z. B. der Freigabelink direkt neben der betroffenen Query-Manipulation), `reviewer-ui` ist eine zusätzliche, vollständige Übersicht, kein Ersatz.
- **`GET /tasks` als generisches, wiederverwendbares Primitiv statt reviewer-ui-spezifischer Logik**: die naheliegende Alternative (die Cross-Instanz-Aggregation clientseitig in `reviewer-ui` selbst vornehmen, z. B. `GET /instances?status=running` gefolgt von N Aufrufen `GET /instances/{id}/tasks`) hätte einerseits deutlich mehr Requests erzeugt, andererseits reine Backend-Logik (welche Task-Typen sind für einen Menschen überhaupt abschließbar) in die Frontend-Schicht verlagert - das hätte bei einem künftigen zweiten Konsumenten (z. B. einer mobilen App oder einem CLI-Befehl) dieselbe Filterlogik dupliziert. Der neue Endpunkt reiht sich stattdessen bei den bereits vorhandenen instanzübergreifenden `GET /instances`-Endpunkten ein, folgt exakt demselben Iterationsmuster wie der bereits bestehende `_sla_poll_loop` (über alle `running`-Instanzen iterieren).
- **Keine neue Autorisierungsschicht für die Aufgaben-Erledigung/Freigabe-Entscheidung**: `workflow-service`s Task-Abschluss war bereits bewusst für jeden authentifizierten Principal offen (P6-S6-Entscheidung, "Alltagsnutzung soll keine Domain-Admin-Rolle brauchen", siehe ADR 0024), `permission-service`s Freigabe-Endpunkte prüfen bereits pro Aktionstyp optional einen `required_permission` sowie strukturell, dass Initiator und Entscheider nicht identisch sind (Kern-Vier-Augen-Regel) - beides bereits ausreichend granular. Eine weitere, App-spezifische Zugriffsprüfung nur für `reviewer-ui`/`migration-console` selbst hätte diese bereits bestehende, service-seitige Durchsetzung dupliziert, ohne echten Mehrwert.
- **`migration-console` bildet nur die drei quellseitig relevanten Endpunkte ab** (`POST/GET /paired-installations`, `POST/GET /transfers`) - die `.../steps/*`-Endpunkte sind Ziele automatischer `connector_call`-Service-Tasks (P12-S2) und die `/inbound/*`-Endpunkte werden von der **gepaarten Gegenseite** aufgerufen, nie vom lokalen Bedienpersonal - beide bewusst nicht in der Konsole verdrahtet, sie sind reine interne Workflow-/Protokoll-Mechanik.
- **Leichtgewichtiges Polling (5s) statt Push in `migration-console`**: ein Transfer durchläuft mehrere Phasen automatisch im Hintergrund (die zugehörige `workflow-service`-Instanz treibt sich selbst voran über `connector_call`-Service-Tasks) - ohne wiederholtes Nachladen bliebe die Konsole auf dem Stand des letzten Seitenaufrufs stehen. Identisches, bereits etabliertes Muster wie `MaintenanceBanner`s 30s-Poll in allen Frontend-Apps - kein neuer WebSocket-/SSE-Mechanismus für eine Referenzimplementierung.
- **Zwei neue Ports (3004/3005) statt der ursprünglich naheliegenden 3003/3004**: `3003` ist bereits durch `GRAFANA_PORT` (10.1) belegt - beim Anlegen der Compose-Blöcke real bemerkt, bevor es zu einem Startkonflikt kam. Nebenbei ein zweiter, unabhängiger Fund: der CORS-Origin-Default in `docker-compose.yml` (`DMS_CORS_ALLOWED_ORIGINS`) enthielt `PROCESS_DESIGNER_PORT` (3002) seit P6-S8 nie - `.env.example`s eigener Default war zwar korrekt, aber `docker-compose.yml`s eingebauter Fallback (greift ohne `.env`-Datei) nicht. Beide Lücken in derselben Zeile mitkorrigiert, da direkt angrenzend an die ohnehin nötige Änderung.

## Konsequenzen

- **Kein Ablehnen-Formular-Komfort über `window.prompt` hinaus** in `reviewer-ui`s Freigabe-Ablehnung - für eine Referenzimplementierung ausreichend, ein eigenes Dialog-Formular wäre reine UI-Politur ohne neue Fachlogik.
- **Kein Server-Push/keine Benachrichtigung an Reviewer/Migrations-Verantwortliche** - beide Apps sind reine Pull-Oberflächen (Aufgabenliste muss aktiv aufgerufen, Transfer-Fortschritt aktiv beobachtet werden). Bereits an anderer Stelle als bewusste Grenze dokumentiert (`permission-service`s ADR 0022: "keine Benachrichtigung an Freigebende"), hier für Tasks/Transfers strukturell identisch.
- **`GET /tasks` liefert Tasks aller Prozessfamilien ungefiltert** - keine rollen-/lane-basierte Vorauswahl ("nur meine Aufgaben"), da `workflow-service` Lane-Zuordnungen bislang nirgends durchsetzt (bereits dokumentierte Grenze, siehe `docs/services/workflow-service.md` "Offene Punkte"). `reviewer-ui` zeigt entsprechend jedem angemeldeten Principal dieselbe vollständige Liste.
