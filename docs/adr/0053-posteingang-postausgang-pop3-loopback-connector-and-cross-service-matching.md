# 0053 — Inbox/Outbox: real POP3 loopback connector, case reference number as new first-class field, proposed instead of silent matching

**Status:** accepted
**Context:** P15-S3 (inbox/outbox + mail room role, concept §2.5/3.3/7.1)

## Decision

Five related decisions, all clarified in advance with the user via follow-up questions:

1. **Real, standard-protocol-based connector instead of a connector-agnostic stub.** New `mail-connector` service retrieves incoming mail via POP3 (`poplib`, standard library). In the development environment, `mailpit`'s own POP3 server, built in since v1.15 (`--pop3-auth-file`), serves as a self-loopback source — the same mail submitted via SMTP can be retrieved again through a real protocol, without needing an external mail server (same principle as the federation hub self-loopback, P6-S9). The retrieval protocol is pluggable as a `MailboxBackend` interface (same "pluggable" principle as storage backends/virus-scan engines) — a future IMAP/Graph API backend only changes `backends/`, not the rest of the service.
2. **Automatic matching against TWO reference types**: the already-existing, document-related `Kennzeichen` (reference number, 2.2, P5e-S1) AND a new, first-class `Case.vorgangsnummer` (case reference number) field (case-service, new in this session). Both are searched via a generic regex candidate extractor (`X-Y` token, 2-10 alphanumeric characters per side) over subject+body, then checked against two new cross-service lookup endpoints (`GET /documents/by-kennzeichen`, `GET /cases/by-vorgangsnummer`).
3. **`Case.vorgangsnummer` as a new first-class, installation-wide unique field** — deliberately NOT via `object-type-service`'s existing reference number generator mechanism (which is strictly limited to `applies_to="document"`, see `object_type_service/schemas.py`). Instead, a dedicated, simpler generator directly in `case-service` (a single installation-wide counter rather than a per-object-type counter as with the reference number) — every new circulation folder automatically gets a case reference number, not an optional feature.
4. **Proposed, not silent, matching**: a unique hit sets a message to `status="proposed_match"` — actual document creation happens only once the mail room explicitly calls `POST /inbound/{id}/confirm-match`. An ambiguous (multiple hits across both reference types) or missing match stays at `status="unassigned"` and awaits manual assignment (`POST /inbound/{id}/assign`).
5. **The message body itself is treated like a (synthetic) attachment** — wrapped as `{Subject}.txt` during the ingestion step and sent through the mandatory virus scan (10.3) exactly like any real file attachment, and created as its own document on assignment. The correspondence itself is just as worthy of archiving as its enclosures.

## Rationale

- **Why a real connector instead of a stub**: the follow-up question to the user established that an actually working connector, tested over a standard protocol, was preferred over a mere "generic receipt endpoint, protocol to follow later" stub — made possible as soon as mailpit's POP3 server was confirmed enable-able (`--pop3-auth-file`, verified via a real `poplib` round trip before implementation began), enabling a complete end-to-end test of this session with no external infrastructure.
- **Why candidate extraction via a generic regex instead of one derived from the actually configured formats**: format-exact extraction would require an extra cross-service call before EVERY candidate search (loading all configured `kennzeichen_format` values of all object types) to dynamically build a regex pattern from them. The generic `X-Y` candidate already covers both default formats (`{YYYY}-{Laufende_Nummer}`) and is sufficient for a reference implementation — an installation with strongly deviating formats must adjust the pattern in `matching.py` (documented, deliberate boundary).
- **Why two independent lookup endpoints instead of a shared one**: `document-service` and `case-service` are independent services with their own schema (concept 3.1) — a shared lookup endpoint would have artificially made one of the two domains dependent on the other. `mail-connector`'s `matching.py` queries both separately and combines the hits itself.
- **Why `vorgangsnummer` is NOT generated via the existing reference number generator**: attempting to extend `object-type-service`'s `applies_to` literal with `"case"` would have touched several already-existing schema/validation paths (concept 2.2a object hierarchy, 2.2b layouts, 4.5 constraints — all explicitly designed only for `"document"`/`"folder"`) — disproportionate for the narrower purpose pursued here (reliable matching). A dedicated, simpler single-counter generator directly in `case-service` achieves the same goal without this risk.
- **Why proposed instead of silent matching**: concept §2.5 itself describes the target workflow as "review/assignment" by the mail room role, not as automatic assignment. In addition, `Kennzeichen` (unlike `vorgangsnummer`) is only unique per object type + year, not globally — an automatic, silent match could in principle (even if unlikely) produce incorrectly assigned correspondence. A human therefore confirms every match, even a recognized one, before it takes effect.
- **Why the message body is treated like an attachment**: avoids special-casing (no separate "message body document" data model) and ensures that plain text also runs through the same mandatory virus scan as any other new file entering the system (10.3 applies consistently to any new content, not only to file attachments in the narrow sense).

## Consequences

- **Two new special folders `inbox`/`outbox`** (folder-service, same fixed-ID pattern as `root`) are protected against renaming/moving/hard deletion/trashing (409) — `root` itself does not have this protection (a pre-existing gap, deliberately not closed retroactively here, see `docs/services/folder-service.md` "Open Points").
- **Mail room role as its own settings role gate** (`poststelle_role`, default `"dms-poststelle"`, NOT `"dms-admin"` as is otherwise usual in this project) — concept §2.5 explicitly describes it as a dedicated operational role, not IT administration.
- **Attachments go through a second virus scan on assignment (`confirm-match`/`assign`)** via the regular `document-service` path (`POST /documents`), even though they were already scanned on arrival — unlike the quarantine release (P15-S2, ADR 0052), this is unproblematic here, since the bytes were classified "clean" on the first scan and a second scan reproduces the same (negative) finding, not the same (positive) one. No bypass mechanism needed, deliberately no unnecessary complexity added.
- **`sent_by` when sending outbound mail comes server-side from `X-DMS-Principal`**, not from the request body — prevents a client-forged origin claim (same principle as `deleted_by`/`confirmed_by`/`resolved_by` elsewhere in this project).
- **An installation that configures `poststelle_role` differently from `"dms-poststelle"`** must manually adjust the corresponding frontend constant in `IconRail.tsx` — the same, already repeatedly accepted limitation as with `TrashPane.tsx`/`QuarantinePane.tsx`.
- **No bulk/re-scan of candidates on a later format change**: if an installation later changes `case-service`'s `case_number_config.format` or an object type's `kennzeichen_format`, already-received, unconfirmed messages are NOT retroactively re-matched — matching runs only at retrieval time.
