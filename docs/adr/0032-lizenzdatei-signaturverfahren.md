# 0032 — Lizenzdatei: JWT/RS256 statt eines neuen Signaturformats

**Status:** akzeptiert
**Kontext:** P9-S0 (Phasen-Kickoff-Planung Phase 9, Konzept 9.1–9.3 "Lizenzsystem"), `IMPLEMENTATION_PLAN.md` benannte für diese Session explizit die Festlegung des Signaturverfahrens für die Lizenzdatei vor P9-S1. Reine Recherche-/Planungssession, kein Implementierungscode.

## Entscheidung

Die signierte Lizenzdatei (9.2: "signierte Lizenzdatei, die alle Dimensionen und Gültigkeitszeitraum enthält") wird als **JWS/JWT im Compact-Format, Algorithmus RS256**, ausgeliefert — die Lizenzdimensionen (9.1: Nutzeranzahl-Modell, lizenzierte Komponenten, Speicher-/Dokumentenobergrenzen) werden als eigene Claims kodiert, `exp`/`nbf` decken den Gültigkeitszeitraum ab. Der private Schlüssel wird **offline** (außerhalb jedes Docker-Images/Repos) erzeugt und verwaltet und erzeugt Lizenzdateien für Kunden; jede Installation erhält nur den **öffentlichen** Schlüssel, eingebettet über eine Einstellung/gemountete Datei im `license-service` (P9-S1), analog zu `dms-auth-client`s `TokenValidator`, aber mit einem statisch eingebetteten Schlüssel statt eines per JWKS-URL abgerufenen.

## Begründung

- **`python-jose[cryptography]>=3.3` ist bereits Abhängigkeit** von `libs/dms-auth-client` (`TokenValidator` prüft dort RS256-signierte Keycloak-Access-Tokens gegen ein JWKS) — `RS256` ist im installierten `jose`-Build bestätigt unterstützt (`jwt.ALGORITHMS.SUPPORTED` enthält `RS256`/`RS384`/`RS512`/`ES256`/`ES384`/`ES512`, **nicht** `EdDSA`/Ed25519). Ein neues Format oder eine neue Bibliothek einzuführen, obwohl das System bereits ein bewährtes, getestetes JWT-Verifikationsmuster besitzt, wäre unnötige Zusatzkomplexität ohne echten Vorteil — dieselbe "wiederverwenden statt neu erfinden"-Linie wie bei den meisten bisherigen Architekturentscheidungen dieses Projekts.
- **Asymmetrisch, nicht HMAC**: anders als `query-service`s Dry-Run-Token (ADR-lose Einzelentscheidung, P8-S2, HMAC-SHA256 mit einem installationsweiten Secret) muss eine Lizenzdatei von jeder Installation verifizierbar sein, ohne dass die Installation selbst signieren können darf — ein geteiltes HMAC-Secret würde jeder Installation die Fähigkeit geben, sich selbst beliebige Lizenzen auszustellen. RS256 (asymmetrisch) trennt Signieren (nur beim Lizenzgeber, offline) von Verifizieren (jede Installation, mit dem öffentlichen Schlüssel).
- **RS256 statt ES256**: `jose` unterstützt beides; RSA wurde gewählt, weil es das in diesem Projekt bereits einzige tatsächlich genutzte asymmetrische JWT-Verfahren ist (Keycloaks Default für signierte Access-Tokens, von `TokenValidator` bereits verifiziert) — keine zweite Kurve/kein zweites Schlüsselformat im selben System pflegen. Für eine selten neu ausgestellte, langlebige Datei (Lizenzlaufzeit typischerweise Monate/Jahre, nicht Sekunden wie ein Session-Token) spielt RSAs größere Schlüssel-/Signaturgröße gegenüber ECDSA keine relevante Rolle.
- **Kein JWKS-Endpunkt, kein Schlüssel-Rotationsmechanismus in dieser ersten Ausbaustufe**: anders als Keycloaks JWKS (Schlüssel können dort über den Realm rotiert werden, `TokenValidator` cached/refresht) gibt es für die Lizenzdatei keinen Online-Dienst, den eine Installation beim Lizenzgeber abfragen könnte (Installationen können offline/luftgetrennt betrieben werden) — der öffentliche Schlüssel wird deshalb statisch mit dem `license-service`-Image/der Konfiguration ausgeliefert. Eine Schlüsselrotation (kompromittierter privater Schlüssel) würde ein neues `license-service`-Release mit neuem öffentlichen Schlüssel erfordern — als bewusste Einschränkung dokumentiert, nicht Teil dieser Session.
- **JWT-Format ist selbstbeschreibend und tooling-freundlich**: Standard-Claims (`exp`, `nbf`, `iat`) decken den Gültigkeitszeitraum ab, ohne eigene Datumsfelder/eigene Parsing-Logik zu erfinden; benutzerdefinierte Claims (z. B. `max_users`, `concurrent_sessions`, `licensed_components`, `storage_limit_gb`, `document_limit`, `installation_id`) transportieren die neun Konzept-9.1-Dimensionen. Menschlich inspizierbar (jedes JWT-Debug-Tool zeigt den Payload, auch ohne Signaturprüfung), was Support-Diagnosen erleichtert.

## Konsequenzen

- P9-S1 (License Service) verifiziert Lizenzdateien mit einem `TokenValidator`-artigen, aber JWKS-losen Verifizierer (statischer öffentlicher Schlüssel aus Settings/gemounteter Datei) — kein neuer Krypto-Code, direkte Wiederverwendung von `python-jose[cryptography]`.
- Der private Schlüssel darf **nirgends** im Repository, in keinem Docker-Image und in keiner Konfigurationsdatei des Systems selbst auftauchen — er lebt ausschließlich außerhalb dieses Projekts beim Lizenzgeber. Eine Lizenzdatei-Ausstellungs-CLI/Skript ist **nicht** Teil dieses Repos (kein Kundenzugriff auf den privaten Schlüssel nötig oder gewünscht) — falls ein Ausstellungswerkzeug gewünscht ist, ist das eine eigene Entscheidung außerhalb der Session-Roadmap.
- Schlüsselgröße: mindestens 3072 Bit RSA empfohlen (aktuelle Best-Practice-Untergrenze für langlebige Signaturen, keine Sekunden-TTL wie bei Session-Tokens) — konkrete Erzeugung liegt aber beim Lizenzgeber, nicht im Scope dieses Repos.
- Schlüsselrotation und ein JWKS-artiger Online-Abrufmechanismus bleiben offener Punkt für eine spätere Session, falls benötigt (z. B. bei einem zentralen Fleet-/Lizenz-Management-Service für mehrere Installationen, Konzept-Abschnitt zu 3.8/9.2 "optional, separater Baustein" — nicht Teil von Phase 9).

## Nachtrag (P13-S1, Konzept 3a)

Das `installation_id`-Claim war in der ursprünglichen Claim-Liste oben bereits benannt, wurde aber bei der P9-S1-Umsetzung nie tatsächlich geprüft — `usage.compute_usage()` bewertete bislang nur `exp`/`nbf` sowie die vier Nutzungsdimensionen. P13-S1 (Mehrfachinstallations-Grundlagen) schließt das:

- **Neue, gemeinsame `installation_id`/`installation_display_name`-Felder in `dms_common.BaseServiceSettings`** (`DMS_INSTALLATION_ID`/`DMS_INSTALLATION_DISPLAY_NAME`, ein Wert für die gesamte Installation) ersetzen die zuvor uneinheitliche Praxis, bei der nur `workflow-service` eine eigene, isoliert konfigurierte `installation_display_name` kannte und jeder andere Service gar keine Installationskennung besaß. `registry-service` exponiert diesen Wert zusätzlich über `GET /installation` für Werkzeuge/die künftige Fleet-Management-Ebene (P13-S2).
- **`license-service` bindet die Prüfung jetzt an dieses Claim**: ist `installation_id` im Lizenztoken gesetzt, muss es exakt der lokal konfigurierten `installation_id` entsprechen, sonst gilt die Lizenz als ungültig (`invalid_reason="Lizenz wurde fuer eine andere Installation ausgestellt"`) — verhindert, dass eine für Installation A ausgestellte, aber weiterhin signaturgültige Lizenzdatei unverändert auf Installation B kopiert und dort ebenfalls akzeptiert wird (3a: "... mit einer eigenen Installations-ID, gegen die ihre Lizenz geprüft wird").
- **Rückwärtskompatibel**: fehlt das Claim (ältere Lizenzdateien, Test-Fixtures), wird nichts geprüft — kein erzwungener Reissue bestehender Lizenzen nötig.
- **Bewusst NICHT mit der Federation-Hub-Kennung vereinheitlicht**: `workflow-service` meldet sich beim Federation Hub (7.4, ADR 0028) weiterhin mit einer eigenen, zufällig erzeugten, rein opt-in genutzten Installations-ID an, unabhängig von der hier eingeführten Fleet-/Lizenz-`installation_id`. Föderationspartner sollen nicht automatisch die interne Fleet-Identität einer Installation erfahren können, nur weil sie an einem föderierten Prozess teilnimmt — zwei getrennte Kennungen für zwei unterschiedliche Vertrauenskreise, keine versehentliche Identitätsverknüpfung.
