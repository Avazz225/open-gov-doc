# 0032 — License file: JWT/RS256 instead of a new signature format

**Status:** accepted
**Context:** P9-S0 (phase kickoff planning for Phase 9, Concept 9.1–9.3 "Licensing system"), `IMPLEMENTATION_PLAN.md` explicitly named deciding on the signature scheme for the license file for this session, before P9-S1. A pure research/planning session, no implementation code.

## Decision

The signed license file (9.2: "signed license file containing all dimensions and validity period") is delivered as a **JWS/JWT in compact format, algorithm RS256** — the license dimensions (9.1: user-count model, licensed components, storage/document ceilings) are encoded as dedicated claims, `exp`/`nbf` cover the validity period. The private key is generated and managed **offline** (outside any Docker image/repository) and is used to produce license files for customers; each installation receives only the **public** key, embedded via a setting/mounted file in `license-service` (P9-S1), analogous to `dms-auth-client`'s `TokenValidator`, but with a statically embedded key instead of one fetched via a JWKS URL.

## Rationale

- **`python-jose[cryptography]>=3.3` is already a dependency** of `libs/dms-auth-client` (`TokenValidator` there checks RS256-signed Keycloak access tokens against a JWKS) — `RS256` is confirmed supported in the installed `jose` build (`jwt.ALGORITHMS.SUPPORTED` includes `RS256`/`RS384`/`RS512`/`ES256`/`ES384`/`ES512`, **not** `EdDSA`/Ed25519). Introducing a new format or a new library when the system already has a proven, tested JWT verification pattern would be unnecessary extra complexity with no real benefit — the same "reuse instead of reinvent" line as most of this project's previous architecture decisions.
- **Asymmetric, not HMAC**: unlike `query-service`'s dry-run token (a single ADR-less decision, P8-S2, HMAC-SHA256 with an installation-wide secret), a license file must be verifiable by every installation without the installation itself being able to sign — a shared HMAC secret would give every installation the ability to issue itself arbitrary licenses. RS256 (asymmetric) separates signing (only at the licensor, offline) from verification (every installation, with the public key).
- **RS256 instead of ES256**: `jose` supports both; RSA was chosen because it is already the only asymmetric JWT scheme actually used in this project (Keycloak's default for signed access tokens, already verified by `TokenValidator`) — no need to maintain a second curve/second key format in the same system. For a rarely reissued, long-lived file (license term typically months/years, not seconds like a session token), RSA's larger key/signature size compared to ECDSA plays no relevant role.
- **No JWKS endpoint, no key-rotation mechanism in this first iteration**: unlike Keycloak's JWKS (keys can be rotated there via the realm, `TokenValidator` caches/refreshes), there is no online service for the license file that an installation could query at the licensor (installations can be operated offline/air-gapped) — the public key is therefore shipped statically with the `license-service` image/configuration. Key rotation (compromised private key) would require a new `license-service` release with a new public key — documented as a deliberate limitation, not part of this session.
- **JWT format is self-describing and tooling-friendly**: standard claims (`exp`, `nbf`, `iat`) cover the validity period without inventing custom date fields/custom parsing logic; custom claims (e.g. `max_users`, `concurrent_sessions`, `licensed_components`, `storage_limit_gb`, `document_limit`, `installation_id`) carry the nine Concept-9.1 dimensions. Humanly inspectable (any JWT debug tool shows the payload, even without signature verification), which eases support diagnostics.

## Consequences

- P9-S1 (License Service) verifies license files with a `TokenValidator`-like but JWKS-less verifier (static public key from settings/mounted file) — no new crypto code, direct reuse of `python-jose[cryptography]`.
- The private key must **never** appear anywhere in the repository, in any Docker image, or in any configuration file of the system itself — it lives exclusively outside this project at the licensor. A license-file-issuing CLI/script is **not** part of this repo (no customer access to the private key needed or desired) — if an issuance tool is desired, that is a separate decision outside the session roadmap.
- Key size: at least 3072-bit RSA recommended (current best-practice lower bound for long-lived signatures, not a seconds-long TTL like session tokens) — actual generation, however, is up to the licensor, not in scope for this repo.
- Key rotation and a JWKS-like online-fetch mechanism remain an open point for a future session if needed (e.g. for a central fleet/license management service across multiple installations, concept section on 3.8/9.2 "optional, separate building block" — not part of Phase 9).

## Addendum (P13-S1, Concept 3a)

The `installation_id` claim was already named in the original claim list above, but was never actually checked during the P9-S1 implementation — `usage.compute_usage()` previously evaluated only `exp`/`nbf` plus the four usage dimensions. P13-S1 (multi-installation foundations) closes this gap:

- **New, shared `installation_id`/`installation_display_name` fields in `dms_common.BaseServiceSettings`** (`DMS_INSTALLATION_ID`/`DMS_INSTALLATION_DISPLAY_NAME`, one value for the whole installation) replace the previously inconsistent practice where only `workflow-service` had its own, separately configured `installation_display_name` and no other service had any installation identifier at all. `registry-service` additionally exposes this value via `GET /installation` for tools/the future fleet-management layer (P13-S2).
- **`license-service` now ties its check to this claim**: if `installation_id` is set in the license token, it must exactly match the locally configured `installation_id`, otherwise the license is considered invalid (`invalid_reason="License was issued for a different installation"`) — this prevents a license file issued for installation A, but still signature-valid, from being copied unchanged to installation B and being accepted there as well (3a: "... with its own installation ID, against which its license is checked").
- **Backward compatible**: if the claim is missing (older license files, test fixtures), nothing is checked — no forced reissue of existing licenses needed.
- **Deliberately NOT unified with the Federation Hub identifier**: `workflow-service` still registers with the Federation Hub (7.4, ADR 0028) using its own, randomly generated, purely opt-in installation ID, independent of the fleet/license `installation_id` introduced here. Federation partners should not automatically learn an installation's internal fleet identity just because they participate in a federated process — two separate identifiers for two different circles of trust, no accidental identity linkage.
