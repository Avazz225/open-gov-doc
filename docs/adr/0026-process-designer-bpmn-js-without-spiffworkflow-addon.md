# 0026 — Process Designer: `bpmn-js` ohne `bpmn-js-spiffworkflow`-Addon

**Status:** akzeptiert
**Kontext:** P6-S8 (Process Designer). ADR 0021 akzeptierte `bpmn-js`/`bpmn-js-spiffworkflow` als Paar für den Process Designer, samt der von der bpmn.io-Lizenz vorgeschriebenen Wasserzeichen-Bedingung. Bei der tatsächlichen Umsetzung dieser Session wurde `bpmn-js-spiffworkflow` erneut recherchiert (npm-Registry + GitHub, nicht aus Trainingsdaten übernommen) — mit einem anderen Ergebnis als zum Recherchezeitpunkt von ADR 0021.

## Entscheidung

Der Process Designer verwendet **nur `bpmn-js`** (weiterhin wie in ADR 0021 akzeptiert, inkl. bpmn.io-Wasserzeichen) **plus `bpmn-js-properties-panel` + `@bpmn-io/properties-panel` + `camunda-bpmn-moddle`** für die Properties-Panel-Funktionalität. **`bpmn-js-spiffworkflow` wird bewusst nicht verwendet.** Der in P6-S7 eingeführte Signature Task (technisch ein Manual Task mit `camunda:properties`-Erweiterungselementen, siehe `services/workflow-service/src/workflow_service/spiff_adapter.py`) bekommt stattdessen einen eigenen, kleinen Properties-Panel-Provider (`SignatureTaskPropertiesProvider.tsx`: Checkbox "Signatur erforderlich" + Niveau-Auswahl SES/AES/QES auf `bpmn:ManualTask`-Elementen), der dasselbe `camunda:properties`-Format liest/schreibt, das `workflow-service` bereits erwartet.

## Begründung

- **`bpmn-js-spiffworkflow` ist seit 2022 nicht mehr auf npm veröffentlicht** (`latest` = `0.0.10`), obwohl auf GitHub weiterhin aktiv committet wird — SpiffWorkflows eigenes Referenz-Frontend (`spiff-arena`) bezieht das Paket deshalb selbst nicht über npm, sondern per `github:sartography/bpmn-js-spiffworkflow#main`-Pin gegen einen sich laufend ändernden Branch. Ein solcher Pin ist ein Reproduzierbarkeits-/Supply-Chain-Risiko (kein fixierter, auditierbarer Release-Stand), das für dieses Projekt nicht eingegangen werden soll.
- **Lizenz-Inkonsistenz entdeckt**: die npm-Metadaten des veröffentlichten Pakets nennen MIT, das `package.json` auf dem aktuellen GitHub-`main`-Branch nennt dagegen LGPL. Ohne eine dieser beiden Angaben vertrauenswürdig auflösen zu können, ist die tatsächliche Lizenzlage zum jetzigen Zeitpunkt nicht eindeutig — ein zusätzlicher Grund, das Paket nicht als Abhängigkeit einzugehen (anders als bei `bpmn-js` selbst, ADR 0021, oder SpiffWorkflow, ADR 0018, wo die Lizenzlage jeweils klar war).
- **Kein eingebautes "Signature Task"-Konzept**: `bpmn-js-spiffworkflow` bringt ohnehin keine fertige UI für den projektspezifischen Signature Task mit — ein eigener Properties-Panel-Provider wäre so oder so nötig gewesen. Der einzige Grund, das unsichere Paket trotzdem einzubinden (SpiffWorkflow-spezifische Skript-Editor-/Properties-Panel-Unterstützung), entfällt damit für den hier tatsächlich gebrauchten Funktionsumfang.
- **Muster verifiziert statt angenommen**: das in `SignatureTaskPropertiesProvider.tsx` verwendete Provider-/Group-/Entry-Registrierungsmuster (`propertiesPanel.registerProvider`, `bpmnFactory.create`, `commandStack.execute('element.updateModdleProperties', ...)`, `properties-panel.multi-command-executor`) wurde gegen den tatsächlich installierten, gebündelten Quelltext von `bpmn-js-properties-panel`/`@bpmn-io/properties-panel` (dessen eingebaute "Extension properties"-Gruppe nutzt exakt dieselbe Mechanik) nachvollzogen, nicht aus der Dokumentation angenommen — dieselbe Verifikationsdisziplin wie bei SpiffWorkflow/pyHanko in früheren Sessions.
- Dieselbe pragmatische Abwägung wie bei früheren Bibliotheks-Ersetzungen dieses Projekts (z. B. ADR 0010, EicarSignatureEngine statt ClamdEngine): eine im Konzept vorgeschlagene Bibliothek wird ersetzt, sobald sich bei der tatsächlichen Umsetzung ein konkretes, dokumentiertes Risiko zeigt, das zum Recherchezeitpunkt der ursprünglichen Entscheidung (hier: ADR 0021) noch nicht bekannt war oder sich seither verschärft hat.

## Konsequenzen

- `bpmn-js` selbst (inkl. bpmn.io-Wasserzeichen, ADR 0021) bleibt unverändert Teil des Process Designer — nur das SpiffWorkflow-spezifische Addon-Paket entfällt.
- Der Signature Task hat keine SpiffWorkflow-spezifische Skript-Editor-Unterstützung im Properties Panel (die es ohnehin nicht bräuchte) — alle anderen Standard-Tasktypen (Manual/Script Task) nutzen bpmn-js' eingebautes Standard-Palette-/Kontext-Pad-Verhalten, ohne SpiffWorkflow-Spezifika im UI.
- Sollte `bpmn-js-spiffworkflow` künftig wieder aktiv auf npm gepflegt werden und seine Lizenzlage sich klären, wäre eine Nachrüstung möglich, aber nicht zwingend nötig — der aktuelle eigene Provider deckt den tatsächlichen Bedarf bereits vollständig ab.
