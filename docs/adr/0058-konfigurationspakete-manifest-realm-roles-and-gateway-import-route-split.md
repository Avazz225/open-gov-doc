# 0058 — Configuration packages: manifest + `realm_roles` category, split of `config/import` and `config/fleet-import` at the gateway

**Status:** accepted
**Context:** P17-S1 (package format + application mechanism, concept §14.1), first session of Phase 17 "Pre-configured configuration packages" with actual code (P17-S0 was pure planning)

## Decision

Three related decisions:

1. **`ConfigDocument` (config-service, 7.3) gets an optional `manifest` field** (`PackageManifest`: `name`, `version`, `compatibility_range`, `description`, `origin`, `license`) as well as a new, regular **`realm_roles`** category (`list[str] | None`) — a package thus remains exactly a `ConfigDocument`, only extended by two new, optional components. `manifest` is purely descriptive (no application logic, `compatibility_range` is not automatically enforced); `realm_roles` is a regular, selectable category like `roles`/`business_calendars` and is applied via a new `AuthServiceClient` against two new `auth-service` endpoints (`GET`/`POST /realm-roles`).
2. **`POST /config/import` and the fleet-agent access path are split into two separate paths**: `POST /config/import` (RBAC via `X-DMS-Principal`/`admin.object_config`, now a regular, Keycloak-token-required gateway path) and a new `POST /config/fleet-import` (public gateway path, exclusively `Authorization: Bearer <DMS_FLEET_AGENT_API_KEY>`). `gateway-service.settings.public_routes` loses the entry `config-service:config/import` in favor of `config-service:config/fleet-import`; `fleet-management-service`'s `agent_client.py` calls the new path.
3. **First-ever admin-UI integration of `config-service`**: new page `/config-packages/` (`ConfigPackages` component) — load package file (parsed client-side), display manifest/categories, preview via the already-existing `POST /config/compare` (7.5, P14-S1), apply via `POST /config/import`. Additionally an "export current configuration" button (`GET /config/export` as a download) as a natural addition.

## Rationale

- **Why `realm_roles` is its own category, not a field in the manifest**: initially sketched as a manifest field during P17-S0 planning, but deliberately generalized into a standalone `ConfigDocument` category during implementation — the manifest is purely descriptive (name/version/origin), `realm_roles` is, like any other category, actually-applied data and must therefore be individually selectable (`?categories=realm_roles`) just like `roles`/`business_calendars`, and must appear in the `POST /config/compare` diff. Hiding a data field inside a purely descriptive metadata object would have broken this consistency.
- **Why a dedicated `AuthServiceClient`/new `auth-service` endpoints instead of reusing `permission-service`'s `roles` category**: verified in real terms during P17-S0 research — Keycloak realm roles (`dms-admin`, `dms-poststelle`) and `permission-service`'s DB-based `Role`s are two fully separate systems. Only the latter were importable before this session; for the former there was no generic creation path at all (`dms-poststelle` is checked by the user-UI frontend, but never created by `auth-service/bootstrap.py`). `POST /realm-roles` generalizes exactly the already-existing, proven primitive `create_realm_role(..., skip_exists=True)` (`bootstrap._ensure_dms_admin_role`, since P5e-S2) to arbitrary, package-supplied names, instead of inventing a second mechanism.
- **Why the gateway route split became necessary (a real bug found during the admin-UI integration)**: `config-service:config/import` had been in `gateway-service.settings.public_routes` since P13-S2 (ADR 0037), so that the installation-independent `fleet-management-service` (no Keycloak principal of this installation) could present its `DMS_FLEET_AGENT_API_KEY`. The gateway, for paths in `public_routes`, **validates no bearer token at all and never sets `X-DMS-Principal`** (`gateway_service.main.proxy`) — regardless of whether the actual caller supplies a valid token or not. This meant that the RBAC branch of `config-service._require_import_permission` was effectively unreachable for ANY call to this path via the gateway, even for a real, logged-in `config-admin`. This went unnoticed at P13-S2 because there was no admin-UI consumer yet (`config-service` had no frontend integration at all until this session) — only building the first real UI usage exposed the gap. The cleanest solution follows the same, already-established pattern as other fleet-agent special paths (`license-service`'s separate `GET`/`POST /license` endpoints): a dedicated, separate path for the non-Keycloak-authenticated caller, with the original path staying regular RBAC.
- **Why no `RequireCapability` wrapper around the new admin-UI page**: inconsistent, already-existing precedent in this project (only `/users`/`/license` use it, the majority of capability-gated pages like `/query-console/` rely only on server-side enforcement plus hiding in the sidebar) — `/config-packages/` follows the more common pattern, sidebar visibility is gated via `requiresCapability: "admin.object_config"`.
- **Why the preview (`POST /config/compare`) is called without an explicit `base` argument**: uses exactly the path intended for precisely this use case at P14-S1 ("what would change if I import this document") — no new comparison mode needed.
- **Why the `realm_roles` diff needs its own, simpler mode (`diff_string_list_category`)**: `compare.py`'s existing `_LIST_IDENTITY_FIELD` logic expects `list[dict]` categories with a name field per entry (e.g. `roles[].name`) — but `realm_roles` is a plain `list[str]`. A third category type (`STRING_LIST_CATEGORIES`) alongside the existing list/singleton categories was the simpler solution, rather than artificially wrapping strings into `{"name": ...}` objects.

## Consequences

- **Existing fleet provisioning does not break**: `fleet-management-service.agent_client.FleetAgentClient.provision_config` now calls `POST /api/config-service/config/fleet-import` instead of `.../config/import` — a pure path change, behavior/payload format identical. Gateway/fleet-management/config-service tests were adjusted accordingly (a new test `test_config_import_route_now_requires_gateway_auth_check` in `gateway-service` explicitly confirms that `config/import` now requires a bearer token).
- **`config-service` now additionally needs the domain admin role `domain-admin-users`** (`admin.user_management`) to be allowed to call `auth-service`'s new `POST /realm-roles` — idempotent self-assignment at startup like the two already-existing roles (`_ensure_bootstrap_permissions`).
- **`docker-compose.yml`**: `config-service` gets `DMS_AUTH_SERVICE_BASE_URL` and a new `depends_on: auth-service` (container DNS name, not `localhost` — the same class of error as with every previous new inter-service call in this project, found and fixed here during the first test run against the container directly).
- **`GET /realm-roles` is ungated** (returns only names, no sensitive content) — identical trust model to `permission-service`'s `GET /roles` and `config-service`'s own `GET /config/export`. `POST /realm-roles` is gated (`admin.user_management`, service-to-service via `X-DMS-Principal`, not a Keycloak JWT endpoint).
- **No marketplace/distribution mechanism** (14.1 literally: "deliberately not part of this concept") — a package remains only a local JSON file uploaded via the new admin-UI page. The eGov configuration package itself (14.2, concrete package data) is assigned to P17-S2/S3, not part of this session.
- **Gaps found at P17-S0, NOT yet resolved here, remain open** (deliberately outside the P17-S1 scope of "package format + application mechanism"): no attribute-based reference-number placeholder (`{Abteilung}`), `is_classified` still a plain bool instead of a multi-level classification — both planned for P17-S2.
