# 0022 — Generic four-eyes approval mechanism: post-approval execution via events instead of a synchronous callback

**Status:** accepted
**Context:** P6-S4 (Concept 4.3, "generic approval mechanism in the Permission Service/Workflow Engine"). Two retrofit cases have deliberately been ungated since earlier sessions: Document Service force-unlock (P3-S2) and Permission Service scope locks (P3-S4). 4.3 requires: an action with an active four-eyes flag creates an approval request that must be confirmed by a second person, different from the initiator, before it **takes effect** — but the actual business action itself (releasing the lock, creating the scope lock) each lives in a different service than the generic mechanism itself.

## Decision

The generic mechanism lives in `permission-service` (new tables `approval_action_config`, `approval_request`; endpoints `GET`/`PUT /approval-config[/{action_type}]`, `POST /approval-requests`, `GET /approval-requests[/{id}]`, `POST /approval-requests/{id}/approve|reject`). `POST .../approve` only marks the request as approved and publishes `permission.approval.approved` (payload: `action_type`, `initiated_by`, `approved_by`, the original `payload`) — **it does not execute the business action itself**. The service that can actually execute the action consumes this event and does so:

- `document-service` gets its first NATS consumer ever for this purpose (`consumer.py`, a second `NatsEventBusClient` with `ensure_stream=False`).
- `permission-service` consumes its own event for its own gated actions (scope locks) — **no** special-case dispatch in the `approve` handler, but the same self-consumption mechanism as for a foreign service.

Both gated endpoints (`POST /documents/{id}/lock/force-release`, `POST`/`DELETE /scope-locks`) first check `GET /approval-config/{action_type}`: if no configuration row exists or `requires_approval=false`, the action runs synchronously as before, unchanged (default behavior remains ungated, see Concept 4.3 "not globally enforced"). Only an explicit `PUT /approval-config/{action_type} {"requires_approval": true}` activates the deferral.

## Rationale

- **Consistent with the established event-bus architecture principle (3.4)** rather than a new synchronous callback/webhook mechanism — otherwise `permission-service` would have to know, per action type, which endpoint on which service to call to execute the action after the fact. Via events it remains fully decoupled: it only knows its own configuration/its own request status, not the internals of other services.
- **Self-consumption instead of inline dispatch for its own action types**: had `approve` executed `permission.scope_lock.*` inline within the same request (no event detour), the mechanism would be implemented differently for "own" versus "foreign" action types — undermining the "generic" claim. The somewhat unusual self-consumption is technically unproblematic: `NatsEventBusClient.subscribe()` works regardless of whether the same client created the stream itself (verified against `libs/dms-eventbus-client`).
- **Initiator≠approver only for `approve`, not for `reject`**: 4.3 explicitly requires that the approving person must not be identical to the initiating one — this only applies to making an action take effect. Withdrawing one's own request (`reject`) is unproblematic and does not need this restriction.
- **Default `requires_approval=false` when no configuration row exists**: a literal implementation of "configurable per action type, not globally enforced" — also prevents this session from interrupting ongoing internal test operations through suddenly active gating.

## Consequences

- **No execution feedback channel**: `permission-service` does not learn whether the action actually executed by an external service (e.g. `document-service`) succeeded — `ApprovalRequest.status` stays at `"approved"`, there is no `"executed"` state. A failed force-unlock (e.g. because the lock was resolved another way in the meantime) is only logged locally by the executing service (see `consumer.py`/`approval_consumer.py`), not visible in the approval request itself.
- **Race window between approval and execution**: the time between `POST .../approve` and the actual processing of the event is non-deterministic (event delivery is asynchronous) — uncritical for the actions gated in this session (force-unlock, scope locks), since both could already remain "open" for an uncontrolled length of time before this session anyway.
- **No notification to approvers**: `notification-service` is deliberately not hooked up to `permission.approval.requested` (the same scope discipline as in earlier sessions, e.g. P6-S2's "no retrofit of existing alerting points") — whoever is supposed to approve currently has to poll `GET /approval-requests?status=pending` themselves.
- **Every future gated action type needs the same three-part retrofit** in the respective executing service: (1) a `requires_approval` check before the action, (2) an `ApprovalClient`-style HTTP client against `permission-service` if external, (3) a consumer for `permission.approval.approved` that filters by `action_type`. No central registration mechanism for this — each service registers its own subject/its own filter logic, the same pattern as for every other new event consumer in this project.
- **Every consumer must read its `payload` field defensively** (`.get(...)`, not `[...]`): since `POST /approval-requests` accepts `action_type`/`payload` freely (no schema enforced per action type), a malformed request with an existing `action_type` can hit the same consumer as a correct one — without defensive reading the handler crashes, the NATS message stays unacknowledged, and gets redelivered endlessly. This actually occurred live during this session's verification (a test request with `action_type="document.force_unlock"` and payload `{"x": 1}` hit the real `document-service` consumer) and was fixed in both consumers (`document_service/consumer.py`, `permission_service/approval_consumer.py`).
