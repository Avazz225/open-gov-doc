# 0023 — Superuser break-glass as a Keycloak attribute + native domain-admin accounts instead of Keycloak realm roles

**Status:** accepted
**Context:** P6-S5 (Concept 4.6, "superuser principle (break-glass) & domain-separated admin roles"). Retrofit mandate: gate Auth Service user management (`/users`, ungated since P4-S3) and Admin UI role checking (ungated since P4-S3). The generic four-eyes mechanism from P6-S4 (ADR 0022) already exists, but so far only requires "any second person, different from the initiator" — 4.6 requires more strictly, for superuser activation, two different members of a permission group designated for that purpose.

## Decision

**Domain-admin "roles" are not Keycloak realm roles** (unlike the existing `dms-admin`, P5e-S2), but **native `Role` rows in `permission-service`** (the same RBAC system, already separated from Keycloak since P2-S2, that also manages resource permissions). `permission-service` idempotently seeds 8 roles on every start: the 7 domains named in 4.6 (`domain-admin-users`, `-config`, `-storage`, `-license`, `-query-console`, `-deletion`, `-deletion-vs`) plus `breakglass-approver`. Each domain gets a capability string (`admin.user_management` etc.), checked via the already-existing `GET /effective-permissions/{principal_id}/{resource_id}` at the root resource — no new endpoint needed.

**Each domain (eventually) gets an automatically created technical Keycloak user account**, username = password following the pattern `<domain>-admin` (e.g. `users-admin`/`users-admin`), to be changed by the operator. `auth-service` creates this account during its own bootstrap and assigns it the matching role at the root resource via an HTTP call against `permission-service` (`GET /roles` to resolve the role ID, `GET`/`POST /role-assignments`, both present since P2-S2, checked idempotently). **Only `users-admin` (domain "user/permission management") is actually created in this session** — the remaining 6 domains stay, for now, roles without an associated account (no account with a guessable default password without a business purpose behind it), until the respective domain is actually retrofitted.

**Superuser break-glass state lives as a Keycloak user attribute** (`dms_superuser_expires_at`), not in a new database — `auth-service` had until now been completely stateless (no own Postgres schema, P2-S1). Same pattern as the theme preference (ADR 0009). The superuser account itself is idempotently created with `enabled=False`; activation sets `enabled=True` + the expiry timestamp, exclusively as a consumer of the generic `permission.approval.approved` event (P6-S4 pattern, `auth-service`'s first NATS consumer ever).

**The generic P6-S4 mechanism gets a new, generic extension**: `ApprovalActionConfig.required_permission: str | None`. When set, both `initiated_by` and `approved_by` must hold this capability (in addition to the existing initiator≠approver rule) — for `auth.superuser.activate` this is fixed to `breakglass.approve`. Real humans are assigned to this role manually via the (now gated) user/permission-management Admin UI page.

**Time limiting**: a single absolute expiry timestamp (`activated_at + superuser_activation_minutes`, default 30 min) instead of separate total-duration and rolling 10-minute inactivity timers, enforced via a poll loop in `auth-service` (`superuser_poll_interval_seconds`, default 30s) — exactly the same poll-instead-of-push principle as workflow-service's SLA time monitoring (ADR 0020).

## Rationale

- **Reuse instead of a third permission system**: `permission-service`'s `Role`/`RoleAssignment` is already the established, Keycloak-separated home for resource-scoped RBAC (since P2-S2) — a new domain-admin-roles table in Keycloak or elsewhere would have duplicated the same function.
- **Technical accounts instead of role assignment to humans** (explicit user decision made during the planning of this session): allows, later on, using the same accounts to also verify that services dialing into the cluster are not forgeries (not part of this session, but the design — separate user/role concepts, user firmly assigned to the role — does not preclude this).
- **Only one domain with a real account**: an automatically created, enabled account with a predictable default password is itself an attack surface — without a business purpose behind it (e.g. license management/query console do not even exist as services yet), that would be unnecessary risk without any corresponding benefit.
- **Keycloak attribute instead of a new Auth Service DB**: consistent with this project's minimalism precedent (ADR 0009) — a new database just for a single timestamp would be disproportionate.
- **`required_permission` as a generic extension, not special-case dispatch**: upholds ADR 0022's promise that the approval mechanism works identically for every action type — break-glass is just an action type with an additional, optional config row, not its own code-path branch in `approve`/`create_approval_request`.
- **A single timer instead of two**: genuine rolling inactivity tracking would need new instrumentation in every service/gateway (every authenticated request as a superuser would have to report a "last activity" time back) - out of scope for this session, honestly named as a simplification rather than silently implementing only part of 4.6.

## Consequences

- **6 of the 7 domains from 4.6 are seeded but not enforced**: `domain-admin-config`/`-storage`/`-license`/`-query-console`/`-deletion`/`-deletion-vs` exist as `Role` rows, without an associated account and without any endpoint checking them — an open point for respective future retrofit sessions (e.g. object-type/workflow configuration, storage guard).
- **No "real" rolling inactivity deactivation**: a superuser who stays active but does nothing for a long time is still only deactivated after the absolute `superuser_activation_minutes` deadline, not after 10 minutes of inactivity as described in the concept text.
- **No increased audit priority for individual actions during activation**: `audit-service` consumes `auth.>` (lifecycle events: requested/activated/deactivated) with normal priority like any other subject — its hash-chain model has no priority concept; a foreign action executed *during* an active superuser session in another service is not specially marked.
- **`permission-service`'s `/roles`/`/role-assignments` remain ungated**: `auth-service`'s seeding logic (bootstrap creates the very first role assignment) would otherwise itself have needed the very permission it is creating - a chicken-and-egg problem avoided by deliberately leaving these two endpoints ungated (in line with the explicitly named, narrower retrofit mandate).
- **Best-effort role assignment at bootstrap**: if `permission-service` is not yet reachable when `auth-service` starts, the assignment is skipped (logged, no retry loop) - only heals on the next restart, analogous to `structure_consumer.py`'s `SubjectNotFoundError` handling.
- **Two different role-checking paths now deliberately coexist**: the existing `dms-admin` flag check (P5e-S2) continues to read `X-DMS-Roles` (Keycloak realm role), while every new check from this session on uses a real `permission-service` call - not retroactively unified, since that is out of this session's scope.
