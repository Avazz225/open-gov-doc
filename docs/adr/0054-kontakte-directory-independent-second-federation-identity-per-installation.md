# 0054 — Contacts: local directory + federated search via a second, independent federation hub identity

**Status:** accepted
**Context:** P15-S4 (contacts, concept §2.5/4.4/7.4)

## Decision

Four related decisions:

1. **New, ungated `GET /users/directory?q=` endpoint (auth-service)** — search via Keycloak's built-in `search` query parameter (username/first/last name/email), available to EVERY authenticated user (no `admin.user_management` gate as with `GET /users`), returns a reduced field set (`id`/`username`/`email`/`first_name`/`last_name`, deliberately without `enabled`). Confirmed via live verification: Keycloak's `search` parameter, contrary to the original assumption, is not true substring/infix matching but a prefix match per field (see "Open Points").
2. **Federated contact search via a SECOND registration, independent of workflow-service's federation hub participation** — auth-service gets its own `FederationIdentity` (own RSA-2048 key pair, own `POST /installations` call to the federation hub, own address-book entry with a display-name suffix of `" (Contacts)"`) instead of (co-)using the already-existing identity of `workflow-service`.
3. **Direct installation-to-installation requests instead of relaying through the hub** — the searching installation calls the target installation directly via its `callback_base_url` stored in the hub's address book, and signs the request (`X-Installation-Signature`/`X-Installation-Id`, identical RSA-PSS/SHA-256 scheme as the already-existing installation-to-hub signing, ADR 0039); the hub itself never sees the request/response.
4. **Capability flagging via the already-existing `Installation.supported_process_types` field** (`"dms.contact-directory.v1"` as a sentinel value) instead of a new field in federation-hub-service — no code change needed to an already-stable service used by `workflow-service`.

## Rationale

- **Why an ungated directory endpoint and not an extension of `GET /users`**: concept §2.5 requires "local, always available" — `GET /users` deliberately remains gated behind `admin.user_management` (user management remains an administrative domain); a separate, deliberately narrower endpoint (no `enabled` field, no create/delete capability) cleanly separates "find a person" from "manage accounts".
- **Why a second federation identity instead of (co-)using the already-existing one from `workflow-service`**: a shared identity would have required either cross-service access to `workflow_service`'s own Postgres schema (forbidden, concept 3.1: "a service reads/writes exclusively its own schema") or a new delegation interface IN workflow-service ("sign this for me") that does not exist today and would have turned workflow-service into a generic signing service for other services — a responsibility that does not belong there. The federation hub only ever knows "installation" as a generic, independently registrable address-book entry anyway (no 1:1 binding to a specific service) — two entries per physical installation (one per participating capability) is a deliberate simplification already possible with the existing data model.
- **Why direct calls instead of relaying through the hub**: concept §2.5 describes federated contact search as "a dedicated capability BUILT ON TOP OF the federation hub" — the hub provides the address book (discoverability) and key distribution (already readable ungated today via `GET /installations`), but is not necessarily the transport path for every future federated capability. Relaying through the hub would either have repurposed its handover mechanism (semantically workflow-specific, `response_model=ProcessInstanceOut` on the receiving side) or required a new, generic relay capability in federation-hub-service itself — both disproportionate for a synchronous request/response with no need for intermediate storage/mediation of the workflow handover pattern (no "end-to-end encryption so the hub never sees plaintext" is needed, since the hub is never in the request path anyway in the direct model).
- **Why `supported_process_types` as the capability marker instead of a new field**: the field is already a generic string array on `Installation`, originally intended for BPMN process type capabilities, but structurally nothing other than "list of capabilities this registration offers". A new, workflow-unrelated field would have required a change to an already-stable service shared with, but not affected by, another service (`workflow-service`) — repurposing an already-existing generic list field is the lower-risk, smaller change.

## Consequences

- **Two address-book entries per physical installation once both workflow federation and contact search are active** — distinguishable by the display-name suffix `" (Contacts)"`, but structurally two independent `Installation` rows with independent key pairs/revocation status. An installation revoking one of the two participations (`POST /installations/{id}/revoke`) must do so separately for the other — no automatic synchronization.
- **auth-service gets its first own Postgres schema** (`auth`, `federation_identity` singleton) — the service was previously fully stateless (pure Keycloak proxy, see `docs/services/auth-service.md`). Deliberately justified by exactly one row, no larger state increase.
- **Live reachability of the target installation is a prerequisite for federated search** — unlike the hub handover pattern (which can track delivery even to a temporarily unreachable target installation via the `status` state), there is no queue/retry here: an unreachable peer is skipped (`directory_federation.PeerQueryError`, logged, no overall abort of the remaining peers).
- **No encryption of the request/response payload** (signature only) — deliberate simplification compared to the handover scheme, see rationale above; TLS between installations is treated as a deployment concern everywhere else in this project as well (ADR 0039), not compensated for at the application level.
- **An installation that configures `AUTH_SERVICE_FEDERATED_DIRECTORY_ENABLED`/`AUTH_SERVICE_FEDERATION_HUB_BASE_URL` differently** must note that BOTH sides (requesting AND requested installation) must have the capability enabled and registered — `federated_search_inbound` rejects requests from installations not themselves registered with `dms.contact-directory.v1`, even if the requesting side has enabled the feature locally.

## Open Points

- **`GET /users/directory?q=` is prefix, not substring, search** (discovered via live verification against the running stack, see `docs/services/auth-service.md`): Keycloak's `search` parameter matches per field (username/first/last name/email) only from the start of the field, not at an arbitrary position — `q=admin` does not find the username `config-admin`, but `q=config` does. For an "employee address book" (typing the first letters of a name), an acceptable, even natural behavior, but it does not match the originally assumed "substring" semantics. Deliberately not compensated for by a dedicated post-filter (would require a full `GET /users` dump plus client-side filtering, disproportionate for a reference implementation) — instead honestly documented as a Keycloak quirk.
- **Repeated test runs against the real, shared `federation-hub-service` leave permanent address-book entries** — the `federation_enabled` fixture in `test_directory.py` registers a new, real installation with the running hub on every single test run (no mocking, see the already-existing self-loopback pattern), since `_clean_tables` resets the local `federation_identity` row before every test and `_ensure_federation_identity()` consistently creates a fresh registration on the next `TestClient` startup. Across many test runs/sessions this accumulates into many `"... (Contacts)"` entries in the hub's address book. Not a local bug — `revoke_installation` is deliberately fully locked down without a configured `hub_operator_key` (see federation-hub-service); no operator key is set in this development environment, so cleanup is not readily possible. Same category as other test leftover data already accepted in this project's shared dev environments (e.g. test objects in folder trees); additionally worth noting here since each entry binds its own key pair.
