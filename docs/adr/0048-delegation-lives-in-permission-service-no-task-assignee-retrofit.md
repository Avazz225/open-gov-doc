# 0048 — Delegation: dedicated record in permission-service instead of a task-assignee retrofit, real check only for "on behalf of"

**Status:** accepted
**Context:** P14-S11 (delegation during absence, concept §4.4a)

## Decision

A new, standalone `Delegation` table lives in **`permission-service`** (not in `workflow-service`, not as its own service) - a time window (`starts_at`/`ends_at`, both required), an optional scope (`scope_object_type_ids`/`scope_process_definition_ids`/`scope_folder_resource_ids`, all `None` = full takeover), never hard-deleted (`revoked_at`/`revoked_by`). A new `GET /delegations/check` endpoint (same response format as the existing `GET /check` for RBAC) is the only real enforcement point: **`workflow-service`'s `POST .../tasks/{id}/complete`** calls it whenever a request includes an `on_behalf_of_principal_id`, and rejects with `403` if no matching active delegation exists. The "delegate" identity checked in the process must come from the gateway-injected `X-DMS-Principal` header (`401` without it), NOT from the still-unchecked free-text field `completed_by`. The audit trail gets a new, second field `on_behalf_of` (`dms-eventbus-client`'s `Event`, `audit-service`'s `AuditEvent`) alongside the existing `actor` - `actor` always remains the person actually acting as delegate, `on_behalf_of` the person being represented.

## Rationale

- **No existing mechanism to "layer onto"**: targeted research before implementation found that `workflow-service` today has **no** concept whatsoever of "this task belongs to person X" - `lane` is purely BPMN metadata with no enforcement, `completed_by` is an unchecked free-text field, `GET /tasks` shows every authenticated principal, without exception, all open tasks system-wide (a pre-existing, documented state, see `docs/services/workflow-service.md`). "Layering delegation onto an existing access restriction" was therefore not an available option - no such restriction exists, and retrofitting one would be its own, considerably larger undertaking (comparable to the P6-S6 retrofit for `admin.object_config`), not part of the concept-4.4a mandate.
- **`permission-service` rather than `workflow-service` as the home**: delegation is at its core an identity/permission question ("who may act as someone else"), not a workflow question - `permission-service` already holds `RoleAssignment` (role grants) and the generic four-eyes mechanism (`ApprovalRequest`) as related "who may do what" concepts. A future second consumer (e.g. a later genuine task-assignee enforcement, or a document approval "on behalf of") can call the same `GET /delegations/check` endpoint without depending on `workflow-service`.
- **`GET /delegations/check` instead of a generic shared cache**: exactly the same request/response pattern as the existing `GET /check` (`{"allowed": bool}`), already called by `document-service`/`search-service` for RBAC checks (P14-S10, P5-S4) - no new cross-service call pattern, just another endpoint following an established convention.
- **Calling identity from `X-DMS-Principal`, not from `completed_by`**: `completed_by` is and remains a caller-chosen free-text field (an existing, unchanged gap). Without this separation, any caller could claim to be acting "on behalf of" a person for whom no delegation actually exists, simply by writing an arbitrary name into the free-text field - the delegation check itself must therefore anchor on an identity actually verified by the gateway, even though `completed_by` itself remains unchecked.
- **Scope checking only for `scope_process_definition_ids`**: of the three scope dimensions named in the concept ("object types/processes/folder areas"), only the process definition can be read directly from a running `workflow-service` instance without an additional cross-service detour (`ProcessInstance.process_definition_id`, a first-class field). `scope_object_type_ids`/`scope_folder_resource_ids` are indeed carried along on the record (the concept wording is fully represented, ready for later use), but are not evaluated at today's single check point (task completion), since a task does not directly carry an object type/folder, only indirectly via `business_key` (a document or a circulation folder, depending on the process) - an additional resolution step would be its own increase in complexity, not required by the concept text for this session.
- **Revocation by the delegating person OR an admin role, NOT by the delegate themselves**: exact concept wording ("can be terminated early at any time by the represented person or an authorized admin role") - the delegate themselves has no revocation right of their own foreseen, the same role-setting convention as `share_link_revoke_admin_role` (P14-S10, new `delegation_revoke_admin_role`, identical default `dms-admin`).
- **`on_behalf_of` as a second event/audit field instead of overwriting `actor`**: concept 4.4a is explicit ("Deliberately logged as a distinct, clearly attributable action rather than an identity switch ... under the delegate's own account, with an additional note"). The existing cutover versioning for `actor` (P7-S2, `AuditMeta.actor_field_cutover_id`) is repeated identically for `on_behalf_of` (`on_behalf_of_field_cutover_id`) - unlike the original `actor` cutover (which newly created the `AuditMeta` row itself), this row already exists here, so the new cutover value is added via a one-time update rather than an insert.
- **Admin UI shows a pure overview, no creation**: per the concept, delegation is a self-service feature ("A person can ... set up ..."). Creation deliberately lives only in `user-ui` (`DelegationsPane`, self-service); the admin-UI page (`/delegations/`) offers only the installation-wide overview plus the admin revocation, which the concept text foresees as the second revocation path.

## Consequences

- **The delegation itself is real and enforced, but the underlying "who may complete a given task" question remains open** - a regular, non-delegated completion (`on_behalf_of_principal_id` not set) proceeds unchanged, without any check, exactly as before this session. The delegation check only kicks in when someone explicitly claims to act "on behalf of" - it is an additional condition, not a tightening of the existing, open baseline.
- **`scope_object_type_ids`/`scope_folder_resource_ids` are currently dead data** (stored, but evaluated by no endpoint) - a deliberate, documented limitation of this session, not an accidental gap.
- **The "I am representing" display in `user-ui`/the "on behalf of" selector in `reviewer-ui` show raw principal IDs (Keycloak `sub` UUIDs), not usernames** - the same already-documented UX gap as with teamspace member lists (P14-S6): a reverse UUID→username resolution does not exist in the system (`GET /users/lookup` only goes username→ID), not retrofitted in this session.
- **A potentially very broad delegation scope under "full takeover"** (all three scope fields `None`): a delegate can then complete ANY process task of the represented person, regardless of business context - concept 4.4a's own wording explicitly foresees exactly this option ("full takeover of all open tasks"), no additional restriction introduced beyond the concept text.
