# 0059 — eGov-Konfigurationspaket Teil 1: Aktenplan-Hierarchie, attributbasierte Kennzeichen-Platzhalter, mehrstufige VS-Einstufung

**Status:** akzeptiert
**Kontext:** P17-S2 (eGov-Konfigurationspaket Teil 1, Konzept §14.2), zweite Umsetzungssession der Phase 17

## Entscheidung

Drei zusammenhängende Entscheidungen:

1. **`ObjectType.is_classified: bool` (P15-S1) wird durch `classification_level: str | None` ersetzt** — die vier im Konzepttext genannten deutschen VS-Einstufungen (`VS-NfD`, `VS-VERTRAULICH`, `GEHEIM`, `STRENG GEHEIM`) als `Literal`-Werteraum, `None` = nicht eingestuft. Jeder gesetzte Wert (unabhängig von der konkreten Stufe) löst weiterhin exakt denselben binären Gate aus wie zuvor das reine Bool (Verschlusssachen-Papierkorb/separate Löschrolle, `domain-admin-deletion-vs`) — die Stufe selbst ist reine Zusatzinformation, keine zusätzliche Rollen-Differenzierung. Betroffene Services: `object-type-service` (Schema/Modell/Repository/Migration), `document-service` (Gate-Prüfung in `purge_document`), `config-service` (`ObjectTypeExport`), `admin-ui` (`ObjectTypeEditor`: Checkbox → `<select>`), `user-ui` (Typ-Deklaration, ungenutzt).
2. **Kennzeichengenerator (P5e-S1) unterstützt seit dieser Session attributbasierte Platzhalter** — jeder Platzhalter in `kennzeichen_format`, der kein Datums-/Zähler-Platzhalter (`{YYYY}`/`{YY}`/`{MM}`/`{DD}`/`{Laufende_Nummer}`) ist, wird als Name eines am Objekttyp definierten Attributs interpretiert (z. B. `{Federführung}`). Validierung beim Speichern des Formats (nicht erst beim ersten Dokumentanlegen); Rendering zieht die Werte aus den beim Dokumentanlegen mitgesendeten Attributen (`document-service` reicht `parsed_attributes` durch `object_type_client.next_kennzeichen()` an `object-type-service`s `POST /object-types/{id}/next-kennzeichen` weiter, neues optionales Body-Feld `attributes`). Fehlt ein referenzierter Attributwert trotzdem (Attribut nicht als Pflichtfeld markiert), liefert der Endpunkt `422` statt eine Kennzeichnung mit stillschweigend leerer Lücke zu erzeugen.
3. **Erstes konkretes eGov-Konfigurationspaket, Teil 1** (`packages/egov/config.json`, `manifest.version` `0.1.0`): die in Konzept 2.5 als Beispiel genannte Hierarchie **Abteilung (Ordner) → Aktenplan (Ordner) → Akte (Dokument)**, jeweils über `allowed_parent_types` (2.2a) erzwungen. `Akte` bekommt `kennzeichen_format: "{Federführung}-{YYYY}-{Laufende_Nummer}"`, die Pflichtattribute `Aktentitel`/`Federführung` sowie `default_retention_days: 3653` (10 Jahre, veränderbare Vorbelegung). Ein zweiter, sonst identischer Objekttyp `Verschlusssache-Akte` demonstriert zusätzlich `classification_level: "VS-NfD"`.

## Begründung

- **Warum Ersetzen statt eines zweiten, parallelen Feldes**: `is_classified: bool` und eine neue `classification_level`-Spalte parallel zu pflegen hätte einen Synchronisationszustand erzeugt, der bei jedem Schreibpfad erneut hätte konsistent gehalten werden müssen - reiner Mehraufwand ohne Nutzen, da der einzige Konsument (der Lösch-Gate) ohnehin nur "gesetzt oder nicht" braucht. `classification_level is not None` ersetzt `is_classified` an jeder Stelle 1:1 (Python-Wahrheitswert eines nicht-leeren Strings verhält sich ohnehin wie `True`). Bleibt architektonisch konsistent mit [ADR 0051](0051-papierkorb-familie-classification-via-object-type-scoped-global-endpoints.md)s Begründung für ein schema-gebundenes Feld statt einer Attribut-Konvention - nur der Werteraum wurde erweitert, nicht das Muster gewechselt.
- **Warum `list_object_types`s Filter-Parameter `is_classified` (bool) beibehalten wird, nicht auf `classification_level` umbenannt**: `document-service`s `list_classified_document_type_ids()` (Verschlusssachen-Papierkorb, P15-S1) braucht "irgendeine Einstufung oder keine", nie eine konkrete Stufe - der Name beschreibt weiterhin exakt die tatsächliche Frage des einzigen Aufrufers. Intern wird er auf `classification_level IS (NOT) NULL` übersetzt.
- **Warum `Akte` ein Dokument-Objekttyp ist, `Abteilung`/`Aktenplan` Ordner-Objekttypen**: Konzept-Abschnitt 2.5 legt das bereits wörtlich fest ("**Akte** (Dokument-Objekttyp) liegt in einem **Aktenplan** (Ordner-Objekttyp), dieser liegt in einer **Abteilung** (Ordner-Objekttyp)") - keine eigene Interpretation nötig, nur die bereits an anderer Stelle im Konzept getroffene Festlegung als konkrete Objekttypen umgesetzt. Das löst auch scheinbare Spannung mit 14.2s Beispielformat `{Abteilung}-{YYYY}-{Laufende_Nummer}`: der Kennzeichengenerator ist ausschließlich für `applies_to="document"` zulässig (seit P5e-S1) - ein Format auf `Akte` (Dokument) selbst ist damit von vornherein konsistent, es kann nur nicht wörtlich `{Abteilung}` heißen, da `Abteilung` kein Attribut von `Akte` ist, sondern der Name eines strukturell übergeordneten Ordner-Objekttyps.
- **Warum `{Federführung}` statt eines zusätzlichen, redundanten `Abteilung`-Attributs auf `Akte`**: 14.2 nennt "Aktenzeichen, Aktentitel, Federführung" als die drei sinnvollen Pflichtattribute (wörtlich) - `Federführung` (die verantwortliche Stelle) ist bereits genau die Information, die der Konzept-Beispielplatzhalter `{Abteilung}` inhaltlich meint. Ein zusätzliches, rein für den Platzhalter eingeführtes `Abteilung`-Attribut hätte mit der bereits strukturell vorhandenen Abteilung (der Ordner-Vorfahre) dauerhaft auseinanderlaufen können (zwei unabhängige Quellen derselben Information) - `Federführung` vermeidet das, indem es die einzige, explizit vom Konzepttext geforderte Attribut-Quelle ist. `{Abteilung}` selbst bleibt als Platzhaltername im Kennzeichen-Format ungenutzt, aber als Mechanismus (jeder Nicht-Datums-/Zähler-Platzhalter = Attributname) identisch nutzbar, falls eine Installation ihn tatsächlich so benennen möchte.
- **Warum "Aktenzeichen" NICHT als eigenes Pflichtattribut modelliert wurde**: der reservierte Attributschlüssel `Kennzeichen` wird seit P5e-S2 serverseitig immer generiert und ein vom Client mitgesendeter Wert dafür immer verworfen (`document-service`) - ein zusätzliches, gleichnamiges Pflichtattribut hätte diesem bereits etablierten Mechanismus widersprochen. "Aktenzeichen" in 14.2s Aufzählung wird hier als "die Aktenzeichen-Generierung ist konfiguriert" gelesen, nicht als zusätzliches manuelles Pflichtfeld.
- **Warum `Verschlusssache-Akte` ein eigener, zweiter Objekttyp ist statt `Akte` selbst standardmäßig klassifiziert zu setzen**: ein normaler Verwaltungsvorgang ist nicht per Default eine Verschlusssache - `classification_level` auf `Akte` selbst vorzubelegen wäre eine fachlich falsche Voreinstellung gewesen. Ein zweiter, ansonsten identischer Typ demonstriert den Mechanismus konkret nutzbar, ohne die Standard-Akte zu verfälschen; eine Installation kann jederzeit weitere klassifizierte Varianten ergänzen oder `Akte` selbst nachträglich umstellen.
- **Warum 10 Jahre (3653 Tage) als `default_retention_days`-Vorbelegung**: ein verbreiteter, plausibler Richtwert für Verwaltungsakten in Deutschland, explizit als **veränderbare Vorbelegung** dokumentiert (Konzepttext wörtlich: "die konkrete gesetzliche Frist bleibt je Bundesland/Rechtsgebiet in der Verantwortung der Installation") - keine Recherche einer verbindlichen bundeseinheitlichen Frist unternommen, da keine existiert.
- **Warum das Paket als `packages/egov/config.json` im Repo liegt, nicht in einem der bestehenden `services`/`apps`-Verzeichnisse**: 14.1 wörtlich: "Pakete werden als eigenständige, versionierte Artefakte gepflegt (z. B. eigenes Verzeichnis/Repository je Paket)" - ein neues, gleichrangiges Top-Level-Verzeichnis (analog zu `services/`/`apps/`/`libs/`) macht das strukturell sichtbar, statt es in einem der bestehenden Services unterzubringen, zu dem es inhaltlich nicht gehört.
- **Warum eine einzige, über P17-S2/S3 hinweg wachsende Datei statt getrennter Dateien je Teil**: ein Konfigurationspaket ist laut 14.1 EIN Konfigurationsdokument - zwei separate Dateien hätten bedeutet, dass eine Installation zwei Importe durchführen müsste, um das vollständige Paket zu erhalten, und stünden im Widerspruch zum "additiv/Upsert, wiederholt anwendbar auf dieselbe Installation"-Prinzip (ein zweiter Import derselben Datei mit mehr Inhalt ist genau dieses Prinzip in Aktion).

## Konsequenzen

- **Migrationspfad**: `object_type_service/main.py`s Ad-hoc-Migration für `is_classified` wurde entfernt (kein `ADD COLUMN` mehr für ein nicht mehr genutztes Feld), eine neue für `classification_level VARCHAR(32)` ergänzt. Eine bereits laufende Installation behält die alte `is_classified`-Spalte unbenutzt in der Datenbank (kein Datenverlust, keine destruktive Migration, aber auch keine automatische Datenübernahme des alten Bool-Werts in eine Stufe - eine vorher klassifizierte Installation muss die gewünschte Stufe nach dem Update einmalig manuell im Objekttyp-Editor nachtragen).
- **`_PLACEHOLDER_RE` wurde von `[A-Za-z_]+` auf `\w+` geweitet**, damit Unicode-Attributnamen (Umlaute wie in "Federführung") als Kennzeichen-Platzhalter funktionieren - Python-Bezeichner/`str.format()` unterstützen das bereits nativ (PEP 3131), nur die bisherige Regex war enger als nötig.
- **Kein Rückwirkungs-Check bestehender Dokumente** bei einer nachträglichen Änderung von `kennzeichen_format` (z. B. Hinzufügen eines neuen Attribut-Platzhalters) - identische, bereits vor dieser Session bestehende Einschränkung wie beim reinen Datums-/Zähler-Format.
- **Teil 2 des eGov-Pakets (P17-S3)** ergänzt dieselbe `packages/egov/config.json` um `realm_roles`/`workflows`/`approval_config`/`business_calendars`/`roles` - `manifest.version` wird dabei erhöht (z. B. auf `1.0.0` als erste vollständige Version).
