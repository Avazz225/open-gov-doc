# 0059 — eGov configuration package part 1: file plan hierarchy, attribute-based reference number placeholders, multi-level classification

**Status:** accepted
**Context:** P17-S2 (eGov configuration package part 1, concept §14.2), second implementation session of Phase 17

## Decision

Three related decisions:

1. **`ObjectType.is_classified: bool` (P15-S1) is replaced by `classification_level: str | None`** — the four German classification levels named in the concept text (`VS-NfD`, `VS-VERTRAULICH`, `GEHEIM`, `STRENG GEHEIM`) as a `Literal` value space, `None` = not classified. Any set value (regardless of the specific level) still triggers exactly the same binary gate as the plain bool did before (classified-documents trash/separate deletion role, `domain-admin-deletion-vs`) — the level itself is purely additional information, no additional role differentiation. Affected services: `object-type-service` (schema/model/repository/migration), `document-service` (gate check in `purge_document`), `config-service` (`ObjectTypeExport`), `admin-ui` (`ObjectTypeEditor`: checkbox → `<select>`), `user-ui` (type declaration, unused).
2. **Reference number generator (P5e-S1) has, since this session, supported attribute-based placeholders** — any placeholder in `kennzeichen_format` that is not a date/counter placeholder (`{YYYY}`/`{YY}`/`{MM}`/`{DD}`/`{Laufende_Nummer}`) is interpreted as the name of an attribute defined on the object type (e.g. `{Federführung}`). Validated when the format is saved (not only on the first document creation); rendering pulls the values from the attributes supplied when the document is created (`document-service` forwards `parsed_attributes` via `object_type_client.next_kennzeichen()` to `object-type-service`'s `POST /object-types/{id}/next-kennzeichen`, new optional body field `attributes`). If a referenced attribute value is still missing (attribute not marked required), the endpoint returns `422` instead of generating a reference number with a silently empty gap.
3. **First concrete eGov configuration package, part 1** (`packages/egov/config.json`, `manifest.version` `0.1.0`): the hierarchy named as an example in concept 2.5, **Abteilung (department, folder) → Aktenplan (file plan, folder) → Akte (file, document)**, each enforced via `allowed_parent_types` (2.2a). `Akte` gets `kennzeichen_format: "{Federführung}-{YYYY}-{Laufende_Nummer}"`, the required attributes `Aktentitel` (file title)/`Federführung` (responsible unit), and `default_retention_days: 3653` (10 years, a changeable default). A second, otherwise identical object type `Verschlusssache-Akte` additionally demonstrates `classification_level: "VS-NfD"`.

## Rationale

- **Why replace instead of a second, parallel field**: maintaining `is_classified: bool` and a new `classification_level` column in parallel would have created a synchronization state that would need to be kept consistent on every write path — pure extra effort with no benefit, since the only consumer (the deletion gate) only ever needs "set or not". `classification_level is not None` replaces `is_classified` 1:1 everywhere (a Python truth value of a non-empty string already behaves like `True` anyway). Remains architecturally consistent with [ADR 0051](0051-papierkorb-familie-classification-via-object-type-scoped-global-endpoints.md)'s rationale for a schema-bound field instead of an attribute convention — only the value space was widened, not the pattern changed.
- **Why `list_object_types`'s filter parameter `is_classified` (bool) is kept, not renamed to `classification_level`**: `document-service`'s `list_classified_document_type_ids()` (classified-documents trash, P15-S1) needs "any classification or none", never a specific level — the name still describes exactly the actual question of its only caller. Internally it is translated to `classification_level IS (NOT) NULL`.
- **Why `Akte` is a document object type, and `Abteilung`/`Aktenplan` folder object types**: concept section 2.5 already states this literally ("**Akte** (document object type) resides in an **Aktenplan** (folder object type), which resides in an **Abteilung** (folder object type)") — no independent interpretation needed, just implementing as concrete object types the specification already made elsewhere in the concept. This also resolves apparent tension with 14.2's example format `{Abteilung}-{YYYY}-{Laufende_Nummer}`: the reference number generator is only allowed for `applies_to="document"` (since P5e-S1) — a format on `Akte` (a document) itself is therefore consistent from the start, it simply cannot literally be called `{Abteilung}`, since `Abteilung` is not an attribute of `Akte`, but the name of a structurally superior folder object type.
- **Why `{Federführung}` instead of an additional, redundant `Abteilung` attribute on `Akte`**: 14.2 names "Aktenzeichen, Aktentitel, Federführung" (file reference number, file title, responsible unit) literally as the three sensible required attributes — `Federführung` (the responsible unit) is already exactly the information the concept's example placeholder `{Abteilung}` refers to in substance. An additional attribute `Abteilung`, introduced purely for the placeholder, could have permanently diverged from the already structurally present department (the folder ancestor) — two independent sources of the same information. `Federführung` avoids this by being the single, explicitly concept-required attribute source. `{Abteilung}` itself remains unused as a placeholder name in the reference number format, but remains identically usable as a mechanism (any non-date/counter placeholder = attribute name), should an installation actually want to name it that way.
- **Why "Aktenzeichen" (file reference number) was NOT modeled as its own required attribute**: the reserved attribute key `Kennzeichen` has always been generated server-side since P5e-S2, with any client-supplied value for it always discarded (`document-service`) — an additional, identically named required attribute would have contradicted this already-established mechanism. "Aktenzeichen" in 14.2's list is read here as "reference number generation is configured", not as an additional manual required field.
- **Why `Verschlusssache-Akte` is its own, second object type instead of setting `Akte` itself classified by default**: a normal administrative matter is not by default classified information — pre-setting `classification_level` on `Akte` itself would have been a substantively wrong default. A second, otherwise identical type demonstrates the mechanism in concrete, usable form without corrupting the standard `Akte`; an installation can add further classified variants at any time, or later switch `Akte` itself.
- **Why 10 years (3653 days) as the `default_retention_days` default**: a common, plausible reference value for administrative files in Germany, explicitly documented as a **changeable default** (concept text literally: "the concrete statutory period remains the responsibility of the installation, per federal state/area of law") — no research into a binding, nationwide-uniform period was undertaken, since none exists.
- **Why the package lives at `packages/egov/config.json` in the repo, not in one of the existing `services`/`apps` directories**: 14.1 literally: "packages are maintained as standalone, versioned artifacts (e.g. their own directory/repository per package)" — a new, peer-level top-level directory (analogous to `services/`/`apps/`/`libs/`) makes this structurally visible, instead of housing it in one of the existing services it does not substantively belong to.
- **Why a single file growing across P17-S2/S3 instead of separate files per part**: a configuration package is, per 14.1, ONE configuration document — two separate files would have meant an installation needing to run two imports to get the complete package, contradicting the "additive/upsert, repeatedly applicable to the same installation" principle (a second import of the same file with more content is exactly this principle in action).

## Consequences

- **Migration path**: `object_type_service/main.py`'s ad-hoc migration for `is_classified` was removed (no more `ADD COLUMN` for a no-longer-used field), a new one added for `classification_level VARCHAR(32)`. An already-running installation keeps the old `is_classified` column unused in the database (no data loss, no destructive migration, but also no automatic carry-over of the old bool value into a level — a previously classified installation must manually re-enter the desired level once in the object type editor after the update).
- **`_PLACEHOLDER_RE` was widened from `[A-Za-z_]+` to `\w+`**, so that Unicode attribute names (umlauts, as in "Federführung") work as reference number placeholders — Python identifiers/`str.format()` already natively support this (PEP 3131), only the previous regex was narrower than necessary.
- **No retroactive check of existing documents** on a later change to `kennzeichen_format` (e.g. adding a new attribute placeholder) — identical, already pre-existing limitation as with a pure date/counter format.
- **Part 2 of the eGov package (P17-S3)** extends the same `packages/egov/config.json` with `realm_roles`/`workflows`/`approval_config`/`business_calendars`/`roles` — `manifest.version` is incremented accordingly (e.g. to `1.0.0` as the first complete version).
