# 0037 — Fleet Management Service: dedicated agent key instead of RBAC, ungated reads publicly exposed through the gateway

**Status:** accepted
**Context:** P13-S2 (fleet/license management service, concept 3a "central management layer, optional, separate building block")

## Decision

A new, **installation-independent** service `fleet-management-service` (analogous to `federation-hub-service`, ADR 0028) gives an operator with multiple installations three capabilities, verbatim from 3a: health/license overview, license assignment/renewal, central provisioning from a configuration template. It reaches every managed installation exclusively through that installation's **gateway** (`{gateway_base_url}/api/{service}/...`), never an internal container address - and exclusively `registry-service`/`license-service`/`config-service`, never `document-service`/`folder-service` (3a verbatim: "no access to document content").

Authentication of this foreign, installation-independent caller is **not** done via Keycloak/RBAC (the fleet service has no principal in any managed installation), but via a new, installation-wide, optional secret `DMS_FLEET_AGENT_API_KEY` (`dms_common.BaseServiceSettings`, continuation of P13-S1). `license-service`'s `POST /license` and `config-service`'s `POST /config/import` accept, in addition to the existing RBAC path, an `Authorization: Bearer <fleet_agent_api_key>` bypass. The two read endpoints that were already ungated before this session (`registry-service` `GET /installation`, `license-service` `GET /license/status`) remain ungated, unchanged. `gateway-service.settings.public_routes` gets four new entries so these four paths are reachable through the gateway without a Keycloak bearer token.

## Rationale

- **No cross-Keycloak-realm trust is possible**: every installation has its own, independent Keycloak realm (3a: "fully isolated"). An external, installation-independent service can structurally never hold a valid principal token for a foreign installation - RBAC is not an applicable model here.
- **A dedicated API-key secret instead of RBAC is already an established pattern**, used twice in this project for exactly this problem: `federation-hub-service`'s `Installation.api_key_hash` (ADR 0028) and `migration-service`'s `PairedInstallation.api_key`/`api_key_hash` (ADR 0034) both authenticate an external, foreign-installation caller without RBAC. A third, cross-service special case (fleet agent) reuses the same principle instead of inventing a fourth, bespoke one.
- **An installation-wide shared key instead of public-key cryptography** (unlike Federation Hub/ADR 0028's end-to-end encryption): 3a requires neither encryption nor non-repudiation for this building block, only an access barrier for two narrowly scoped write actions - a simple, statically configured shared secret (like ADR 0032's license public key) is sufficient for this scope and considerably simpler than a PKI scheme.
- **`registry-service`/`license-service` do not change their already-ungated read endpoints**: `GET /installation` (P13-S1) and `GET /license/status` (P9-S2) have deliberately had no principal check since their respective introduction, because other internal services call them without their own identity (e.g. `registry-service`'s `ComponentLicenseCache`). Extending this existing trust decision to the gateway (rather than tightening it) is the consistent, smallest-possible change - a documented, deliberate propagation of an already-made decision, not a new one.
- **`gateway-service.public_routes` is the already-established mechanism** for "this path needs no Keycloak token" (used since P6-S9 for `workflow-service:federation/inbound(-result)`, an identical scenario: an external, coordinating service with no installation principal). No new gateway feature needed.
- **A pure pass-through instead of its own template management**: `POST /installations/{id}/provision` accepts a raw 7.3 configuration document without curating or storing it - a template library is concept §14/phase 17 ("preconfigured configuration packages"), deliberately not part of this session since it does not yet exist.
- **`asyncio.gather` for `GET /installations/status`**: a single unreachable installation must not delay the overview of the rest - each individual status fetch catches its own errors (`reachable=False`) instead of propagating an exception, the same principle as other poll loops in this project.

## Consequences

- `DMS_FLEET_AGENT_API_KEY` is `None` by default (no fleet access possible) - an installation must actively decide to opt in (3a: "optional, separate building block"). In the bundled dev/test stack (`infra/docker-compose.yml`) it is preset to a fixed `dev-fleet-agent-key` value so that `config-service`'s live-container tests can exercise it (config-service has no in-process `TestClient`, see its `tests/test_api.py` module docstring) - a real installation overwrites or clears it.
- Four additional `gateway-service.public_routes` entries mean: `registry-service:installation` and `license-service:license/status` are now reachable through a productively exposed gateway **without any proof of identity whatsoever** (a deliberate, documented extension of the already-existing ungated decision for these two endpoints - purely configuration values or license usage numbers, no document content). `license-service:license` and `config-service:config/import` are likewise reachable through the gateway without a Keycloak token, but remain protected by each target service's own `_is_fleet_agent()` check - the gateway itself does not know `DMS_FLEET_AGENT_API_KEY`.
- `fleet-management-service` stores `fleet_agent_api_key` per managed installation in **plaintext** (not hashed) - unlike `federation-hub-service`'s `Installation` (which only needs a hash because the hub never signs itself), this service must present the key on every outgoing call, and a hash would make that structurally impossible (identical rationale to `migration-service`'s `PairedInstallation`, ADR 0034).
- No key rotation mechanism at this stage - a compromised fleet agent key requires manually changing `DMS_FLEET_AGENT_API_KEY` on the installation side and a corresponding `DELETE`+recreate cycle on the fleet side, analogous to the already-documented lack of rotation for the license signing key (ADR 0032).
