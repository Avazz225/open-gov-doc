# 0037 — Fleet-Management-Service: dedizierter Agent-Schlüssel statt RBAC, ungegatete Reads über den Gateway öffentlich

**Status:** akzeptiert
**Kontext:** P13-S2 (Fleet-/Lizenz-Management-Service, Konzept 3a "Zentrale Verwaltungsebene, optional, separater Baustein")

## Entscheidung

Ein neuer, **installationsunabhängiger** Service `fleet-management-service` (analog `federation-hub-service`, ADR 0028) gibt einem Betreiber mit mehreren Installationen drei Fähigkeiten, wörtlich aus 3a: Health-/Lizenz-Überblick, Lizenzvergabe/-verlängerung, zentrales Provisioning aus einer Konfigurationsvorlage. Er erreicht jede verwaltete Installation ausschließlich über deren **Gateway** (`{gateway_base_url}/api/{service}/...`), nie eine interne Container-Adresse - und ausschließlich `registry-service`/`license-service`/`config-service`, nie `document-service`/`folder-service` (3a wörtlich: "keinen Zugriff auf Dokumenteninhalte").

Authentisierung dieses fremden, installationsunabhängigen Aufrufers erfolgt **nicht** über Keycloak/RBAC (der Fleet-Service hat keinen Principal in irgendeiner verwalteten Installation), sondern über ein neues, installationsweites, optionales Geheimnis `DMS_FLEET_AGENT_API_KEY` (`dms_common.BaseServiceSettings`, P13-S1-Fortsetzung). `license-service`s `POST /license` und `config-service`s `POST /config/import` akzeptieren zusätzlich zum bestehenden RBAC-Pfad einen `Authorization: Bearer <fleet_agent_api_key>`-Bypass. Die beiden bereits zuvor ungegateten Lese-Endpunkte (`registry-service` `GET /installation`, `license-service` `GET /license/status`) bleiben unverändert ungegatet. `gateway-service.settings.public_routes` bekommt vier neue Einträge, damit diese vier Pfade ohne Keycloak-Bearer-Token durch den Gateway erreichbar sind.

## Begründung

- **Kein Keycloak-Realm-übergreifendes Vertrauen möglich**: jede Installation hat ihren eigenen, unabhängigen Keycloak-Realm (3a: "vollständig isoliert"). Ein externer, installationsunabhängiger Dienst kann strukturell keinen gültigen Principal-Token für eine fremde Installation besitzen - RBAC ist hier kein anwendbares Modell.
- **Dediziertes API-Key-Geheimnis statt RBAC ist bereits zweimal etabliertes Muster** in diesem Projekt für genau dieses Problem: `federation-hub-service`s `Installation.api_key_hash` (ADR 0028) und `migration-service`s `PairedInstallation.api_key`/`api_key_hash` (ADR 0034) authentisieren beide einen externen, installationsfremden Aufrufer ohne RBAC. Ein dritter, service-übergreifender Spezialfall (Fleet-Agent) wiederverwendet dasselbe Prinzip, statt ein viertes, eigenes zu erfinden.
- **Installationsweiter, geteilter Schlüssel statt Public-Key-Kryptografie** (anders als Federation Hub/ADR 0028s Ende-zu-Ende-Verschlüsselung): 3a fordert für diesen Baustein weder Verschlüsselung noch Nicht-Abstreitbarkeit, nur eine Zugriffsschranke für zwei eng begrenzte Schreibaktionen - ein einfacher, statisch konfigurierter Shared Secret (wie ADR 0032s Lizenz-öffentlicher-Schlüssel) ist für diesen Umfang ausreichend und deutlich einfacher als ein PKI-Schema.
- **`registry-service`/`license-service` verändern ihre bereits ungegateten Lese-Endpunkte nicht**: `GET /installation` (P13-S1) und `GET /license/status` (P9-S2) sind seit ihrer jeweiligen Einführung bewusst ohne Principal-Prüfung, weil andere interne Services sie ohne eigene Identität aufrufen (z. B. `registry-service`s `ComponentLicenseCache`). Diese bestehende Vertrauensentscheidung auf den Gateway auszuweiten (statt sie zu verschärfen) ist die konsistente, kleinstmögliche Änderung - dokumentierte, bewusste Weitergabe einer bereits getroffenen Entscheidung, keine neue.
- **`gateway-service.public_routes` ist der bereits etablierte Mechanismus** für "dieser Pfad braucht keinen Keycloak-Token" (seit P6-S9 genutzt für `workflow-service:federation/inbound(-result)`, identisches Szenario: ein externer, koordinierender Dienst ohne Installations-Principal). Kein neues Gateway-Feature nötig.
- **Reiner Durchreicher statt eigener Vorlagen-Verwaltung**: `POST /installations/{id}/provision` nimmt ein rohes 7.3-Konfigurationsdokument entgegen, ohne es zu kuratieren oder zu speichern - eine Vorlagen-Bibliothek ist Konzept §14/Phase 17 ("Vorkonfigurierte Konfigurationspakete"), bewusst nicht Teil dieser Session, da diese noch nicht existiert.
- **`asyncio.gather` für `GET /installations/status`**: eine einzelne nicht erreichbare Installation darf die Übersicht der übrigen nicht verzögern - jeder einzelne Statusabruf fängt seine eigenen Fehler ab (`reachable=False`) statt eine Exception zu propagieren, gleiches Prinzip wie andere Poll-Schleifen in diesem Projekt.

## Konsequenzen

- `DMS_FLEET_AGENT_API_KEY` ist `None` per Default (kein Fleet-Zugriff möglich) - eine Installation muss aktiv entscheiden, daran teilzunehmen (3a: "optional, separater Baustein"). Im gebündelten Dev-/Test-Stack (`infra/docker-compose.yml`) ist er auf einen festen `dev-fleet-agent-key`-Wert vorbelegt, damit `config-service`s Live-Container-Tests ihn prüfen können (config-service hat kein In-Prozess-`TestClient`, siehe dessen `tests/test_api.py`-Moduldocstring) - eine echte Installation überschreibt oder leert ihn.
- Vier zusätzliche `gateway-service.public_routes`-Einträge bedeuten: `registry-service:installation` und `license-service:license/status` sind ab sofort über einen produktiv exponierten Gateway auch **ohne jeden Nachweis** erreichbar (bewusste, dokumentierte Ausweitung der bereits bestehenden Ungegatet-Entscheidung dieser beiden Endpunkte - reine Konfigurationswerte bzw. Lizenz-Nutzungszahlen, keine Dokumentinhalte). `license-service:license` und `config-service:config/import` sind über den Gateway ebenfalls ohne Keycloak-Token erreichbar, aber weiterhin durch die jeweils eigene `_is_fleet_agent()`-Prüfung der Zielservices geschützt - der Gateway selbst kennt `DMS_FLEET_AGENT_API_KEY` nicht.
- `fleet-management-service` speichert `fleet_agent_api_key` je verwalteter Installation im **Klartext** (nicht gehasht) - anders als `federation-hub-service`s `Installation` (die nur einen Hash braucht, weil der Hub nie selbst signiert) muss dieser Service den Schlüssel bei jedem ausgehenden Aufruf präsentieren, ein Hash würde das strukturell unmöglich machen (identische Begründung wie `migration-service`s `PairedInstallation`, ADR 0034).
- Kein Schlüssel-Rotationsmechanismus in dieser Ausbaustufe - ein kompromittierter Fleet-Agent-Schlüssel erfordert manuelles Ändern von `DMS_FLEET_AGENT_API_KEY` auf der Installationsseite und einen entsprechenden `DELETE`+Neuanlage-Zyklus auf der Fleet-Seite, analog zur bereits dokumentierten fehlenden Rotation des Lizenz-Signaturschlüssels (ADR 0032).
