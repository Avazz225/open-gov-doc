# 0024 — Emergency shutdown: gateway as enforcement point + header broadcast instead of service polling

**Status:** accepted
**Context:** P6-S6 (Concept 4.8, "emergency shutdown"). System-wide emergency lockdown tool: freely configurable as to who may trigger it, optional four-eyes principle on triggering, immediate effect (terminate sessions, reject new logins except for the superuser, halt running workflow instances/scheduled jobs/plugin instances, block write access to storage/DB, pause federation-hub operations), maintenance mode as the resulting state (only the activated superuser from 4.6, [ADR 0023](0023-superuser-breakglass-and-domain-admin-accounts.md), remains able to act), highest audit priority + optional alerting. Federation (7.4), plugin instances (3.8), and the CLI tool (6.2) do not yet exist in this repo — the implementation is necessarily an honestly limited subset, as with P6-S4/S5 before it. Additional retrofit mandate (user decision, see below): Workflow Service authorization and Notification Service call authorization.

## Decision

**Maintenance-mode state lives as a new singleton table `SystemMaintenanceMode` in the Permission Service** (`id=1`, `active`, `reason`, `triggered_by`, `activated_at`, `lifted_by`, `lifted_at`) — the same pattern as `OcrConfig`/`GuardConfig`. The Permission Service is already home to all system-wide RBAC/approval concepts (4.1/4.3/4.6/4.7); the gateway itself has no database.

**Who may trigger it is configurable via RBAC, not hardcoded**: a new, native role `domain-admin-emergency` (capability `system.not_shutdown.trigger`), seeded like the other domain-admin roles from P6-S5 — deliberately **without** an automatic technical account (like `breakglass-approver`, unlike `users-admin`/`config-admin`), since an emergency lockdown should remain attributable to a real, individually accountable person.

**`POST /maintenance-mode/trigger` always first checks a baseline capability**, regardless of whether four-eyes is activated: a new `repository.require_capability()` function extracted from the existing `_require_permission_if_configured` logic. If `ApprovalActionConfig("system.not_shutdown.trigger").requires_approval` is set (default `false`, unlike break-glass, which is **not** hard-defaulted to `true`, since 4.8 describes the four-eyes involvement as "optional"), activation runs through the existing generic four-eyes mechanism (P6-S4/[ADR 0022](0022-four-eyes-approval-via-events.md)) — otherwise directly.

**Lifting is reserved exclusively for the currently active superuser** (4.8 literally: "only the activated superuser ... may specifically lift the lockdown again"). `POST /maintenance-mode/lift` therefore asks the Auth Service, via the Permission Service, for the active superuser (`GET /superuser/status`, extended with `principal_id`) and refuses unless `lifted_by` is exactly this ID or no superuser is active. New, thin `auth_client.py` in the Permission Service — **this service's first cross-service call in this direction** (the Auth Service has already been calling the Permission Service since P6-S5, now the reverse also happens). This bidirectional dependency is **not a runtime cycle** (independent, non-nested HTTP calls, each occurring only at request time, not at startup), but it is a real **Docker Compose `depends_on` cycle risk** — resolved by giving `permission-service` the new `DMS_AUTH_SERVICE_BASE_URL` environment variable, but deliberately **no** `depends_on: auth-service` (the call only happens on `POST /maintenance-mode/lift`, not at its own startup, so there is no real startup-order dependency).

**The gateway is the central enforcement point**, since its `proxy()` function is already the only code path that every proxied request passes through (existing `public_routes` mechanism, ADR 0005). A new `MaintenanceStateClient` (mirrored on `InstanceResolver`, short caching via `maintenance_cache_ttl_seconds`) queries the Permission Service through the registry — not via a fixed service URL, since the gateway never knows a fixed backend address anyway. When maintenance mode is active, all proxied requests are rejected with `503`, except for a new `maintenance_mode_allowed_routes` allowlist (login/refresh/me/superuser-status/maintenance-mode-status/-lift). On an error while querying the Permission Service, the client **fails open** (last cached value, default `false`) — an unreachable Permission Service should not take down all proxied traffic.

**Header broadcast instead of service polling**: every request let through (even outside maintenance mode) additionally carries an `X-DMS-Maintenance-Active: true`/`false` header. Backend services that themselves need to react to the state (Auth Service `/login`, Workflow Service `start_instance`/`complete_task`) read this header directly instead of maintaining their own polling connection to the Permission Service. The SLA poll loop in the Workflow Service is the only exception (no incoming request to attach a header to) — it gets its own thin `permission_client.py` that queries `GET /maintenance-mode` directly.

**Auth Service `/login` reads the header**: if maintenance mode is active and the requested username is not the superuser account, the login is rejected with `503` — a literal implementation of "new logins except for the superuser are rejected".

**Halting running workflow instances/scheduled jobs — deliberately limited, honest interpretation**: `POST .../instances` (instance start) and `POST .../tasks/{id}/complete` (task completion) reject with `503` when the header is active — no new instances/progress during the lockdown. The SLA poll loop skips its tick when maintenance mode is active. **Not implemented**: an actual "hard stop with consistency check" of already-running, synchronously executed SpiffWorkflow calls — this project has no long-lived background executions beyond the poll loop (full state serialization per instance, synchronous per request, [ADR 0019](0019-workflow-full-state-serialization.md)) that would need to be "halted".

**System-wide blocking of write access to storage/DB — not implemented except indirectly via gateway blocking**: covers every user-/UI-driven write access, since all frontends go exclusively through the gateway. Direct service-to-service calls (bypassing the gateway, internal Docker network) remain unaffected — the same structural boundary as with the directly published backend ports (ADR 0005). A generic "block all write paths of all services" mechanism would be its own, significantly larger session.

**Federation Hub (7.4) and plugin instances (3.8) do not exist** — the corresponding 4.8 requirements ("pause federation operations", "halt plugin instances") remain unimplemented, a documented open point.

**Workflow Service retrofit (user decision)**: `POST /process-definitions` (BPMN/script-task upload) and `DELETE /process-definitions/{id}` require the `admin.object_config` capability via a real Permission Service call (`403` otherwise) — `auth-service` creates a second technical account `config-admin`/`config-admin` for this (domain "workflow configuration", symmetric to `users-admin` from P6-S5). Instance start/task completion remain open to any authenticated principal (normal business use) and instead respect the new maintenance-mode lock. Since script code only enters the system via the now-gated BPMN upload (no separate execution endpoint), this effectively also secures script-task execution.

**Notification Service retrofit (user decision)**: `POST /notifications` checks, for `channel in {"email","in_app"}`, that the recipient exists against real Auth Service accounts (`GET /users`, new `auth_client.py`) — `400` for an unknown recipient. `channel="webhook"` remains unchecked (the target is a URL, not an identity). Notification Service stays **deliberately reachable during maintenance mode** — it is needed for the security alerting itself (`permission.maintenance_mode.activated` as a third consumed subject, email to `security_officer_email`). The new recipient check calls `GET /users` on the Auth Service, which has been gated behind `admin.user_management` since P6-S5 — Notification Service authenticates for this as the existing `users-admin` account (`POST /login` per call, no token caching, latency trade-off accepted for a low-frequency internal check) instead of introducing a third technical account.

**No increased audit priority**: `AuditEvent` still has no priority field ([ADR 0023](0023-superuser-breakglass-and-domain-admin-accounts.md), "Consequences") — remains an open point.

## Rationale

- **Gateway as the sole enforcement point instead of N service integrations**: every proxied request already passes through `proxy()` anyway — a single blocking check there covers every UI-/API-driven access, without every individual backend service needing its own enforcement logic.
- **Header broadcast instead of N×polling**: without the header, every service that itself wants to react to the state (Auth Service, Workflow Service) would have to maintain its own polling connection to the Permission Service — the gateway already computes the state once per request anyway for its own blocking decision, so an additional header is essentially free.
- **Baseline capability check as its own, reusable function instead of a copy**: no four-eyes precedent from P6-S4/S5 ever had a permission check *without* four-eyes (break-glass is always gated, scope locks/force-unlock have no permission check at all) — extracting from `_require_permission_if_configured` avoids duplicated check logic between the direct and the approval path.
- **Permission Service asks the Auth Service for the superuser identity instead of maintaining a second source of truth**: the superuser identity already lives unambiguously in the Auth Service (P6-S5); duplicating this state in the Permission Service would be a source of synchronization errors without any corresponding benefit.
- **No `depends_on` cycle, since the cross-service call is request-time, not startup-time**: the Permission Service does not need to talk to the Auth Service at its own startup, only when `POST /maintenance-mode/lift` is actually called — so the environment variable alone suffices, with no startup-order constraint.
- **Fail-open instead of fail-closed for the gateway maintenance check**: an unreachable Permission Service should not take down all proxied traffic just because a single health state could not be queried — consistent with the existing fail-open behavior of the `InstanceResolver` cache.
- **Notification Service as an exception to the gateway lockdown**: 4.8 itself requires "optional alerting" upon triggering — a lockdown that also prevents notification about itself would be self-contradictory.
- **Workflow/Notification Service retrofit scope from explicit user clarification**: since neither lane-to-role resolution nor service-to-service authentication exists, the narrower, recommended option was chosen (gate admin actions, leave everyday use open) rather than a broader interpretation building on infrastructure that does not exist.

## Consequences

- **Federation Hub (7.4) and plugin instances (3.8) remain completely unaddressed** — the corresponding 4.8 effects ("pause federation operations", "halt plugin instances") are not implemented, since the underlying services do not exist.
- **No system-wide write ban beyond the gateway** — direct service-to-service write calls (bypassing the gateway) remain possible during maintenance mode, the same structural boundary as with the directly published backend ports.
- **No "hard stop" of already-running executions** — only new instance starts/task completions are blocked, but there are no long-lived background executions to interrupt anyway (see above).
- **No increased audit priority** — `permission.maintenance_mode.*` events are handled by the Audit Service with the same priority as any other `permission.>` event.
- **New bidirectional dependency Permission Service ↔ Auth Service** — when consulting `docs/architecture.md`, note that both services now make HTTP calls in both directions (Auth Service → Permission Service since P6-S5 for role assignment/checking, Permission Service → Auth Service since P6-S6 for the superuser check on lifting) — deliberately not a cycle in the runtime sense, but deliberately modeled as only one direction in the Docker Compose `depends_on` graph.
- **6 of the 7 domain-admin roles from 4.6 still without an associated technical account** — `domain-admin-emergency` (new, P6-S6) joins `breakglass-approver` as a second role without an automatic account (deliberate, see above), the remaining 5 stay as documented in ADR 0023.
- **Only one technical account for the user-existence check** — Notification Service does not present its own identity, but authenticates as `users-admin`; a future overuse of this pattern (every service that needs a gated foreign API logging in as a foreign technical account) should be revisited as this grows further (already foreshadowed in ADR 0023).
