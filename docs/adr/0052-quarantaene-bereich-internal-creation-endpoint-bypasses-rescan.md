# 0052 — Quarantine area: internal creation path bypasses the re-scan on release

**Status:** accepted
**Context:** P15-S2 (quarantine area, concept §2.5/10.3)

## Decision

1. **`POST /documents/from-quarantine-release` (new, `document-service`)** creates a real document from bytes that never went through the regular `POST /documents` path — without the `virus_scan_client.scan()` call built in synchronously there. Refactored: the shared validation/creation logic (`_prepare_document_fields`/`_persist_new_document`) is used by both endpoints, only the scan step remains exclusive to `POST /documents`.
2. **Two independent role gates instead of one**: `virus-scan-service`'s new `quarantine_admin_role` setting checks release authorization first; `document-service`'s new `quarantine_release_admin_role` setting checks it a second time, based on the `X-DMS-Principal`/`X-DMS-Roles` headers forwarded by the caller. Both independently default to `"dms-admin"`.
3. **One role for viewing, releasing, and permanent deletion** (`virus-scan-service`'s `quarantine_admin_role`) instead of separate role settings per action — concept §2.5 literally speaks of "a dedicated, narrowly scoped role" covering all three actions.
4. **`GET /scans` gets an additive `status` query parameter**: only `status=infected` is role-gated (401/403), any other/no `status` remains exactly ungated as before — the same additive pattern as the `scope` parameter of the trash family (P15-S1, ADR 0051).
5. **`ScanResult` gets two new, generic columns `resolved_by`/`resolved_at`** instead of four separate `released_by`/`released_at`/`purged_by`/`purged_at` — both actions are mutually exclusive terminal states (`status="released"` or `"purged"`), a row only ever needs to know the one applicable resolver.
6. **`quarantine_object_key` is never set to `NULL`**, even after the bytes themselves have been removed from the storage service (release or permanent deletion) — it remains as a historical reference, analogous to the unchanged `DeletionRegisterEntry` pattern of the trash family.
7. **No entry in `audit-service`'s `FORCE_DELETION_EVENT_TYPES` ledger (10.4)** for `virus_scan.purged` — the regular audit trail via `virus_scan.>` (already subscribed since P5-S1) fully satisfies concept §2.5's "audited process (5.3)"; the separate append-only ledger is, per existing code comment, deliberately limited to forced deletions of physical (not already-quarantined) objects.

## Rationale

- **Why no re-scan on release is possible**: `POST /documents` scans every attachment unconditionally (10.3, ADR 0010). If the release called the same endpoint with the same bytes, the scan engine would deterministically reproduce the same finding (now classified as a false positive) — release would structurally never be possible, most obviously with the `eicar` test engine (this project's default configuration), which always flags EVERY EICAR signature as infected, regardless of context. A bypass is therefore not a convenience, but the only way to implement concept §2.5's "release after clarifying a false positive" at all.
- **Why two role gates instead of one**: this project has no internal service-to-service auth mechanism anywhere (no shared secret, no `X-Internal-*` header) — every existing cross-service call (e.g. `dms_connector_sdk`'s `POST /documents`) is unauthenticated and relies on network trust within the Docker network. A new endpoint that bypasses the mandatory virus scan is security-relevant enough not to depend on a single check — `virus-scan-service` forwards the `X-DMS-*` headers of the original caller, already validated by the gateway, unchanged; `document-service` independently validates them a second time (cost: two lines of `httpx` header handling, no new mechanism).
- **Why no per-action roles like in the trash family**: P15-S1 deliberately separates `trash_hard_delete_admin_role`/`classified_trash_hard_delete_admin_role` because both roles can in practice be assigned to different people (regular vs. classified-documents deletion administration). Concept §2.5, for quarantine, instead explicitly names ONE role for all three actions — an artificial split with no concept basis would be an unjustified deviation.
- **Why `resolved_by`/`resolved_at` instead of four columns**: `status` alone already disambiguates which of the two actions took place — four columns would in every row be half fundamentally empty, with no additional insight compared to two generic columns plus the already-existing `status` field.

## Consequences

- **An installation that configures `quarantine_admin_role` (virus-scan-service) and `quarantine_release_admin_role` (document-service) differently from `"dms-admin"` AND differently from each other** must note that release only succeeds if the calling principal holds BOTH roles — a deliberate, documented design decision (defense in depth), not an inconsistency. The frontend (`IconRail.tsx`) only knows the virus-scan-service-side role for the visibility of the icon-rail entry itself; a differently configured installation must manually adjust this constant, as with `TrashPane.tsx` (P15-S1).
- **The quarantine area, unlike the trash family, has no "personal" view** — anyone not holding the limited role does not see the icon-rail entry at all (client-side) and would get 401/403 server-side on `GET /scans?status=infected` anyway. Concept §2.5 provides no reduced self-service view for this (unlike trash, where every user may at least see their own deletion markers).
- **Release requires manually supplying `folder_id`/`object_type_id`/`attributes`** — none of these values were known at the time of the originally failed upload (since no document was ever created). The new `QuarantinePane` form only asks for `title` (required) and `folder_id` (optional, free text instead of a dedicated folder picker, which was out of scope for this session) — `object_type_id`/`attributes` can be added afterward via the existing PATCH endpoints if needed.
