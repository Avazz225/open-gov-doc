# 0055 — Records disposal access area: hydrated, read-only view over archival-service's existing state machine

**Status:** accepted
**Context:** P15-S5 (records disposal access area, concept §2.5/5.6/7.2)

## Decision

Three related decisions:

1. **New, hydrated `GET /released-items?q=` endpoint (archival-service)** — combines `ArchivalTransfer` and `CaseArchivalTransfer` rows with `status="released"` (already-existing state machine, P7-S3/S3b) and enriches them live via `document_client.get_document`/`case_client.get_case` with title/reference number or name/case reference number. Pure aggregation/filter view, no new data store — `browse.py`'s `build_released_items` is stateless, there is no new table/field in `models.py`.
2. **Role gate reused instead of a new setting** — `GET /released-items` checks the same `settings.archive_retrieval_role` (default `dms-admin`) that already protects `POST /archival-transfers/{id}/retrieve` and `GET /case-archival-transfers/{id}/package`, instead of introducing a second, redundant role setting.
3. **Searchability as server-side substring filtering after hydration**, not a dedicated search index — `q` is checked case-insensitively against title/name and reference number/case reference number after the metadata has been loaded (`browse._matches`). No `pg_trgm`/full-text search as in `query-service` (5.4) — the expected result set (disposed items not yet permanently deleted) is small enough that in-memory filtering after a live fetch suffices.

## Rationale

- **Why no new data store**: `IMPLEMENTATION_PLAN.md` explicitly describes the session as "a pure filtered view, no new data store" — `archival-service` already owns the full, resumable state machine including the `released` status via `ArchivalTransfer`/`CaseArchivalTransfer` (P7-S3/S3b); `document-service`/`case-service` remain the sole authority for title/reference number/case reference number (existing principle, see `clients.py` docstrings). A new endpoint that merges both at display time fulfills the mandate without data duplication.
- **Why the retrieval role is reused instead of a new setting**: concept 2.5 states for this special area "access generally restricted to the same roles that had access before disposal, plus optionally a dedicated archive/registry role" — genuinely enforcing "the same roles as before" would require a per-object ACL check, which does not exist consistently in this project for documents/circulation folders (see the repeatedly documented authorization gap, e.g. `docs/services/document-service.md` "Open Points"). The already-existing `archive_retrieval_role` is exactly the "dedicated archive/registry role" named in the concept — reusing it avoids a second setting that would in practice always be configured identically, without diluting the concept requirement (whoever may retrieve may also view).
- **Why prefix/substring filtering instead of a search index**: the target set is structurally small (only items within the transition-period window, typically a volume of days to a few months) and must already be fully hydrated in order to display title/reference number at all — additional search infrastructure (like `query-service`'s `pg_trgm` fuzzy search, 5.4) would be disproportionate at this scale.
- **Why fault tolerance during hydration instead of a 502**: a single no-longer-resolvable `document_id`/`case_id` reference (e.g. due to a later hard deletion, see `docs/services/document-service.md`) must not hide the other, correctly resolvable hits — same fault-tolerance principle as `directory_federation.search_all_peers` (ADR 0054): skip + log instead of aborting entirely.

## Consequences

- **Circulation folders never automatically "disappear" from this area** — concept 5.6 literally says "after the transition period expires, an item disappears from this area (regular deletion in the active system)", but `CaseArchivalTransfer` (unlike `ArchivalTransfer`) has no `dehydrated` status and no own live storage content that could be removed (see `models.py` docstring, P7-S3b). `purge_at` therefore deliberately stays `null` for circulation folders instead of an invented expiry date. **Deliberately open point** — a real case-purge concept (what would "deleted" even mean for a circulation folder, when the referenced documents have their own independent lifecycle?) is not part of this session.
- **`GET /released-items` reads live from `document-service`/`case-service`** (no cache) — with a high hit count this produces an N+1 request pattern (one HTTP call per transfer). Uncritical for the expected scale (see above); with very many simultaneously `released` items, a batch query would be a later optimization, not a current need.
- **Frontend only offers already-existing actions** — "retrieval" (documents, `POST /archival-transfers/{id}/retrieve`) and "download package" (circulation folders, `GET /case-archival-transfers/{id}/package`) already existed before this session; `AussonderungPane` makes them visible/reachable for regular end users in the user UI for the first time (previously only via the pure administration/status table in the admin UI, see `docs/services/archival-service.md` "Open Points" prior to this session).
- **Icon-rail entry role-gated** (`dms-admin`, same default as `archive_retrieval_role`) — unlike contacts (P15-S4, ADR 0054, deliberately ungated), this special area is not "local, always available", but requires a dedicated role per concept 2.5.
