# 0047 — Public share link: token as a query parameter, 404 instead of 403 on disablement, real read-permission check at creation

**Status:** accepted
**Context:** P14-S10 (public share link, concept 4.2a)

## Decision

A time-limited, unauthenticated read-access link to exactly one document is implemented directly in `document-service` (no new, standalone service - the same principle as locks/retention/legal hold, which already live there). Four design decisions carry the implementation:

1. **The share-link token travels as a query parameter (`?token=...`), not as a path segment.** The two new public endpoints (`GET /public/share-links`, `GET /public/share-links/content`) have fixed paths; only the query parameter varies per link.
2. **`ShareLink.token` is both the primary key AND the secret used in the URL** (`secrets.token_urlsafe(32)`) - no separate, guessable ID field alongside it with the same access power.
3. **Disabling the feature (`ShareLinkConfig.enabled = False`) returns `404` instead of `403`** on all affected endpoints (create, list, both public read endpoints) - AND thereby also breaks already-issued, otherwise still-valid links.
4. **Creating a share link performs a real check against `permission-service`** to verify the requesting person has `document.read` on the target folder (new `permission_client.py`) - the first genuine read-permission check in `document-service`, which previously only knew the four-eyes approval mechanism but otherwise enforces no access control of its own.

## Rationale

- **A query parameter instead of a path segment satisfies the gateway's `public_routes` exception list without changing its matching logic.** `gateway-service` allows bearer-token-free access via an exact `"{service_type}:{path}"` string list (`settings.public_routes`, established since P6-S9 for Federation Hub inbound routes). A per-link-varying token as a path segment (`/public/share-links/{token}`) would have required either wildcard matching at the gateway (new logic, not just new configuration) or would not have been representable at all via the exact-match list. As a query parameter, the two new entries (`document-service:public/share-links`, `document-service:public/share-links/content`) remain simple, static strings - FastAPI's path parameters (`path: str`) never contain a query-string component, and the `route_key` comparison in `gateway_service.main.proxy()` remains unchanged.
- **Token as primary key instead of a separate ID avoids a second, unnecessary secret.** An additional numeric/UUID `id` alongside the token would have brought no security benefit (whoever knows the token already has full read access anyway) and would only have added extra fields/indexes to maintain.
- **`404` instead of `403` is the closest approximation of "no API route reachable".** The concept wording for the installation-wide disable switch ("the feature is not even offered in the UI (no menu entry, no reachable API route)") describes a behavior that an already-running FastAPI instance cannot technically reproduce exactly without a restart - a route cannot be unregistered at runtime. `404` ("Not Found") is closer to "not reachable" than `403` ("Forbidden", which implicitly confirms the route exists and access is merely denied). Applied consistently across all four affected endpoints.
- **Disabling also breaks already-issued links, not just new creation.** The wording "disable entirely" (installation-wide switch) would otherwise only be a block on new creation, while links long since distributed on the internet would keep working - that would contradict the discernible intent of a kill switch. `_resolve_active_share_link()` checks `config.enabled` BEFORE token validity, precisely for this reason.
- **A real `permission-service` check at creation, even though `document-service`/`folder-service` direct access remains unenforced elsewhere in the project** (a documented gap, see `docs/architecture.md`): issuing an anonymous link to a document, potentially reachable publicly on the internet, is qualitatively a bigger security step than yet another internal, already-authenticated API call - the same tradeoff already made in P14-S6 for teamspace search-result filtering (a real check where the harm from omitting it would be greatest, not everywhere). `PermissionServiceClient.check_read()` calls `permission-service`'s already-existing `GET /check` single-resource endpoint for this.
- **Two separate audit event types for view vs. download** (`document.share_link.viewed` / `document.share_link.accessed`) follow the already-established granularity of `AuditTraceConfig` (`log_viewed`/`log_downloaded`, since P7-S2) - metadata display and an actual byte download are events of different significance.
- **`PublicShareLinkOut` is deliberately minimized to four fields** (`title`, `content_type`, `size_bytes`, `expires_at`) - no `attributes`/`folder_id`/`created_by`, which would go beyond the minimum needed for a pure preview/download (a literal concept requirement).
- **`410 Gone` instead of `404` for expired/revoked (but known) links** - unlike an entirely unknown token, there is no information-leak risk here: the requesting person already legitimately possesses the token (it was given to them), so distinguishing "expired" from "revoked" in the error message reveals nothing they don't already know.
- **The public `/share` page in `user-ui` is client-side rendered, not SSR/SSG**, and still satisfies concept 8's requirement for public exception pages ("no Python data access per request needed") - the dynamic fetch runs via `fetch()` in the browser against the public gateway route, there is no Python process reloading data per page view. The page is part of the same purely static Next.js export as every other `user-ui` page (`output: "export"`, served via nginx, no Node runtime server in production), just deliberately not wrapped in `<RequireAuth>`.

## Consequences

- **A share-link token is a bearer secret like a password**: whoever knows it (e.g. through accidental forwarding, server logs, browser history on a shared machine) has full read access until expiry or revocation - the same inherent property of every link-based sharing mechanism (e.g. cloud-storage "anyone with the link" shares), not specific to this project, but documented here.
- **No rate limiting or brute-force protection specifically for share-link tokens** beyond the gateway-wide generic rate limiting (IP-based fallback for routes without an identity header, already existing). With 32 random bytes (`secrets.token_urlsafe(32)`, ~256 bits of entropy), guessing is practically infeasible, so no additional mechanism was built for a reference implementation.
- **`max_validity_days` applies only to NEWLY created links** - a subsequent reduction of the installation-wide upper bound does not retroactively shorten the validity of already-issued links (unlike full disablement, which locks all links immediately). A deliberate, documented difference between the two configuration fields.
- **The downgrade check `document.folder_id or "root"` treats rootless documents like root-folder documents** - consistent with the pattern already established in `search-service` (the `_grant_root_read` test convention), no new special case introduced.
