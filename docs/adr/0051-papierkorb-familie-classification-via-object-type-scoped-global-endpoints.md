# 0051 — Papierkorb-Familie: Verschlusssachen-Kennzeichnung über den Objekttyp, opt-in installationsweite Endpunkte statt Retrofit

**Status:** akzeptiert
**Kontext:** P15-S1 (Papierkorb-Familie, Konzept §2.5/4.6)

## Entscheidung

Vier zusammenhängende Entscheidungen für die Papierkorb-Familie (regulärer Papierkorb, persönlicher Papierkorb, strukturell getrennter Verschlusssachen-Papierkorb):

1. **Verschlusssachen-Kennzeichnung als neues, schema-gebundenes `ObjectType.is_classified: bool`** (nur `applies_to="document"`) statt einer attribut-wert-basierten Konvention (z. B. `attributes["Verschlusssache"] == "true"`). `document-service` fragt bei Bedarf `object-type-service`s bereits bestehenden `GET /object-types`-Endpunkt (neu um `is_classified`-Filter erweitert) ab, um die Menge klassifizierter Objekttyp-IDs zu erhalten - keine Änderung an `document-service`s eigenem Datenmodell nötig, `Document.object_type_id` existierte bereits.
2. **Zwei neue, unabhängig konfigurierbare Admin-Rollen-Settings pro Service** (`trash_hard_delete_admin_role`/`classified_trash_hard_delete_admin_role` in `document-service`, nur `trash_hard_delete_admin_role` in `folder-service` - Ordner kennen keine Verschlusssachen-Klassifizierung) - exakt dasselbe Setting-Muster wie `kennzeichen_admin_role`/`share_link_revoke_admin_role`/`delegation_revoke_admin_role`, beide mit Default `"dms-admin"`.
3. **Neuer manueller Purge-Endpunkt (`POST /documents/{id}/purge`, `POST /folders/{id}/purge`) baut auf der bereits bestehenden `retention_actions.purge_expired_trash_entry()`-Funktion auf** (bislang nur vom automatischen `_retention_poll_loop` nach Ablauf der Wiederherstellungsfrist aufgerufen) - um einen optionalen `trigger`/`triggered_by`-Parameter erweitert (`"manual_purge"` statt `"trash_expiry"`), keine zweite Lösch-Implementierung.
4. **`GET /documents/deleted`/`GET /folders/deleted` bekommen einen neuen, rein additiven `scope`-Query-Parameter** (`personal`/`admin`/`admin_classified` bei Dokumenten, `personal`/`admin` bei Ordnern) - ohne `scope` bleibt das bisherige Verhalten (kein Auth-Check, ordnerbezogene Auflistung) exakt unverändert. Erst mit explizit gesetztem `scope` gelten die neuen Sichtbarkeitsregeln (eigene Löschmarkierungen bzw. rollengeschützter voller/Verschlusssachen-Papierkorb).

Frontend: ein komplett neuer, installationsweiter **`TrashPane`**-Sonderbereich in der `IconRail` (🗑️) - bewusst getrennt vom bereits bestehenden ordnerbezogenen Papierkorb-Umschalter in `ExplorerPane.tsx`, der unverändert bleibt.

## Begründung

- **Schema-gebundene Klassifizierung statt Attribut-Konvention**: Konzept §2.5 sagt wörtlich "Kennzeichnung über einen Objekttyp/ein Attribut" - beide Varianten sind textlich vorgesehen, aber eine Objekttyp-Eigenschaft ist robuster (kein Tippfehler-/Leerstring-Risiko wie bei einem Attributwert, keine Notwendigkeit für ein zusätzliches, magisches Attribut-Namensschema wie beim Kennzeichengenerator) und lässt sich in EINEM Aufruf für die gesamte Objekttyp-Menge auflösen (`GET /object-types?applies_to=document&is_classified=true`) statt pro Dokument einzeln nachzuschlagen.
- **Wiederverwendung von `purge_expired_trash_entry()` statt einer zweiten Lösch-Implementierung**: diese Funktion enthält bereits die korrekte Logik (Storage-Bereinigung ohne Governance-Bypass bei Dokumenten, Legal-Hold-Historie-Bereinigung bei Ordnern, Löschregister-Eintrag, physische Entfernung) - ein neuer `trigger`-Wert (`"manual_purge"`) mit echtem `triggered_by` reicht, um den Auslöser im Löschregister (5.2a) korrekt zu dokumentieren, ohne Code zu duplizieren.
- **Additiver `scope`-Parameter statt Retrofit der bestehenden Endpunkte**: `GET /documents/deleted`/`GET /folders/deleted` werden aktuell von zahlreichen Tests und (potenziell) externen Aufrufern ohne jeden Auth-Header aufgerufen (bestätigter, bereits vorbestehender Zustand - `document-service`/`folder-service`-Tests setzen standardmäßig keine `X-DMS-*`-Header). Ein hartes Erzwingen von Rollen-/Prinzipal-Prüfungen auf dem bestehenden, ordnerbezogenen Pfad hätte dutzende bestehende Aufrufer kaskadenartig brechen können, ohne dass das der eigentliche Auftrag dieser Session war. Der neue `scope`-Parameter ist stattdessen rein additiv: ohne ihn bleibt der Endpunkt exakt wie zuvor, die neuen, tatsächlich durchgesetzten Sichtbarkeitsregeln (persönlicher Papierkorb/Löschadministration) gelten ausschließlich für Aufrufer, die den neuen Parameter explizit setzen - genau die neue `TrashPane`-UI dieser Session.
- **Neuer `TrashPane`-Sonderbereich statt Erweiterung des bestehenden `ExplorerPane`-Papierkorb-Umschalters**: der bestehende Umschalter zeigt bewusst nur, was IM GERADE GEÖFFNETEN Ordner gelöscht ist (folder-scoped, Teil der normalen Explorer-Navigation) - das entspricht nicht dem Konzept-Verständnis eines eigenen, installationsweiten Sonderbereichs (2.5, "vergleichbar den Sonderordnern eines E-Mail-Programms"). Ein neuer Icon-Rail-Eintrag ist konsistent mit der bereits etablierten Behandlung anderer Sonderbereiche in dieser Codebasis (Favoriten, Team-Arbeitsbereiche, Stellvertretung, Genehmigungen - alle eigene Panes, keine Erweiterungen von `ExplorerPane`).
- **Kein "Öffnen"-Button im `TrashPane`**: `folder_service.repository.get_folder()` behandelt einen bereits im Papierkorb liegenden Ordner bewusst wie nicht existent (verhindert u. a. neue Kinder unter einem gelöschten Ordner) - eine In-Place-Vorschau eines gelöschten Objekts hätte eine neue, ungegatete Zugriffsart auf sonst verstecktes `get_folder`-Verhalten erfordert. Name/Attribute in der Papierkorb-Liste selbst erfüllen bereits Konzept §2.5's "durchsuch-/einsehbar"-Anforderung.
- **Echter, bei der Implementierung gefundener Bug**: `deleted_by` wurde an mehreren Stellen entgegengenommen (`document_service.repository.delete_document`/`cascade_trash_by_folder_ids`, `folder_service.repository.soft_delete_folder`), aber NIE tatsächlich auf die jeweilige Zeile geschrieben - eine Voraussetzung, die der persönliche Papierkorb erst überhaupt sichtbar machte. Behoben durch eine neue `deleted_by`-Spalte auf `Document`/`Folder` (Expand-Contract-Migrationsmuster) plus die entsprechenden Zuweisungen in allen betroffenen Funktionen, inkl. Zurücksetzen bei Wiederherstellung.

## Live-Verifikationsfund: `object_type_id`-Schema-Drift

Die Live-Verifikation dieser Session gegen den langlebigen, über sehr viele Sessions gewachsenen Dev-Compose-Stack deckte einen echten, vorbestehenden Schema-Drift auf: `document.document.object_type_id` trug in dieser Installation noch `VARCHAR(128)`, obwohl `Document.object_type_id` im Model schon lange `Integer` deklariert — `Base.metadata.create_all` ändert nie den Typ einer bereits bestehenden Spalte, nur `ADD COLUMN IF NOT EXISTS` für neue. Einfache Gleichheitsvergleiche (`object_type_id = $1`) blieben davon unauffällig (asyncpg castet implizit über den Parameter), aber der neue `object_type_id NOT IN (...)`-Filter für den Verschlusssachen-Papierkorb schlug mit `operator does not exist: character varying <> integer` fehl (reproduziert sowohl über die API als auch direkt per `psql`). `folder.folder.object_type_id` war davon nicht betroffen (bereits korrekt `integer`) — der Drift betraf ausschließlich `document.document`, vermutlich ein Überbleibsel einer sehr frühen Projektphase. Behoben durch eine neue, geschützte Migrationsprüfung in `document-service`s Lifespan (`information_schema.columns`-Check vor `ALTER COLUMN ... TYPE INTEGER`, kein Lock/Rewrite auf bereits korrigierten Installationen) statt eines reinen manuellen Einmal-Fixes — jede andere langlebige Installation mit demselben historischen Drift wird beim nächsten Neustart automatisch korrigiert.

## Konsequenzen

- **Der bestehende, ordnerbezogene Papierkorb-Umschalter in `ExplorerPane.tsx` bleibt weiterhin ohne jede Sichtbarkeits-/Rollenprüfung** (unverändertes, bereits vorbestehendes Verhalten) - nur der NEUE, installationsweite `TrashPane`-Weg setzt die Konzept-4.6-Anforderungen tatsächlich durch. Wer die alte, ordnerbezogene Route direkt aufruft, sieht weiterhin alle gelöschten Elemente eines Ordners unabhängig von Rolle/Urheberschaft - dokumentierte, bewusste Grenze dieser Session, kein Rückschritt gegenüber dem vorherigen Zustand.
- **Eine Installation, die `trash_hard_delete_admin_role`/`classified_trash_hard_delete_admin_role` abweichend von `"dms-admin"` konfiguriert, muss die entsprechenden Frontend-Konstanten in `TrashPane.tsx` manuell anpassen** - gleiche, bereits mehrfach akzeptierte Einschränkung wie bei `MetadataPanel.tsx`s Kennzeichen-Admin-Prüfung (das Frontend kann den konfigurierten Rollennamen nicht dynamisch vom Backend erfragen).
- **Manuelles Purgen eines Ordners scheitert mit `409`, solange auch nur eine Unterordner-Zeile existiert** (selbst wenn diese selbst bereits im Papierkorb liegt) - identische, bewusst konservative Sicherheitsprüfung wie die automatische Zwangslöschung (`has_any_child_folder_row`, verhindert eine FK-Constraint-Verletzung). Ein verschachtelter Baum muss deshalb von den Blättern nach oben einzeln geleert werden - kein rekursives Bulk-Purge in dieser Session.
