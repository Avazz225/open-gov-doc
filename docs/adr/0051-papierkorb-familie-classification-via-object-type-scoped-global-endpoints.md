# 0051 — Trash family: classified-documents flagging via the object type, opt-in installation-wide endpoints instead of a retrofit

**Status:** accepted
**Context:** P15-S1 (trash family, concept §2.5/4.6)

## Decision

Four related decisions for the trash family (regular trash, personal trash, structurally separate classified-documents trash):

1. **Classified-documents flagging as a new, schema-bound `ObjectType.is_classified: bool`** (only `applies_to="document"`) instead of an attribute-value-based convention (e.g. `attributes["Verschlusssache"] == "true"`). `document-service` queries `object-type-service`'s already-existing `GET /object-types` endpoint when needed (newly extended with an `is_classified` filter) to obtain the set of classified object type IDs — no change to `document-service`'s own data model needed, `Document.object_type_id` already existed.
2. **Two new, independently configurable admin-role settings per service** (`trash_hard_delete_admin_role`/`classified_trash_hard_delete_admin_role` in `document-service`, only `trash_hard_delete_admin_role` in `folder-service` — folders have no classified-documents flagging) — exactly the same settings pattern as `kennzeichen_admin_role`/`share_link_revoke_admin_role`/`delegation_revoke_admin_role`, both defaulting to `"dms-admin"`.
3. **New manual purge endpoint (`POST /documents/{id}/purge`, `POST /folders/{id}/purge`) builds on the already-existing `retention_actions.purge_expired_trash_entry()` function** (previously only called by the automatic `_retention_poll_loop` after the restore period expires) — extended with an optional `trigger`/`triggered_by` parameter (`"manual_purge"` instead of `"trash_expiry"`), no second deletion implementation.
4. **`GET /documents/deleted`/`GET /folders/deleted` get a new, purely additive `scope` query parameter** (`personal`/`admin`/`admin_classified` for documents, `personal`/`admin` for folders) — without `scope`, existing behavior (no auth check, folder-scoped listing) remains exactly unchanged. Only when `scope` is explicitly set do the new visibility rules apply (own deletion markers, or role-protected full/classified trash).

Frontend: a brand-new, installation-wide **`TrashPane`** special area in the `IconRail` (🗑️) — deliberately separate from the already-existing folder-scoped trash toggle in `ExplorerPane.tsx`, which remains unchanged.

## Rationale

- **Schema-bound flagging instead of an attribute convention**: concept §2.5 literally says "flagging via an object type/an attribute" — both variants are textually foreseen, but an object type property is more robust (no risk of typos/empty strings as with an attribute value, no need for an additional, magic attribute-naming scheme like the reference number generator) and can be resolved in ONE call for the entire object type set (`GET /object-types?applies_to=document&is_classified=true`) instead of looking it up per document.
- **Reuse of `purge_expired_trash_entry()` instead of a second deletion implementation**: this function already contains the correct logic (storage cleanup without governance bypass for documents, legal-hold history cleanup for folders, deletion register entry, physical removal) — a new `trigger` value (`"manual_purge"`) with a real `triggered_by` is enough to correctly document the trigger in the deletion register (5.2a), without duplicating code.
- **Additive `scope` parameter instead of retrofitting the existing endpoints**: `GET /documents/deleted`/`GET /folders/deleted` are currently called by numerous tests and (potentially) external callers with no auth header at all (confirmed, already pre-existing state — `document-service`/`folder-service` tests do not set `X-DMS-*` headers by default). Hard-enforcing role/principal checks on the existing, folder-scoped path could have broken dozens of existing callers in cascading fashion, which was not the actual mandate of this session. The new `scope` parameter is instead purely additive: without it, the endpoint stays exactly as before; the new, actually enforced visibility rules (personal trash/deletion administration) apply only to callers that explicitly set the new parameter — exactly the new `TrashPane` UI from this session.
- **New `TrashPane` special area instead of extending the existing `ExplorerPane` trash toggle**: the existing toggle deliberately shows only what is deleted WITHIN THE CURRENTLY OPEN folder (folder-scoped, part of normal Explorer navigation) — this does not match the concept's understanding of a dedicated, installation-wide special area (2.5, "comparable to the special folders of an email client"). A new icon-rail entry is consistent with the already-established treatment of other special areas in this codebase (favorites, team workspaces, delegation, approvals — all their own panes, no extensions of `ExplorerPane`).
- **No "open" button in `TrashPane`**: `folder_service.repository.get_folder()` deliberately treats a folder already in the trash as non-existent (among other things, preventing new children under a deleted folder) — an in-place preview of a deleted object would have required a new, ungated access path into otherwise hidden `get_folder` behavior. Name/attributes in the trash list itself already satisfy concept §2.5's "browsable/viewable" requirement.
- **Real bug found during implementation**: `deleted_by` was accepted in several places (`document_service.repository.delete_document`/`cascade_trash_by_folder_ids`, `folder_service.repository.soft_delete_folder`), but NEVER actually written to the row — a prerequisite that personal trash first made visible at all. Fixed with a new `deleted_by` column on `Document`/`Folder` (expand-contract migration pattern) plus the corresponding assignments in all affected functions, including resetting on restore.

## Live-verification finding: `object_type_id` schema drift

Live verification of this session against the long-lived dev compose stack, grown over very many sessions, uncovered a real, pre-existing schema drift: `document.document.object_type_id` still carried `VARCHAR(128)` in this installation, even though `Document.object_type_id` has long been declared `Integer` in the model — `Base.metadata.create_all` never changes the type of an already-existing column, only `ADD COLUMN IF NOT EXISTS` for new ones. Simple equality comparisons (`object_type_id = $1`) went unnoticed (asyncpg implicitly casts via the parameter), but the new `object_type_id NOT IN (...)` filter for the classified-documents trash failed with `operator does not exist: character varying <> integer` (reproduced both via the API and directly via `psql`). `folder.folder.object_type_id` was not affected (already correctly `integer`) — the drift affected only `document.document`, presumably a leftover from a very early project phase. Fixed via a new, guarded migration check in `document-service`'s lifespan (`information_schema.columns` check before `ALTER COLUMN ... TYPE INTEGER`, no lock/rewrite on already-fixed installations) instead of a purely manual one-time fix — any other long-lived installation with the same historical drift gets automatically corrected on its next restart.

## Consequences

- **The existing, folder-scoped trash toggle in `ExplorerPane.tsx` remains without any visibility/role check** (unchanged, already pre-existing behavior) — only the NEW, installation-wide `TrashPane` path actually enforces the concept-4.6 requirements. Anyone calling the old, folder-scoped route directly still sees all deleted items of a folder regardless of role/ownership — documented, deliberate boundary of this session, not a regression relative to the previous state.
- **An installation that configures `trash_hard_delete_admin_role`/`classified_trash_hard_delete_admin_role` differently from `"dms-admin"` must manually adjust the corresponding frontend constants in `TrashPane.tsx`** — the same, already repeatedly accepted limitation as with `MetadataPanel.tsx`'s reference number admin check (the frontend cannot dynamically query the configured role name from the backend).
- **Manually purging a folder fails with `409` as long as even a single subfolder row exists** (even if it itself is already in the trash) — an identical, deliberately conservative safety check as the automatic forced deletion (`has_any_child_folder_row`, prevents an FK constraint violation). A nested tree must therefore be emptied leaf-first, one level at a time — no recursive bulk purge in this session.
