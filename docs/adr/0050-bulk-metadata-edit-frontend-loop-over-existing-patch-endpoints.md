# 0050 — Sammelbearbeitung von Metadaten: frontend-seitige Schleife über bestehende Einzel-PATCH-Endpunkte, kein neuer Bulk-Endpunkt

**Status:** akzeptiert
**Kontext:** P14-S12 (Sammelbearbeitung von Metadaten, Konzept §8), letzte Session der Phase 14

## Entscheidung

Die Sammelbearbeitung mehrerer ausgewählter Dokumente/Ordner bekommt **keinen neuen Backend-Endpunkt**. `user-ui`s neues `BulkEditModal.tsx` ruft für jedes ausgewählte Objekt einzeln, nacheinander, den bereits bestehenden Einzel-PATCH-Endpunkt auf (`PATCH /documents/{id}` bzw. `PATCH /folders/{id}`) - dieselben Endpunkte, die auch eine einzelne Metadatenänderung über `MetadataPanel.tsx` verwenden. Das Ergebnis ist bewusst **nicht atomar**: jeder PATCH-Aufruf gelingt oder scheitert unabhängig von den übrigen, das Ergebnis wird nach Abschluss je Objekt als Erfolg/Fehlschlag zusammengefasst angezeigt. Ein leer gelassenes Formularfeld bedeutet "für dieses Objekt unverändert lassen", nicht "leeren" - nur tatsächlich befüllte Felder werden pro Objekt in dessen eigene, bereits bestehende `attributes` gemergt, bevor der PATCH-Aufruf erfolgt. Die Auswahl muss homogen sein (ausschließlich Dokumente ODER ausschließlich Ordner, alle mit demselben, gesetzten Objekttyp) - andernfalls zeigt das Modal einen blockierenden Hinweis statt eines Formulars. Als Nebenfund wurde `folder-service`s `PATCH /folders/{id}` so korrigiert, dass es (wie `document-service`s Pendant) die Objekttyp-Constraint-Prüfung (4.5) bei **jeder** Attributänderung ausführt, nicht nur bei einer Verschiebung.

## Begründung

- **Wörtliche Erfüllung von "läuft über dieselbe Regel-Engine/Constraint-Prüfung wie eine Einzeländerung"**: Konzept §8 verlangt ausdrücklich denselben Prüfpfad wie bei einer Einzeländerung. Eine Schleife über den bereits bestehenden, bereits vollständig getesteten Einzel-PATCH-Endpunkt erfüllt das buchstäblich (identischer Code-Pfad), statt die Constraint-Validierung ein zweites Mal in einem neuen Bulk-Endpunkt zu reimplementieren - letzteres wäre eine unnötige Duplizierung mit dem Risiko, künftig auseinanderzudriften.
- **Nicht-atomares Ergebnis ergibt sich von selbst**: Konzept §8 verlangt ausdrücklich, dass die Auswahl "gezielt für einzelne, nicht passende Objekte fehlschlägt" statt die gesamte Auswahl stillschweigend inkonsistent zu machen, und dass das Ergebnis je Objekt klar zusammengefasst wird. Eine Schleife aus unabhängigen Einzel-PATCH-Aufrufen liefert dieses Verhalten ohne zusätzlichen Code - eine echte Backend-Transaktion über mehrere, potenziell verschiedene Services (Dokumente und Ordner leben in unterschiedlichen Services) wäre ohnehin nicht sinnvoll atomar umsetzbar gewesen.
- **Homogene Auswahl als bewusste Grenze**: Attributschemata sind objekttyp-gebunden (`ObjectType.attributes`/Layout) - ein einzelnes Formular kann sinnvoll nur ein Schema rendern. Eine gemischte Auswahl (verschiedene Objekttypen, oder Dokumente gemischt mit Ordnern) hätte entweder mehrere Formulare gleichzeitig oder eine Schnittmengen-Logik über mehrere Schemata erfordert - beides eine im Konzepttext nicht geforderte Komplexitätssteigerung für diese Referenzimplementierung. Eine homogene Auswahl mit klarer Fehlermeldung ist die einfachere, ehrlichere Grenze.
- **Leeres Feld = unverändert, nicht = leeren**: Der Server ersetzt `attributes` vollständig (kein serverseitiges Merge, bestehendes Verhalten seit `document-service`/`folder-service`s ursprünglicher PATCH-Implementierung). Ein naiver Bulk-Aufruf, der nur die im Formular ausgefüllten Felder sendet, hätte deshalb bei jedem Objekt sämtliche anderen, nicht im Bulk-Formular vorkommenden Attribute stillschweigend gelöscht - eine dedizierte Recherche vor der Implementierung identifizierte dieses Risiko. Das Modal mergt deshalb die tatsächlich befüllten Felder client-seitig in eine Kopie der jeweils eigenen, bestehenden `attributes` jedes Objekts, exakt das bereits etablierte Muster aus `MetadataPanel.tsx`s Einzelbearbeitung.
- **`folder-service`-Fix ist eine notwendige Voraussetzung, keine unabhängige Zusatzarbeit**: eine dedizierte Recherche vor der Implementierung ergab, dass `folder-service`s `PATCH /folders/{id}` die Objekttyp-Constraint-Prüfung bislang nur bei einer tatsächlichen Verschiebung ausführte - eine reine Attributänderung ohne Verschiebung überging sie vollständig, anders als `document-service`s symmetrisches Pendant. Ohne diesen Fix hätte die Sammelbearbeitung von Ordnern die vom Konzept geforderte Constraint-Prüfung für Ordner faktisch nicht erfüllt (obwohl der Code-Pfad formal derselbe gewesen wäre) - der Fix war deshalb erforderlich, um die Kernaussage dieser Session ("dieselbe Constraint-Prüfung wie eine Einzeländerung") für Ordner überhaupt wahr zu machen, nicht nur für Dokumente.
- **Mehrfachauswahl nur in der Listenansicht, nicht in der Baumansicht**: Checkboxen wurden ausschließlich in `ExplorerPane.tsx`s Listenansicht ergänzt - eine Mehrfachauswahl über mehrere Ebenen der Baumansicht hinweg wäre eine eigenständige UX-Frage (z. B. rekursive Auswahl von Unterordnern) und explizit außerhalb des Umfangs dieser Session.
- **Titel bewusst nicht Teil der Sammelbearbeitung**: ein Bulk-Formular mit einem Titelfeld würde bei gemeinsamer Übernahme allen ausgewählten Objekten denselben Namen zuweisen - offensichtlich nicht der Sinn einer Sammelbearbeitung von Metadaten, deshalb wurde `title`/`name` bewusst aus dem Formular ausgeschlossen (nur die objekttyp-spezifischen Attribute sind bearbeitbar).

## Konsequenzen

- **Bei einer großen Auswahl entstehen entsprechend viele sequenzielle HTTP-Aufrufe** vom Client aus - für eine Referenzimplementierung akzeptabel (kein Performance-Ziel im Konzepttext genannt), bei sehr großen Auswahlen (hunderte Objekte) spürbar langsamer als ein echter Batch-Endpunkt. Bewusste, dokumentierte Grenze.
- **Kein serverseitiger Bulk-Audit-Eintrag** - jede Änderung erscheint im Audit-Trail als eigenständiges, normales `document.metadata.updated`/`folder.metadata.updated`-Ereignis (bestehendes Ereignisschema, unverändert), es gibt keinen übergreifenden "Sammelbearbeitung X betraf Objekte A, B, C"-Datensatz. Wer diesen Zusammenhang braucht, muss die Ereignisse zeitlich clustern - keine neue Audit-Semantik für diese Session eingeführt.
- **Der `folder-service`-Fix ändert bestehendes Verhalten**: eine reine Attribut-PATCH auf einen Ordner mit gesetztem Objekttyp, die zuvor unvalidiert durchging, kann jetzt mit `400` abgelehnt werden, falls die neuen Attribute nicht mehr zum Objekttyp passen - eine Korrektur einer vorbestehenden, undokumentierten Lücke, kein neues Feature, aber ein sichtbares Verhaltensänderung für bestehende Aufrufer.
