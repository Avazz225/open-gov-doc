# 0050 — Bulk metadata editing: frontend loop over existing single-object PATCH endpoints, no new bulk endpoint

**Status:** accepted
**Context:** P14-S12 (bulk metadata editing, concept §8), last session of Phase 14

## Decision

Bulk editing of several selected documents/folders gets **no new backend endpoint**. `user-ui`'s new `BulkEditModal.tsx` calls the already-existing single-object PATCH endpoint (`PATCH /documents/{id}` or `PATCH /folders/{id}`) individually and sequentially for each selected object — the same endpoints already used for a single metadata change via `MetadataPanel.tsx`. The result is deliberately **not atomic**: each PATCH call succeeds or fails independently of the others, and the result is shown as a per-object success/failure summary once complete. Leaving a form field blank means "leave unchanged for this object", not "clear it" — only fields that are actually filled in are merged, per object, into that object's own already-existing `attributes` before the PATCH call is made. The selection must be homogeneous (only documents OR only folders, all with the same, set object type) — otherwise the modal shows a blocking notice instead of a form. As a side finding, `folder-service`'s `PATCH /folders/{id}` was fixed so that (like `document-service`'s counterpart) it runs the object type constraint check (4.5) on **every** attribute change, not just on a move.

## Rationale

- **Literal fulfillment of "runs through the same rule engine/constraint check as a single change"**: concept §8 explicitly requires the same validation path as a single change. A loop over the already-existing, already fully tested single-object PATCH endpoint fulfills this literally (identical code path), instead of reimplementing constraint validation a second time in a new bulk endpoint — the latter would be unnecessary duplication with the risk of future drift.
- **Non-atomic result falls out naturally**: concept §8 explicitly requires that the selection "fails specifically for individual, non-matching objects" instead of silently making the entire selection inconsistent, and that the result is clearly summarized per object. A loop of independent single PATCH calls delivers this behavior with no extra code — a real backend transaction across multiple, potentially different services (documents and folders live in different services) would not have been meaningfully atomic to implement anyway.
- **Homogeneous selection as a deliberate boundary**: attribute schemas are object-type-bound (`ObjectType.attributes`/layout) — a single form can meaningfully render only one schema. A mixed selection (different object types, or documents mixed with folders) would have required either multiple simultaneous forms or intersection logic across multiple schemas — both a complexity increase not required by the concept text for this reference implementation. A homogeneous selection with a clear error message is the simpler, more honest boundary.
- **Blank field = unchanged, not = clear**: the server replaces `attributes` entirely (no server-side merge, existing behavior since `document-service`'s/`folder-service`'s original PATCH implementation). A naive bulk call that sends only the fields filled in the form would therefore have silently deleted, for every object, all other attributes not present in the bulk form — dedicated research before implementation identified this risk. The modal therefore merges the actually filled-in fields client-side into a copy of each object's own existing `attributes`, exactly the already-established pattern from `MetadataPanel.tsx`'s single-object editing.
- **`folder-service` fix is a necessary prerequisite, not independent extra work**: dedicated research before implementation found that `folder-service`'s `PATCH /folders/{id}` previously ran the object type constraint check only on an actual move — a pure attribute change without a move bypassed it entirely, unlike `document-service`'s symmetric counterpart. Without this fix, bulk editing of folders would not actually have fulfilled the concept-required constraint check for folders (even though the code path would formally have been the same) — the fix was therefore required to make the core claim of this session ("same constraint check as a single change") true for folders as well, not only for documents.
- **Multi-selection only in the list view, not in the tree view**: checkboxes were added exclusively in `ExplorerPane.tsx`'s list view — a multi-selection spanning multiple levels of the tree view would be its own UX question (e.g. recursive selection of subfolders) and explicitly out of scope for this session.
- **Title deliberately not part of bulk editing**: a bulk form with a title field would assign the same name to all selected objects if applied jointly — clearly not the point of bulk metadata editing, so `title`/`name` was deliberately excluded from the form (only object-type-specific attributes are editable).

## Consequences

- **A large selection produces a correspondingly large number of sequential HTTP calls** from the client — acceptable for a reference implementation (no performance goal named in the concept text), noticeably slower than a real batch endpoint for very large selections (hundreds of objects). Deliberate, documented boundary.
- **No server-side bulk audit entry** — each change appears in the audit trail as an independent, normal `document.metadata.updated`/`folder.metadata.updated` event (existing event schema, unchanged), there is no cross-cutting "bulk edit X affected objects A, B, C" record. Anyone needing that correlation must cluster the events by time — no new audit semantics introduced for this session.
- **The `folder-service` fix changes existing behavior**: a pure attribute PATCH on a folder with a set object type that previously went through unvalidated can now be rejected with `400` if the new attributes no longer match the object type — a correction of a pre-existing, undocumented gap, not a new feature, but a visible behavior change for existing callers.
