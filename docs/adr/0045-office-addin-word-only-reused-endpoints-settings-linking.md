# 0045 — Office-Add-in: nur Word, vollständige Wiederverwendung bestehender Endpunkte, Dokument-Verknüpfung über `document.settings`

**Status:** akzeptiert
**Kontext:** Konzept 3.3a, Session P14-S8 (Microsoft-Office-Add-in-Teil; P14-S9 folgt für LibreOffice/OpenOffice)

## Entscheidung

Ein neues, eigenständiges Frontend `apps/office-addin` implementiert ein Office-Add-in (Office.js, `TaskPaneApp`) für **ausschließlich Word** (Host `Document`). Es spricht **keinen neuen Backend-Endpunkt** an — jede Aktion (Öffnen/Speichern, Metadaten, Workflow, Vorlagen) läuft über bereits bestehende `document-service`/`workflow-service`/`object-type-service`/`folder-service`/`search-service`/`auth-service`-Endpunkte durch dasselbe Gateway wie jedes andere Frontend (3.3a wörtlich: "denselben bereits bestehenden ... API-Weg ... statt eigener, paralleler Dokumentenlogik"). Welches DMS-Dokument zu einer geöffneten Word-Datei gehört, wird über `Office.context.document.settings` (add-in-eigener, in der Datei selbst gespeicherter Zustand) verfolgt, nicht über einen neuen Server-Zustand.

## Begründung

- **Nur Word, nicht Excel/PowerPoint**: Der zentrale Mechanismus zum "Öffnen" eines DMS-Dokuments in das gerade aktive, leere Office-Dokument ist `Word.run(context => context.document.body.insertFileFromBase64(base64, Word.InsertLocation.replace))` - eine reine **Word**-JS-API (WordApi 1.5). Weder Excel (`Workbook.insertWorksheetsFromBase64` fügt nur Arbeitsblätter ein, keine vollständige Arbeitsmappe) noch PowerPoint bieten eine vergleichbare "gesamtes Dokument ersetzen"-Fähigkeit über die stabile JS-API. Anstatt eine schwächere, inkonsistente Notlösung für Excel/PowerPoint zu bauen, bleibt diese Session bewusst auf Word beschränkt - konsistent mit P14-S8/P14-S9s eigener Aufteilung (zwei separate Erweiterungen für zwei separate Office-Suiten), hier zusätzlich verschärft auf eine einzelne App innerhalb von Microsoft Office.
- **Kein neuer Backend-Endpunkt**: Jede der vier verlangten Fähigkeiten (Öffnen/Speichern, inline Metadaten, Workflow-Start/-Fortsetzung, Vorlagenbibliothek) lässt sich vollständig über bereits vorhandene Endpunkte abbilden:
  - Öffnen/Speichern: `GET /documents/{id}/content` (document-service, bereits vorhanden), `POST /documents/{id}/versions` (Check-in, bereits vorhanden - `expected_base_version_number` liefert dieselbe optimistische Konflikterkennung wie jeder andere Check-in-Client).
  - Inline-Metadaten: `PATCH /documents/{id}` + `GET /object-types/{id}` (beide bereits vorhanden, dieselben Endpunkte wie `user-ui`s Metadaten-Panel).
  - Workflow: `GET /instances?business_key=`, `GET /instances/{id}/tasks`, `POST /instances/{id}/tasks/{id}/complete`, `POST /process-definitions/{id}/instances` (alle bereits vorhanden) - Korrelation über `business_key = document_id`, derselbe Mechanismus, mit dem im gesamten System bereits jeder Prozess an ein fachliches Objekt gebunden wird.
  - Vorlagenbibliothek: siehe eigener Punkt unten.
  Damit ist 3.3a wörtlich erfüllt ("denselben ... API-Weg ... statt eigener, paralleler Dokumentenlogik") - nicht nur im übertragenen, sondern im buchstäblichen Sinn: kein einziger neuer Endpunkt in irgendeinem bestehenden Service.
- **Vorlagenbibliothek als Namenskonvention statt neuem Speicher-/Berechtigungsmechanismus**: eine Vorlage ist ein gewöhnliches Dokument im Wurzelordner "Vorlagen" (Name konfigurierbar, `NEXT_PUBLIC_TEMPLATE_LIBRARY_FOLDER_NAME`) - "rollenbasiert" (3.3a-Wortlaut) ist damit automatisch die bereits bestehende Ordner-Leserechtsprüfung (`permission-service`), keine neue Berechtigungslogik. Bewusst **nicht** dasselbe Konzept wie die künftige, strukturelle "Vorlagen" aus 2.5/P15-S6 (Aktenplan-Rohbau-Vorlagen über den JSON-Struktur-Export, 7.3) - dieselbe deutsche Bezeichnung, aber zwei unterschiedliche Konzepte (Konzept-Tabelle 2.5 vs. 3.3a-Fließtext), die absichtlich getrennt bleiben: 3.3a verlangt eine Bibliothek einzelner **Dokumentvorlagen** (z. B. eine Word-Vorlage für Standardverträge), nicht Ordnerstrukturen.
- **`derived_from_document_id`/`derived_from_version_number` (document-service) wird zum ersten Mal tatsächlich gesetzt**: beide Felder existierten bereits im Schema (Herkunfts-Nachverfolgung), aber kein bisheriger Client hat sie je befüllt - das "Neu aus Vorlage"-Anlegen ist der erste echte Anwendungsfall.
- **Dokument-Verknüpfung über `Office.context.document.settings` statt eines eigenen Server-Zustands**: `settings` ist add-in-spezifischer Schlüssel/Wert-Zustand, der in der Word-Datei selbst (eigene XML-Custom-Part) gespeichert wird - genau für "welches externe Objekt gehört zu dieser Datei" vorgesehen. Nach Schließen/erneutem Öffnen derselben Datei (mit aktiviertem Add-in) ist die Verknüpfung automatisch wieder da, ohne dass irgendein Backend eine Datei-zu-Dokument-Zuordnungstabelle pflegen müsste.
- **Bestehende, bislang ungenutzte Sperre (`POST/DELETE /documents/{id}/lock`) statt rein optimistischer Konfliktprüfung**: `user-ui` nutzt bewusst nur optimistische Versionsprüfung beim Check-in (ADR 0002, kurze Bearbeitungsvorgänge). Eine Word-Bearbeitungssitzung kann dagegen lange dauern - "wird gerade von jemand anderem bearbeitet" ist hier ein echter, sinnvoller Hinweis VOR dem Verlust von Bearbeitungszeit, nicht nur ein Konflikt beim Speichern. Der Add-in ist der erste Client, der diese bereits vorhandene, bislang von keinem Frontend genutzte Sperre tatsächlich verwendet. Ein Sperrkonflikt (`409`) blockiert das Öffnen NICHT (das Dokument wird trotzdem schreibgeschützt geladen), deaktiviert aber den Speichern-Button - `checkin_version` würde den Schreibversuch ohnehin serverseitig mit `409` ablehnen (siehe `repository.checkin_version`, `lock.locked_by != created_by`).
- **Eigenständige, schlanke UI statt Wiederverwendung von `user-ui`-Komponenten**: der Taskpane ist strukturell ein winziges (~300-450px) Seitenpanel innerhalb von Word, keine volle Drei-Spalten-Arbeitsfläche - `user-ui`s `MetadataPanel`/`LayoutFormFields`-Maschinerie (2.2b, layoutgesteuerte Mehrspalten-Formulare) passt nicht in diesen Platz. `MetadataForm` ist deshalb bewusst ein einfaches Ein-Textfeld-je-Attribut-Formular ohne Typ-spezifische Widgets/Layout-Anordnung - eine dokumentierte, begründete Vereinfachung, kein Versehen.
- **Kein Theme-Umschalter/Wartungsbanner** (anders als jede andere App dieses Projekts): der Taskpane hat für zusätzliche Chrome keinen Platz: ein Add-in sollte sich idealerweise am Office-eigenen Theme orientieren (`Office.context.officeTheme`), nicht an einem eigenen Schalter - nicht Teil dieser Session, dokumentierter offener Punkt.

## Konsequenzen

- **Keine Verifikation gegen einen echten Office-Host möglich** in dieser Entwicklungsumgebung (kein Windows, kein installiertes Microsoft Office, kein gültiger Microsoft-365-Sideloading-Mandant) - es gibt keine headless/containerisierte Möglichkeit, Word tatsächlich auszuführen (anders als der ephemere-Playwright-Ansatz für Browser-UIs, P14-S2/P14-S4/P14-S6). Verifiziert wurde stattdessen: (a) `office-addin-manifest validate manifest.xml` (echtes, offizielles Microsoft-Tool, lief erfolgreich gegen das erzeugte Manifest), (b) Komponententests gegen einen handgeschriebenen `Office`/`Word`-Fake (`tests/office-mock.ts`, identisches Prinzip wie das Mocken von `fetch` in den übrigen Apps), (c) alle wiederverwendeten Backend-Endpunkte live gegen den laufenden Stack per `curl` bestätigt. Ein Mensch sollte das Add-in vor Produktivnutzung tatsächlich in Word sideloaden und durchklicken (siehe README.md "Lokales Sideload-Testen").
- **HTTPS-Pflicht für Office-Add-ins** (Office lädt Add-in-Webinhalte nur über HTTPS, außer wenigen dokumentierten Ausnahmen) trifft in diesem Stack erstmals auf eine App, die bislang durchgehend über HTTP betrieben wurde - `office-addin`s Produktivbetrieb bräuchte einen eigenen TLS-Terminierungspunkt, den keine andere App dieses Projekts benötigt. Nicht gelöst in dieser Session, dokumentierter Betriebsschritt vor echtem Sideload.
- **Excel/PowerPoint/Outlook bleiben vollständig unangetastet** - eine spätere Erweiterung bräuchte für Excel/PowerPoint einen strukturell anderen "Öffnen"-Mechanismus (keine 1:1-Portierung von `insertFileFromBase64`).
- **Nur Word 2016+/aktuelle Microsoft-365-Word-Versionen** unterstützen `insertFileFromBase64` zuverlässig (WordApi-Anforderungssatz 1.5) - ältere Word-Versionen (2013) könnten die Öffnen-Funktion nicht nutzen, obwohl der Manifest-Validator sie formal als unterstützte Plattform listet (reine Manifest-Struktur-Prüfung, keine Laufzeit-API-Verfügbarkeitsprüfung).
- **Vorlagenbibliothek erfordert manuelle Admin-Einrichtung** (Ordner "Vorlagen" anlegen, Leserechte vergeben) - kein automatisiertes Bootstrap, kein Admin-UI-Baustein dafür in dieser Session.
