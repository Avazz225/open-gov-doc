# 0045 — Office add-in: Word only, full reuse of existing endpoints, document linking via `document.settings`

**Status:** accepted
**Context:** Concept 3.3a, session P14-S8 (Microsoft Office add-in part; P14-S9 follows for LibreOffice/OpenOffice)

## Decision

A new, standalone frontend `apps/office-addin` implements an Office add-in (Office.js, `TaskPaneApp`) for **Word only** (host `Document`). It talks to **no new backend endpoint** — every action (open/save, metadata, workflow, templates) runs through already-existing `document-service`/`workflow-service`/`object-type-service`/`folder-service`/`search-service`/`auth-service` endpoints, through the same gateway as any other frontend (3.3a verbatim: "the same already-existing ... API path ... instead of separate, parallel document logic"). Which DMS document belongs to an open Word file is tracked via `Office.context.document.settings` (add-in-owned state stored in the file itself), not via any new server-side state.

## Rationale

- **Word only, not Excel/PowerPoint**: the central mechanism for "opening" a DMS document into the currently active, empty Office document is `Word.run(context => context.document.body.insertFileFromBase64(base64, Word.InsertLocation.replace))` - a pure **Word** JS API (WordApi 1.5). Neither Excel (`Workbook.insertWorksheetsFromBase64` inserts only worksheets, not a full workbook) nor PowerPoint offer a comparable "replace the entire document" capability via the stable JS API. Rather than building a weaker, inconsistent workaround for Excel/PowerPoint, this session deliberately stays limited to Word - consistent with P14-S8/P14-S9's own split (two separate extensions for two separate office suites), here additionally narrowed to a single app within Microsoft Office.
- **No new backend endpoint**: each of the four required capabilities (open/save, inline metadata, workflow start/continue, template library) can be fully mapped onto already-existing endpoints:
  - Open/save: `GET /documents/{id}/content` (document-service, already existing), `POST /documents/{id}/versions` (check-in, already existing - `expected_base_version_number` provides the same optimistic conflict detection as any other check-in client).
  - Inline metadata: `PATCH /documents/{id}` + `GET /object-types/{id}` (both already existing, the same endpoints as `user-ui`'s metadata panel).
  - Workflow: `GET /instances?business_key=`, `GET /instances/{id}/tasks`, `POST /instances/{id}/tasks/{id}/complete`, `POST /process-definitions/{id}/instances` (all already existing) - correlation via `business_key = document_id`, the same mechanism the whole system already uses to bind any process to a business object.
  - Template library: see its own point below.
  This fulfils 3.3a literally ("the same ... API path ... instead of separate, parallel document logic") - not just figuratively, but literally: not a single new endpoint in any existing service.
- **Template library as a naming convention instead of a new storage/permission mechanism**: a template is an ordinary document in the root folder "Vorlagen" (name configurable, `NEXT_PUBLIC_TEMPLATE_LIBRARY_FOLDER_NAME`) - "role-based" (3.3a wording) is thereby automatically the already-existing folder read-permission check (`permission-service`), no new permission logic. Deliberately **not** the same concept as the future, structural "templates" from 2.5/P15-S6 (file-plan scaffolding templates via the JSON structure export, 7.3) - the same German term, but two different concepts (concept table 2.5 vs. 3.3a prose), which deliberately remain separate: 3.3a requires a library of individual **document templates** (e.g. a Word template for standard contracts), not folder structures.
- **`derived_from_document_id`/`derived_from_version_number` (document-service) is actually populated for the first time**: both fields already existed in the schema (provenance tracking), but no prior client had ever filled them in - the "new from template" creation is the first genuine use case for them.
- **Document linking via `Office.context.document.settings` instead of new server-side state**: `settings` is add-in-specific key/value state stored inside the Word file itself (its own XML custom part) - designed exactly for "which external object belongs to this file". After closing and reopening the same file (with the add-in enabled), the link is automatically restored, with no backend needing to maintain a file-to-document mapping table.
- **The existing, previously unused lock (`POST/DELETE /documents/{id}/lock`) instead of purely optimistic conflict checking**: `user-ui` deliberately uses only optimistic version checking at check-in (ADR 0002, short editing sessions). A Word editing session, by contrast, can last a long time - "currently being edited by someone else" is a genuinely useful hint here BEFORE losing editing time, not just a conflict at save time. The add-in is the first client to actually use this already-existing, previously unused lock. A lock conflict (`409`) does NOT block opening (the document is still loaded read-only), but disables the save button - `checkin_version` would reject the write attempt server-side with `409` anyway (see `repository.checkin_version`, `lock.locked_by != created_by`).
- **A standalone, lean UI instead of reusing `user-ui` components**: the task pane is structurally a tiny (~300-450px) side panel inside Word, not a full three-column workspace - `user-ui`'s `MetadataPanel`/`LayoutFormFields` machinery (2.2b, layout-driven multi-column forms) does not fit this space. `MetadataForm` is therefore deliberately a simple one-text-field-per-attribute form with no type-specific widgets/layout arrangement - a documented, justified simplification, not an oversight.
- **No theme switcher/maintenance banner** (unlike every other app in this project): the task pane has no room for additional chrome: an add-in should ideally follow Office's own theme (`Office.context.officeTheme`) rather than its own switch - not part of this session, a documented open point.

## Consequences

- **No verification against a real Office host possible** in this development environment (no Windows, no installed Microsoft Office, no valid Microsoft 365 sideloading tenant) - there is no headless/containerized way to actually run Word (unlike the ephemeral-Playwright approach for browser UIs, P14-S2/P14-S4/P14-S6). Verified instead: (a) `office-addin-manifest validate manifest.xml` (a real, official Microsoft tool, ran successfully against the generated manifest), (b) component tests against a hand-written `Office`/`Word` fake (`tests/office-mock.ts`, the same principle as mocking `fetch` in the other apps), (c) all reused backend endpoints confirmed live against the running stack via `curl`. A human should actually sideload and click through the add-in in Word before production use (see README.md "Local sideload testing").
- **HTTPS is mandatory for Office add-ins** (Office only loads add-in web content over HTTPS, aside from a few documented exceptions), which for the first time confronts this stack, previously run entirely over HTTP, with such a requirement - `office-addin`'s production deployment would need its own TLS termination point, which no other app in this project needs. Not solved in this session, a documented operational step before real sideloading.
- **Excel/PowerPoint/Outlook remain entirely untouched** - a later extension would need a structurally different "open" mechanism for Excel/PowerPoint (no 1:1 port of `insertFileFromBase64`).
- **Only Word 2016+/current Microsoft 365 Word versions** reliably support `insertFileFromBase64` (WordApi requirement set 1.5) - older Word versions (2013) could not use the open function, even though the manifest validator formally lists them as a supported platform (pure manifest structure check, no runtime API availability check).
- **The template library requires manual admin setup** (create the "Vorlagen" folder, grant read permissions) - no automated bootstrap, no admin-UI building block for this in this session.
