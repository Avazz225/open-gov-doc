# Implementation Plan: DMS Concept → Runnable System (Multi-Session Roadmap)

## Context

`Business__DMS-Konzept.md` (in this folder) describes a very extensive, distributed DMS (microservices, Python/FastAPI-first, ~25 independent services spanning auth, storage, workflow, signature, federation, licensing, monitoring through to backup/restore). That is too large for a single session — this plan is designed so that **future Claude Code sessions can work through it step by step**, keeping the repo cleanly structured and documented throughout (not just tidied up at the end), and using `graphify` to navigate the concept and the growing codebase.

Clarified requirements:
- **Only `dms/` is relevant** — other folders in the parent working directory belong to independent projects and provide no reusable conventions for this stack.
- **Sequencing**: vertical MVP slice first (Phases 0–4 deliver a runnable core DMS), then incremental breadth.
- **Scope**: full coverage of all ~25 services planned from the start, including the Federation Hub, Fleet Management, delta comparison — not just a rough backlog.
- **Repo root**: `dms/` itself becomes the repo (currently neither here nor in the parent directory is Git present) — concept, plan, and future code live together in one place.

## Target structure of the repo (`dms/`)

```
dms/
  Business__DMS-Konzept.md      # existing spec, remains reference document (source of truth)
  IMPLEMENTATION_PLAN.md        # this plan (persisted, extended/versioned as needed)
  PROGRESS.md                   # living progress tracker, updated by EVERY session
  README.md                     # project overview, monorepo map, quickstart (docker-compose up)
  CONTRIBUTING.md               # conventions: branching, commit style, service template, DoD
  CLAUDE.md                     # project instructions incl. graphify section (via `graphify claude install`)
  docs/
    adr/                        # Architecture Decision Records, one file per decision
    services/                   # 1 short doc per service (responsibility, API, schema, sensors)
  services/
    registry-service/
    auth-service/
    document-service/
    ...                        # per service: src/, tests/, Dockerfile, README.md, pyproject.toml
  libs/                         # shared Python packages (no in-process coupling of business logic!)
    dms-common/                 # settings, logging, OpenTelemetry base
    dms-db-base/                # SQLAlchemy async setup, schema-per-service convention
    dms-eventbus-client/        # publish/consume interface over NATS JetStream (swappable)
    dms-auth-client/            # OIDC/JWT validation against Keycloak
  infra/
    docker-compose.yml          # local dev environment: Postgres, NATS, Keycloak, MinIO
    k8s/                        # later, once relevant
  tools/
    cli/                        # the DMS CLI tool (6.2)
  graphify-out/                 # generated, see graphify plan below
  .github/workflows/            # CI: lint + tests per service
```

**Monorepo rationale**: The services are architecturally independently deployable, but for the development phase a monorepo is more pragmatic (shared libs, one `docker-compose up` for everything, consistent conventions, a single place for `graphify`). This does not contradict the concept — each service remains an independently containerized process with its own schema (3.1).

## Cross-cutting: Definition of Done (applies to EVERY session)

Every session that produces code is only complete once:
1. The affected service/lib has: `README.md`, tests (`pytest`), `Dockerfile`, an entry in `infra/docker-compose.yml`, structured logging.
2. `docs/services/<service>.md` exists/is current (responsibility, endpoints, schema, events it publishes/consumes).
3. Non-trivial architecture decisions (e.g. search backend choice in P5-S4) are recorded as a short ADR in `docs/adr/`.
4. `PROGRESS.md` is updated: completed session checked off, next session named, open questions noted.
5. On substantial code growth: `graphify <path> --update` (see below) — not mandatory after every session, but mandatory at the end of every phase.
6. Tests run green (`pytest` per service, `docker-compose up` starts without errors).

This makes "cleanly structured and documented" not a closing step but built into every session.

## graphify deployment plan

- **P0-S1 (immediately)**: `/graphify dms/Business__DMS-Konzept.md` — builds the first knowledge graph over the concept itself. From then on: `graphify explain "<topic>"` instead of re-reading the full 1003 lines of text whenever a later session needs details on a section.
- Once the repo skeleton is in place (end of P0-S1): `graphify claude install` (writes a `## graphify` section into `dms/CLAUDE.md`, so future sessions automatically check/update without `/graphify` needing to be invoked manually) and `graphify hook install` (Git post-commit hook, updates the graph automatically on code changes).
- **At the end of every phase** (not every individual session): `graphify dms/ --update` — incremental, since only new/changed files are reprocessed (manifest diffing), the existing graph is preserved.
- **At the start of every future session**, especially from Phase 5 onward as the code grows: use `graphify query "<question>"`, `graphify path "A" "B"`, or `graphify explain "<service/concept>"` to orient ("what depends on the Document Service", "where is the OCR pipeline wired up") instead of manually grepping through all services.
- No API key needed for code (pure AST extraction); the optional Gemini key only matters if concept documents/images should later be re-evaluated semantically in more depth.

### Phase 5 — Processing: Scan, Rendering, OCR, Search

Before starting this phase (at user request), planned in depth against the spec, analogous to the level of detail that P4-S4/S5/S6 only got retroactively through real user feedback — anticipated here by reading concept sections 10.3/2.4/3.9/3.7 in depth beforehand. Open architecture questions (search backend) are deliberately **not** decided in advance, but remain, as always, an ADR decision within the respective session (Definition of Done, see above).

| Session | Deliverable |
|---|---|
| P5-S1 | ✅ **Virus Scan Service** (10.3): new service including a quarantine state, engine swappable via the same plugin principle as storage backends/OCR engines (3.3/3.8) — the spec does not name a concrete engine (e.g. ClamAV as an obvious open-source choice). **Core question, to be recorded as an ADR within the session**: 10.3 requires "virus scan mandatory before release of an upload", but the existing upload path (Document Service `POST /documents`/`POST /documents/{id}/versions`) makes content immediately retrievable via `GET /documents/{id}/content` before an asynchronous event consumer could react — a pure consumption of `document.version.created` would violate the release promise. To be decided: a synchronous scan call directly in the Document Service's upload path before the version is committed, or a new gating state (`scan_status`: pending/clean/infected) on `document_version` that blocks `GET .../content` and any downstream processing (rendering/OCR, P5-S2/S3) until the result is available. On detection: quarantine instead of automatic deletion (traceability/evidentiary value), audit event, notification of the uploader. Own Postgres schema, events, self-registration like every service. |
| P5-S2 | ✅ **Rendering/Preview Service** (3.7/2.4): thumbnails, PDF/A conversion, watermarks, as well as **substitute representations** as its own focal point — unlike what the name "Preview" suggests, substitute representations are, per 2.4, not a transient cache entry but **independent, durably persisted, versioned objects** (2.1a): resilience must not depend on the functioning of the same renderer that they are meant to safeguard against — so persistence goes through the Storage Service, not Redis/in-memory. Generation is rule-based/configurable per source format (e.g. ".docx → always .txt substitute representation", ".pptx → .pdf") and itself plugin-/service-based (3.3/3.8). Docks onto `document.version.created` after the scan gating from P5-S1. **Session order deliberately deviates from the concept pipeline**: 3.9 places OCR *before* rendering, but here OCR only comes in P5-S3 — the text-based substitute representation for image-based/scanned documents (which, per 3.9, builds on the OCR text layer) therefore cannot be served by this session yet; deliberately restrict to formats that do not need OCR (Office formats, video), add OCR-backed substitute representations as a follow-up effect of P5-S3. Substitute representations are subject to the same permissions as the original (2.4), unless configured otherwise. |
| P5-S3 | ✅ **OCR Service** (3.9): PaddleOCR as the default engine (Apache-2.0, more robust for tables/multi-column/multi-language layouts), Tesseract as a resource-efficient alternative — swappable via the same plugin interface principle as storage backends (3.3/3.6/3.8). Automatic detection of whether a document needs OCR at all (existing usable text layer yes/no), instead of forcing it uniformly per file type; the result (OCR text layer) is stored durably linked to the respective document version and feeds both the Search Service (P5-S4) and, optionally, a text-based substitute representation (2.4, follow-up effect for documents from P5-S2 that could not previously be served due to lack of OCR). **BPMN dependency, deliberately non-blocking**: 3.9 optionally envisages a manual review as a BPMN process step for low confidence scores — but the Workflow Engine does not exist until P6-S1. This session therefore only builds a simple intermediate state: confidence score + `needs_review` flag on the OCR result, published as an event, without blocking document availability (unlike the virus scan). The real BPMN integration follows later, presumably together with the generic approval mechanism planned for P6-S4. OCR results, like any document processing, must be audited (5.3) — the Audit Service must be extended to cover the new `ocr.>`/`virus-scan.>`/`rendering.>` streams. |
| P5-S4 | ✅ **Search Service** (3.7): full-text index + faceted search. **Backend decision deliberately left open** (Postgres full-text search vs. dedicated search index) — not anticipated here but decided as an ADR within this session. Facets follow the existing structure: object type, folder, attributes per object-type schema (different filter logic per attribute type `string`/`decimal`/`integer`/`boolean`/`date`/`reference`, e.g. range filters for `date`/`decimal`), creator, creation date, status. Metadata is indexed (`document.created`/`document.version.created`/`document.metadata.updated`) as well as full text from the OCR text layer (P5-S3) or the text-based substitute representations (P5-S2), once available — re-indexing is needed since OCR/rendering finish after the initial upload event. **Easy to overlook**: per its own docs, the Object-Type Service publishes no events ("pure reference data service") — attribute schema changes must be queried synchronously via HTTP. **Permission filtering**: search results must respect the Permission Service's permission cache that has existed since P2-S2; since each service owns only its own schema (3.1), this goes through its API. The existing `GET /check` however only checks one principal/resource/permission triple per call — for a result list with potentially many documents, a new **batch check endpoint** on the Permission Service is likely needed and is part of this session. |

### Phase 5d — Content-Type Governance & Upload/Preview UX

Inserted retroactively after completion of Phase 5c, same precedent pattern as Phase 5b (real user feedback from actual use, this time on preview gaps, OCR cost control, format governance, and upload UX). Two design decisions clarified in advance: OCR restriction is coupled to the **file type/MIME type** (not the object type) — the same configuration axis as the new format whitelist, no new connection between ocr-service and object-type-service needed; text preview (`text/plain`, `application/json`, ...) is done **directly on the client side** (User UI renders the original content in a `<pre>` block) instead of via a new rendering-service renderer — no substitute-representation overhead for content that is already text-based.

| Session | Deliverable |
|---|---|
| P5d-S1 | ✅ **Document Service: content-type detection + configurable format whitelist** (3.1/3.6): `DocumentVersion.content_type` is now determined server-side from the actual file content (sniffing, not the unchecked `file.content_type` header sent by the browser) — fixes the fact that e.g. `.txt`/`.json` arrive with a generic or incorrect content type depending on browser/OS. New, DB-backed, Admin-UI-editable configuration of allowed content types (same pattern as `OcrConfig`/`GuardConfig`) — uploading an unlisted format is rejected with `400` instead of silently accepted. **OCR Service** gets the same configuration axis mirrored: an additional, admin-editable content-type **allowlist** (`OcrConfig` extension, `allowed_content_types`), which applies in addition to the existing technical `select_engine()` logic — empty = no restriction, otherwise only a listed content type actually triggers OCR even though `select_engine()` might technically support further ones. |
| P5d-S2 | ✅ **User UI: upload as a pop-up with drag & drop + text preview** (8): `UploadForm` changes from a form shown inline in `ExplorerPane` to a real modal dialog (overlay), which additionally accepts drag-and-drop of files onto the open area. `PreviewPane` gets client-side direct display for `text/*` content types (as well as `application/json` etc.) — no new renderer, no rendering-service detour. |

### Phase 5e — Reference Number Generator (File Reference Number)

Inserted retroactively after completion of Phase 5d, same precedent pattern as 5b/5c/5d (user request, this time raised during P5d-S2 planning). Three design decisions clarified in advance by query: the running number in the format string resets **per year** (each object type has its own counter `{object_type_id, year}`); the display location before the file name is a **single global switch with an optional per-document-type override** (no catalog of multiple independent display points); a subsequent change to a generated reference number is allowed only for privileged users, for everyone else it is read-only — for this, **for the first time in the entire system**, the `X-DMS-Roles` header already injected by the gateway but so far evaluated by no service is read (new Keycloak realm role `dms-admin`, created idempotently in the Auth Service bootstrap).

| Session | Deliverable |
|---|---|
| P5e-S1 | ✅ **Object-Type Service: reference-number generator configuration + atomic counter** (2.2): `ObjectType` gets two new fields, relevant only for `applies_to="document"` — `kennzeichen_format` (format string with placeholders `{YYYY}`/`{YY}`/`{MM}`/`{DD}`/`{Laufende_Nummer}`, `null` = no generator) and `kennzeichen_display_override` (tri-state `null`/`true`/`false` — when set, overrides the global display default from P5e-S2 for this document type). New table `object_type_sequence` (`object_type_id`, `jahr`, `naechste_nummer`) for a counter that is independent per object type + year and safeguarded against concurrency. New endpoint `POST /object-types/{id}/next-kennzeichen` — atomic increment+format call, returns the fully rendered string (e.g. `2026-001`); `404` if no format is configured. |
| P5e-S2 | ✅ **Document Service: reference-number assignment on creation + privileged change** (2.2/4.4): `POST /documents` calls `POST /object-types/{id}/next-kennzeichen` server-side when a generator is configured and writes the result under the reserved attribute key `Kennzeichen` in `attributes` — a value sent by the client for this key is discarded. `PATCH /documents/{id}` rejects a change to `attributes["Kennzeichen"]` with `403`, unless the calling principal's `X-DMS-Roles` header contains the new realm role `dms-admin` (settings field `kennzeichen_admin_role`, default `"dms-admin"`) — the first real role check anywhere in the system, until now no service evaluated this header (see `PROGRESS.md` "Authorization"). **Auth Service**: `ensure_realm_and_client` creates the `dms-admin` role idempotently in the realm (analogous to the existing theme-attribute bootstrap), assignment to specific users continues via the existing role management (`/users`, Admin UI). |
| P5e-S3 | ✅ **Admin UI + User UI: generator configuration and display** (2.2/8): `ObjectTypeEditor` gets (only for `applies_to="document"`) a format-string field as well as the tri-state display override; new global setting (same single-line configuration pattern as `OcrConfig`/`UploadConfig`) for the default display switch "show reference number before file name". User UI (`ExplorerPane` list, tab titles in `DocumentWorkspace`) shows `attributes["Kennzeichen"]` before the file name when the resolved switch (object-type override if set, otherwise global default) is active; `MetadataPanel` shows the field editable only for holders of the `dms-admin` role, otherwise read-only. |

### Phase 11 — Monitoring & Backup/Restore

**P11-S0 kickoff findings**: five findings that refine the P11-S1–S4 session breakdown, no split needed. **(1) Infrastructure state confirmed**: still exclusively Docker Compose (39 Compose services), no Prometheus/Grafana/CheckMK anywhere in the repo, not a single `/metrics` endpoint in any of the 25 services — P11-S1/S2 therefore find no existing integration, but must add Prometheus/Grafana/CheckMK themselves as new Compose services for the first time. **(2) Sensor registry belongs in the existing `registry-service`, not a new discovery mechanism**: 10.1's own text places it there ("in addition to service discovery (3.2), the Registry Service maintains a sensor registry"), analogous to the P9-S2 precedent (license mediation was likewise attached to the registry, no dedicated service). ## PROGRESS.md — Resume Mechanism

`dms/PROGRESS.md` is created as the first order of business in P0-S1 and is the entry point for every new session:
- Table of all sessions (taken from this plan) with status (open/in progress/done)
- "Last Completed" / "Next Session" at the top, so a new session immediately knows where to pick up
- Section "Open Decisions" (e.g. search backend, SpiffWorkflow license) with the current state
- Short change log per session (1–2 lines: what was built, what is the next logical step)

## Verification per Session

- `docker-compose up` in the affected area must start without errors.
- `pytest` per service runs green (unit + simple integration tests against the Compose environment).
- For UI sessions (P4-S2, P4-S3, P4-S4, P4-S5, P4-S6, P5b-S3, P5b-S4, P6-S8, P14-S2, P15-S1, P15-S3, P15-S4, P16-S1): start the dev server, click through the core path (login → navigation → upload/release depending on the session) manually in the browser, not just typecheck/build. **Lesson learned from P4-S2/S3**: pure curl-based verification is not sufficient — a CORS bug (missing preflight handling in the gateway) and layout/UX shortcomings only became visible through real browser testing by the user. If no browser is available in the given session environment, this must be explicitly communicated as a limitation instead of silently treating curl checks alone as sufficient.
- From P8 onward, additionally: CLI smoke test of the respective new functionality.
